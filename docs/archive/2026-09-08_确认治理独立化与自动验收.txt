======================================================================
一、项目目标与本次决策
======================================================================

设计依据：docs/tp.txt；记录习惯：docs/tp2.txt。
项目是基于 OpenClaw 的 QQ 个人助手 Kurumi，不能以天气功能作为所有能力和控制机制的容器。

修复前确认的偏离（修复后的剩余问题见第五节）：
1. personal-weather 同时承载 Weather、Profile、Planning、Reminder 和跨领域确认治理。
2. Profile/Planning 共用 weather.sqlite，Profile 地点解析依赖天气模块的 QWeather GeoAPI。
3. 天气定时简报与提醒调度各有实现；鉴权、审计、配额等跨能力治理尚未统一。
4. 尚无可作为策略输入的统一能力目录：能力类别、副作用、确认需求、依赖和运行状态分散声明。

这些是实际边界问题。没有完整 DAG、动态 Router 或中央控制库，本身不构成偏离；
tp 明确要求由真实重复需求推动抽象，不能为了架构完整性先搭一个大框架。

本轮已作出的选择及原因：
- 从多个现有领域已经共同使用的确认机制入手，迁出公共逻辑并独立消息入口。
  新功能复用确认时依赖 @kurumi/confirmation-core，不需要依赖 personal-weather。
- 公共层只定义确认契约、候选路由与 grant 规则；业务库和本地事务仍由领域拥有。
  不做跨库业务事务、不搬生产表、不为此次故障同时重写全部调度器。
- 新插件通过 Host 实际等待的 reply_dispatch 记录确认，返回 void 继续默认模型回合。
  模型仍需调用已有 commit 工具；入站记录本身不提交业务、不发送回复。
- 这是第一次边界纠偏，不能据此宣称 tp 架构已经全部实现。

三、确认故障的证据与修复后的链路
======================================================================

3.1 已确认的旧入口问题
原 personal-weather 注册 inbound_claim。
当前 Host dist/dispatch-DnzGTpPs.js:1489–1508 只在 pluginOwnedBinding 分支定向调用
runInboundClaimForPluginOutcome；2026-09-07 只读核对 current_conversation_bindings 为 0。
因此当前普通 QQ 消息不能通过该分支进入旧处理器。源码和已部署入口当时一致。
不能仅因 SDK 有钩子名称就认定消息路径实际会调用它，也不能由此直接断言上游回归。

3.2 新源码链路
主人私聊可信工具上下文（Host senderIsOwner=true）
  -> 领域 propose 写待确认业务提案及公共提案索引
  -> 下一条真实 QQ 消息的 reply_dispatch
  -> personal-confirmation 从原始上下文构造确认事件
  -> confirmation-core 遍历已注册存储适配器，所有库候选合计恰好一条
  -> 候选所属业务库事务内签发 grant
  -> 回到默认模型回合，由已有 commit 工具检查主人权限并消费 grant
  -> 领域事务提交业务变更。

运行期注册的适配器：profile-planning、personal-reminder。
使用带版本的 process-local Symbol 注册表，解决 Host 分别加载公共包副本时的发现问题。
注册项由业务服务 start 注册、stop 注销；重复注册失败，部分启动失败会撤销已注册项。
不是中央业务数据库，也没有允许模型注册任意后端的工具。

3.3 新入站边界
- 只接受 qqbot、ChatType=direct、明确 c2c 对象。
- 只用当前 RawBody、MessageSidFull/MessageSid、SenderId、Timestamp。
- 不回退到历史 ID、runId、模型正文、引用正文或处理时刻伪造消息证据。
- 拒绝引用、尾部分发、sendPolicy=deny、字段缺失、超过 5 分钟的陈旧消息、超前 30 秒的时间。
- 账号缺省按 Host 默认账号 default；保留实际 AccountId 和 SessionKey。
- 新工具 scope 带账号；账号、私聊对象、发送者或两端明确会话键冲突时拒绝。
- 两端必须有明确且一致的私聊对象，unbound 与 unbound 相等不再能授权。
- 历史无账号 scope 在当前带账号入站下不匹配，需要重新生成提案。
  修改前所有已查到的旧提案均已过期，无需以清理旧提案作为本次故障修复前提。

3.4 确认协议与事务
- 规范文本：确认 proposalId=… payloadHash=…
- ID 与 Hash 必须同时精确匹配；多个 ID/Hash 的混合确认直接拒绝。
- 保留已有肯定前缀/否定式检查，包括“我确认变更 …”；未承诺理解任意自然语言条件句。
- 普通聊天与引用不打开确认存储。多个库拥有同一候选时不去重，按歧义拒绝。
- 任一后端打开或查询失败，不对另一个库的部分结果签发 grant。
- grant TTL 仍为 5 分钟且不超过提案有效期；同一提案和消息 ID 有唯一约束。
- Profile/Planning、Reminder 原有 grant 消费与业务事务不迁移；提醒 Cron 策略不变。
- 新建确认表的 domain 允许独立领域名；已有生产表保留原 CHECK，不做 DDL 迁移。
  新领域使用其自己的存储适配器/新库，不能假定可直接往旧 Weather 库塞新领域。

3.5 诊断
日志只记 component、outcome 和适配器名，不记录正文、完整身份标识、ID/Hash 或异常原文。
结果区分 no_backends、no_match、ambiguous、recorded、rejected、storage_error。
recorded 表示确认记录已存在或本次成功记录，不等于模型已提交、更不等于业务已投递。
不合资格的原始消息和普通聊天静默忽略；此类情况需核对入口元数据，不能只凭缺日志判断钩子未调用。

七、需要保留的纠错结论
======================================================================

- 旧解释“Host 总是在入站钩子之后才解析主人身份”错误：绑定分支实际先解析再调用定向钩子。
  旧入口的主要问题是当前无绑定场景不可达；已删除相关错误源码注释。
- 旧 scopesMatch 的 OR 匹配不能泛化为跨账号、跨发送者安全；本轮加入冲突拒绝和无绑定拒绝。
- 旧“清理过期提案才能消除歧义”不是成立前提：查询原本已经按有效期过滤。
- message_received 的 fire-and-forget 不能保证异步处理完成后模型才执行；本轮选择实际被等待的 reply_dispatch。
- 代码、单元测试、Host 加载、真实 QQ 端到端是不同证据，不能互相冒充。
- 当前 Host engines 接受 >=22.22.3 <23 || >=24.15.0 <25 || >=25.9.0；
  台式机 Node26.5.1 满足，本地历史 Node22.17 不满足，不能把 Node24 写成唯一可用版本。
