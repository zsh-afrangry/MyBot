| 上游机制 | 借鉴方向与适配要求 |
| --- | --- |
| SOUL / INNER | 分别描述外在表达与内在背景；素材里的恋人关系、纪念日及共同经历必须移到本人专属关系层，不能留在成员共享内容中 |

| 日记与 MEMORY | 将近期互动整理为长期认识；当前受管 MEMORY 格式与上游自由文本格式不兼容，不能直接复制覆盖 |
| 每2小时 heartbeat | 由模型按提示词写日记、整理记忆、维护情绪并判断主动联系；本机未启用，照搬需要额外执行能力、调度与预算设计 |
| 主动联系 | 上游给出09:00–22:00窗口、默认6小时冷却、未回复暂停等思路；这些值仅为参考，不是本项目已批准的默认值 |
| 自动成长 | 上游让模型修改 SOUL/INNER/USER；本项目拟将学习结果独立保存，避免覆盖受管人格、授权与运行规则 |
| Telegram互动与模型建议 | 其反应、贴纸、发送工具及 Claude 配置不直接适用于当前 QQ/DeepSeek；应分别验证，不能复制整份 example 配置 |

已安装SDK的reset实现保留原sessionId并更新lifecycleRevision；隔离运行也观察到`/new`前后sessionId相同而历史已清理。所以不能把sessionId变化当作重开成功或许可失效的唯一依据，也不能仅按固定sessionKey继承旧许可。压缩钩子只提供会话归属与消息计数，本次没有sender、runId或toolAuthority，不能单独拿它授予业务写权限。后续实现须基于可信入站和当前回合授权维护自己的失效边界。

**对P2的影响与风险（推断，待隔离宿主证实）**

1. 冲刷回合写不进记忆：通用写文件工具已禁用；`kurumi_memory`写入要求绑定本回合可信RawBody、实际runId和宿主调用授权，而冲刷是没有新入站的静默回合，预期被拒（失败关闭）。结果是冲刷只花一次模型调用而没有收益；在生产里就是一次付费DeepSeek调用。在`memory=none`时冲刷究竟跑不跑，文档没有说清，必须实测。
2. 授权时序：可选维护在回复送达后才开始，此时`agent_end`已经作废本回合授权，压缩期间不会有合法写入，这符合设计。超限恢复是在回合中途压缩再重试，重试若换了runId，同一回合的合法记忆写入会被拒，只是降级不会误写，需要实测确认。
3. 摘要不是事实来源：宿主摘要可能转述受限注入的记忆参考或用户原话，但本域只接受当前RawBody，摘要不会被晋升为事实，与第3条“原生压缩历史不作为自动提取源”一致。主人摘要只存在主人会话里，成员会话的记录和压缩是分开的；成员读不到主人摘要已在手动压缩调查中观察到，自动路径仍需复验。
4. 注入持续性：记忆参考由`before_prompt_build`每回合重新生成，压缩后应继续注入；需确认压缩后的第一回合模型输入同时包含摘要和最新记忆参考，且没有把旧参考当新参考重复叠加。
5. 失败路径：摘要审核失败时原记录继续有效；需确认回复照常送达、没有向QQ发出“压缩完成”之类误报（`notifyUser`默认关）、记忆revision不变。
