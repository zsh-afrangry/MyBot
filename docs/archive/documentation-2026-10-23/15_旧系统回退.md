## 启动前风险审计（原时点）

下表是 **2026-10-05 的实测值，属历史记录**；旧 Cron、外发白名单和 bridge 暂停状态都可能已经变化，
**每次真正启动旧系统前都必须重跑 `./scripts/fusion/restore-legacy.sh` 的【6】段重新核对**，不能直接引用下表：

| 风险项 | 2026-10-05 实测结果 |
|---|---|
| 旧 Cron | **3 个 enabled**。其中 `kurumi 每日天气简报` 为 `30 10 * * *` Asia/Shanghai，`delivery=announce/qqbot` —— **启动后每天 10:30 会真实向本人 QQ 外发**。另两个（Memory Dreaming Promotion、skill-collection-review）`delivery=none` |
| 旧提醒 | 全部终态（cancelled=3, delivered=6），启动后不会补投 ✓ |
| 旧外发白名单 | 私聊 1 个（本人），**群 1 个** —— 旧系统允许向群外发，而新系统是仅本人私聊 |
| 旧 bridge 模式 | `social-v2.paused = false`，**未暂停**，启动后会主动参与会话 |
| 旧单元 | `openclaw-gateway` 仅 `EnvironmentFile` 引用原路径（ExecStart 用全局安装）；`qq-bridge` 有 `WorkingDirectory`。还原后都能按原路径生效，**无需改单元** |

因此启动旧系统前必须先处理：禁用不再需要的旧 Cron、确认那 1 个群是否仍应可达、
决定 bridge 是否要先暂停。

## mask 实施与核验

2026-10-10 实测确认 `systemctl --user start openclaw-gateway.service` 会真的被执行，
随后因 `Missing config` 以 `status=78/CONFIG` 退出（`RestartPreventExitStatus=78`，所以不会反复重启）；
`qq-bridge` 则因 `WorkingDirectory=/home/afrangry/桌面/qq-bridge` 已不存在，以 `status=200/CHDIR` 失败。
两者都不会真正接管 QQ，但**手动启动本身不该发生**，因此已按下述方式 mask。

验证结果（2026-10-10）：

```text
openclaw-gateway   enabled=masked   active=inactive
qq-bridge          enabled=masked   active=inactive
systemctl --user start openclaw-gateway.service
  -> Failed to start openclaw-gateway.service: Unit openclaw-gateway.service is masked.
```
