# 融合助手运行维护

日常先运行健康检查；修改只在融合源码中进行，按模块验证后重启融合服务。架构、资产和最新验收状态分别见[文档入口](README.md)中的 9、12、16。

## 常用操作

```bash
cd /home/afrangry/kurumi-fusion
node scripts/fusion/health.mjs
systemctl --user status kurumi-fusion.service
journalctl --user -u kurumi-fusion.service -n 100 --no-pager
systemctl --user restart kurumi-fusion.service
```

`health.mjs`只读、不发QQ、不创建任务；兼容入口`probe-final.mjs`已指向同一检查。合法活动提醒会列出状态而不会一律报错。QQ断线时先看SnowLuma/QQ两个服务及online状态；不要重启旧bridge。额度按物理消息计数，默认滚动24小时500条，不清空历史来绕过。

```bash
systemctl --user status snowluma.service snowluma-qq.service
systemctl --user stop kurumi-fusion.service
systemctl --user start kurumi-fusion.service
```

停止systemd服务时不要仅杀子进程，否则Restart策略会把它拉起。`run-gateway.mjs`是前台入口，日常不要与systemd并开。首次安装入口`install-service.mjs`会禁用旧用户助手并启用融合，只用于明确切换。`configure-production.mjs`会先要求审阅活动任务，不能当日常重置脚本。

## 开发与验证

源码：`/home/afrangry/kurumi-fusion`。运行配置/密钥/数据库：`/home/afrangry/.openclaw-fusion`。不把后一目录提交Git。人格行为模板在`scripts/fusion/templates/AGENTS.md`，修改后明确同步到私有workspace；SOUL/USER/MEMORY保持私有。

运行时固定使用 OpenClaw **2026.9.7** 和 `ws` **8.21.3**；依赖检查以 `verify-dependencies.mjs` 为准。领域包在各自目录按锁文件 `npm ci`，第三方 Tavily 安装由 `install-plugins.mjs` 和 `config/plugins.package-lock.json` 管理。新系统不依赖旧 `.openclaw` 或归档树。本机检查需要 Git、Bubblewrap、Poppler 和 prlimit。

升级须单独更新版本契约、锁文件、构建与验收，再部署。隔离恢复使用固定哈希 SDK 包，具体流程见[验收总表](16_验收与测试总表.md)。

离线测试、真实验收和探针的完整清单见[测试与证据索引](verification/INDEX.md)。`scripts/fusion/test-*.mjs` 可能真实发本人 QQ、创建任务或重启服务，不能按普通离线测试批量运行。执行前审阅脚本，使用独立会话/项目和有限发送预算；结束后关闭 `testIngress`、正常取消测试任务并检查真实终态，不删除账本。

日常配置只使用 [config/README.md](../config/README.md) 中的同步入口；`prepare.mjs`、`configure-*.mjs`、`copy-domain-state.py` 为迁移工具，不是日常更新命令。

## 代码项目接入与合入

当前`fusion`是`.openclaw-fusion/projects/fusion`独立副本，主聊天可说“让后台检查fusion项目……”，完成后查询或取消。模型可读写项目并做本地Git，固定检查在隔离环境运行，不提供宿主shell、网络安装或push。副本提交不会自动部署；操作者审阅diff/测试后再合入`kurumi-fusion`，重启服务。

新增项目时：

1. 在`.openclaw-fusion/projects/<id>`建立独立Git clone --no-hardlinks，原项目不改，移除不需要的remote；不能把两套旧原件注册成工作目录。
2. 在`projects.json`新增唯一id、`agentId:project-<id>`、canonical root、checks（固定argv/timeout）、必要的只读依赖和外部fixtures。不要挂载密钥、私有主目录或任意根目录。
3. 在openclaw.json的agents.entries增加同名agent，workspace指该副本，沿用project-fusion的精确工具allow和workspaceOnly。加项目AGENTS，忽略Host生成的IDENTITY/SOUL/USER/MEMORY。
4. 先由操作者运行登记的Bubblewrap检查，确认依赖可见、项目可写、外部检查只读、主机私有目录及网络不可达，再重启融合服务；用kurumi_task list验证。

注册表由操作者管理，模型只收项目ID。扩大检查范围应修改已有checks而不是新增第二套任务引擎；复杂项目的依赖需要预先准备并在隔离环境验证。

## 研究与提醒

长篇论文通过kurumi_task kind=research进入后台。来源PDF在research-cache，报告在research-workspace/reports；按URL/哈希/下载时间区分版本。未提取、未看图或未复现实验时必须说明。可要求后台读取已有报告进一步展开；主会话不直接读取任意文件。

一次性提醒使用领域提案和短码确认；固定runner到点执行不依赖模型。周期天气使用原生automations，仅允许天气读取工具和本人投递；依赖模型与天气API。没有默认替主人开启每天播报，验收周期任务已删除；主人可自行指定日常时间。所在地与行程改变仍需原文确认。

## DSH与融合栈统一启停

以afrangry普通用户执行：

```bash
cd /opt/deepseek-harness
./Start-DSH.sh
./Stop-DSH.sh
```

Start启动系统dsh-web和用户snowluma、snowluma-qq、kurumi-fusion，停止旧qq-bridge/openclaw-gateway；Stop先停消费者，再停QQ传输及DSH。操作保留源码、登录信息、聊天、提醒与开机启动设置。停机期间助手不可用。所谓“新bridge”是融合服务中的QQ插件，没有额外创建同名bridge进程；SnowLuma复用已有传输服务。

版本源文件在`scripts/fusion/launchers/`；实际入口在`/opt/deepseek-harness/`；旧入口备份在`/opt/deepseek-harness/launcher-backup-before-fusion/`。修改源文件后应同步install到实际入口，文件所有者dsh:dsh、权限755。脚本不保存sudo密码。Start会等待实际健康检查，失败以非零退出并显示原因，允许重复执行。

启停证据见 [stack-lifecycle.json](verification/deepseek-whale/stack-lifecycle.json)，各阶段覆盖范围见[验收总表](16_验收与测试总表.md)。历史记录中 SnowLuma 曾超过停止期限并被 SIGKILL；操作时应检查 `ActiveState` 和 `Result`，不能把“进程停止”当作“正常退出”。

### 紧凑启动输出

默认Start仅显示DSH 3080、Fusion 18890、SnowLuma WebUI 3082、OneBot HTTP 3083、OneBot WS 3084、QQ在线状态及最终结果，最后保留DSH认证入口。健康探测仍检查数据库、Cron、旧消费者与测试入口等，显示层为`scripts/fusion/stack-summary.mjs`，不以端口监听替代实际链路状态。

终端等待行原地更新，重定向时不输出控制字符。`./Start-DSH.sh --verbose`查看完整健康JSON和附加诊断；只在健康探测进程隐藏已知ExperimentalWarning。`./Stop-DSH.sh --verbose`显示原始ActiveState/Result；默认停机输出区分“已停止”和“已停止，退出状态异常”。默认隐藏已停止的旧助手行，旧助手异常仍显示。

启动输出同时显示DSH本地与Tailscale远端认证入口。远端域名读取dsh-web.service的`--trusted-host`（限定*.ts.net），使用HTTPS并保留本地入口路径和认证参数；沿用现有Tailscale Serve转发，不修改网络配置。
