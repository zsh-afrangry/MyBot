1. 文档目标与核心结论
本项目的目标不是把 Kurumi 做成“一个会调用很多工具的聊天机器人”，而是逐步形成一个可扩展、可控、可审计的个人智能体能力体系。其核心挑战不是单个工具能否工作，而是：当能力数量增加后，模型如何选择能力、不同能力如何共享基础技能、定时与暂停如何横跨领域复用、多步骤任务如何组织、权限如何不随能力数量失控，以及外部信息如何安全地进入模型上下文。
本次讨论形成的核心共识如下：
•	模型的理解、抽取、规划、比较、综合和生成属于认知过程，不应被机械地全部工具化。
•	Calculator、Current Time、Web Search、OCR、文件解析等更适合归类为可复用的基础能力（Primitive Capability）。
•	Weather、Stock、Paper、Git/Repository、Travel 等属于具有明确领域语义的领域能力（Domain Capability）。
•	Scheduler、Workflow、Notification、任务状态协调等属于控制平面（Control Plane），不应等同于普通领域工具。
•	鉴权、权限、审计、预算、限流、超时、隐私检查、幂等、信任标记等属于横切治理，应包围每次能力调用。
•	搜索和计算会改变任务结果，必须作为显式步骤或依赖被记录，不能像日志一样在后台透明发生。
•	系统拥有某项工具，不等于每轮对话都应该向模型暴露该工具；按需暴露是准确率、上下文效率和安全性的共同要求。
•	智能体可以组合已有现实能力，但不能凭空创造尚未接入的现实世界能力。
•	当前阶段应优先做原子/单元能力和通用控制语义，等真实多步骤需求出现后再扩展 sequence、scheduled 和更复杂工作流。
一句话概括
模型负责认知；显式 Capability 提供外部能力；领域能力声明依赖；控制平面负责触发、编排和投递；横切治理负责安全与可观测性。

2. 总体架构：认知、能力、控制与治理
建议把整个系统理解为五个相互分离、但在运行时协作的层次。
层次	主要职责	典型内容	是否直接改变业务结果
认知层（Cognitive Plane）	理解用户、抽取事实、形成计划、综合结果、生成自然语言	理解、抽取、规划、比较、总结、综合	通过决策间接影响
计划层（Plan / TaskSpec）	表达用户目标、显式能力步骤、触发方式和策略	Goal、CapabilityPlan、Trigger、Policy	是
策略层（Policy Plane）	判断某能力在当前身份、场景和风险条件下是否允许	权限、风险、确认、预算	决定能否执行
执行与控制层（Execution / Control Plane）	负责何时执行、步骤衔接、状态推进和投递	Scheduler、Workflow、Notification	执行层面影响
能力层（Capability Plane）	真正访问专业数据源、外部系统或执行可验证动作	Search、Weather、Stock、Paper、Git 等	直接影响

此外，身份、审计、限流、预算、隐私与输入输出校验等不是第六个业务层，而是贯穿所有显式能力调用的横切治理。
3. 模型能力、外部能力与执行策略的边界
3.1 认知能力
认知能力是模型内部对自然语言任务的处理能力。它包括意图识别、实体和时间抽取、任务分解、比较、总结、多来源综合和表达。在普通任务中，这些过程可以留在 LLM Runtime 内部，不需要为每个动词设计一个 Tool。
只有当某个认知阶段具有独立的运行语义时，才有必要把它显式化。例如：需要使用不同模型、独立预算、独立复核或独立失败恢复。
3.2 外部增强能力
外部增强能力弥补模型在实时性、精确计算、外部感知或文件读取方面的不足。例如 Calculator、Current Time、Web Search、OCR、文件解析。它们通常可以被多个领域共享。
3.3 模型执行策略
“使用哪个模型、推理强度、最大时间、Token/费用预算、是否允许 fallback、是否使用第二模型复核”等，属于 ExecutionPolicy。它描述的是“怎样运行模型阶段”，而不是“模型会不会理解、规划和总结”。
关键边界
模型能力不等于执行策略。认知能力回答“模型能做什么思考”；ExecutionPolicy 回答“这次模型阶段以什么资源和可靠性要求运行”。

4. 任务表达：Goal、Plan、Trigger 与 Policy
任务不应再被理解为“用户一句话对应一个工具”。更合理的抽象是：用户提出 Goal，模型在当前能力和权限范围内形成一个显式或隐式的 CapabilityPlan，同时任务还具有触发、执行、权限和投递语义。
组成	含义	示例
Goal	用户真正想获得的结果	“解释英伟达最近一个月上涨的原因”
CapabilityPlan（可选）	为完成目标需要显式执行的外部能力步骤	行情数据 + 搜索公开新闻
Trigger	任务何时发生	立即、某个时间、受控周期
ExecutionPolicy	运行资源与失败策略	超时、预算、模型选择、fallback
PermissionPolicy	谁在什么场景下可执行什么动作	主人私聊允许，群聊不允许
DeliveryPolicy	结果何时、以什么方式送达	当前对话回复、下午四点主动推送

CapabilityPlan 应允许为空。纯粹的解释、改写、总结等任务可能只需要 LLM Runtime，不应为了形式统一而强行加入“模型生成工具”。
4.1 Plan 的复杂度应渐进
•	single：单个显式能力调用。
•	sequence：少量固定顺序步骤，后一步使用前一步结果。
•	scheduled：在 single 或 sequence 外增加时间触发。
•	DAG：仅在真实并行、汇合、补偿或复杂依赖出现后再考虑。
因此，数据模型可以为未来复杂工作流预留空间，但执行系统不必在第一阶段就支持完整 DAG。
5. 能力分类与 Capability Registry
Capability Registry 的作用是形成系统的“能力目录”和策略输入，使每个能力有清晰的类型、信任等级、数据外发属性、上下文限制、依赖和运行状态。它不是权限授予器，也不意味着所有登记能力都会展示给模型。
能力类别	定义	示例
Primitive Capability	跨领域共享的基础外部能力	Search、Calculator、Time、OCR、文件解析
Domain Capability	具备明确领域语义和专业数据源的能力	Weather、Stock、Paper、Git、Travel
Model Stage	只有在需要独立运行语义时显式化的模型阶段	金融分析、第二模型复核
Internal Control	内部控制平面能力，原则上不作为普通 Tool 暴露	Scheduler、Workflow、Notification

Registry 的价值主要体现在一致性、路由、权限策略和审计，而不是让模型自由发现并调用一切。
6. 能力可见性、授权与按需加载
“系统装了什么”“用户有权用什么”“这一轮模型看见什么”“最后实际执行了什么”是四个不同问题。如果不区分，未来做 Tool Router 时很容易把“任务需要”错误地变成“自动获得权限”。
状态	含义
Installed	系统中已经实现或接入了该能力。
Authorized	当前身份、通道和场景被允许使用该能力。
Exposed	本轮对话中，该能力被展示给模型作为候选工具。
Executed	本次任务中，该能力真正被调用并产生结果。

后续若引入 Tool Router，可进一步区分 Candidate 与 Selected，但 Router 的职责仍应只影响“向模型暴露哪些候选能力”，不能改变底层 Authorization。
有效能力集合
可把有效能力理解为：已安装 ∩ 当前身份获准 ∩ 当前任务需要 ∩ 当前风险策略允许。这同时服务于工具选择准确率、上下文控制和安全最小化。

7. 搜索的定位：基础能力，而非透明增强
联网搜索可以被视为通用 Agent 的基础感知能力之一，但不应被理解为“所有问题默认后台偷偷联网”。它在实现上是一项 Tool/Capability，在架构上则是一项可以被多个领域显式复用的 Primitive Capability。
Search 与 Calculator 的共同点是：它们都用于增强模型自身不足。但两者存在显著的信任差异：
能力	主要价值	信任特征	是否应显式记录
Calculator	精确计算	确定性、高可信	是
Web Search	获取最新、外部、长尾信息	不可信外部内容，可能存在错误或提示注入	是
Current Time	提供可靠当前时间	确定性/系统来源	是

Search 不能被做成类似日志的透明 AOP 切面，因为是否搜索会改变最终结论，还伴随数据外发、来源选择、时效和外部不可信内容进入上下文。
8. 专业数据源、搜索增强与 Fallback
搜索不应取代专业 API。对于有权威结构化数据源的领域，应优先使用领域能力；Search 更适合作为补充背景、发现更多来源或处理通用时效性问题。
场景	首选能力	Search 的角色
“广州现在多少度？”	Weather 专业数据源	通常不参与，不作为实时天气的静默 fallback
“最近 AI Agent Security 有哪些论文？”	Paper 论文数据源	可作为发现范围的可选补充
“英伟达最近一个月为什么上涨？”	Stock 行情数据 + 计算	用于补充新闻、事件和公开背景
“某公司今天发生了什么？”	Web Search	可以直接作为主要信息源
“解释一个稳定的基础概念”	模型知识	通常无需搜索，除非用户要求核验或信息可能过时

因此，信息源路由不是固定的“模型知识 → 专业 API → Search”阶梯，而应根据用户所问的 claim 类型选择最合适的数据源。
8.1 Dependency、Augmentation 与 Fallback
建议在概念上区分三种关系：Dependency 是完成某领域操作所必需的能力；Augmentation 是可选增强；Fallback 是首选能力失败后的受控替代。这三者不要混成同一概念。
9. 控制平面：立即、定时、暂停、恢复与禁止
“立即执行”“定时执行”“暂停/禁止直到恢复”不应分别在天气、股票、论文、Git 中重复实现。它们属于跨领域的控制语义，应由控制平面统一承载。
控制语义	含义	例子
立即执行	任务在当前会话中立刻发生	立即提交当前项目、立即查询天气
定时执行	任务在未来某个时间或周期发生	下午四点搜索论文并推送
暂停/禁止	在明确恢复前阻止某类自动动作	暂停每日天气播报直到再次允许
恢复	重新启用此前被暂停的行为	恢复每日天气播报

模型应能够表达“调度语义”，例如某个任务在下午四点执行，但不应直接获得底层 Scheduler 的通用管理权限。
声明式控制
模型表达“做什么、何时做、是否允许继续做”；控制平面决定如何可靠地执行和维护这些状态。

10. 从“3×3×3”到能力—控制—编排解耦
最初的“3×3×3”设想本质上是一个排列组合问题：不同领域能力、不同操作、不同触发和控制方式可以组合。如果每一种组合都单独开发工具，系统会迅速僵硬；如果把这些维度解耦，就可以通过有限能力实现大量组合。
可以把任务理解为三个主要维度：
维度	回答的问题	例子
能力层	要做什么业务动作？	查天气、查论文、查股票、Git 提交
控制层	什么时候、是否允许执行？	立即、定时、暂停、恢复、确认
编排层	一个任务由几个步骤、如何衔接？	单步、顺序、延迟投递、多来源综合

这样，“论文搜索 + 下午4点推送”不是新的领域工具，而是“论文能力 × 定时控制 × 投递”的组合。
“立即 Git 提交”不是新的 Git 工具类别，而是“Git 提交能力 × 立即触发”。
“暂停天气播报”也不是“disable_weather”式领域操作，而是控制平面对某一自动任务/策略的状态改变。
11. 单元能力优先，多 Step 与工作流后置
当前阶段应优先把每个单元工作做成稳定、可验证、输入输出边界清晰的能力，再考虑多步骤工作流。这是为了避免在业务能力还不稳定时，先承担编排、恢复、失败传播、持久化和权限传递等系统复杂度。
11.1 当前适合先完成的单元能力
•	天气：按需查询当前有效地点天气。
•	论文：搜索或发现论文并得到结构化结果。
•	股票：查询行情、K 线或区间数据。
•	代码仓库：状态查询、提交、推送等明确领域动作。
•	搜索：在受控边界内查询公开网页信息。
11.2 多 Step 后置的原因
•	多步骤任务需要明确步骤依赖、失败语义和结果传递。
•	定时任务跨越会话和时间，需要更严格的状态和幂等语义。
•	当一步结果在未来被另一任务使用时，需要稳定的“结果身份/引用”概念。
•	过早开发通用工作流会把一个简单能力问题升级成平台工程。
因此，“先实现论文搜索，再实现通用定时执行，最后组合成‘现在搜索、下午四点推送’”是合理的演进顺序。
12. 动态事实、偏好与自动联动
用户只陈述现实事实，而没有明确说“修改天气设置”，智能体未来仍可能根据长期策略自动联动相关功能。例如用户确认一段旅行，系统可以根据“天气跟随已确认行程”的长期偏好，在合适时间切换天气关注地点。
为避免把这种行为混成提示词技巧，建议概念上区分三层：
层	含义	示例
事实（Facts）	用户现实状态或计划	“周日去无锡，下周回来”
策略/偏好（Policies & Preferences）	事实发生后系统默认如何响应	“确认行程后，天气跟随目的地”
动作（Actions）	系统最终执行的现实操作	更新天气关注地点、安排提醒

这种“联想、历史记忆和偏好驱动的跨功能自动化”属于后续工作流与上下文管理问题，可以在原子能力和控制平面稳定后再展开。
13. 天气能力作为领域案例
天气是本项目第一个领域能力，因此它可以作为后续能力设计的样板。其最重要的架构结论不是具体 API，而是：实时天气应依赖专业天气数据源；时间、地点和播报启停属于动态配置/控制；用户行程属于事实；未来的自动联动属于策略。
13.1 时间与地点的临时/永久变化
“明天改成下午两点提醒”与“以后都改成下午三点”，以及“临时去另一个城市”与“以后长期住在另一个城市”，本质上都可以理解为默认值与有效期覆盖的关系。
变化	临时语义	永久语义
提醒时间	只在指定日期/时间范围内覆盖默认提醒时间，到期恢复	改变后续默认提醒时间
关注地点	在旅行或临时停留时间段内覆盖默认地点，到期恢复	改变长期默认地点或未来长期生效地点
播报状态	暂停到某个日期或直到显式恢复	长期关闭，直到再次改变策略

动态地点和临时计划不应依赖不断修改系统提示词。系统提示词更适合描述稳定边界和原则，而不是作为动态事实数据库。
13.2 天气与 Search 的边界
“广州现在多少度”应走 Weather 专业能力；“为什么今年广州特别热”可能同时需要天气数据与 Web Search。Search 可以增强解释，但不应静默替代实时天气数据源。
14. 论文、股票与代码仓库案例
14.1 论文
论文能力负责论文领域的结构化发现和元数据；Web Search 可以作为可选的广泛发现能力。例如“查最新 AI 安全论文”优先使用论文能力；“最近大家在讨论哪些 Agent Security 方向”则可能组合论文能力与公开网页搜索。
“现在查论文，下午四点发给我”属于典型的 sequence/scheduled 组合：搜索和总结先发生，未来时点只负责投递已有结果。
14.2 股票
行情、K 线、区间涨跌等应由专业 Stock 能力提供；精确涨跌计算可依赖 Calculator；解释价格变化时，Web Search 可补充新闻、公告和公开事件。
因此“分析英伟达最近一个月为什么上涨”不是一个超级股票工具，而是领域数据、基础计算、公开搜索和模型综合的组合任务。
14.3 代码仓库
仓库能力应按领域动作组织，例如查看状态、提交、推送、测试等。“立即提交”“测试通过后再推送”“下午四点执行”属于控制和编排语义，而不是每个仓库动作都需要另外复制一套定时/禁用工具。
代码仓库与数据库操作通常具有明显副作用，因此权限、确认和失败恢复策略应比只读查询更严格。
15. 安全、信任与 AOP 式横切治理
AOP 类比最适合解释那些“不改变用户业务目标，但每次能力调用都必须经过”的治理逻辑。
适合作为横切治理的内容	原因
身份与通道检查	决定当前请求是谁、从哪里发起。
授权与确认	决定该身份是否能执行特定能力和副作用。
参数与输出校验	防止模型构造越界参数或错误结果进入后续步骤。
审计与追踪	记录调用链、来源、状态和失败。
限流、预算、超时	约束资源、费用和异常循环。
隐私与数据外发检查	防止无关私人信息被发送给外部 Provider。
幂等与重放保护	避免定时任务、重试或重启造成重复副作用。
信任标记	区分确定性计算、专业 API 与不可信网页内容。

15.1 Search 的特殊风险
Search 返回的是不可信外部内容，可能包含错误信息、恶意指令或提示注入。搜索结果应被视为“资料”，而不是新的系统指令。Search 还会把 query 发送给第三方，因此存在数据外发和隐私边界。
这也是为什么搜索必须显式存在于计划或调用记录中，而不能在某个领域工具背后悄悄发生。
15.2 专业能力与权限不自动继承
领域能力可以声明“需要或可选使用 Search”，但这不意味着领域能力自动获得 Search 权限。依赖只能在当前身份已授权、任务确实需要且风险策略允许的交集中生效。
16. 设计中明确暂缓的事项
以下能力并非永远不做，而是当前没有足够真实需求支撑其复杂度：
•	完整动态 Tool Router：当前工具数量较少，先用清晰能力描述和确定性路由规则。
•	通用 DAG Workflow Engine：只有真实并行、汇合、补偿和复杂恢复需求出现后再立项。
•	浏览器、登录态、任意 Web Fetch、任意 HTTP：与简单 Search 相比风险面显著扩大，应独立评审。
•	模型自由生成 Capability ID 或动态扩大工具权限：容易突破 Authorization 边界。
•	把每个认知动词注册成 Tool：会导致 Registry 膨胀并增加工具选择难度。
•	跨插件大一统公共 Runtime：只有多个独立能力出现稳定、真实的重复需求后再抽象。
•	自动把搜索结果写入长期记忆：外部网页不可信，记忆写入应有独立验证和策略。
17. 推荐的演进路线
建议按“能力先行、控制复用、组合后置、复杂编排最后”的顺序演进。下列阶段是架构层面的路线，不规定具体实现技术。
阶段	主要目标	退出条件
阶段 1：原子领域能力	天气、论文、股票、Git 等单元能力稳定	每项能力可独立调用、独立验证、边界清晰
阶段 2：基础能力	Search、Calculator、Time 等共享能力	领域可显式依赖，但权限不自动扩张
阶段 3：通用控制语义	立即、定时、暂停、恢复、禁止、确认	控制逻辑不需要为每个领域重复开发
阶段 4：固定组合	真实需求驱动的 sequence / scheduled 模板	步骤依赖、结果传递、失败语义稳定
阶段 5：偏好与自动联动	事实、长期策略、历史与跨功能联动	自动行为可解释、可撤销、不会误把讨论当事实
阶段 6：复杂工作流	并行、汇合、补偿、动态计划等	存在至少多个真实任务证明简单模型无法满足

18. 新功能归类与设计检查清单
以后每新增一个功能，不必先问“我要加几个工具”，而应依次回答以下问题：
1.	这是模型内部认知过程，还是必须接入外部现实世界能力？
2.	如果是外部能力，它是跨领域 Primitive，还是具有领域语义的 Domain Capability？
3.	它是否会产生副作用？副作用是否可逆？是否需要确认？
4.	它是否依赖专业数据源？Search 是主要来源、增强来源，还是禁止作为 fallback？
5.	这项能力需要立即执行、定时执行、暂停/恢复，还是只在当前对话中使用？
6.	这些控制语义能否复用现有 Control Plane，而不是新增领域专用工具？
7.	这个任务是 single 就能完成，还是确实需要 sequence/scheduled？
8.	外部结果的 trust level 是什么？是否可能携带提示注入或隐私外发风险？
9.	系统中该能力的 Installed、Authorized、Exposed、Executed 状态分别是什么？
10.	是否真的出现了重复需求，足以支持抽象新的公共层？还是应该保持局部简单？
19. 术语表
术语	本文含义
LLM Runtime	模型负责理解、抽取、规划、综合和生成的认知运行环境。
Primitive Capability	可以被多个领域复用的基础外部能力。
Domain Capability	具有领域语义、专业数据或专业动作的能力。
Capability Plan	为了完成 Goal 而显式执行的一组能力步骤；可以为空。
Control Plane	负责调度、工作流状态、通知、暂停恢复等控制语义的内部系统。
ExecutionPolicy	模型/Provider、预算、超时、重试、fallback 等运行策略。
PermissionPolicy	决定谁、在什么上下文、能使用哪些能力以及是否需要确认。
DeliveryPolicy	决定结果发送到哪里、什么时候发送以及如何避免重复。
Capability Registry	系统能力的统一目录和策略输入，不等于权限授予器。
AOP / Cross-cutting	跨越各能力统一执行的鉴权、审计、限流、隐私、校验等治理逻辑。
Fallback	首选能力失败时，在明确策略允许下使用的替代能力。
Augmentation	首选领域能力之外的可选增强信息源。
Trust Level	对能力输出可信程度和使用方式的分类。
Plan IR	用于表达 Goal、步骤、触发和策略的中间任务表示。

20. 最终架构原则
原则一：认知与执行分离：模型负责理解和规划，外部能力负责可验证的现实世界动作。
原则二：能力与控制分离：天气、论文、股票、Git 不各自重复实现定时、暂停和恢复。
原则三：搜索显式化：Search 是可复用基础能力，但调用必须可见、可追踪，不作为透明切面。
原则四：专业数据优先：实时天气、行情、论文元数据等优先使用专业能力；Search 只在明确策略下增强或降级。
原则五：权限不继承：领域依赖基础能力不等于自动获得基础能力权限。
原则六：按需暴露：系统拥有能力不等于每轮都向模型展示能力。
原则七：控制平面声明式：模型表达“何时、是否、如何触发”，但不直接掌握底层调度器和任意外发控制权。
原则八：先单元后组合：先把原子能力做稳，再加入 sequence、scheduled；真实需求出现前不做完整 DAG。
原则九：动态事实不写死提示词：位置、行程、临时提醒等动态信息应作为状态/事实管理，系统提示词只保存稳定边界。
原则十：自动联动基于策略：“旅行后天气跟随地点”属于事实 + 长期策略 + 动作，而不是为每句话增加一个工具。
原则十一：外部内容默认不可信：搜索和网页结果作为资料使用，不能反向改变系统权限、工具或计划。
原则十二：抽象必须由真实重复需求驱动：不为了未来可能出现的复杂度提前造大而全的框架。

最终结论
Kurumi 的长期方向不是“工具越多越智能”，而是形成一套稳定的能力边界、选择机制、控制语义与安全策略，使模型能够在有限且可审计的现实能力集合中，自然理解用户意图、组合已有能力并可靠执行。
