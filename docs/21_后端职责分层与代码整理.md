# 后端职责分层与可插拔实现

分层、依赖规则、插件和共享包清单在[文档1](1_总体架构与设计原则.md)。本文只写文档1没有的内容：共享代码的归属、同步适配器契约、插件生命周期、模型与后端的分工，以及统一表达与通知。确认机制见[文档6](6_二次确认.md)，权限见[文档24](24_统一身份与权限管理.md)，连续性记忆和自主行动的契约见[文档25](25_人格、记忆与会话连续性.md)。

## 功能

- 每个领域独立装配工具、服务和确认后端，只在出现第二个真实使用者时才抽共享代码，不建全局容器或通用工作流引擎。
- 存储和策略的实现可以按配置选择，选择不出现在模型工具参数里。
- 助手的说明、确认邀请与进度由模型按人格生成。后端提供执行状态、冻结业务事实和结构化错误，领域 runner 仍可能返回技术故障文本。

## 接口

### 共享代码的唯一实现

| 职责 | 位置 |
| --- | --- |
| 沙箱执行与进程树终止 | `chatbot/packages/sandbox/index.js` |
| 可信入站与引用边界 | `chatbot/packages/trusted-inbound/index.js`，领域再加准入策略 |
| 结构化事件与脱敏 | `chatbot/packages/observability/index.js`、`tool-trace.js`（可信工具 runId 关联）、`query-privacy.js`（日志无正文白名单）；查询归 `chatbot/packages/log-query/`，见[文档18](18_跨模块链路日志查询.md) |
| 公开学术 PDF 下载 | `chatbot/packages/scholarly-source/index.js`，研究和翻译共用 |
| 论文阅读文本与页图 | `chatbot/plugins/kurumi-research/papers.js`，缓存目录由 `kurumi-research.config.cacheRoot` 配置 |
| 翻译与受管文档 | `chatbot/plugins/kurumi-papers/service.js`、`chatbot/packages/documents/index.js`，翻译不要求阅读提取成功 |
| 四个个人领域的默认实现 | `chatbot/packages/personal-domains/src/`，各 `*-plugin.ts` 独立装配 |
| 原生 exec 的参数约束与写目录围栏 | `chatbot/packages/host-exec`，复用 `coding-runtime/write-fence.js`，不导入编码插件 |
| 业务通知的表达 | `chatbot/packages/response-core/` |
| 集中构建与兼容 CLI | `chatbot/scripts/build-personal-plugins.mjs` |

个人领域的只读入口是 `chatbot/packages/personal-domains/read-model.js`。`readPlanning(stateRoot)` 返回所在地、天气设置和行程，`readActiveReminders(stateRoot)` 返回活跃的一次性提醒，`readWeatherBrief({stateRoot, config, runId, signal})` 查询当前有效地点的天气。入口按传入的运行根打开已有数据库，天气可以复用缓存并向已配置的上游查询。QQ 组合层负责授权和结果返回前的天气调用复核。

论文、编码与 QQ 频道共用 `chatbot/packages/qq-delivery/index.js` 的目标校验、限额和投递账本。`createQqDelivery(getConfig)` 提供文件和文字投递。记忆插件使用 `chatbot/packages/memory-continuity/index.js` 的 P2 存储，自主行动使用同包 `read-model.js` 的有界只读投影。后端边界测试拒绝跨插件导入。

### 适配器注册表

`chatbot/packages/domain-adapters/index.js`（类型 `index.d.ts`，包说明见[README](../chatbot/packages/domain-adapters/README.md)）只管实现身份、契约检查和固定选择：

- `registerPolicy(id, implementation)`、`registerStore(id, open)`、`resolve({policy, store})`、`ids()`。
- 每次注册有独立身份，返回只删除这一次注册的注销函数。同一工厂重新注册不会被旧句柄删除，重复 ID 被拒。解析后方法表与工厂固定，注销或重新注册只影响之后的组合，不热换运行实例。
- 接口要求同步。打开存储时检查必需方法并返回绑定原对象的契约视图；每次调用拒绝返回 Promise 或 thenable（含 `close`），并接收其 rejection。缺方法、异步实现、未知选择、打开失败都明确报错，已打开但无效的资源尽力关闭，不回退默认或临时存储。
- 测试或嵌入时，可用 `createReminderListPlugin({registry})`、`createMemoryPlugin({registry})` 或 `create*Application({registry, ...})` 注入独立注册表。

| 领域 | 配置键（`plugins.entries.<领域>.config`） | 当前生产值 |
| --- | --- | --- |
| 本人连续性记忆 | `continuityPolicyAdapter`、`continuityStoreAdapter` | `current-owner` / `sqlite` |
| 旧提醒列表、旧显式记忆（未切换模式、兼容探针和隔离回归用） | `policyAdapter`、`storeAdapter` | 默认 `default` / `sqlite`（列表）、`explicit` / `memory-file`（记忆） |

新增实现的步骤：实现领域接口，在领域的持久 `adapters.js` 注册，跑一致性测试，配置实现 ID，按[配置契约](../config/README.md)同步并重启。应用服务不用改。方法存在检查不证明事务正确，新实现还须覆盖对应领域的事务、查询、备份恢复和迁移。

领域 `policy.js` 提供默认规则，`inbound.js` 校验可信请求，`application.js/adapters.js` 固定组合；`service.js` 只消费注入的 Policy/Store 与领域模型，不导入具体实现，`store.js` 不读聊天原文。旧本地列表的 `requests.js` 管请求有效期/幂等，Store 同一事务内校验目标与版本、提交业务/审计/请求账本；文件记忆比较 revision 并原子替换。

提醒列表的独立 Cron 程序也从持久组合入口解析存储。非默认存储 ID 写入固定 payload 的 `KURUMI_LIST_STORE_ADAPTER`，只在宿主自定义入口里注册不足以让 runner 识别它，runner 不接收任意模块路径。调度器拒绝接管绑定到另一存储的旧任务。

### 通知生成 RPC

提醒列表和一次性提醒的固定 Cron CLI 只传 slot 或 UUID，调用本机鉴权 RPC `personal-reminder-list.compose`、`personal-reminder.compose`（scope `operator.admin`）。它们不能选目标、文本或路径，也不注册成模型工具。

## 原理

### 语义与执行的边界

模型把真实需求转成动作、ID、版本和结构化字段。后端负责可信身份、当前请求、参数、事务、版本和幂等，不再用聊天动词或标题正则裁决已有项的维护。ID 是不含事项正文的不透明键。后端不能证明任意自然语言与 ID 必然对应。"第六条"的列表对应、歧义澄清和单消息多项上限归[文档23](23_KnowledgeMap业务能力桥接.md)。

### 同步适配器与异步业务 API

适配器注册表只承载同步契约。KnowledgeMap 通过专门的异步客户端调用，不把 HTTP Promise 伪装成同步 Store。事项的业务事实只在 API，本地的设置、调度控制和投递账本不是业务副本。换成异步驱动要显式调整应用契约，不会静默回退旧库。

### 插件生命周期

- 四个个人领域（天气、资料、行程、一次性提醒）分别登记工具、服务和确认后端，共用集中构建。资料和行程共用历史业务库，天气从中只读有效地点，缓存使用独立库。存储契约见[文档2](2_天气模块.md#接口)。一次性提醒用 `state/personal-reminders/`。
- 宿主服务必须显式登记 `stop(ctx)`，异步清理返回 Promise 供宿主等待，不依赖 `start(ctx)` 返回的函数。论文插件把停止转交 `PaperService.stop()`，邮件插件在停止或启动失败时注销自己持有的确认注册。一次性提醒停止时还要等在途维护批次结束。
- 确认注册：每次注册有独立身份，旧注销句柄不影响后续注册，即使复用同一 provider 对象。确认后端的注册表用带版本的 `Symbol.for` 在多个宿主加载副本间共享；领域适配器注册表则属于一次组合，避免独立插件实例和测试互相污染。确认候选和记录按持久 domain 隔离，资料和行程各用自己的 provider，一次性提醒的 domain 是 `personal_reminder`，provider ID 不写入持久提案和授权。
- 带锁文件的共享库 `personal-domains` 用 `file:` 链接声明工作区依赖（`confirmation-core`、`access-control`、`knowledgemap-client`、`host-scheduling`），源码按包名导入。没有锁文件的纯 JS 插件使用公开文件的相对路径。
- Cron 的稳定执行地址是 `personal-weather/dist/reminder-cli.js`，由 `chatbot/scripts/build-personal-plugins.mjs` 在构建时生成最小的兼容转发（生成物 `dist/` 不进仓库）。新提醒用 `personal-reminders` 的 runner。旧地址不删：从备份恢复的旧任务还会用到它。

### 宿主调度

一次性提醒和提醒列表通过 `chatbot/packages/host-scheduling/` 共用原生 Cron 的注册、分页和运行观测。各领域核对自身任务归属，保留固定 runner、标识、业务状态和对账规则。

一次性提醒对账、提醒列表设置对齐和 N3 唤醒使用 OpenClaw 的 V2 服务时钟。宿主取消未来回调并等待运行中的回调。N3 按墙钟安排未来 slot，执行和停机语义见[文档25](25_人格、记忆与会话连续性.md)。

### 统一表达与通知

表达边界是"自由说明加关键事实明细"：

- 开场、称呼、语气、解释和确认邀请由模型按人格生成。业务工具只提供事实和执行状态，不指定必须原样发送的成句。
- 时间、事项、收件人等重要信息可以单独列出供核对，不预设固定标题或排列。事实含义不随表达风格改变。
- 邮件正文、论文译文等业务产物按各自任务生成。已确认的正文、附件和待投递内容保持发送时的版本，表达层不为口吻而改写。
- 相对时间理解和歧义澄清由模型负责。表达层不增加聊天关键词解析。
- 走统一表达的业务通知等模型生成后再由宿主投递。没有有效生成时记录生成失败。Cron runner 的技术错误输出另由宿主处理，边界见[文档23](23_KnowledgeMap业务能力桥接.md#限制与已知问题)。模型超时、推理或错误输出、空回复都不自动重试，也不伪造"已通知"注入下一回合。平台已受理、未知和生成失败分别记录。

`chatbot/packages/response-core/` 只处理有效可见文本、绑定会话的模型说明和不可丢失的事实，不导入业务插件或投递器：

- 后台通知经公开会话准入读取最新会话、人格和模型选择，绑定原 Agent、账号和请求人。开始、生成中和投递前复核权限与业务版本，不把后台结果当成新的本人操作。
- 说明回合关闭工具执行、消息工具、搜索和 Code Mode。OpenClaw 2026.11.1 仍可能向模型保留 3 个发现或历史回放 schema，执行侧拒绝这些调用。
- 确认领域提供 `presentationFacts` 和冻结预览哈希。回复保留模型说明，只补齐缺少的不可变事实片段。没有有效模型回复时不单独发事实清单。只有最终正文包含全部事实且平台回执成功，才记为已展示，进度、候选查询和工具输出不算。旧提案没有事实数组时用冻结预览整体。
- 列表和一次性提醒的播报：宿主读取真实事项，先认领原账本，再生成说明并保留完整事实；设置或权限变化时抑制输出。模型预算 45 秒，RPC 超时 65 秒，受管 Cron 执行 75 秒、无输出 70 秒。生成失败明确记为未发送，消费本次机会，不自动补发。
- 列表播报只让模型根据本次时刻、时区和有效项数量写一段自然开场，不给它逐项资料。宿主把当前权威快照的完整事实按原顺序追加一次。开场含任何换行、事项 ID 或至少 4 字且完整重复的标题、内容或备注时，记为生成失败并保持未发送，不静默删改，也不退回固定开场。
- 附件全部失败且无文字、引用和有效媒体时，走同一个绑定说明入口，不调用业务工具，也不拿旧文件顶替。论文和编码结果沿用原投递幂等键。完成生成后才进入发送状态，延迟的生成或回执不覆盖较新的执行轮次。

开场与进度：表达习惯归[文档25](25_人格、记忆与会话连续性.md)。QQ 入口使用公开 SDK 的 commentary 回调，在真实工具开始时发出模型已生成的进度，按回合去重。推理、工具正文、错误和媒体不进入进度。进度内容必须与实际状态一致，不能把准备尝试说成已完成。开场和进度不签发确认授权，也不替代最终结果或预览的送达回执。

### 宿主控制与自主行动

`chatbot/packages/proactive-core/` 管策略、SQLite 执行与逐条投递、自身记录、短期投影、固定 slot 调度和编排，不导入具体插件或宿主私有 dist。`kurumi-host-control` 装配全部工具授权、原生 exec 围栏及可选的 `proactive/` 组件。QQ 频道的强制钩子通过 `chatbot/packages/host-control/` 交给当前宿主配置绑定的服务。服务启动前及停止后拒绝工具调用。QQ 只转交已准入的入站元数据，主动行动接入公共 SDK 模型、只读投影、领域适配器和共享投递器。业务 Store 提供显式 `readOnly` 打开方式：不建库、不迁移、不改业务数据。完整契约见[文档25](25_人格、记忆与会话连续性.md)。

## 限制与已知问题

- 适配器接口只支持同步，不支持异步数据库驱动。调用后的契约检查不能取消第三方适配器已经启动的异步副作用，也不能替代存储自己的原子性。
- 换存储不迁移旧数据，要另做数据和 Cron 迁移验收。日志查询和备份恢复校验目前只针对默认的 SQLite 和文件格式，换库需同时补这些。
- 资料和行程的历史共库、集中构建和旧 Cron 地址保持原样，未做独立版本发布和任意热替换的验证。
- 分层规则的偏离列在[文档1](1_总体架构与设计原则.md#限制与已知问题)。
- 自主行动的源码已有离线测试，生产配置里没有启用它，启用前须主人具体批准。没有做真实付费模型和 QQ 测试，判断质量、表达和长期成本都未验证。
- 统一表达与通知在隔离环境中验证了模型样本、真实宿主和模拟平台，没有真人体验验证。事实片段检查只保证冻结快照里的片段出现，不证明自由说明的语义永远正确。
