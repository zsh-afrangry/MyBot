# 统一身份与权限管理

用一张权限矩阵管理身份敏感功能：每个 QQ 一行，每个功能一列。名单只有一名主人，群聊记录只能禁用。源配置与运行名单可通过下文的查询工具核对。

## 功能

- 主人使用矩阵显式授予的能力。成员只开放 10 项共享权限：聊天、基本会话命令（`/new`、`/reset`）、公开检索、自身论文的导入/读取/翻译/取消、QQ 回复、文件回传、任务通知。
- 成员使用独立 Agent、workspace、会话、文档目录和任务归属，默认不共享主人资料。
- 邮件、提醒、记忆、账单、Profile、行程、KnowledgeMap、代码和自动化都是主人专属，成员不开放。
- 新身份必须由操作者显式登记。系统不因“换了 QQ”推断是同一个人，聊天正文、自报身份、昵称、引用、网页、PDF 和模型参数都不能授予身份或改变接收人。
- 统一的只是身份授权。插件加载、Agent 工具上限、网络域名、文件路径、翻译模型与费用限制各自继续生效。
- 群聊授权、账号合并共享、可视化编辑器、每身份费用上限、撤回已发或已计费内容均不在范围内。

## 接口

### 身份来源

[config/access-control.json](../config/access-control.json) 是唯一编辑来源。`version=1` 是结构版本，`revision` 在每次修改时递增。`subjects` 每行字段：

| 字段 | 规则 |
| --- | --- |
| `qq` / `kind` | QQ 为字符串；`kind` 只有 `user` / `group`，身份键为 `qq:user:<QQ>` / `qq:group:<QQ>` |
| `role` / `enabled` | 恰好一个启用且不设过期的 owner（必须是 user），其余为 member；角色不隐含未来新增权限 |
| `permissions` | 权限键对应布尔值；缺省、未知身份/权限、禁用、到期一律拒绝 |
| `mailRecipients` | 只有 owner 可以配置，精确邮箱，无通配符，不按 QQ 推断 |
| `mailSenders` | 只有 owner 可以配置（最多 50 条），精确小写邮箱，无通配符 |
| `note` / `expiresAt` | 备注可选；过期后即使路由存在也不能进入 |

校验失败整份配置不应用：成员持有任何 owner-only 权限或邮件目标，返回 `capability_requires_owner_isolation`；群记录须为禁用、无授权的 member，否则校验拒绝。

### 权限

权限词汇、工具到权限的映射只在 [permissions.js](../chatbot/packages/access-control/permissions.js) 维护，未知工具拒绝；新增业务工具必须同时登记映射和测试。

| --- | --- | --- |

| 论文 | `papers.import/read/translate/cancel` | 共享权限，按 action 授权并校验归属。受管文档的入库、读取和取件同时校验 `papers.read` |
| 论文改名 | `papers.rename` | 仅 owner，映射 `kurumi_document action=rename`，不继承 read/import |
| 邮件 | `mail.status/draft/send/history`、`mail.inbox.read/attachment/manage` | 仅 owner；发信受 `mailRecipients` 约束，收件箱受 `mailSenders` 与 `mail_inbox` 确认域约束（[文档6](6_二次确认.md)、[文档20](20_邮件能力与横切扩展.md)） |

| E7 | `e7.read`、`e7.image` | 均仅主人，分别映射 `e7_data` 和 `e7_image`，见[文档27](27_E7数据插件设计.md) |
| 终端执行 | `host.exec` | 仅 owner 主私聊；可信宿主重写原生参数并限制在登记的写入范围（[文档28](28_本机编码工具委托与实验任务.md)） |
| 受控系统操作 | `host.sudo.read/manage` | 仅 owner；已在 `revision 13` 授予 owner，映射 `kurumi_host_admin` 与 `host_sudo` 确认域（[文档37](37_编码委托扩展与受控电脑管理.md)） |

| 有界任务租约 | `lease.read/manage` | 仅 owner；已在 `revision 14` 授予 owner，映射 `kurumi_lease` 与 `scoped_lease` 确认域（[文档37](37_编码委托扩展与受控电脑管理.md)） |
| 主人日志 | `logs.read` | 仅 owner，映射 `kurumi_logs`（见下） |

生产配置里 owner 当前未持有 `memory.raw.read`、`memory.organize` 和四项 `proactive.*`。

`kurumi_code` 的 `list/status/result/diff` 要求 `tasks.read`，`start/continue/cancel/rollback/reconcile/preview/merge` 要求 `tasks.code`；`personal_confirmation` 的 `coding` 域查询/预览用 `tasks.read`，确认用 `tasks.code`。`kurumi_task` 的 `start` 按 kind 要求 `tasks.research` 或 `tasks.code`，其余为 `tasks.read`。

### 主人代办白名单

`kurumi_access` 只在主人 QQ 私聊可用，执行时核验可信身份与 `access.manage`。`kurumi-access-admin.config.sourceRoot` 由操作者固定到仓库。QQ 成员默认开放；其余类别由操作者通过同一插件的 `config.enabledCategories` 逐类启用。生产配置开放下列六类。

| `category` | 可维护的条目 | 限制 |
| --- | --- | --- |
| `member`（可省略） | 按精确 `qq` 新增、调整或移除成员。可授予或收回单项共享权限、启停、改备注和到期时间（`null` 清除可选字段） | 新增须显式选权限。移除保留会话、文档和任务 |
| `mail_recipient` | 主人的 `mailRecipients`，按精确邮箱新增、移除或替换 | 同步后 To、Cc 都受约束，旧草稿也复核；空名单拒绝所有地址。维护名单不发信 |
| `mail_sender` | 主人的 `mailSenders`，按精确邮箱新增、移除或替换 | QQ 二次确认且写入后即时影响收件箱。邮件认证失败仍按单封确认处理，见[文档20](20_邮件能力与横切扩展.md) |
| `owner_tool` | `agents.entries.main.tools.alsoAllow`，按工具名新增、移除或替换 | 只新增宿主已加载、策略允许且主人持有对应权限的工具；保护 `kurumi_access`、`personal_confirmation`。查询标明其他规则仍提供的工具 |
| `exec_root` | `kurumi-host-control.config.exec.writeBoundary.additionalRoots`，按绝对目录新增、移除或替换 | 新目录须位于操作者配置的 `execDirectoryBases` 内；拒绝软链接、重叠或受保护目录，并复核固定围栏与默认工作目录。同步配置时一并更新主人提示 |
| `coding_project` | `kurumi-coding.config.projects`，按稳定项目 ID 新增、更新或移除 | 用现有编码围栏；新增、换路径或换类型须选操作者预设的 `projectCheckProfiles`，不能传命令。变更前须处理进行中和待核对的任务。项目行为见[文档28](28_本机编码工具委托与实验任务.md#工作树检查与合入) |

`list/get` 对照源与运行名单，非成员类别用 `key` 查单项。`propose` 一次冻结一个条目的前后内容及相关源配置指纹；替换算一项。主人在后续消息调用 `personal_confirmation` 的 `access` 域逐项[确认](6_二次确认.md)。`commit` 核对当前权限、提案与版本，消费单次授权并原子写入仓库；身份表变动递增 `revision`。记录存于私有 `state/access-admin/changes.sqlite`。

用 `commit` 的结果和 `status(proposalId)` 的只读反馈核对各类变更。`feedback.status` 表示写入结果。`evidence.source.status` 表示仓库配置仍符合提案或已被覆盖。`evidence.runtime.status` 根据宿主已加载的名单报告已生效、待同步或当前未生效。除 QQ 确认的发件人变更外，仓库已覆盖的旧变更可以持续生效到后续配置加载。发件人反馈中的运行版本包含本类别已生效的确认记录。两端均返回类别名单指纹。

`plugins.entries.kurumi-access-admin.config.feedbackActions` 可逐类选择 `access.member`、`access.mail_recipient`、`access.mail_sender`、`access.owner_tool`、`access.exec_root` 和 `access.coding_project`，省略时启用全部。除 QQ 确认的发件人变更外，更新后由操作者审阅配置差异、同步并重启。主人身份、群聊、权限定义、全局禁用项、管理入口、项目检查方案及执行围栏由操作者维护。 [配置同步契约](../config/README.md#同步契约)

## 原理

### 配置编译

- `sync-config.mjs` 校验来源并编译进运行配置：策略写入 `channels.kurumi-qq.accessControl`，同时派生频道 `ownerId`、`commands.ownerAllowFrom`、天气 `scheduledOwnerId`、邮件 `allowedRecipients`（以及声明 `mailSenders` 时派生的 `allowedSenders`），以及成员的 Agent 和 binding。运行配置不另存第二份权限表，消费者读编译后的运行配置。
- 写入走单文件原子替换并保存私有预备份；非法策略不写入。主人 QQ 变更被 `owner_change_requires_explicit_data_migration` 拒绝，不能靠改矩阵把旧个人资料移交给另一个 QQ。
- 收件箱在编译名单上应用晚于运行版本、绑定已消费授权且写入成功的发件人变更。新增地址须仍在仓库名单内。解析失败时暂停自动信任。操作者直接编辑配置或管理台保存，仍按标准同步流程生效。其他身份策略在配置同步和宿主重启后生效。
- 白名单反馈按冻结条目对照仓库与运行快照。成员和收件人还需达到提案要求的身份表版本。旧成员提案按留存的变更字段核对，缺少明确写入证据时保留原状态。
- `commands.ownerAllowFrom` 只服务宿主管理命令兼容，由同步派生，不手工维护。

### 执行

- 宿主强制钩子 `registerTrustedToolPolicy` 覆盖内置工具及 `tool_call`、`dispatch_action` 的内层调用。授权服务缺失时拒绝调用，装配见[文档21](21_后端职责分层与代码整理.md#宿主控制与自主行动)。`dispatch_action` 与 `tool_call` 同映射为 `chat.use`，目标工具仍独立授权。
- 授权从可信宿主取得发送者、频道、account、Agent、会话，并检查一致：owner 标志必须与实际角色相符，成员不会被标成主人。领域工具在执行入口再次复核；工具展示过滤不是唯一防线。
- 成员的 `session_status` 不能指定他人会话或更改模型。成员 Agent 的工具上限为 `MEMBER_TOOLS`（`session_status`、`web_search`、`web_fetch`、`kurumi_document`、`kurumi_translate`、`kurumi_document_send`），并显式拒绝 `read`、`write`、`edit`、`exec`、`message`、`sessions_spawn/list/history`、`automations`、`kurumi_memory` 等工具。RPC 的 `includePlugins` 目录列出可选工具，不代表成员可执行。
- 配置显式 `tools.codeMode=false`：OpenClaw 的自动 Code Mode 与本项目同名 `exec` 宿主命令策略冲突，不靠放宽 `exec` 解决。
- 后台研究/项目任务只接受 `agent:<researcher|project-…>:kurumi-task-<24位hash>` 通道、对应 Agent 和已配置工具，并复核主人的 `tasks.research` / `tasks.code`。OpenClaw 交接保留可信 channel/account/owner 标志但可能省略 senderId：只在这些固定通道接受该明确 owner 授权，或真正无 requester 的系统调用。空对象、仅缺 senderId、成员、错误频道/account 均不构成委托。main 普通回合缺少可信身份仍拒绝。
- 天气 Cron 只允许 main 的规范 UUID 会话（含 `:run:<uuid>`）和 `personal_weather_get_brief`，要求主人 `chat.use` 与 `weather.read`，不因此取得邮件等权限。OpenClaw 的 Cron 运行只带投递频道/account，没有 senderId 和 owner 标志；这种纯投递身份只在天气 Cron 通道视同系统调用，后台任务通道不接受。带 senderId 或 owner 标志、频道或 account 不对，仍按委托规则判断。
- 关闭一个管理权限不撤销已登记的 Cron，也追不回已发内容；取消已有任务按领域工具处理。禁用 `chat.use` 或身份会拒绝后续入口和投递。

### 资源与投递隔离

- owner 沿用 main、`workspace/` 和旧会话。成员使用 Agent `qq-user-<QQ>`，会话 `agent:qq-user-<QQ>:kurumi-qq:direct:<QQ>`，workspace 在 `.openclaw-fusion/users/<QQ>/workspace/`。路由与身份必须一致，成员工作区未就绪或符号链接逃逸时拒绝入站。
- `sync-persona.mjs` 向主人及启用且授予 `chat.use` 的成员投影 SOUL/IDENTITY/AGENTS/USER 四份受管文件。成员共享角色卡，用专用 [MEMBER_AGENTS.md](../scripts/fusion/templates/MEMBER_AGENTS.md)，不复制主人 USER、MEMORY、历史或研究资料。人格本身不是身份授权，人格契约见[文档25](25_人格、记忆与会话连续性.md)。
- owner PDF 在 `documents/`，成员在 `documents/subjects/<QQ>/`；同字节哈希可得到相同 ID，但目录和元数据独立，猜到 ID 取不到他人文件。上传 URL 查询的 OneBot user_id 取自发送者，忽略正文 URL；媒体缓存和暂存图片同样按身份分目录。
- `documents/jobs/` 是共享任务账本和唯一串行队列，新增任务保存可信 subject/account/Agent/会话/目标绑定，查询、取消、重发按绑定过滤。历史上无 requester 的任务只解释为主人任务。
- 翻译在准入、排队执行前、执行中（500ms 轮询）和回传前复核身份与权限；撤权会拒绝排队启动或中止活动 worker，但追不回上游已产生的费用。重启后遗留的 queued/running 标 interrupted，不自动重付费；dispatching 标未知，不盲重发。
- QQ 消息和文件始终回传被绑定的身份，不从异步闭包重新读 owner 当接收人。成员的幂等键带身份命名空间。全局滚动配额和最多 5 个等待任务仍共享，没有每身份费用上限或调度公平性保证。
- 邮件、记忆、Profile/行程、提醒、KnowledgeMap、研究/代码数据保持 owner-only；`confirmation-core` 的主人 scope 不放宽。

### 主人日志与审计

- `logs.read` 只属于 owner，映射 `kurumi_logs`，成员配置声明该权限直接拒绝。main 工具白名单另需允许 `kurumi_logs`。宿主入站提供可信 QQ 身份，执行前后检查同一身份、会话和权限；天气 Cron、研究/编码任务和后台自主不继承。查询范围、验收状态和输出限制归[文档18](18_跨模块链路日志查询.md)，不扩展到任意文件读取、写入、重启或修复。
- 授权审计写入 `.openclaw-fusion/channel/access-events.jsonl`：工具、权限、允许或拒绝码、策略 revision、可信 requester 的有限元数据和 session/run/toolCallId；不记录工具参数、聊天或 PDF 正文、凭据。

```bash
node chatbot/scripts/log-query.mjs --source access-control --json
node chatbot/scripts/log-query.mjs --source access-control --contains capability_not_allowed
```

### 后台自主身份（N3，生产未启用）

- `proactive.use/notify/read/manage` 已在词汇中登记，成员校验器拒绝；生产 `access-control.json` 没有授予任何身份。后台还需逐领域的既有读取权限，公开检索另核对 `search.use`，不继承前台 exec、文件、通用 message 或业务写入。
- 组件只在 `plugins.entries.kurumi-host-control.config.proactive.enabled=true` 且用途、主人授权、工具上限都具备时启动，生产运行配置没有这一节。运行凭据由服务端在真实宿主运行前签发，不序列化；工具参数里的主人标志、runId 或路由都不产生授权。
- 前台生命周期适配只用于撤销后台权限，不能签发权限。主动行为的规则归[文档25](25_人格、记忆与会话连续性.md)。

### 登记与撤权

新增成员：

1. 在 `config/access-control.json` 增加 `kind=user, role=member` 的真实号码，显式勾选共享权限，邮箱目标为空，递增 `revision`。不要把测试号码写入生产。
2. 运行 `access-control.mjs --check/--matrix`，审阅 `sync-config.mjs --diff` 和 `sync-persona.mjs --diff`。
3. 无活动任务时先 `sync-persona.mjs --apply` 准备隔离工作区，再 `sync-config.mjs --apply`，重启 `kurumi-fusion.service`，检查配置、人格、依赖、健康。
4. 核对同步后的准入、独立会话和跨身份拒绝。验明某个真实账号的发消息、上传或收件能力时，另核对该账号的 QQ 回执。
