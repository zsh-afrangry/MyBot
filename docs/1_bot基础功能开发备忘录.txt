======================================================================
一、当前应从哪里继续
======================================================================

没有预设的“必须立刻开工”的通用引擎。后续按主人的真实需求打开对应模块：

- 天气、行程和地点策略：见《2_天气模块的开发》。
- 提醒的新需求或故障：见《3_个人提醒》。
- 搜索质量、来源治理、留存治理或新 Provider：见《4_受控搜索模块设计》。
- 主模型、fallback、视觉或模型原生联网：见《5_主模型fallback处理》。
- 跨领域 proposal/后续确认/commit 控制边界：见《6_受控变更与二次确认机制》。

当前近期目标分为两条：继续完成 Profile P0 中不涉及 commit 的 QQ 验收；并设计、实施跨领域的
受控变更与二次确认机制，修复同轮自提交后再重测 Profile 写入。Profile 解决主人明确陈述
“我已经到了江苏省镇江市扬中市”后的当前所在地变更；天气只是读取该事实的第一个消费者，不拥有该事实。
验收完成后、选择第一个大型领域需求（如论文、股票或游戏知识）之前，先做一次架构就绪审计；审计用于
确认边界和缺口，不以提前建成通用 Router、DAG 或 Workflow Engine 为目标。

在出现多用户、远程访问、云同步或新的高风险写操作前，优先补齐权限分层、会话/轨迹留存、备份和恢复演练；
这些不是当前单机主人私聊 MVP 的阻塞项。

Profile P0 设计与实施状态（先设计完整边界、只实现首个真实字段）：

1. [x] 定义 Profile 字段目录和所有权：身份/认证不属于 Profile；提醒偏好属于提醒；行程属于 Planning；
   当前所在地属于 Profile。第一版不添加 `home_location`，也不做任意 key/value 资料编辑器。
2. [x] 把 `current_location` 定义为受控地点引用及其确认元数据，而不是自由文本、街道地址、精确 GPS 或模型记忆。
   地点先由固定 QWeather GeoAPI 消歧；唯一候选才能进入提案。
3. [-] 新增窄的 Profile 读取、`current_location.set` 提案和提交路径；当前 ID/hash/TTL/事务/审计可校验
   提案完整性，却尚不能强制“后续主人消息确认”。2026-08-23 QQ 验收发现模型可同轮 propose → commit；
   统一确认闸门见《6_受控变更与二次确认机制》，不把它扩张为通用 Task Engine。
4. [x] 将“未指定地点的天气”改为读取 Profile 的当前所在地。临时天气查询仍只影响本轮；行程、提醒、Cron
   和长期记忆不因本次 Profile P0 自动改动。
5. [-] 已完成离线迁移/回归、构建、插件/配置验证，以及只读 Profile 状态 QQ 验收；地点歧义 QQ 验收
   已通过并由后续只读状态确认无副作用。普通更新请求的“先预览、后续确认”验收失败（同轮自提交），
   必须在确认闸门接入后重测；未找到 QQ 验收已通过并由后续状态读取确认无副作用。天气已在 QQ 验收中
   正确读取当前 Profile 扬中所在地而非旧广州天河。2026-08-24 12:02（Asia/Shanghai）QQ 工具验收中，
   确定性 `formattedText` 已以“镇江扬中：”开头，未退化成“镇江”；真正的后续确认、过期/重复确认仍须在
   确认闸门接入后验收。

Profile 字段目录（设计边界，不代表全部上线）：

- `current_location`：主人当前所在的城市/区县级受控地点；Profile P0 唯一实施字段。
- 展示与本地化偏好（如称呼、语言、显示时区）：未来有真实需求时分别立项；不能从聊天自动推断。
- 提醒偏好、日程、行程、天气缓存、搜索资料、会话摘要和长期记忆：各自属于既有领域，不复制进 Profile。
- `home_location`：当前不建模；“我已经到达某地”只变更 `current_location`，不推断常住地。
- 身份认证、QQ 准入、密钥、精确地址、健康/财务等高敏感资料：不放入此 MVP Profile；如未来需要必须单独
  定义最小化、留存、读取和删除策略。

Profile P0 实际实现（2026-08-23）：

- 逻辑所有权属于 Profile；第一版为复用已审计的受控地点目录和同一 SQLite 事务，代码暂由
  `personal-weather` 插件承载，但使用独立的 `profile_current_location` 表和 Profile 服务/Repository。
  这只是 MVP 部署容器，不代表天气拥有该事实；出现第二个非天气 Profile 消费者时，再评估提取独立插件/存储。
- 迁移 v3 将已确认的旧天气默认地点一次性写入 `profile_current_location`；表内来源种类为
  `migration_seed`，对外摘要显示为 `migrated_from_weather_default`。旧
  `notification_preferences.default_place_id` 仅保留兼容读取，
  不参与后续双写；Profile 成为当前所在地的唯一事实来源。
- 主人私聊专用工具为 `personal_profile_state_get`、`personal_profile_change_propose`、
  `personal_profile_change_commit`。唯一地点候选才产生 `current_location.set` pending proposal；当前 commit
  检查 ID/hash/TTL/已有上下文并可原子更新 Profile、标记 proposal、写入最小审计，但尚未能要求后续入站主人
  消息的 approval grant。因此不能将其表述为已完成二次确认，修复设计和验收见《6_受控变更与二次确认机制》。
- `getEffectivePlace(now)` 先读取未来可能存在的已确认 `location_period`，否则读取 Profile 的
  `current_location`；因此后续未指定地点天气和每日简报会消费 Profile。临时天气查询、行程提交、提醒、
  Cron、记忆和预计航班到达均不会自动修改 Profile。
- v4 为 `places` 增加 `locality_name`：保存 QWeather GeoAPI 唯一候选返回的原始叶子地点名，而非依据
  Provider 的 `type` 或 `district` 推断。旧记录在迁移中以明确行政前缀/原 district/完整展示名依次回填，
  新写入受非空触发器保护。简报紧凑标题使用“上级市 + 叶子名”，所以“江苏省镇江扬中”显示为“镇江扬中”，
  不会退化成“镇江”；这不改变 Profile 当前所在地、坐标、QWeather 请求、行程、提醒或 Cron。
- 本轮已通过 TypeScript 构建、插件验证、配置验证，以及 14 个测试文件共 120 项回归；其中覆盖 v2→v4
  数据库迁移、县级市 `type=city` 的保存/展示、唯一地点、歧义/未找到、Hash 拒绝、过期、幂等提交和天气
  有效地点切换。2026-08-24 QQ 对 `personal_weather_get_brief` 的 `formattedText` 验收已通过；固定
  `daily-brief` CLI 复用同一 WeatherService/Formatter 路径。

二、系统快照
======================================================================

- 入口：OpenClaw Gateway + 主人 QQ 私聊；群聊永久关闭，陌生人按准入策略不应获得业务工具权限。
  受控搜索的真实非主人 QQ 回归仍在其模块待办中。
- 默认模型链：百炼 Token Plan 的 qwen3.7-plus 为主模型，naiccc/gpt-5.6-terra 为 fallback。
  这是同一 Agent 的故障回退链，不是两个独立人格或两个并行 Agent。
- 已上线能力：
  - 正常文本对话和 QQ 图片输入；
  - Profile 当前所在地的受控天气查询、每日简报、行程 proposal/confirm；持久地点保留 GeoAPI 叶子名，
    简报不会把县级市或区县缩写成上级城市；
  - 一次性提醒的 proposal/confirm、受控 Cron 投递和状态查询；
  - 仅主人私聊可调用的 personal_web_search，由 DeepSeek Search Worker 执行受控公开检索。
- 明确未开放：通用 Shell、任意文件读写、通用 Cron、任意 QQ 发送、通用浏览器/web_fetch、
  通用 web_search，以及未经确认的外部写入。

模型负责理解、归纳和生成；外部事实、时间、持久化写入、消息投递和公开检索必须经过窄接口与确定性后端。
模型说“已经完成”不等于外部动作已被执行或验证。

======================================================================
三、长期设计原则
======================================================================

1. 先做窄领域能力，再抽象

天气、提醒和搜索目前各自拥有清晰的领域动作、状态和确认边界，尚未完全解耦为通用任务系统。这是有意的
MVP 选择：在没有第二、第三个真实组合需求前，不为了抽象而提前建设 Task Engine、DAG 或通用工作流。
未来若真实组合反复出现，再从证据中提取 TaskSpec、TriggerSpec、ExecutionContext、Provenance 等公共边界。

2. 写操作必须可预览、可确认、可审计

需要改变外部状态的能力应遵循“typed proposal → 同一上下文明确确认 → 受限 commit”的顺序。
读操作与写操作分离；失败和未知状态必须如实呈现，不用自然语言掩盖。

3. 事实来源、时间和不确定性必须可见

工具返回应说明数据源、查询/数据时间、时区、缓存或核验状态。时间字段先区分本地时区与 UTC，
不能仅凭模型常识改写；公开搜索资料默认是不可信外部内容，不视为指令。

4. 最小权限与可回滚

每项能力只暴露它必需的输入、输出和权限；配置、数据和审计分离。新增能力先有离线验证，再做主人 QQ
端到端验收；回滚优先移除精确工具准入或 Provider 配置，不破坏业务数据。

======================================================================
四、配置、数据与文档边界
======================================================================

- 运行配置：openclaw.json。密钥仅在 gateway.systemd.env 中以环境变量保存，仓库和文档只保留变量名。
- Gateway：用户级 systemd 服务 openclaw-gateway.service；改动配置后先校验，再 daemon-reload/restart。
- 人格与工具提示：chatbot/AGENTS.md、chatbot/TOOLS.md；业务插件各自拥有实现、测试和本地 SQLite。
- 运行数据：state/ 下的模块独立目录。不要通过手改 Gateway SQLite 或生产业务库来“修复”状态。
- 文档职责：
  - 本文只记录系统级边界、跨模块决定和未开始的通用工作；
  - 2、3、4、5 分别是天气、提醒、受控搜索、主模型 fallback 的唯一实施记录；
  - 临时探查、一次性脚本改造过程和被正式结论替代的草稿不再保留在 docs 中。

五、全局待办（已记录，尚无触发条件时不提前实施）
======================================================================

- 文件与附件能力（暂缓）：未来按 Attachment Ingress、格式/大小/安全检查、Markdown/CSV/XLSX/DOCX
  解析、LLM 理解和受控文件输出分层设计。Skill 只描述使用规则，不能替代附件传输、二进制解析和权限边界。
- 会话、记忆与 RAG（暂缓）：先区分会话上下文、工作摘要、显式长期记忆、领域业务状态和文档知识库；
  在没有稳定语料规模与检索需求前不引入向量数据库，也不自动从全部聊天提取长期记忆。
- 权限与留存治理：在多账号、远程访问、云同步或共享主机前，明确原始会话、trajectory、备份和日志的
  访问控制、保留期、清理与恢复演练。
- 大型领域需求前审计：检查能力清单、工具可见性、读写/确认边界、来源与时区、状态和审计、错误/超时、
  模型 fallback 及回滚；以第一个真实大型需求验证架构，不把该需求强行抽象成最终通用架构。
- 新外部能力：邮箱、代码执行、第三方账号或支付类能力均单独立项，先定义输入、确认、审计和回滚。
- 运维：版本升级、Provider 更换、成本或异常告警、备份恢复均应先在可回滚环境验证。

======================================================================
六、统一开发与验收流程
======================================================================

1. 先把需求归入已有模块，或说明为何需要新模块；写清楚能力边界和非目标。
2. 为外部读写定义最小工具契约、数据来源、错误语义、时区和审计字段。
3. 做离线单元/集成测试、构建、插件检查与配置校验。
4. 重载 Gateway 后，由主人在 QQ 做最小端到端验收；记录最终结果，不保留反复试错过程。
5. 出现异常时先读取状态、日志和审计；避免通过删除数据或开放更大权限来绕过问题。
6. 验收结论稳定后更新对应主体文档，删除已被该结论取代的临时记录。
