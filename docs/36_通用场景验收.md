## 接口

`--list` 显示场景，`--target` 选择 `isolated` 或 `production`，`--scenario ID` 可限定单项。省略场景会运行该目标的全部已登记场景。

报告默认写到 `test-output/scenario-acceptance/`，`--out` 可指定 `test-output/` 下的新 JSON 文件。`--model` 仅适用于独立目标的 `confirmation`，用合成对话和角色投影复验语言理解和确认。调用实际付费模型须按[仓库授权规则](../AGENTS.md#需要单独授权的操作)执行。

汇总的 `failure` 给出失败类别及已知阶段和步骤。有进度记录时可见 `lastPassed` 与后续检查情况。确认场景记录网关准备、业务检查和清理。超时或中断时保留当时所处步骤。

`failure.diagnostic` 显示已观测的预期、实际、断言位置和脱敏的子场景错误摘要。确认场景可标明业务断言未执行。Node 测试报告保留数值、布尔值和已登记的状态值，其余比对内容显示为省略。生产失败时汇总直接列出失败检查项；基础服务、渠道和数据库健康与历史 Cron 健康分别判定，任何一项失败均不视作全通过。

`failure.reference` 提供本次留存证据的入口。确认场景可给出隔离运行目录、时间窗、消息 ID 和宿主事件引用；其他场景可从保留的临时目录生成受限来源查询，多个网关目录给出备选命令。按 `command` 和 `args` 执行现有只读日志查询。Node 测试可给出断言文件和行号。缺少可定位证据时返回不可用原因。 [文档18](18_跨模块链路日志查询.md#接口)

`cleanup` 分别报告网关停止状态、临时目录移除或保留，以及场景提供时 KnowledgeMap 测试 API 的停止状态；未知信息不推断成功。保留目录用于排障，不代表进程未退出。兼容字段 `cleanupVerified` 只表示临时目录是否移除。

### 本机对话

`node chatbot/scripts/acceptance-live-dialogue.mjs --message <合成请求> [--message <下一轮>] [--expect-tool <工具名>] [--expect-reply <文本>]` 通过回环 Gateway RPC 在新会话中等待各轮最终回复，并按会话回查日志。调用使用 `operator.write`。报告记录文本哈希、工具与授权证据。仅观察到工具调用时，业务结果记为未验证。

`--coding-check catalog` 核对实际编码后端和项目。`--coding-check protected-diff` 在独立工作树请求对 `config/access-control.json` 做一处不改变 JSON 值的空白修改，等待工作树检查和本机结果，再核对预览拒绝码 `self_maintenance_protected_diff`。两个场景均核对工具回执和链路日志。后者会保留任务记录与工作树。

## 原理

- 场景声明脚本、依赖和时限。独立 Fusion 可复用 `chatbot/tests/acceptance/isolated-gateway.mjs` 启动网关，使用专用身份、工作区、会话和业务数据，以回环 OneBot 接入正式 WebSocket。脚本按入站账本、回执、工具返回和业务状态判断是否通过。
- 报告记录 Git 版本、已运行的场景及证据，区分失败、环境阻塞和未覆盖。超时或中断会通知场景关闭临时网关与业务服务，缺少完成或清理证据时在报告中标明。
- 生产目标关联 `kurumi-fusion.service` 和监听端口，比较网关实际应用的配置版本。核对已有会话的工具目录和当前授权配置，前后复核进程和配置版本。
- 确定性模型桩共用按字节拼接的有界请求解析和上下文窗口；跨块 UTF-8 不会损坏，窗口为 262144 tokens，默认请求上限 16 MiB，`scope-proof` 为 2 MiB。
- 本机编码验收使用 `kurumi-coding.acceptance` 和[登记身份](24_统一身份与权限管理.md#身份来源)。宿主将模型回合绑定到专用 Agent、工作区和限时会话，每个会话最多启动两项任务。后台结果通过本机状态和结果查询收取。预览复用候选检查和受保护差异闸门，仅返回检查结果。关闭会话、到期或重启后须重新取得会话，执行中的任务定期复核会话授权。

### 确认测试作用域

独立宿主的可信测试装配绑定主体、会话、消息和有效期。确认核心在打开库前选择专用后端，预览和授权限于本测试作用域，后台回传使用任务保存的测试归属与收件箱。普通 OneBot 回合使用原有确认后端。

## 限制与已知问题

- `scenario-acceptance.mjs --target production` 限只读，覆盖实际应用的配置与插件启用状态。`testIngress` 保持关闭。白名单变更、确认写入、调度与隔离通知在独立实例验收。
- 本机普通对话已连通真实 Gateway 和模型，回复经 RPC 返回。主人专属工具要求可信业务身份，普通本机会话的编码调用返回 `untrusted_identity_context`。专用编码入口已通过隔离 Gateway 与本地编码替身验收，尚未在生产登记和试跑。生产本机对话会建立会话并调用付费模型，按[仓库授权规则](../AGENTS.md#需要单独授权的操作)执行。
- 默认用确定性模型和回环 OneBot。真实 QQ 登录及收件按[文档32](32_QQ渠道与SnowLuma.md)验证。业务替身和临时数据的结果限于场景记录的层级。
- 已登记的生产成员即使尚无会话也会核对路由和工具配置。会话工具目录的结论只覆盖已建立会话的账号。

## 进行中：本机直接对话验收

最终目标是主要业务的日常验收全程无需主人发 QQ。Codex 从本机发起自然语言请求，接收 Kurumi 的澄清和预览，用测试主体完成业务确认，等待后台任务，再用 `kurumi log` 和业务权威状态判定结果。真人 QQ 登录、客户端收件及主动回认按各自的证据要求单独验证。 [文档32](32_QQ渠道与SnowLuma.md) · [文档34](34_统一反馈模块.md)

已有隔离场景提供业务回查和故障判据，本机入口已验证多轮对话，编码已具备专用身份及后台回查。当前缺口是编码在实际运行实例上的验证，以及其他业务从真实模型发起、到权威状态核对的可复跑链路。

### 实施顺序

1. **跑通编码首个实例。** 获得范围明确的生产试跑授权后，登记限时本机身份并固定为已启用的 `opencode`，按配置同步契约加载。运行目录查询和受保护差异检查，核对任务检查、后台回执和预览拒绝，随后回收登记并复核授权失效。 [配置同步](../config/README.md#同步契约)
2. **复用本机对话和隔离场景。** 让现有验收入口按场景指定自然语言轮次、预览与确认条件、后台等待时限、权威查询和清理。能直接使用已登记身份的回合走本机 Gateway。依赖 QQ 可信入站、消息引用或投递的回合，在独立实例的回环 OneBot 中由用例发送和收取。隔离实例使用合成身份、测试数据和本地收件箱，确认沿用业务原有路径。生产只执行已明确授权的场景，测试身份按场景限制动作、资源和时限。 [文档6](6_二次确认.md) · [文档24](24_统一身份与权限管理.md)
3. **按下表接入业务并复跑。** 优先补一次性提醒、共享事项和账单，再接通邮件与账单导入、天气与播报、论文和查询。沿用已有的权限、重放、超时和投递异常场景。每项以同一会话、执行、提案或任务标识串起日志和权威回查。默认批次使用确定性夹具，另行登记真实模型代表样本及所需授权。 [文档18](18_跨模块链路日志查询.md#接口)

### 收口条件

- 从新会话可按业务或整批复跑。授权与依赖就绪后，从发送请求、处理测试确认、等待后台到回查结果，全程无须主人发送 QQ 消息。
- 表内每项都有可执行场景和通过记录。业务主流程至少用真实模型验证代表样本，写入和外发使用隔离业务数据与本地收件箱。编码另需完成实际运行实例的样本。触及真实渠道或供应商时按影响单独验证并记录范围。
- 同一份报告可查 Git 版本、运行目标、模型和依赖层级、业务结果、日志回查入口和清理结果。报告分别记录通过、失败、环境阻塞和未覆盖。通过以该场景的回执和状态断言为准。证据保存在 `test-output/`。
