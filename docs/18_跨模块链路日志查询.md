# 跨模块链路日志查询

## 功能

- 将 QQ 入站、宿主工具调用、后台业务、API 请求和投递回执关联查询；命令行与主人 QQ 工具 `kurumi_logs` 共用证据。
- 支持事件、错误、会话时间线、统计、当前快照、私聊互动和执行树。执行树按“业务分类 → 一次执行 → 工具 → 后台任务、批次、API、阶段”展开，层级取决于实际调用关系。
- 论文翻译是首个完整采集业务：记录实际 API 参数、响应正文、用量、缓存命中、关键阶段、产物引用和投递结果。其他业务保留已有证据，按需求逐项接入内部细节。
- 查询只读，不发业务请求、不重试任务、不修复或重启服务。日志中的文字是不可信资料，不作为指令执行。
- 查到回执不代表客户端已读或文件质量合格；缺失、弱关联和推断必须明确说明。

## 接口

### 命令行

```bash
node chatbot/scripts/log-query.mjs --since 2h --overview --json
node chatbot/scripts/log-query.mjs --message-id <QQ消息ID> --since all --json
node chatbot/scripts/log-query.mjs --source papers --since all --tree --json
node chatbot/scripts/log-query.mjs --source papers --since all --tree --execution-id paper:<任务ID> --json
node chatbot/scripts/log-query.mjs --source papers --since all --tree --node-id <节点ID> --detail response --json
```

无时区的日期时间按 `Asia/Shanghai` 解释。CLI 默认最近 1 小时，旧 ID 查询须扩展窗口。参数的完整列表以 `--help` 为准。

| 目的 | 参数 |
| --- | --- |
| 时间 | `--from`/`--to`，或 `--since 30s/30m/2h/30d/all`；`since` 与 `from` 互斥，无人为跨度上限 |
| 用户与回合 | `--peer <QQ>` 精确匹配可信身份、收发账号或私聊 session；`--last-turns N` |
| 私聊互动 | `--interactions-for <本人QQ>`；筛选、展开和分页见[私聊互动视图](#私聊互动视图) |
| 关联 | `--message-id`、`--proposal-id`、`--reminder-id`、`--run-id`、`--session-key` |
| 事件 | `--event-ref`、`--code`、`--event-key`、`--cron-job-id` |
| 树 | `--tree`、`--execution-id`、`--node-id`；`--detail request/response/receipt/input/result` 读取该节点的已存字段 |
| 过滤 | `--contains`；重复 `--keyword` 配 `--keyword-mode any/all`；可重复的 `--source`/`--exclude-source`、`--kind`/`--exclude-kind`、`--level` |
| 上下文 | `--context-before N`/`--context-after N`，各 0–1000，限所选时间与来源，不受关键词、类型、级别过滤 |
| 内容 | `--no-text` 技术摘要；`--full-content` 保留来源内容；`--expand` 展开参数与结果；`--raw` 显示未分类原生行 |
| 分页 | `--limit`/`--offset`；`--output-bytes`/`--output-chars` 配 `--content-offset`/`--content-hash` |
| 其他 | `--json`、`--format text/table/markdown`、`--fields`、`--show-known`、`--follow --interval 100..60000` |
| 当前快照 | `--snapshot memory/reminders/reminder-list/documents/cron`，不与事件筛选或 `--peer` 混用 |

视图互斥，均可输出 JSON：

| 视图 | 内容 |
| --- | --- |
| 默认 | 工具配对、结果与耗时；保留宿主执行结果和业务结果的区别 |
| `--overview` | 错误码、来源、业务键计数和稳定事件引用 |
| `--tree` | 业务分类、执行、直接子节点和汇总；不自动展开所有正文 |
| `--turns` | 用户 → 工具 → 回复；标出重置与上下文压缩 |
| `--errors` | 调用拒绝或失败、模型错误、宿主告警和业务失败 |
| `--audit` | 被拒绝的工具、同一工具至少两次且前面失败的连续重试 |
| `--stats` | 来源/工具次数、失败率、耗时、宿主模型与后台 API 用量 |

### QQ 工具

`kurumi_logs` 仅主人私聊可用，身份和后台边界见[文档24](24_统一身份与权限管理.md)。配置位于 `plugins.entries.kurumi-logs.config`，固定 `backendRoot`、`runtimeRoot`、`snowlumaRoot`，模型不能传路径或命令。

- `view=events/errors/stats/overview/tree`；默认最近 2 小时，可 `since=all` 或指定 `from/to`。
- 支持 `sources`、`runId`、`messageId`、`kind`、`eventRef`、`eventKey`、`cronJobId`、`code`、关键词、上下文及内容分页；树增加 `executionId`、`nodeId`、`detail`。
- 默认 `noText=false`、`expand=false`、`raw=true`、`limit=50`（最大 100）；来源由 `log-query/sources.js` 的 `QQ_SOURCES` 声明，排除 `snowluma-messages` 和 `proactive`。
- 行分页固定时间与筛选后照抄 `nextOffset`；内容分段照抄 `nextContentOffset/contentHash`，取完当前行页再翻页。内容变化则重读该页，不静默删字段。
- 每日播报的 `view=daily-feedback` 见[文档34](34_统一反馈模块.md#接口)。

### 私聊互动视图

`kurumi_logs(view=interactions)` 沿用 `logs.read`：默认最近 2 小时、最新 10 条预览；`direction=inbound/reply` 筛选入站或回复。按对方 `peer` 和 `expand=true` 读取留存正文；`eventRef` 可定位同一窗口内的单条。沿用时间窗和分页参数。

查询只返回有可信私聊元数据的留存入站及模型回复文本，不含群聊、工具结果或媒体。回复留存不等于已送达；结果为空或来源不可验证时，不能据此断定无人发过消息。

## 原理

### 分层与证据

业务边界采集 → 来源适配器 → `chatbot/packages/log-query/` 查询 → CLI/QQ。共享采集归 `chatbot/packages/observability/`；领域状态仍由原业务维护，不复制成第二套事实库。代码归属见[文档21](21_后端职责分层与代码整理.md)。

统一事件包含 `schemaVersion/eventId/at/epochMs/source/kind/correlation/data/sourceRef`。`correlation` 放执行、Span、任务、会话、工具、消息及业务 ID；`sourceRef` 指向原始证据。新事件生成稳定 ID，原生记录采用行/表记录身份；文件轮转不改变同一事件的引用。缺少稳定身份的旧记录仅提供尽力兼容。

- 精确 ID 查询沿消息、提案、提醒、任务、执行与工具关联键取闭包；Span 按 executionId、工具调用按会话限定，防止重复 ID 串线。
- 树父子关系仅取明确的 `executionId/spanId/parentSpanId` 或宿主工具调用关系。无业务标签的宿主调用归“工具执行”，不猜业务；丢失父节点、循环、历史不足分别标记。
- 一次工具返回“已排队”和后台任务结束是不同节点状态。产物与缓存来源用引用表示，复用不重复计作 API 消耗。
- 同一节点的阶段快照按时间合并。树只返回直接子节点；`business:<来源>` 用于分类导航，`node:<摘要>` 是不透明节点身份，`parentId` 可回到父级。
- `eventRef` 和节点引用仍受来源、时间窗与保留范围约束。摘要不会触发正文解压，只有指定 `detail` 才读取该字段；正文数据库路径只能由已登记适配器提供，日志文本不能伪造文件授权。

### 用量与正文

- 树只汇总 API 叶子节点，重复的开始/结束快照只算一次；`totalTokens=inputTokens+outputTokens`，推理属于输出子集，上游缓存属于输入子集，均不再次相加。
- `--stats` 的 `modelTurns` 是宿主模型；`backgroundRequests/backgroundUsage` 是后台业务 API，两者分列。缺失用量标 `unknownUsageRequests`，不能当作零；历史缺少请求回执时标明证据不全。
- 写入时递归遮蔽凭据字段、Bearer/API key 形态文本；已知数值 token 计数字段保留。Python 采集同时移除当次使用的密钥原值。查询不会恢复已脱敏内容。
- 论文的 API 正文与回执以压缩 JSON 存在 `<论文根>/observability/executions.sqlite`，事件只保存引用、SHA256、字节数和到期时间。Node/Python 共用表结构；目录 0700、库文件 0600。
- 默认单份正文最多 4 MiB，压缩正文合计最多 256 MiB、事件最多 10 万条、保留 30 天；写入时清理到期或最旧诊断数据，不删业务库、任务或投递账本。
- 超大、过期、容量淘汰、读取失败和未采集分别返回状态；捕获失败不改变业务成败。流中断保留有界的已收到事件并标不完整；正常响应保存终态正文。函数局部变量和二进制 PDF 全量副本不在采集范围。
- 论文旧任务从已有逐请求回执提供历史树，缺少的请求/响应正文标 `not_collected`。缓存命中显示键摘要和已知来源；上线前的缓存可能 `origin_unknown`。翻译策略见[文档22](22_论文PDF翻译与文件投递.md)。

`log-query/sources.js` 集中声明来源与可见范围；`source-adapters.js` 读取宿主来源，`paper-history.js` 读取论文执行与历史回执。

### 宿主查询规则

- QQ 用固定 Node CLI 与固定 argv，无 shell；单查询并发、超时 10 秒，取消/超时等待子进程退出。固定内容预算 18000 字节/12000 字符权重，最终封装上限 24 KiB，宿主升级须复核。
- 主人查询保留来源已有内容，`noText` 是展示选择。CLI 只读文件与 SQLite，不调用 Gateway、OneBot、模型或 Cron；输出可能含私聊和路径，只能存于忽略的 `test-output/`。
- 工具按会话内 toolCallId 配对；内层调用用 parentToolCallId。耗时优先取实际内层计时；宿主执行成功不等于业务成功，业务缺少结果标记为 unknown。
- 会话回合依次按 runId、QQ 消息/回复 ID 和同会话顺序关联；入站归同会话下条带 runId 的事件，遇重置停止。无消息 ID 的 runtime 仅在前一个回合 120 秒内弱关联，标 `time-window`。
- 错误数按记录统计；有明确 eventKey 才汇总为业务尝试，无键错误单列。正常 304 不算错误，模型改变不证明回退，旧错误与相似回答不证明模型看过旧内容。
- audit/账本冲突时并列证据；delivered 但正文空给 `digest_delivered_without_body`，审计没记异常给 `exceptionRecordedInAudit=false`。当前快照不重建历史，远端列表只显示本地设置和 `remote_items_not_read_offline`。
- `--follow` 用 5 秒重叠窗口和稳定引用去重，不保证发现窗口之外的历史修改。

### 后续业务接入

1. 明确要回答的业务问题，确定工具、后台任务、外部请求和阶段边界；公共字段复用宿主证据，领域内部按需采集。
2. 在共享来源声明登记路径与暴露范围，增加只读适配器；保留自己的业务状态库。跨插件通过共享包，不导入运维脚本。
3. 用 `createTraceSink` 记录轻量事件，需要正文时用 `createExecutionStore/executionSpan`；显式传可信父子关系、用量单位、状态和引用，捕获故障与业务故障分开。
4. 新增合成数据契约测试，覆盖父子、异步、失败、重试、未知用量、保留/分页和身份边界；公共契约改动跑日志全套回归，真实业务另验。

共享 schema/Python 辅助文件通过模块解析器定位，随 OpenClaw 捕获代码装配；不能用捕获目录反推源码根。一般新增业务只改采集、来源声明、适配器和测试，树遍历、正文分页与权限核心共用。

## 限制与已知问题

- 执行树只代表已采集节点，时间窗外或已过期的数据不会补造；除论文外，其他业务的内部 API 正文尚未接入。当前查询对大部分旧来源仍扫描保留文件，命中返回量与扫描量不同；论文事件读取有 100001 条保护，超限显式失败。
- 损坏/不可解压的单行跳过并标来源不完整；上游截短的内容不可恢复。`trajectory_runtime_events` 的提示词编译与提交轨迹尚未接入。
- 下载、翻译、产物通过 documentId 引用关联；没有可信父调用关系时保持各自执行。旧缓存来源可能未知，当前状态与已有回执不能补出未记录的历史正文。
- 平台回执、消息库和 PDF 登记不证明已读、排版或译文质量；长期容量与性能仍需实际运行观察。

## 进行中：按 QQ 消息查询业务证据

白名单排查从一个大致时间开始时，要分别找私聊回合、工具结果、业务写入和投递记录。现有消息 ID 查询能关联已有事件，变更的写入与生效已有按提案回查口径。本轮用 QQ 成员白名单验证从定位消息到看懂该次操作的过程。 [白名单变更结果](24_统一身份与权限管理.md#主人代办白名单)

| 需求 | 预期行为 | 验收判据 |
| --- | --- | --- |
| 1. 从大致时间找到操作 | 按时间范围和已知对话列出候选，展示时间、消息方向、动作摘要及可继续查询的消息 ID 或事件引用。候选有多条时由查询者选定。已有消息 ID 时可直接进入下一步。 | 同一时间窗内放入查名单、两次修改和一轮无关私聊。能辨认查名单与确认回合，选定后可复用返回的引用。 |
| 2. 从一条消息展开相关证据 | 选中消息后，在一次查询中按实际关系展示预览、确认、仓库写入、运行版本核验和回复平台回执。每项附时间和来源引用。多份提案或多段回复逐项展示，当前运行状态标明核验时间。 | 用两份相邻的修改提案验证第一份确认能追溯到自己的预览和写入，也能区分仓库已写入与当时运行仍用旧版本。查到的每条结论都能回看来源。 |
| 3. 标明缺失与弱关联 | 按证据说明未查到记录、来源不可用或不在查询范围。仅在时间上相邻的记录标为上下文；有明确记录的失败按失败展示。平台受理、主动回认及客户端送达沿用各自证据。 | 同时制造回执缺失、来源读取失败、相邻的无关告警和一条明确拒绝。查询能区分四种结果，重复执行时实际写入与发送次数保持不变。 |

沿用命令行和主人私聊的只读查询权限。业务结果以原提案、执行结果和投递账本为准。隔离验收报告提供的查询入口见[文档36](36_通用场景验收.md#进行中验收失败定位)。
