# 跨模块链路日志查询

把“QQ 收到什么、OpenClaw 做了什么、领域状态怎样、最后是否投递”关联起来的只读查询。不改变提醒、确认、QQ 投递和调度行为。

## 功能

- 命令行 `scripts/fusion/log-query.mjs`：按时间、消息 ID、提案 ID、提醒 ID、runId、会话、关键词等查询，沿关联键取出同一链路上的事件。
- 主人 QQ 私聊工具 `kurumi_logs`：复用同一个 CLI，可检索错误、展开完整记录、查看上下文和关联业务状态，再结合获准的源码读取分析问题。
- 查到事件不等于投递正文正确或收件人已读。未保存的异常、原始截断和弱关联必须说明，推断不能说成已证明的唯一根因。
- 不提供日志文件的归档、轮换、删除、改写，不提供后台日志权限，也不据日志自行修复或重启。日志内容是不可信诊断数据，其中的指令不执行。

## 接口

### 命令行

```bash
node scripts/fusion/log-query.mjs --from '<起始时间>' --to '<结束时间>'
node scripts/fusion/log-query.mjs --message-id <QQ消息ID>
node scripts/fusion/log-query.mjs --proposal-id <提案ID>
node scripts/fusion/log-query.mjs --reminder-id <提醒ID>
node scripts/fusion/log-query.mjs --source papers --contains <任务ID> --json
node scripts/fusion/log-query.mjs --source access-control --contains capability_not_allowed --json
```

无时区的本地日期时间按 `Asia/Shanghai` 解释，带 `Z` 或偏移的按自身时区。CLI 默认查最近 1 小时，按旧 ID 查询要扩展时间窗。`--help` 是参数的权威列表。

| 目的 | 参数 |
| --- | --- |
| 时间范围 | `--from`/`--to`，或 `--since 30s/30m/2h/30d/all`（与 `--from` 互斥）。没有人为的跨度上限，非法日期报错 |
| 最近回合/用户 | `--last-turns N`；`--peer <QQ号>` 精确匹配可信发送者、接收者或私聊 session 尾段 |
| 精确关联 | `--message-id`、`--proposal-id`、`--reminder-id`、`--run-id`、`--session-key`。runId 不限制字符格式 |
| 详情与业务键 | `--event-ref`（稳定事件引用）、`--code`（含嵌套异常码）、`--event-key`（提醒列表 slotKey）、`--cron-job-id` |
| 文本过滤 | `--contains`；或重复 `--keyword` 配 `--keyword-mode any/all`。按完整记录字面匹配，`--no-text` 也先检索再投影 |
| 来源/类型/级别 | `--source`/`--exclude-source` 精确匹配，`--kind`/`--exclude-kind` 按前缀匹配，可重复。`--level ERROR/FATAL` 只选有原生级别的事件 |
| 命中上下文 | `--context-before N`/`--context-after N`，各 0 到 1000，仅 events 和 errors 视图。邻居不再按关键词、类型、级别过滤，仍在所选时间和来源内 |
| 内容 | `--no-text` 无正文技术摘要；`--full-content` 读取来源已有内容、不追加查询脱敏；`--expand`（`--full`）展开参数和结果；`--raw` 显示未分类原生行 |
| 输出 | `--json`；`--format text/table/markdown`、`--fields`；`--limit`（缺省 500）、`--offset`；`--output-bytes`、`--output-chars` 配 `--content-offset`/`--content-hash` 做内容分段 |
| 快照 | `--snapshot memory/reminders/reminder-list/documents/cron`，只读当前状态，不能与事件筛选或 `--peer` 组合 |
| 其他 | `--stats`、`--follow --interval 100..60000`（JSON 为逐行事件包）、`--show-known`、`--runtime-root`、`--snowluma-root` |

视图（`--overview`、`--turns`、`--errors`、`--audit`、`--stats`、快照）互斥，`--json` 可与任一视图组合。

| 视图 | 内容 |
| --- | --- |
| 默认 | 一次工具调用合并为一行 `[tool.call]`：真实工具名、成功/失败/拒绝/未返回、错误码、耗时、每条访问决定 |
| `--overview` | 错误码、来源和业务键计数，给出稳定 eventRef |
| `--turns` | 每条会话入站为一回合，列出“用户 → 工具 → 回复”，`/new` 和上下文压缩显示为分段线 |
| `--errors` | 失败或拒绝的调用、模型错误、回合中断、宿主 WARN/ERROR/FATAL、失败 HTTP、业务失败，按错误码计数 |
| `--audit` | 每回合被拒绝的工具，和同一工具的连续重试（至少两次且前面有失败）。不判断空结果、漏检或答案是否正确 |
| `--stats` | 次数、失败率、实际测量耗时、已记录的模型用量，缺失值不补 0 |

### QQ 工具 `kurumi_logs`

- 权限点 `logs.read`，仅主人私聊。成员、群聊、天气 Cron、编码和研究任务、后台任务不继承。每次执行前后复核身份、授权和有效调用。权限归[文档24](24_统一身份与权限管理.md)。
- 参数：`view`（`overview`/`events`/`errors`/`stats`）、`since`（缺省 2h，可 `all`）或 `from`/`to`、`sources`、`runId`、`messageId`、`kind`、`eventRef`、`eventKey`、`cronJobId`、`code`、`contains`、`keywords`+`keywordMode`、`levels`、`noText`（缺省 false）、`expand`（缺省 false）、`raw`（缺省 true）、`contextBefore`/`contextAfter`、`contentOffset`/`contentHash`、`limit`（缺省 50，上限 100）、`offset`。
- 可选来源是 `chatbot/plugins/kurumi-logs/policy.js` 的 `SOURCES`，不含 `snowluma-messages` 和 `proactive`。
- 配置在 `config/runtime.config.json` 的 `plugins.entries.kurumi-logs.config`：`runtimeRoot`、`snowlumaRoot`、`backendRoot`，都必须是绝对路径。

## 原理

**QQ 工具的执行方式**

- 插件用固定 Node 脚本 `<backendRoot>/scripts/fusion/log-query.mjs` 和固定配置根启动 CLI，没有 shell，模型不能指定命令或路径。`backendRoot` 由部署者显式配置，启动前校验该脚本存在，不从 `import.meta.url` 推导，因为宿主会把插件复制到临时目录加载。
- 调用 CLI 时固定带 `--json --full-content --show-known --output-bytes 18000 --output-chars 12000`。单次超时 10 秒，单查询并发，取消或超时会等子进程退出。最终返回封装上限 24 KiB（`RESULT_BYTES`）。核更新或宿主升级时要复核这些预算，不能直接放大字节上限。
- 已授权的主人查询不强制无正文，不追加字段白名单和查询脱敏，只读登记来源里实际存在的内容。写入时已脱敏或没有记录的内容无法恢复。`noText` 只是调用者选择的摘要，不是权限边界。
- 默认窗口最近 2 小时，允许显式起止、任意有效跨度或 `since=all`。没有查到数据不证明历史上没出过错。存储保留时间不作为权限期限。
- 预算内优先返回完整事件，实际 `shown` 可能少于 `limit`，翻页照抄返回的 `nextOffset`。单条或上下文过大时用 `contentOffset`/`nextContentOffset` 分段，照抄 `contentHash` 并固定时间和全部筛选，取完后再翻行页。内容变化则重读该页，不静默删字段。
- 每个事件有稳定 `eventRef`，可用 `view=events`、`eventRef`、`expand=true` 展开单条。引用仍受时间和来源范围约束，源位置改变后可能无法解析。

**命令行的读取方式**

- 读取登记的日志、定位来源所需的本机配置和只读 SQLite，不调用 Gateway、OneBot、模型或 Cron。`--json` 输出可能含本机绝对路径（`sourceRef`）和私聊原文，不提交进 Git。
- 查询先按指定 ID 找种子事件，再沿 `qqMessageId`、`replyToId`、`proposalId`、`payloadHash`、`reminderId`、`cronJobId`、`eventKey`、`runId`、`taskId`、`toolCallId`（`parentToolCallId` 视为同一命名空间）做关联闭包。按一条 QQ 消息查，可以看到后续确认、创建 Cron、到点投递和对账结果。
- 默认隐藏未分类的原生行 `openclaw.log`、`snowluma.log`，`hiddenRaw` 给出隐藏数。
- 工具调用的配对键是外层 `toolCallId`。宿主为 `tool_call` 包装内的真实工具另写一条 `agent.tool_nested` 记录，用 `parentToolCallId` 指回外层调用。耗时取真实工具的 `timestamp - startedAt`，没有内层记录时取调用到结果的间隔。错误码优先用结果里的 `code`，否则按文本归为 `validation`、`timeout`、`tool_error`。宿主 `blocked` 和访问拒绝都算“拒绝”。
- 每次调用分别给出 `executionOutcome`（宿主执行返回）和 `businessOutcome`（结构化业务 `ok/status`，没有标记为 `unknown`）。不遍历业务文档内部任意 `ok` 字段，不由宿主未抛错推断业务成功。
- 回合归属依次按 runId、QQ 消息 ID、回复 ID、同会话时间顺序。会话入站没有 runId，绑定到同会话下一条带 runId 的事件，遇到 `/new` 停止。上下文压缩只显示 token 前后和摘要字数。
- `--errors` 中宿主行的错误码只取 `子系统:级别`。正常 HTTP 304 不算错误。错误计数按记录算，`businessAttemptCount` 只按“来源 + 明确 eventKey”计带键错误组，无键的单列为 `unkeyedErrorRecords`，不当作独立事故数，也不按时间或同码伪造因果。
- `--stats` 的模型用量来自原生 transcript。宿主没记录回退标记时 `fallbackKnown:false`，不能由模型变化推断是否发生回退。
- `--follow` 用 5 秒重叠窗口和不含文件行号的事件指纹去重，回看窗口之外的旧事件被修改不保证发现。
- 列表适配器同时读 audit 和 deliveries 账本：账本是当前保存状态，标 `snapshotOfCurrentState`；旧 audit 与账本冲突时都保留，delivered 但正文为空时给 `digest_delivered_without_body`，不回写历史库。`exceptionRecordedInAudit=false` 表示审计没保存具体异常，通用失败码和命令退出码不能冒充抛错原因。
- Cron 历史从 `task_runs.detail_json` 读取，按分区、job、起始时刻附接回执和 `error_text`，不用当前任务配置充当历史命令。

### 统一事件契约

所有适配器输出同一个 envelope，写入契约和脱敏 sink 的唯一实现是 `chatbot/packages/observability/index.js`。查询编排归 `scripts/fusion/log-query.mjs`，共享包不反向导入它。代码归属见[文档21](21_后端职责分层与代码整理.md)。

```json
{
  "schemaVersion": 1,
  "at": "2026-10-10T17:12:35.000Z",
  "epochMs": 1791652355000,
  "source": "snowluma",
  "kind": "qq.inbound",
  "correlation": {"qqMessageId": "<id>", "sessionKey": "agent:main:kurumi-qq:direct:<QQ>"},
  "data": {"text": "..."},
  "sourceRef": {"path": "...", "line": 23}
}
```

- `correlation` 只放关联键，不放凭据。支持 `sessionId`、`sessionKey`、`runId`、Trace/Span ID、QQ 消息 ID、回复 ID、提案 ID、payload hash、提醒 ID、Cron ID、event key、任务 ID。`data` 放适配器要展示的事实，`sourceRef` 只用于回到原始证据，不是抛错源码位置。
- 写入 sink 和缺省查询会递归遮蔽名为 `token`、`secret`、`password`、`authorization`、`apiKey` 等的字段，以及 Bearer/API key 形态的文本。`--full-content` 只在读取层保留来源已有内容，不改变写入格式。
- `--json` 保持 `schemaVersion/from/to/total/shown/events` 等既有字段，只增不改。消费者要读实际游标，不能只看首批就说取完了。

### 适配器与关联规则

| 适配器 | 读取位置 | 事件范围 |
| --- | --- | --- |
| `snowluma` | `snowluma/runtime/logs/snowluma-YYYY-MM-DD.log` | QQ 入站、出站、Bridge 警告。只有秒级时间，同秒内按日志顺序和消息 ID 区分 |
| `snowluma-messages` | SnowLuma `messages.db`，须显式 `--source` 加 `--message-id` 或 `--peer` | 仅已登记的私聊，不读群聊和媒体表。默认给方向、文本长度、字节数、SHA256 和与同 ID 日志预览的匹配（equal/prefix/different/unavailable），`--expand` 才给文本段 |
| `openclaw-runtime` | `runtime.log` 及留存的 `runtime.N.log` | Gateway、工具搜索、Cron、确认插件、出站会话警告 |
| `openclaw-session` | `agents/*/agent/openclaw-agent.sqlite` | 会话入站、助手文本、工具调用和结果、`agent.tool_nested`、`/new`、压缩、模型错误、回合中断，自动解压 `event_zstd` |
| `openclaw-receipt` | `channel/*-receipts.jsonl` | 任务、提醒、原生工具回执的小型摘要 |
| `personal-reminders` | `state/personal-reminders/reminders.sqlite` | 提案当前状态、授权、审计、提醒状态与投递 |
| `personal-reminder-list` | `state/personal-reminder-list/list.sqlite` 的 audit 和 deliveries 表 | 事项和设置审计、生成诊断、投递迁移 |
| `channel-delivery` | `channel/channel.sqlite` 的 outbound 账本 | sent/failed/unknown、平台消息 ID、时间。不是已读证明，当前状态标为快照 |
| `cron-runs` | `state/openclaw.sqlite` 的 `task_runs` 和 `cron_run_receipts` | 开始/结束、状态、耗时、历史命令诊断、exitCode、`error_text`。无历史时标 `historyAvailable=false` 并给回执快照，缺失退出码保持 null |
| `access-control` | `channel/access-events.jsonl`（及 `.1`） | 工具和权限点、允许/拒绝码、策略 revision、有限的 requester 元数据，不记参数和正文。规则见文档24 |
| `trace-events` | `channel/trace-events.jsonl`（及 `.1`） | 新模块主动发出的结构化旁路事件，包括编码委托的 `source=coding` 事件 |
| `kurumi-memory` | `channel/memory-events.jsonl`（及 `.1`） | 记忆工具的动作、revision 前后、结果 ID/拒绝码/耗时，不记查询、证据或正文 |
| `e7` | `channel/e7-events.jsonl`（及 `.1`） | 固定资源、HTTP 状态、缓存新鲜/304/陈旧回退、耗时，不记关键词、URL、正文 |
| `papers` | `kurumi-papers.config.root/events.jsonl`（默认 `documents/`，及 `.1`） | 翻译任务状态、附件接收类型和状态、模型分流决策、QQ 文件上传回执，不写文件名、正文、凭据 |
| `web-deepseek` | `kurumi-web-deepseek.config.traceFile`（及 `.1`），未配置则无 | Search/Fetch 的工具、状态、错误码、HTTP 状态、耗时、结果数，不记 query、URL、正文。宿主不提供 run/toolCallId，只能按时间和会话对照，设计见[文档8](8_检索功能.md) |
| `knowledgemap` | `state/knowledgemap/trace.jsonl`（及 `.1`） | API 方法、固定路径、状态、请求键、run 和业务 ID，不记正文或 token |
| `proactive` | `state/proactive/trace.jsonl`（及 `.1`） | 主动运行的技术事件：模型用量、只读查询来源哈希、自身记录 ID/version、逐条投递结果。生产未启用时没有该文件，只能经 CLI 查询 |

关联强度：`openclaw-runtime` 没有 QQ 消息 ID 的行按会话时间窗关联并标 `data.correlationQuality=time-window`；其余来源用各自的原生 ID 或事件自带的关联键。

- SnowLuma 每条带时间戳的发送记录对应一次 OneBot 发送，正文换行是同一条预览的续行，不算额外发送。适配器拼接多行预览并保留顺序。
- 附件入口用 `paper.qq_receive` 记录每项类型、状态、错误码，`paper.qq_ingress_route` 记录 `assistant_notice`/`model`（旧记录可能是 `direct_notice`）和 `modelDispatched`。查询 `--source papers --message-id <ID>`，规则见[文档22](22_论文PDF翻译与文件投递.md)。
- 对话里的 KnowledgeMap 调用通过 `chatbot/packages/knowledgemap-client/tool-trace.js` 取真实 runId：宿主 before/after_tool_call 钩子按会话和 toolCallId 关联。HTTP 头、旁路事件和后端写入日志用同一个 runId。固定 Cron 没有对话 run 时留空。
- 编码委托的 `trace-events` 记录内部任务、可信宿主 runId、外部会话/工具 ID、检查、确认、合入和投递状态，不记提示词、代码、完整终端输出。runId 只由 `chatbot/packages/observability/tool-trace.js` 从可信调用钩子关联。详见[文档28](28_本机编码工具委托与实验任务.md#日志与链路关联)。
- 五类快照只读当前状态，不重建历史。远端事项切换后只给本地设置和 `remote_items_not_read_offline`，不访问 API 或回退旧库。文档快照不验证 PDF 字节完整性。
- 追踪旁路日志在写入前检查大小，默认达到 4 MiB 时轮转，仅保留主文件和一代 `.1`，单条事件可使文件超过阈值，调用 `createTraceSink` 时可显式传 `maxBytes: 0` 关闭轮转。

### 适配器扩展契约

新模块接入日志查询的做法是“适配器 + 统一契约 + 可选旁路 sink”，不在 OpenClaw 或 SnowLuma 里注入全局 hook，也不在每个业务函数里复制切面。

1. 模块保留自己的业务日志和状态库。
2. 在模块边界调用 `createTraceSink(path).emit({...})`，或增加一个只读适配器。
3. 只发事件类型、关联键和必要摘要，不发 token、完整请求头、数据库私密字段、不必要的聊天原文。
4. 给适配器加使用合成数据的离线测试，不把真实私聊复制成夹具。

论文插件把同一契约的事件写入自己的 `events.jsonl`，由 `papers` 来源读取；提醒列表用只读审计表适配器，接入见[文档23](23_KnowledgeMap业务能力桥接.md)。读取时不拒绝未知 `schemaVersion`。参数变化要同时更新 `--help` 和本文，宿主升级后复核工具输出预算。

## 限制与已知问题

- runtime 日志没有稳定的 QQ MessageSid，时间窗关联只是辅助。没有 sessionKey 的 runtime 行只归给它之前最近的一个回合，且最多在该回合开始后 120 秒内。需要严格证明时以 SnowLuma 消息 ID、会话 transcript 和领域审计表为准。
- 没有显式关联键的旧来源可能按时间窗进入候选链路，需要核验。提醒列表的定时审计没有聊天 sessionKey，不进入最近聊天时间窗。
- `reminder_proposals`、`reminders` 是当前状态快照，不是历史。历史动作看 `reminder_audit_log`，提案原文看会话 transcript。
- 损坏或不可解压的 zstd 单行会被跳过，其他事件保留。上游日志截短的内容不可恢复，`qq.outbound` 只是日志预览，不是完整正文或已读证明。
- 宿主会话库的 `trajectory_runtime_events`（`context.compiled`、`prompt.submitted`、`model.completed`）尚未接入 `openclaw-session`，原生轨迹写入时可能已被截断。“同会话出现旧错误且输出相似”只支持历史污染的推断，不能证明模型实际看到了什么。
- 日志不为判断漏检自动联网重查，不用当前缓存补造历史 HTTP 或记忆轨迹。平台回执和消息库都不证明媒体加载、客户端排版或已读。
- 日志文件的归档、轮转、删除没有 QQ 入口。
- 长期稳定性和推断的严谨性没有观察数据，只有单轮真实使用的结论。
