# 跨模块链路日志查询

本文是当前链路查询规则。它解决“QQ 收到什么、OpenClaw 做了什么、领域状态怎样、最后是否投递”的关联问题，不改变提醒、确认、QQ 投递或调度行为。文档入口在 [`README.md`](README.md)，验收规则在 [`16_验收与测试总表.md`](16_验收与测试总表.md)。

## 当前结论

2026-10-11 已实现只读查询入口：

```bash
cd /home/afrangry/kurumi-fusion
node scripts/fusion/log-query.mjs \
  --from '2026-10-11 01:12:23' \
  --to '2026-10-11 01:14:50'
```

时间没有时区时按 `Asia/Shanghai` 解释；带 `Z` 或显式偏移的 ISO 时间按其自身时区解释。查询默认读取最近一小时，最多显示 500 条；可以用 `--json` 得到稳定的机器可读事件包。

常用关联查询：

```bash
node scripts/fusion/log-query.mjs --message-id=-1908656766
node scripts/fusion/log-query.mjs --proposal-id 3679fa2d-5059-42cc-98cf-59fd75e54f0f
node scripts/fusion/log-query.mjs --reminder-id ac8f22fe-6b90-47d8-ba65-595a8c25bda8
node scripts/fusion/log-query.mjs --contains '确认 e7d02c4363c7'
node scripts/fusion/log-query.mjs --source snowluma --source openclaw-session --json
node scripts/fusion/log-query.mjs --source papers --contains job_实际任务ID --json
```

命令只打开日志和 SQLite 的只读连接，不调用 Gateway、OneBot、模型、Cron，也不写生产运行目录。不要把 `--json` 输出直接提交到 Git：其中的 `sourceRef` 可能包含本机绝对路径，事件正文也可能包含私聊内容。

## 统一事件契约

所有适配器输出同一 envelope；`chatbot/packages/observability/index.js` 是契约与脱敏sink的唯一实现，运行插件和运维查询共同消费。查询编排仍归 `scripts/fusion/log-query.mjs`，共享包不反向导入查询脚本；代码归属见[文档26](26_基础能力插件边界整理与检索接入设计.md)：

```json
{
  "schemaVersion": 1,
  "at": "2026-10-10T17:12:35.000Z",
  "epochMs": 1791652355000,
  "source": "snowluma",
  "kind": "qq.inbound",
  "correlation": {
    "qqMessageId": "-1908656766",
    "sessionKey": "agent:main:kurumi-qq:direct:365999865"
  },
  "data": {"text": "1分钟之后提醒我做测试"},
  "sourceRef": {"path": "…", "line": 23}
}
```

`correlation` 只放关联键，不放凭据；当前支持 `sessionId`、`sessionKey`、`runId`、Trace/Span ID、QQ 消息 ID、回复 ID、提案 ID、payload hash、提醒 ID、Cron ID、event key、任务 ID 和会话 ID。`data` 保存适配器需要展示的事实，`sourceRef` 只用于回到原始证据。

契约会递归遮蔽名为 `token`、`secret`、`password`、`authorization`、`apiKey` 等字段，并遮蔽 Bearer/API key 形态的文本。新增适配器必须先通过 `normalizeTraceEvent`，不得自己定义第二种事件格式。

## 适配器与关联规则

| 适配器名 | 读取位置 | 事件范围 | 关联强度 |
| --- | --- | --- | --- |
| `snowluma` | `/home/afrangry/snowluma/runtime/logs/snowluma-YYYY-MM-DD.log` | QQ 入站、出站、Bridge 警告 | 原始日志时间和 QQ 消息 ID |
| `openclaw-runtime` | `/home/afrangry/.openclaw-fusion/runtime.log` | Gateway、工具搜索、Cron、确认插件、reconciler、出站会话警告 | 原始 Trace/Span；没有 QQ ID 的日志按会话时间窗标记为 `data.correlationQuality=time-window` |
| `openclaw-session` | `agents/*/agent/openclaw-agent.sqlite` | 会话入站、助手文本、工具调用和工具结果；自动解压 `event_zstd` | 会话库原生 `sessionId/sessionKey/runId` |
| `openclaw-receipt` | `channel/*-receipts.jsonl` | 任务、提醒和原生工具回执 | 回执中的 ID；只保留小型摘要 |
| `personal-reminders` | `state/personal-reminders/reminders.sqlite` | 提案当前状态、授权 grant、审计事件、提醒状态/投递 | 提案/提醒/Cron ID；数据库当前状态明确标为 `snapshotOfCurrentState` |
| `personal-reminder-list` | `state/personal-reminder-list/list.sqlite` 的 `audit` 表 | 添加、修改、完成、作废、过期、播报设置和 prepared/delivered/failed/unknown | 写入时保存的可信 QQ 消息/会话/事项 ID；定时汇总仅使用 slot/Cron ID，省略事项正文 |
| `trace-events` | `channel/trace-events.jsonl`（可选） | 新模块主动发出的结构化旁路事件 | 事件自身提供的关联键 |
| `papers` | `kurumi-papers.config.root/events.jsonl`（默认 `documents/`） | 翻译任务状态、本人 PDF 接收、QQ 文件上传回执 | 可信 QQ 消息/会话/任务 ID；不写 PDF 正文、凭据或下载令牌 |
| `knowledgemap` | `state/knowledgemap/trace.jsonl` 及 `.1` | API方法/固定路径、状态、请求键、run和业务ID；不记录正文或token | 与助手工具调用按runId、请求键和businessId关联 |

KnowledgeMap账单、事项与天气的对话调用通过共享 `chatbot/packages/knowledgemap-client/tool-trace.js` 取得真实runId：宿主before/after_tool_call钩子按会话和toolCallId关联，TTL/容量有界并在完成或重置清理；工厂上下文不提供runId，模型参数不参与关联。HTTP头、旁路事件及后端写入日志使用同一runId。固定Cron没有对话run时允许留空，不伪造。第二轮12条真实API事件及3条后端写日志核对见[专项证据](verification/knowledgemap-bills-round2-2026-10-17/README.md)。

查询会先按指定 ID 找种子事件，再沿 `qqMessageId`、`replyToId`、`proposalId`、`payloadHash`、`reminderId`、`cronJobId`、`eventKey`、`runId` 和 `taskId` 做关联闭包。因此按一条 QQ 消息查询时，可以看到后续确认、创建 Cron、到点投递和对账结果；按提案查询时，可以看到授权、提交和提醒投递。

SnowLuma 的一条多段发送记录可能在原始日志中占多行，查询保留各行，因为每行对应一次 OneBot 发送调用。OpenClaw runtime 也可能记录两条相同的 Cron 日志；查询不擅自删除原始证据。

## 面向未来功能的扩展

没有把 OpenClaw 或 SnowLuma 改造成共享日志系统，也没有在每个业务函数里复制一套 AOP。两套程序有自己的日志格式和升级节奏，强行注入全局 hook 会增加升级冲突、私聊泄露和停机风险。当前采用“适配器 + 统一契约 + 可选旁路 sink”：

1. 先让新模块保留自己的业务日志和状态库。
2. 在模块边界调用 `createTraceSink(path).emit({...})`，或者为它增加一个只读适配器。
3. 只发送事件类型、关联键和必要摘要，不发送 token、完整请求头、数据库私密字段或不必要的聊天原文。
4. 给适配器添加离线测试，并在 `docs/verification/SCRIPTS.md` 登记脚本或证据。

频道通用 `trace-events.jsonl` 仍是可选扩展点；论文插件将同一契约的事件写入自己的 `events.jsonl`，由 `papers` 来源读取。读取时归一化事件、筛选时间范围并按字段/字符串模式脱敏，当前不会拒绝未知 schemaVersion。提醒列表采用只读审计表适配器，接入方法和验收见[文档 19](19_提醒列表与定时汇总.md)；论文任务用量明细在对应私有任务记录中，接入与验收见[文档 22](22_论文PDF翻译与文件投递.md)。

## 已知边界

- SnowLuma 文本日志只有秒级时间；同一秒内的多条消息以日志顺序和消息 ID 区分。
- OpenClaw 原生 transcript 的部分事件以 zstd 存储，查询器已支持解压；损坏或不可解压的单行会跳过并保留其他事件。
- runtime 日志没有稳定地重复 QQ MessageSid，因此时间窗关联是辅助关系，查询会显式标注；需要严格证明时以 SnowLuma 消息 ID、会话 transcript 和领域审计表为准。
- SQLite 的 `reminder_proposals`、`reminders` 是当前状态快照，不是完整历史；历史动作使用 `reminder_audit_log`，模型提案原文使用 `openclaw-agent.sqlite` transcript。
- 无显式关联键的旧来源可能按时间窗进入候选链路，需要核验，查询不是关联正确性的自动证明；投递结论应同时查看 OneBot/频道回执和领域状态。提醒列表的定时审计没有聊天 sessionKey，不进入最近聊天时间窗。
