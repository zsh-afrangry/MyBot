## 3. 备份与恢复

### 3.1 制作备份

```bash
cd /home/afrangry/kurumi-fusion
node scripts/fusion/backup-state.mjs --label <名字>            # 在线快照
node scripts/fusion/backup-state.mjs --label <名字> --quiesce # 停写快照（跨库一致）
```

期望：`backup ok: every required item present`，退出码 0。任必需项失败即退出码 1
并声明"该备份不是有效恢复点"。

产物结构：

| 路径 | 内容 |
|---|---|
| `git/*.bundle` | 三个仓库的全部分支与标签 |
| `patches/*-uncommitted.patch` | 已跟踪的文本改动 |
| `patches/*-binary-modified.tar` | 二进制修改（文本补丁带不了内容） |
| `patches/*-untracked.tar` | 未跟踪文件（`git diff HEAD` 不含） |
| `config/` | 运行配置、凭据平面、token、插件清单与锁文件、systemd 单元 |
| `state/runtime/.../*.sqlite` | 每个数据库的 `VACUUM INTO` 一致快照（保留绝对路径层级） |
| `state/<其余目录>` | 反向白名单复制：除跳过项外全部（含 `workspace/` 记忆） |
| `EXPECTED.json` | 预期清单：仓库引用、数据库列表、必需文件、`quiesced` 真值 |
| `MANIFEST.sha256` | 全量哈希 |

**`--quiesce` 的意义**：`VACUUM INTO` 保证**单库**一致，但提醒库、调度状态、投递账本
是依次快照的，可能来自不同时刻。作为提醒对账的回退点应加 `--quiesce`。

## 4. 已知缺口（**不要把左边的结论读成右边的意思**）

### 4.1 恢复演练 ≠ 完整恢复已验收（高）—— ❌ **仍未修**

20/20 的准确定义是：**材料、主要目录与数据库的恢复检查通过**。它**没有**证明恢复副本能跑起来。
实测在恢复副本中：

```text
QQ 插件解析 ws                                 MODULE_NOT_FOUND
QQ 插件解析 openclaw/plugin-sdk/media-runtime  MODULE_NOT_FOUND
personal-weather/dist/index.js                 不存在
personal-confirmation/dist/index.js            不存在
openclaw.json 中指向生产运行目录的绝对路径      9 处
```

原因：

1. **构建产物不在 Git 里**。`**/dist/` 被 gitignore，而 `personal-weather`、
   `personal-confirmation` 靠 `dist/index.js` 加载 → 恢复副本没有。
2. **SDK 与 `ws` 靠仓库根的固定软链**，该 `node_modules` 不进 Git → 克隆出来的仓库解析不到。
3. **路径改写只覆盖了 `plugins.load.paths`**。`agents.*.workspace`、
   `channels.kurumi-qq.{httpTokenFile,wsTokenFile,stateDir,mediaRoot}`、`logging.file`
   共 9 处仍指向 `/home/afrangry/.openclaw-fusion` —— 若真按这份配置启动，
   它会读写**生产状态**。

因此隔离副本验收需要：补齐所有依赖、执行构建、改写全部必要路径、**实际加载核心插件**，
并验证它访问不到生产状态。当前脚本没做到。

**修法（尚未实施）**：区分「恢复到原路径」与「隔离副本验收」两种模式；隔离模式必须准备
全部依赖（含仓库根的 SDK/`ws` 固定软链）、执行各插件构建、改写 `workspace`/`stateDir`/
`mediaRoot`/token 文件/`logging.file` 等全部路径，并实际 `import` 核心插件入口。

### 4.2 `--quiesce` 的失败路径不可靠（高）—— ✅ 已修

`backup-state.mjs` 中：

- 停止服务后**没有 `try/finally`**（全文 `finally` 出现 0 次），中途抛异常会留下**已停止的服务**；
- `restoreService()` 只打印错误，**不影响退出码**；
- 它**无条件**启动服务，原本就是停止状态的服务也会被拉起；
- 停止失败时调用的 `fail` 定义在调用点**之后**（第 58 行调用、第 76 行定义），会触发 TDZ 异常。

本次 FINAL 快照的数据库未发现损坏，`quiesced=true` 记录正确；**问题在工具的失败路径**。

**已修**：`fail` 声明提前到调用点之前；记住服务原本是否在跑，只在原本运行时才自动恢复；
加 `process.on('exit')` 与 `uncaughtException`/`unhandledRejection` 兜底；恢复失败计入
failures 并使退出码非零；停止后校验确实已 inactive，未生效则判为未 quiesce。已实测：
原本运行 → 停写并恢复；原本已停 → 保持停止不被拉起。

### 4.3 旧系统回退指令把旧 A / 旧 B 混为一套（高）—— ✅ 已修

`docs/15` 的启动段同时启动 `openclaw-gateway` 与 `qq-bridge`，且此前要求停止 SnowLuma。
实际拓扑是：

- **旧 A**：OpenClaw + 自带 `qqbot` 频道（不依赖 SnowLuma/qq-bridge）；
- **旧 B**：DSH + qq-bridge + SnowLuma（3083/3084）。

两者是不同方案，且旧 B 需要的传输被前面的步骤停掉了。回退应拆成**互斥的 A / B 两个选项**，
不要一次启动两个旧助手。****已修**：`docs/15` 已拆成互斥的「回退 A」与「回退 B」两套命令，并标明旧 B 需要
`sudo systemctl start dsh-web.service`、以及 DSH 就是当前网页本身。**

### 4.4 恢复端没有还原未跟踪文件与二进制修改（中）—— ✅ 已修

备份会产出 `*-untracked.tar` 与 `*-binary-modified.tar`，但 `restore-verify.mjs`
**只处理 `.patch`**，不解包也不核验这两个 tar。本次 FINAL 快照这两项为空，
所以不影响已保存内容。

**已修**：`restore-verify.mjs` 现在会解包两类 tar 并核验解出的文件确实存在。
已用含中文名未跟踪文件的备份实测通过（21/21，文件确实出现在恢复仓库里）。未来带这类改动的快照会"备份有、恢复丢"。

### 4.5 `restore-legacy.sh` 的检查强度不足（中）—— ✅ 已修

| 问题 | 现状 |
|---|---|
| 停服是否成功 | **未检查**，失败仍继续复制 |
| 复制校验 | 只比条目数与链接数，**不证明内容一致**；bridge 完全没有对应校验 |
| 目标存在性 | 用 `[ -e ]`，**漏掉失效符号链接**（`-L` 才可靠） |
| mask 检查 | 正则匹配到任意一个即报"旧单元已被 mask" |
| "最新备份" | 按名称排序，实际输出 `legacy-baselines-2026-10-05`，不是 FINAL 快照 |

**已修**：停服失败即中止且不复制任何内容；改用逐文件 sha256 清单与符号链接目标清单
比对两个还原目录（不再只比条目数）；目标存在性判断改为 `[ -e ] || [ -L ]`（能发现失效链接）；
mask 状态逐服务检查；恢复点改为按 `EXPECTED.json` 里的 `quiesced` 真值判定，
并在输出里明确说明「通过」只覆盖哪一层。

原描述如下（已不成立）：默认检查模式可用，但"通过"只代表**归档与目标路径这一层**检查通过。

| **本次通过** | 本文件最近更新那一轮实际执行并记录在 §5 |
| **历史通过** | 更早轮次记录过，本轮未复跑 |
| **未验证** | 没有执行过，不得当作已通过 |
