一、原始目标与实际边界

模型生成提案不等于主人确认；ID/hash/TTL 只能证明哪份提案，不能证明授权来源。
Profile、Planning、Reminder 保留各自提案、业务校验、数据库、事务与审计；公共核心只统一确认校验和 grant。
天气是 Profile 的消费者；确认机制没有把其他领域变成天气功能。MVP 的插件装配根不等于业务所有权。
当前不要求“一领域一插件”，拆分由实际耦合问题和重复需求推动。

二、当前实现

- chatbot/packages/confirmation-core/src/gate.ts：确认文本、提案引用、scope、时效和 grant 校验。
- chatbot/packages/confirmation-core/src/registry.ts：版本化进程注册表；跨领域候选唯一，歧义拒绝。
- chatbot/plugins/personal-confirmation/src/inbound.ts、index.ts：从可信原始 QQ 字段适配确认事件，通过 reply_dispatch 接入。
- chatbot/plugins/personal-weather/src/index.ts：装配 profile-planning、personal-reminder 两个确认后端；启动/停止时注册/解除。
- profile.ts、planning.ts、reminders.ts：领域提交事务检查并消费 grant，保留各自错误、幂等与副作用边界。
- WeatherStore 和 ReminderStore：领域库保留 confirmation_proposals / approval_grants，不新增共享 control.sqlite。

旧 personal-weather/src/confirmation-gate.ts 已删除。旧 inbound_claim 在当前没有 plugin-owned binding 的路径不可达；
“先修改 Host owner mapper 才能修复”不是现行方案。当前方案不修改 Host dist。

三、确认协议

主人后续消息的规范正文：确认 proposalId=<提案ID> payloadHash=<完整哈希>
D20：单成功提案、同 run/session、QQ final 且没有先前输出时，由 controlled-replies 交付后端 previewText 原文，其中包含完整 confirmationInstruction 和截止时间；混合/错误/分段等保留原流程。展示口令不构成授权，仍等待后续可信原始确认。
D21：confirmation-core/public-id.ts 为新的公开提案/提醒 UUID 避开 fc- 片段，解决 Host 密钥模式误脱敏普通 UUID 的已复现冲突。保留 UUID/hash/授权语义，不关闭脱敏、不迁移旧记录，内部 grant ID 不变。
必须使用可信 QQ 原始消息和身份字段；模型总结、工具输出、引用、网页、附件不能签发 grant。
仅主人私聊；account、peer、sender、session 必须与提案绑定一致。缺字段、未绑定、跨范围、候选不唯一时拒绝。
引用/转述、否定、裸确认、缺 ID/hash、错误配对、旧消息、未来异常时间均不能成为有效确认。
入站消息时效最多 5 分钟，未来容差 30 秒；grant 最多 5 分钟且不超过提案 TTL。
相同提案/入站消息不能重复签发授权。提交时校验业务状态、ID/hash、TTL、scope 和 grant，消费与业务提交在事务内完成。
已经提交的同一请求按领域幂等规则返回已有结果；不再次执行外部动作。

四、领域边界

Profile 只实现受控 current_location.set；唯一地点候选才能提案，不影响行程、提醒或 Cron。
Planning 只保存明确的 planned trip；不自动切换所在地、创建 location_period 或生成提醒。
Reminder 创建、修改、取消均先提案，再独立确认；受限 Cron adapter 的 unknown/重试/对账逻辑继续归 Reminder。
各领域的授权不随依赖继承；Profile grant 不能提交 Planning 或 Reminder。
只读能力不要求二次确认，但仍需工具级主人私聊守卫。状态查询中的既有对账写入不能被称为完全无持久化。
确定性时间显示由后端提供：Planning displayTimes；Reminder expiresAtDisplay 区分确认截止与实际触发时间。
D10 已将 expiresAtDisplay 补齐到 Planning/Profile propose 与 pending state，三个领域直接复用 time-display；不将显示值写入冻结 action payload。
