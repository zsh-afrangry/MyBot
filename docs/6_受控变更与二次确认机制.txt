一、已经做出的范围决策
======================================================================

本阶段已经决定只解决一个问题：

  主人提出有副作用的变更
      -> 领域能力创建 typed pending proposal 与预览
      -> 后续一条可信的主人 QQ 私聊消息明确确认
      -> Confirmation Gate 签发一次性 approval grant
      -> 领域 commit 校验并消费 grant，在自己的事务中写入业务状态和审计

proposal_id、payload_hash、TTL 和领域版本只能证明“要提交哪一份冻结提案”，不能证明
“主人已经在后续消息中确认”。模型在同一运行回合中看见 ID/hash，也不能因此取得 commit 权限。

这样收窄的原因已经确认：

- 当前真正暴露的是 Profile 同轮自提交，缺少的是后续可信入站事件的强制边界，而不是缺少通用任务表达式。
- Profile、Planning、Reminder 已各自拥有 typed proposal、业务校验、SQLite 事务、幂等和领域审计；
  先统一确认事实和 commit 准入即可复用这些能力。
- docs/tp.txt 要求先稳定原子能力，再由真实组合需求推动 Goal、Trigger、ExecutionPolicy 和更高阶编排；
  当前没有足够的重复组合需求证明需要立即建设完整 Control Plane。
- 统一协议不等于统一数据库。跨 SQLite 的分布式事务会把本来独立的领域绑死，因此 MVP 不建立中央
  control.sqlite。

本文件后续只记录 Gate 的实现、边界和回归结论。通用 TaskSpec、TriggerSpec、Plan IR、Capability
Registry、动态 Router、DAG、Workflow、通用 Scheduler、跨领域暂停/恢复和自动化编排均明确延期。

四、Confirmation Gate 的最小契约
======================================================================

4.1 ProposalRef

领域提案必须能够提供以下最小引用：

- domain：personal_profile、planning 或 personal_reminder；
- proposal_id、payload_hash、action_kind；
- subject_id，当前部署为 owner；
- conversation_scope：QQ 私聊及其会话/线程范围；
- created_at、expires_at；
- 领域自己的 base revision、预览和幂等信息。

提案仍由领域工具创建。Gate 不解析地点、时间、行程或提醒内容，也不替领域判断业务有效性。

4.2 ConfirmationEventRef

确认事实只能由适配器提供的可信 QQ 入站事件产生，至少应绑定：

- channel=qqbot、private-chat 标识和 subject_id；
- message_id 或同等不可伪造的入站事件 ID；
- sender_id/主人判定、会话或线程范围；
- 可用时记录 run_id、session_key、接收时间和事件摘要；
- 明确的确认解析结果，以及它唯一指向的 proposal_id。

消息正文中的“我是主人”、模型总结、工具返回值、引用文本、网页或附件中的确认都不能生成
ConfirmationEventRef。多个 pending proposal 无法唯一指向时，只能请求澄清。

4.3 ApprovalGrant

Grant 是服务端签发的一次性准入证明，不是模型参数中可自由填写的字符串。它至少绑定：

- proposal_id、payload_hash、domain、subject_id、conversation_scope；
- 产生它的 confirmation_message_id；
- issued_at、expires_at、status=pending|consumed|expired|rejected；
- 不可逆的审计摘要和消费结果。

同一确认事件最多签发一个对应提案的 grant。grant 过期、主体/私聊范围不匹配、已消费或被重放时，
commit 必须确定性拒绝且不得写入业务状态。

4.4 CommitContext

领域 commit 接收现有的 proposal_id、payload_hash 和运行时可信上下文；后端必须自行找到并
校验 grant，不把“模型是否传入了正确 ID/hash”当作确认事实。最小检查顺序为：

1. subject、QQ 私聊和会话范围匹配；
2. proposal 存在、状态仍可提交、hash/TTL/base revision 匹配；
3. grant 未消费、未过期，且绑定的是提案创建之后的可信确认事件；
4. 在领域自己的事务中同时消费 grant、改变 proposal 状态、写业务实体和写最小审计；
5. 返回明确成功、幂等成功或 approval_required/proposal_expired/proposal_unavailable/grant_replayed 等失败；
   pending 提案在本次 commit 中刚超过 TTL 时返回 `proposal_expired`，已经持久化为 expired/cancelled 等终态
   的提案返回 `proposal_unavailable`，两者都必须 fail closed 且不得写入业务状态。

模型在同一运行回合中自提 proposal 再调用 commit，必须没有有效 grant，因此必须失败。若运行时
能按当前入站事件动态隐藏 commit 工具，提案回合不暴露 commit；即使不能隐藏，后端检查仍是最终防线。

4.5 数据库和事务决定

MVP 不建立中央 control.sqlite，也不做跨 SQLite 分布式事务：

- Profile 和 Planning 的 proposal、grant、业务状态、审计先由
  state/personal-weather/weather.sqlite 所属适配器维护；
- Reminder 的 proposal、grant、提醒、审计先由
  state/personal-reminders/reminders.sqlite 所属适配器维护；
- 统一的是契约、校验顺序、失败码和回归矩阵，不是所有领域共享同一张业务表；
- 一次 commit 只写一个领域。若将来某个组合动作必须跨多个数据库原子提交，当前 Gate 不假装支持，
  应先停在 proposal 或另立 Control Plane 设计。

这样保留领域隔离，也避免“为了一个确认记录而让 Reminder 依赖 Weather schema”或引入不可恢复的
分布式提交。若某个 grant 无法和领域写入放在同一事务中消费，实施时必须 fail closed，而不是
用事后补审计掩盖窗口。

4.6 隐私与审计

审计只保留动作、领域、proposal/grant 引用、确认事件不可逆摘要、时间、结果、幂等状态和必要版本；
不保存完整 QQ 原文、完整聊天轨迹、精确地址原文、附件或网页全文。确认来源必须来自适配器元数据，
而不是用户自称或模型转述。

七、验收矩阵
======================================================================

CG-01  同轮自提交拒绝

- 对 Profile、Reminder、Planning 各执行“请求变更 -> propose -> 同一模型回合 commit”。
- 预期：三个 commit 均无有效 grant，返回确定性拒绝；revision、提醒、行程和 Cron 均不变。
- 状态：本地 Gate 回归已覆盖三个领域；Profile 的旧真实失败记录保留，新的真实 QQ 负向回归待执行。

CG-02  后续唯一确认恰好提交一次

- 主人先收到 pending 预览，再发送下一条明确确认；提案、grant 和业务写入只完成一次。
- 重发同一确认必须是定义良好的幂等结果，不创建第二条提醒、不产生第二个 trip、不增加 Profile revision。
- 状态：本地已通过；真实 QQ 待执行。

CG-03 不能由不可信文本取得确认

- 无确认、含糊确认、转述、引用、附件/网页中的“确认”、模型自述和多个 pending proposal 都不能提交。
- 无法唯一指向提案时必须请求澄清。
- 状态：本地已通过；附件/引用和真实 QQ 文本边界待执行。

CG-04 提案和确认上下文必须绑定

- 错误 ID/hash、过期 proposal、过期/已消费 grant、跨 subject、跨 QQ 私聊、跨线程、旧入站事件和
  grant 重放均不得写入。
- Gateway 重启后，未过期 pending/grant 保留明确状态；过期和已消费状态不因重启重新生效。
- 状态：本地已通过；Gateway 重启后的 durable 状态待执行。

CG-05 领域输入失败不得产生 Gate 凭证

- 地点歧义或未找到时，不创建 Profile proposal，不签发 grant，不改 Profile。
- 2026-08-23 朝阳区歧义和 Kurumi不存在地点20260823 未找到测试已通过；当前扬中、revision=2
  保持不变。该结论保留，后续只需确认 Gate 不会在失败输入上补发 grant。

CG-06 只读能力不被 Gate 误拦

- Weather、Search、Profile/Reminder/Planning state read 和计算不需要二次确认。
- 2026-08-23 天气回归已证明无显式地点时读取当前扬中并返回实际 QWeather/fresh 数据，不触发业务写入。
- Search 仍保持公开网页、来源不可信、只读和审计边界；不能因为 Gate 上线而要求无意义确认。

CG-07 Reminder 领域回归

- 创建、修改、取消、重复确认、过期/不匹配、Gateway unknown、最多 3 次明确 delivery failure retry、
  重启恢复和原地 cron.update 均保持现有语义。
- Cron 已登记不等于 QQ 已送达；状态以 Reminder state/audit 和 Gateway 对账为准。
- 状态：领域级路径和本地 Gate 已通过；真实 Gateway/Cron 回归待执行。

CG-08 Planning 领域回归

- trip proposal 只能在明确“记录/保存”意图下产生；commit 需后续确认 grant。
- 地点未消歧、时间不完整或提案过期时不切换天气地点、不创建 location period、不改提醒/Cron。
- 状态：已有 proposal/commit 和本地 Gate 回归；真实 QQ 待执行。

CG-09 身份守卫一致性

- Profile、Planning、Reminder、Search 和 Weather brief 都必须在插件执行边界拒绝非主人或群聊；
  不只依赖模型提示词、静态 allowlist 或工具描述。
- 当前 Weather brief 入口已补齐插件级主人私聊守卫。
- 状态：本地守卫测试已通过，真实 QQ 群聊/非主人负向验证待执行。

CG-10 最小审计与隐私

- 审计只保存不可逆引用/摘要、时间、结果和 grant 消费状态；不保存完整 QQ 原文和附件。
- 检查 Gateway 重启、失败和幂等路径没有把敏感原文写入业务 SQLite、会话持久化或搜索审计。
- 状态：本地审计字段检查已通过；真实 Gateway 重启和失败路径待执行。

======================================================================
八、回滚、故障处理和延期边界
======================================================================

Gate 出现异常时，优先采取以下可恢复动作：

- 禁止对应 commit 工具或让 Gate 拒绝所有 grant；保留 pending、grant、审计和业务 SQLite。
- 不删除 Profile 当前事实、不回退 revision、不删除 Reminder/Planning 历史来伪造“验收通过”。
- 对不确定的 Gateway/投递结果保持现有领域的 unknown 语义，禁止自动重发或二次修改。
- 修复后从只读状态、提案状态和审计重新建立验收证据，再恢复 commit 准入。

以下内容延期，不属于本阶段验收：

- TaskSpec、TriggerSpec、Plan IR、Capability Registry 和动态 Tool Router；
- 跨领域 DAG、Workflow、通用 Scheduler、暂停/恢复、撤销和自动补偿；
- 一个中央控制数据库或跨 SQLite 分布式事务；
- 把 Search、Weather、Reminder、Planning 抽象成任意 JSON action。

只有在出现至少一个真实、重复的组合需求，并且现有领域 Gate 因组合原子性、统一暂停/恢复或统一审计
出现可复现的维护成本时，才另立 Control Plane 文档。届时必须以真实组合案例和回归证据决定抽象边界，
不能仅因 tp.txt 中存在长期蓝图就提前实现平台。
