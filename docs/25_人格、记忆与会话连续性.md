## 回应与进度告知习惯

这类行为归人格与工具交互习惯：人格描述表达倾向，工具交互提供真实状态，统一表达层支持可见消息。它不依赖长期记忆来触发，也不把任务进度写成长期个人事实。

- 遇到需要查询或操作的请求，倾向先自然应一声，让用户知道请求已被接住。
- 处理较久或进入值得告知的阶段时，适时说明正在做什么、为何还需要等待。
- 遇到问题时，依据已知情况说明困难和接下来的打算；后续尝试须与实际行动一致。
- “我看看哈”“我帮你查查”等是用户给出的行为示例，不是要求逐字重复的台词。是否需要先回应、何时告知和具体措辞，应结合人格、当前对话与任务状态决定；不要求每轮或每次工具调用都添加前缀。

QQ显式可见进度已在隔离宿主验证；是否自然、频率和陪伴感仍需真实使用观察。表达倾向纳入受管人格／交互提示，通用工具执行规则继续说明真实状态和能力边界。任务运行状态留在本次会话或业务状态中，不新增长期记忆机制。运行事件与中途投递的技术职责归[文档21](21_后端职责分层与代码整理.md#统一表达与通知方案)。

<a id="23-检索与多个会话"></a>

### 检索与多个会话

[application.js](../chatbot/plugins/kurumi-memory/continuity/application.js) 的显式 `search` 对规范化文本做子串匹配；当前没有向量相似检索、embedding或跨会话RAG。`context()`从本次原文提取拉丁字母/数字词和连续两个汉字片段，按命中数、更新时间给事实排序；先放事实，再按新到旧放摘要，超预算的整条跳过，不截断成半条。

默认 `maxContextChars=6000`（可配置2000–12000）是选择事实/摘要的资料预算，固定规则和本次 `currentUserText` 另计，不是整个模型请求的字符上限。命中分数只影响排序，零命中事实也可能在预算内被带入；`list/search`工具返回与自动注入是不同接口。

多个QQ身份由路由分到不同Agent、workspace和会话；本人重新开聊仍读取自己的同一记忆库。后端权限映射只登记 `sessions_list`、`sessions_history` 为 `sessions.read`，还要通过宿主工具策略；`sessions_search`未登记，会拒绝，不能把“模型曾尝试搜索会话”解释成已具备全会话搜索能力。连续性插件不会遍历旧会话抽取事实，遗忘后也不得借会话工具恢复失效内容。

## 写入、更正与遗忘

模型决定当前普通话语是否值得记住，并调用受限工具；后端验证来源、结构、版本和事务，不从回复末尾自动抓取，也没有 `agent_end`后的后台全对话归纳。稳定事实/偏好与有限期摘要分开，敏感凭据拒绝，没有值得保存的内容可以不写。具体动作见[动作与参数契约](#动作与参数契约)。

<a id="术语"></a>

### 术语与并发保护

- **revision**：本人记忆状态的版本号，每次成功写入加1。写入必须带上读取时的 `expectedRevision`，与当前值不同即拒绝，调用方重新读取后再试。
- **CAS**（compare-and-set，比较后写入）：上面这种“版本相同才写入”的并发保护，在同一个SQLite事务里完成，防止两个回合互相覆盖。
- **generation**：记忆的“代”。更正一条事实的文本或遗忘一条事实时加1，并清空近期摘要。回合开始时记下generation，写入时若已变化就拒绝，旧回合因此不能把已更正或遗忘的内容写回。插件加载时的运行generation是OpenClaw的另一个字段，变化不表示记忆被改写。
- **遗忘屏障**：被更正或遗忘的原事实文本的哈希（最多保留256条）。自动记忆遇到相同文本时不再保存；本人显式要求重新记住时移除对应屏障。

### 动作与参数契约

本节维护有效工具契约；原两轮试聊、误参定位、修前失败、部署及22:41复验见[阶段记录](archive/documentation-2026-10-23/25_人格、记忆与会话连续性.md)。模型理解意图、选择动作和真实ID；后端不新增自然语言裁决，也不猜版本或静默转换字段。

| 动作 | 参数契约 |
| --- | --- |
| `list` | 只传`action` |
| `search` | `action`、必填`query` |
| `observe` | 当前普通陈述的自动保存；必填`expectedRevision`，`facts`（最多4条）与`summary`至少有一项非空；不接收顶层`text/evidence/id/kind` |
| `upsert` | 当前用户明确要求记住或更正；必填`expectedRevision`、顶层`text`，可选`evidence/kind/id`；更正使用真实ID，不接收`facts/summary`；带ID更正时`text`可由旧记录与本次原话片段拼成（见下） |
| `delete` | 遗忘传`action`、`expectedRevision`、`evidence`（本次明确要求的原话），以及`id`（一条）或`ids`（1–8个不重复真实ID）二选一；不接收`text/facts/summary` |

<a id="2026-10-21参数补正"></a>

### 参数、版本与单消息事务

以下为有效参数和执行契约；老会话模型是否刷新工具描述、真人复验是否通过，分别以实际输入与验收记录为准：

- 批量遗忘（N5）：一次`delete`可带`ids`。全部ID存在才提交，任一不存在则整批不提交并在报错中指明该ID；一次提交、generation只加一，每条被删事实各留遗忘边界。仍保持“一条消息最多成功提交一次”，因为同消息第二次写入会被回执与generation边界拒绝，所以多条遗忘必须放进同一次调用，而不是放开同消息多次提交。
- 更正拼接（G2，主人选定“允许拼接旧记录”）：只适用于带ID且文字有变化的`upsert`。新文字（规范化后）须能切分为每段至少2字的片段，每段逐字出现在旧记录或本次`evidence`中，且至少一段来自`evidence`；`evidence`仍须逐字取自本次本人原文。不带ID的新增仍要求`text`逐字取自`evidence`。模型成功后在回复里复述存下的内容。
- 少一次失败（G2）：`expectedRevision`和真实ID直接取本回合`KURUMI_PERSONAL_MEMORY_V2`的`revision`与`facts[].id`，资料里没有或版本冲突时才`list/search`；缺字段时一次报告全部缺项。
- 遗忘后不找回（G3）：被遗忘或记忆里查不到的内容直接说不记得，不调用会话搜索等其它工具找回。
- 混合写入：一句话同时要求两种写入（例如忘掉A并记住B）时先做一项，告诉主人另一项再发一句。
- 离线证据：`chatbot/tests/persona/memory.test.mjs`新增批量遗忘全有或全无、拼接更正边界（凭空内容、纯删减、2字下限、缺evidence）、缺字段合并报错用例。

唯一参数契约在[tool-contract.js](../chatbot/plugins/kurumi-memory/continuity/tool-contract.js)，同时生成模型可见说明和运行结构校验。保留提供商兼容的扁平JSON schema；`upsert.evidence`省略时仍以`text`自身作证，兼容已有调用。动作/字段误用报告具体位置和正确参数，不回显参数正文，也不静默转换`upsert + facts`。

[plugin.js](../chatbot/plugins/kurumi-memory/continuity/plugin.js)授权后校验读写；[application.js](../chatbot/plugins/kurumi-memory/continuity/application.js)复用同一校验保护直接调用，移除原笼统错误。参数校验失败不提交状态或回执，可在同一消息修参重试；成功后仅允许同参幂等重放，再变参仍被拒绝。版本冲突可重读，结果未知先查询；可信当前原文、revision/generation、来源及凭证保护不变。类型声明同步在[contracts.d.ts](../chatbot/plugins/kurumi-memory/continuity/contracts.d.ts)。

工具说明、参数描述、运行规则及[主人AGENTS模板](../scripts/fusion/templates/AGENTS.md)一致区分自动`observe`与显式`upsert`。普通陈述是否值得延续仍由模型判断，不能因为模型认为值得保存就改用显式动作；后端不加聊天关键词匹配。

<a id="何时形成跨会话记忆"></a>

### 形成跨会话记忆的时点

一次成功的 `observe/upsert`事务提交后，事实或摘要才持久化，并可在后续有效回合及`/new`后使用；回复“记住了”本身不是落库依据。每条消息最多成功写入一次，可合并最多4条事实与1条摘要；成功回执最多256条。参数失败不占成功写入，同消息可修参；成功后仅同参幂等重放。长期事实满128条时明确失败，不自行淘汰其他事实。

`observe`只根据当前可信本人原文提取，不能从模型自己的回复、旧聊天、角色虚构或业务库自动汇总成长期事实。来源保留可信message/session/run、时间、原文hash及evidence；摘要标为模型归纳并带期限，不晋升为确认事实。

### 更正与遗忘屏障

更正事实文本或遗忘时推进generation、清空本域全部近期摘要，为原文本留下最多256条哈希屏障；自动observe不能原样重存，显式重新记住可移除对应屏障。旧回合无法跨代写回。屏障是同文保护，不能解释为所有语义改写都被识别或历史材料已全部擦除。

<a id="可信来源与会话生命周期"></a>

## 会话生命周期

`reply_dispatch`只接受实际本人私聊的可信 `RawBody`，不是拼装prompt、引用、附件、网页或旧messages。`inbound.js`拒绝超过2000字符或时间偏差超过5分钟的原文，`plugin.js`另排除斜杠命令；超过长度的回合不会注入本人记忆，是否放宽仍为待决定需求。宿主声明中的 `currentUserMessage/currentUserMessageId` 在实际prompt钩子中未提供，不能据类型声明替代实际RawBody。

`before_prompt_build`核对Agent、workspace、会话、sender/channel/account、实际run和短期toolAuthority后注入；工具调用钩子再绑定真实toolCallId。写入许可从接收原文起最多5分钟，插件与应用层各自复核；`agent_end`、`before_reset`、`session_end`立即作废，旧run、旧会话或压缩钩子不能单独授予写权限。

`/new`只重开宿主可见聊天历史，保留有效事实和未过期摘要。固定宿主的reset保留sessionId、推进lifecycleRevision，不能只看sessionId是否变化来判断重开或许可有效性。原始聊天与压缩历史仍保留，不作为自动提取来源。

### 实施结构与一次机会的执行过程

沿唯一主仓库和现有Gateway/QQ插件实现，不新增系统服务、插件安装、仓库或竞争用户任务队列。

| 代码归属 | 职责 |
| --- | --- |
| chatbot/packages/proactive-core/policy.js、authority.js、store.js | 可信绑定、进程内活跃凭据、SQLite租约/事件/逐条投递及最终效果检查 |
| proactive-core/service.js、engine.js | 单次机会、模型控制结果、实际查询/来源、记录、通知与可取消编排 |
| proactive-core/scheduler.js | 固定墙钟slot、并发与停止；不创建OpenClaw Cron或修改原生heartbeat |
| proactive-core/context.js、records.js | 有限短期投影、独立自身记录、CAS/期限/代际和主人分页维护 |
| chatbot/plugins/kurumi-qq/proactive/index.js、host.js | 现有QQ注册实例内装配、唯一强制策略委托、公共SDK准入与模型、主人工具及生命周期 |
| kurumi-qq/proactive/adapters.js | P2窄读取、领域只读端口和绑定主人实际QQ传输；共享包不反向导入插件 |
| kurumi-memory/continuity/read-model.js | 当前P2事实/摘要的有限只读投影；不导入N2应用、镜像、原文或迁移 |
| personal-domains/src/read-only.ts、store.ts、reminder-store.ts | 打开现有真实只读SQLite，不创建/迁移/对账，不写缓存 |

1. 宿主到未来固定slot，先经过主人前台工作准入，再取得独立后台会话准入；正在前台处理或收到新输入时，后台让出机会。同一组件一次只运行一个机会，跨进程由SQLite租约防并发。
2. 公共SDK生成独立后台sessionId，绑定规范sessionKey、owner、策略版本、当前记忆generation、明确工具集合和唯一QQ路由，再签发本进程持有的凭据。参数里的runId、owner位、trigger或会话名均不能签发凭据。
3. 装载下面的有限信息，模型自主决定查询、维护自身记录、发言、追问或静默。可多次循环，但只用该次实际提供且已授权的工具；没有每次一条消息等限制。
4. 每次工具和最终HTTP派发前重验实际runId/agent/session、当前配置与权限、代际、租约、暂停/抢占和必要的深夜依据；通用消息/文件/执行工具及业务写入不在绑定集合中。
5. 只有显式notify会进入投递器。最终文本严格为内部JSON的done/silent，不自动发QQ；有通知请求的运行可以completed，但每条delivered/unknown独立保留，completed不代表消息成功或主人已读。

QQ仍只有原kurumi-access-control强制策略。规范N3会话委托同次注册的组件，其他会话走原身份策略；undefined代表允许，须原样传递。未装配、无活跃凭据、错主体/会话/工具或模型伪造参数全部拒绝，不另注册一个允许策略抵消拒绝。实际before_tool_call提供runId和调用ID，工具工厂参数不能替代该可信上下文。

### 唤醒、预算与上下文

| 参数 | 工程示例 / 当前机制 |
| --- | --- |
| enabled / notifyEnabled | 均false；分别控制组件和固定本人主动投递 |
| revision | 1；参数改变使旧凭据失效，重新装配后生效 |
| intervalMs | 1800000，即30分钟机会；支持明确1分钟至1天的周期，按Unix墙钟slot认领 |
| timeoutMs | 60000，即单次60秒；支持1至120秒的技术期限，不是发言次数或计费硬上限 |
| night | Asia/Shanghai 23:00–08:00；15分钟内的可信活动才可深夜发送，均待生产审核 |
| reads / publicSearch | weather、planning、reminders、reminder_list与公开Search/Fetch用途待审核；不推导额外领域权限 |

定时器首次只安排未来边界，不启动即发、不补停机旧slot、不排队积压；正在运行时不重叠，恢复后只接受新机会。暂停时仍保留调度器，但不调用模型；恢复不补跑。原生heartbeat保持0m，现有列表/天气Cron不改。30分钟意味着理论每天48次机会，实际还会因停机、暂停或前台工作减少，不等于48条消息。成本取决于每次上下文、模型/工具轮数与实际用量；fixture请求数不估算真实人民币成本，上线后应观察真实duration/usage。

上表包含宿主原生装配和N3额外提供的上下文；后者由engine生成`KURUMI_PROACTIVE_CONTEXT`，并与host的自主机会指令一起作为本次prompt交给SDK，不能把这段JSON当作模型的全部输入。实际wake使用`agentId=main`、`sessionKey=agent:main:kurumi-proactive:<owner>`，不属于Cron或子agent，也没有请求lightweight或关闭bootstrap；因此不触发上述会话类型对人格文件或根MEMORY的裁剪。当前未配置`contextInjection`，宿主默认为`always`；每次机会另有新的detached sessionId，不续接上一机会的完整历史。人格文件会参与每次自主运行的输入，仍受宿主预算、文件可读性及后续配置变化约束；P2 maxContextChars和自身记录条数只限制各自投影，不是整个prompt的总预算。人格上下文不签发工具权限或投递身份。

短期投影拒绝缺失/未来/过期平台时间与斜杠命令，凭据形态做有限脱敏；这不保证任意聊天文字绝无敏感信息，故保留私有、有限、易清除的生命周期。每次detached模型运行不持久化该次完整对话，不把上一轮自主历史反复喂回；上下文里的命令、网页及工具结果都不是授权。

### 只读端口、独立记录与工具契约

后台query只接受固定kind，不接收路径、SQL、命令、收件人或工具代理参数。领域仍独立检查主人当前权限及真实运行有效性；外部异步查询前后都复核。weather使用当前有效地点/真实天气读取与现有解析；planning投影已存地点/天气设置/行程；reminders只投影当前提醒，不reconcile；reminder_list沿KnowledgeMap GET读取，最多返回60项并给出total/truncated，用户事项事实仍归其业务API。天气可读既有缓存但不清理/写入，不运行业务迁移。

统一窄工具kurumi_proactive按可信来源区分动作：

| 调用方 / 动作 | 契约 |
| --- | --- |
| 后台query | 四类配置目录中已授权kind；返回实际sourceId/asOf/data，不签发业务写权限 |
| 后台sources | 返回本回合实际原生Search/Fetch钩子观察到的sourceId/工具/结果/时间；失败只证明尝试失败 |
| 后台remember | 仅自身interest、experience、intention；实际本回合已见且未过期的sources，更新带真实id/expectedVersion |
| 后台forget | 仅本回合已见自身记录的真实ID/version；不触碰主人事实或业务 |
| 后台notify | 只接受1–2000字符实际正文，固定主人路由；一调用对应一条平台请求，无额外发言配额 |
| 主人status / records | 分别返回调度/暂停/运行状态，或自身记录；records每页50条，用nextOffset继续，含已过期/旧代记录与active标志 |
| 主人pause / resume | 可信本人私聊加用途权限；写持久暂停/恢复并使旧机会失效，不因重启自动解除 |
| 主人record_put / record_remove | 按真实ID/version更正或删除自身记录；更正来源绑定真实主人当前运行/调用，先撤销在途判断；不修改人格/主人记忆 |

唯一新私密状态为运行根state/proactive/proactive.sqlite。wake_control保存暂停、epoch及真实活动；wake_run保存slot/租约/绑定；wake_message以实际runId+toolCallId认领逐条发送并保存哈希/真实回执；wake_source保存实际来源ID、kind、结果哈希与时效，不保存查询正文；proactive_record保存自身文字、来源ID、版本、代际、更新/到期。执行账本不是自身记忆。

自身记录每条1–1200字符、1–90天期限、1–8个已见来源，最多200条当前有效记录；这是有限上下文/存储工程界限，不是发言约束。模型可自主更新/删除或选择较短期限，不要求逐条批准。到期只停止自动注入，主人仍可分页查看、更正或删除；删除清正文/来源并留无正文的版本墓碑。旧代记录不会偷偷重新注入，主人可明确更正重新确认。这里只保存待续想法，不提供执行队列、优先级、自动完成用户事项或编码任务。

来源证明能核对实际提供或查询及结果哈希，不能证明模型推论正确、兴趣长期稳定或经验有用。业务数据仍须按需查当前事实；不能把自身意向当主人已交办，不把角色虚构当真实经历。反复调用不会更新模型权重，长期偏好只能通过后续可用的真实记录影响判断。

### 深夜、前台抢占、重启与投递

- 真实OneBot本人消息通过身份、持久去重和规范主会话路由后，先以最小元数据撤销后台，再处理附件/模型。成员、群聊、合成/重复入站不提供主人活动；缺失、未来、陈旧或乱序时刻可撤销旧判断，但不伪造刷新或回拨活动时钟。
- 深夜notify只在最后检查仍有新鲜活动时允许；无依据可继续内部只读/选择静默，不能外发。活动是必要条件，有依据也不强制说话；普通聊天回复和既有业务通知按各自规则。
- 新消息、pause、主人更正/删除记录、reset/end、权限或配置/代际变化、停机均撤销旧运行。reset/end仅匹配实际main及绑定主人/独立后台会话，拒绝事件/上下文不一致，不推导在线，不删除记录或账本。
- /new清空本功能短期投影并撤销在途决定，保留有效自身记录/暂停。P2遗忘generation变化清投影、使旧关联记录不自动注入；不从后台旧历史恢复被忘内容。P2一般聊天仍可能看见旧原文的既有边界见N7，这里未实施N2历史遮罩。
- 同一slot不重跑，同一真实调用ID不重发，复用调用ID换正文拒绝。一次新自主发言与同一发送的技术重试分开；未知不自动补发，也不据此全局禁言。
- 只有sent且有实际平台messageId记delivered，其余未知如实留账。HTTP发出后无法靠暂停撤回，迟到真实回执仍可收敛为已送达，仅更新账本，不回填已清空或较新的短期上下文，也不能凭回执取得新权限。重启将过期在途租约/发送记interrupted或unknown，既有结果不清空；停机等待已启动模型/工具/投递收束后关库。
