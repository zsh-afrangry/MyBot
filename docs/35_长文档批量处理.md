# 长文档批量处理

## 功能

让 Kurumi 一次处理几十页以上的长文档，并能按指令对照、修改和产出结果，而不是逐页人工往返。处理方式尚未确定，RAG、长上下文、分段摘要或其他方案都在待评估范围。

已有能力边界：论文 PDF 的获取、翻译和投递归[文档22](22_论文PDF翻译与文件投递.md)，公开 PDF 下载归[文档21](21_后端职责分层与代码整理.md)的 `scholarly-source`，网页检索归[文档8](8_检索功能.md)；本需求只处理这些能力之外的长文档批量理解与操作，不重复已有管线。

初步驱动场景：一次读几十页 PDF，在此基础上对照内容做修改或整理，输出可核验的产品和进度。

## 限制与已知问题

- 尚未进行调研和需求分析，技术路线未定。
- 输入格式、单批页数/大小上限、是否需要 OCR、产物形态和失败恢复方式均未知。
- 与文档22的翻译管线边界未定：翻译不等于长文档批量理解，不能把两者混成一个流程。
- 长上下文/RAG 的成本、延迟和效果未验证；不能先承诺“支持几十页”。

## 进行中：长文档批量处理

- 需求来源：2026-11-21 与 Kurumi 的聊天，主人希望一次读几十页 PDF 并对照修改。
- 待调研：RAG、长上下文、分段与检索的可行性和成本；现有论文翻译管线的哪些部分可复用。
- 待需求分析：典型文档、页数/批次上限、对照修改的语义、产物与进度、失败与恢复边界。
- 待决定：是否复用 `documentId`/论文任务存储，是否引入向量库，以及是否需要独立后台任务类型。
