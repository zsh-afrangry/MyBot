# 文档入口

这是本项目唯一的文档阅读入口，也是 `docs/` 顶层文件的**唯一目录说明**。先读本页，再按任务进入当前规则文档；
测试输出只通过[验证索引](verification/INDEX.md)与[脚本与证据索引](verification/SCRIPTS.md)查找，不把测试文件当作配置或操作说明。

`docs/` 之外还有两个文件：仓库根目录 [`AGENTS.md`](../AGENTS.md)（开发指引）与
[`README_FUSION.md`](../README_FUSION.md)（项目总览，规则指向本页）。

## 阅读顺序

1. 了解项目：先读[文档9](9_QQ融合助手架构与开发计划.md)，确认源码、运行目录和能力边界。
2. 操作或开发：读[文档10](10_融合助手运行维护.md)、[配置契约](../config/README.md)与所涉领域文档；开发助手同时遵守根 `AGENTS.md`。
3. 判断完成程度：读[文档16](16_验收与测试总表.md)；需要原始结果时进入 `verification/INDEX.md`，运行脚本前看 `SCRIPTS.md` 的授权与副作用。

## 维护规则

- 通用写作规则、规则文档模板和需求完成时的收尾清单见 [`tp2.txt`](tp2.txt)；下面各条是本项目的具体补充，冲突时以本页为准。
- 文档按职责整理，不强求一种正文模板。规则文档说明范围、现行契约、代码/数据入口、理由与待办指针；操作手册说明前提、步骤、检查与恢复；待办清单维护目标与验收；证据保留日期、版本、结果及未覆盖范围；历史资料保留原文并补替代入口。
- 状态按用途各维护一处：实现/部署范围写在规则文档开头的“状态”行；验收结论与未覆盖范围写在[文档16](16_验收与测试总表.md)；任务排期、下一步和验收负责人写在[待办清单](待办清单.md)。规则文档正文不再追加逐轮进度。本页、`AGENTS.md`只放指针；冻结证据保留取证时的原文。
- 上述状态位置与待办完成记录是本项目对 `tp2.txt` 通用模板的补充：规则文档不再单列重复的“现状”节；永久待办清单保留已完成条目，临时执行清单仍可在结论归位后撤销。`tp2.txt` 原件不改写。
- 规则文档只回答“现在怎样做、为什么有这个限制”；[文档 16](16_验收与测试总表.md)回答“哪些已经证明、哪些尚未证明”；
  详细证据放 `docs/verification/`，不复制进正文。同一条规则只在一处完整展开，其他文档链接过去。
- 新增或改变行为时，先更新对应的规则文档（9、10、12、15、16、18、19、20、21、22、23、24、25、26 或 `config/README.md`），再添加验证证据。
- 测试输出放入 `docs/verification/`，并在[验证索引](verification/INDEX.md)增加条目；不要把长日志复制进规范文档。
- 失败实验和被替代方案移入 `docs/archive/`，保留原因和替代文档链接。
- 新增、移动或归档 `docs/` 顶层文件时更新本页，并检查**正文中的路径引用**（不只是 Markdown 链接）：
  至少 `rg -n "<文件名>" docs scripts chatbot config roles`。
- 文件名是稳定的链接标识，标题可以随范围调整，不为对齐标题而改名。文档 9、21、26 的标题已与文件名不同，按本页目录里的标题理解；
  改名会让 `verification/` 里冻结证据中的链接失效。
- 历史文件只加标记与指针，不改写原始记录；过期结论写“已于 <日期> 作废”并保留原句。
- 功能完成不自动归档规则文档。只要仍承担现行操作或契约，就继续维护；已完成的实施过程可移入带来源版本的历史记录。12负责资产归属，15负责回退操作，继续分开；同一能力的后续迭代更新原归属文档，不按开发轮次新建编号；任务使用独立稳定ID。独立新主题才新增文档，从下一编号继续，不填补空号。
- 涉及具体状态的表述（工作区是否干净、远端是否同步、服务是否健康、恢复点对应哪个提交）必须带**日期与提交号**，
  不能写成永久状态。

## 文档职责与归属

- 现行编号文档共14份；历史编号1–8保留7份，不把它们列为当前待办。入口保持 `README.md`，不另建 `0_README.md`。
- 主文档保存需求、已定规则、关键理由和未完成项；16只汇总验收结论与边界；`verification/`保存阶段结果、原始输出和复验入口。长过程不在三处复制。
- 脚本/测试可按文件或套件目录关联文档；验收材料按明确目录或文件组关联文档。归属源为 [`scripts/fusion/documentation-map.json`](../scripts/fusion/documentation-map.json)，索引工具检查归属目标存在，生成表格必须与 `SCRIPTS.md` 一致。
- `chatbot/plugins/*/test/`与共享包`src/*.test.ts`是组件就地测试；`chatbot/scripts/`、`chatbot/tests/`和`scripts/fusion/`分别承担领域脚本、领域验收和运维。`docs/verification/`只放证据；`docs/archive/personal-search-tests/`的两份已退役脚本保留归档说明，不是现行测试入口。
- 新需求优先更新已有归属文档；只有产生独立维护对象才新增编号。跨仓库问题按代码归属记录，Fusion只保留外部问题指针。

## Agent 指令来源

运行/开发的 Agent 指引来源如下，改动前先确认读者与身份：

| 文件 | 读者 | 维护方式 |
| --- | --- | --- |
| `/AGENTS.md`（仓库根目录） | 开发助手 | 唯一开发指引：开发路径、保护范围、验证与授权边界 |
| `scripts/fusion/templates/AGENTS.md` | 主人运行时聊天 agent | 主人提示词模板；经 `config/persona.json` 的 `agentsSubstitution` 替换后由 `sync-persona.mjs` 写入运行 workspace |
| `scripts/fusion/templates/MEMBER_AGENTS.md` | 已登记成员的独立聊天 agent | 不带主人资料；同一同步命令写入 `users/<QQ>/workspace/`，共享人格不共享历史/记忆 |
| `chatbot/AGENTS.md` | `chatbot/tests/acceptance/` 离线脚本 | **融合前遗留**的能力登记，只作历史提示词使用，不代表当前规则 |
| 各后台工作区的 `AGENTS.md` | `project-fusion`、`researcher` | 由对应 `configure-*.mjs` 生成，随工作区存在，不在仓库维护 |

运行副本（`.openclaw-fusion/workspace/AGENTS.md`）是生成结果，不是来源：改模板后跑 `node scripts/fusion/sync-persona.mjs` 核对是否一致，不能直接改副本后声称已生效。
