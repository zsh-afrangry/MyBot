======================================================================
一、核心结论（一句话诊断）
======================================================================

一句话：偏离不在于某个模块做错了，而在于所有跨领域的东西都长在了名为
personal-weather 的第一个领域容器里。

  跨领域的 Profile、Planning、Reminder、Confirmation Gate、地点消歧 ——
  全部住在 personal-weather 内部。

weather 已从"第一个领域能力"悄悄变成事实上的公共底座。14 个业务工具全部注册在该插件下，
weather.sqlite 同时存放 Profile 事实、Planning 行程和 Gate 提案：
Profile 的"我在哪"这个人的事实，存在一个叫天气的库里。

这就是"能感觉到但说不上来"的那个偏离。它不是任何单条设计的错误，而是容器归属的错误，
因此不会体现在任何一份模块文档的自查里。

======================================================================
二、项目定位（主人 2026-08-31 明确确认，作为硬约束）
======================================================================

weather 是众多计划能力中的第一个，不是项目主题；项目目标不是天气机器人，
也不应变成"围绕 weather 开发"。

- 后续任何设计不得以 weather 为中心。
- 不得因为"personal-weather 已有现成机制"而把新能力塞进该插件。
- 新增跨领域机制（治理、控制、Primitive）必须落在领域之外的位置。
- 判断新需求归属时，先问"它属于哪个领域"，不问"weather 那边有没有现成的"。

======================================================================
三、逐条偏离（按对"说不上来的偏离感"的解释力排序）
======================================================================

① 容器错位（根因）
  现状：personal-weather 内含 Weather、Profile、Planning、Reminder 四个领域。
  证据：14/14 业务工具在该插件；store.ts 约 53KB、reminder-store.ts 约 49KB、
        reminders.ts 约 39KB、index.ts 约 35KB；state/personal-weather/weather.sqlite
        同时是 Profile 与 Planning 的库。
  后果：下一个能力只有两条路——复制机械，或也塞进 personal-weather。引力已形成。
  注：文档已承认这是"MVP 部署容器"，但承认不消除结构后果。

② 阶段跳跃
  tp.txt 阶段1=原子领域能力（天气/论文/股票/Git），阶段2=Primitive，阶段3=控制语义
  （立即/定时/暂停/恢复/确认）。实际：阶段1 只有天气一家，阶段2 只有 Search，
  却已在做阶段3 的"确认"，且是在阶段1 的容器里做。
  判断：Gate 本身必须做（同轮自提交是真实安全缺陷），偏的是位置与范围框定，不是决策。

③ 地点消歧方向倒置
  现状：Profile 的 current_location 由 QWeather GeoAPI 消歧——天气 Provider 成了
        个人资料事实的身份来源。
  tp.txt：受控地点目录应是 Primitive Capability（与 OCR/Calculator/Time 同级）。
  后果：任何"我在哪/去哪"类能力都必须经天气插件借路。

④ 控制语义已重复实现，却仍被当作"未到抽象时机"
  现状：Reminder 自建完整私有控制平面（reminder-gateway.ts / reminder-reconciler.ts /
        reminder-reconciler-service.ts：Cron adapter、reconciler、lease、稳定声明键、
        有限重试、unknown 闸门）；Weather 每日 10:30 简报另有固定 CLI/Cron。
  tp.txt 原则二：能力与控制分离，不各自重复实现定时/暂停/恢复。
  判断：重复需求已出现（约 1.5 套），阶段3 的触发条件其实已满足。
        "等真实重复需求再抽象"本是防过早抽象，目前正被用来为累积重复背书。

⑤ 能力分类未落地
  现状：只有 openclaw.json 里 15 条字符串的平铺 tools.alsoAllow，无类型/信任等级/
        外发属性/依赖/状态。只读 personal_weather_get_brief、不可信外发
        personal_web_search、需 grant 的 personal_profile_change_commit 完全同级。
  实证代价：doc 6 的 "[x] 修正 personal_weather_get_brief 缺少插件级主人私聊守卫"
        —— 守卫逐工具手写，所以会漏。

⑥ 横切治理是复制而非横切
  现状：审计三套并行（weather.sqlite 的 audit_log、reminders.sqlite 的
        reminder_audit_log、personal-search/src/audit.ts）；主人校验逐工具手写；
        配额只有 personal-search 有 quota.ts；预算/限流/超时全局缺失。
  tp.txt §15：这些应包围每一次能力调用。
  复合后果：唯一真正跨领域的 Gate 却位于 personal-weather 内，Search 与未来插件无法复用。

⑦ 文档重心失衡
  现状：doc 6 已 1411 行 / 127KB，超过其余文档之和，内容几乎全是单一机制的
        LIVE-01～16 试错流水；同期第二个领域能力进展为零。
  后果："能力—控制—编排解耦"只有在第二个非天气领域出现时才可能被验证，目前无法验证。
  附带：这也违反 tp2.txt 的"状态快照而非意图追踪"规则。

======================================================================
四、不算偏离的部分（避免过度纠偏）
======================================================================

- 缺 ExecutionPolicy 与显式 Model Stage：正确。tp.txt 只在需要独立运行语义时才要求显式化。
- 无 DAG / 动态 Router / TaskSpec / 中央 control.sqlite：正确，属明确延期项。
- 领域各自持有 SQLite、不做跨库分布式事务：正确决定，应保留。
- Gate 采用"统一契约与失败码，领域继续拥有状态与事务"：边界选得准，应保留。

======================================================================
五、纠偏方向（原则，非实施方案）
======================================================================

1. 把 Confirmation Gate 移出 personal-weather：它按定义就是跨领域治理组件。
2. 把 Profile、Planning、Reminder 从 weather 容器中析出；weather 只保留天气。
3. 把受控地点目录/消歧提为独立 Primitive，与"谁是天气 Provider"解耦。
4. 让能力目录成为真的目录：每个工具声明类别、是否写入、是否需 grant、信任等级、
   是否外发；主人校验/审计/幂等由同一边界统一施加，而非逐工具手写。
5. 把已存在的约 1.5 套调度实现记为阶段3 的触发证据，做最小共享控制面
   （立即/定时/暂停/恢复/确认），仍不做 DAG。
6. 用第二个非天气领域的薄纵切片验证解耦是否成立——这是唯一真实检验。

排序约束：不在卡点未解时做大重构；但容器拆分要早于（或同期于）第二个领域能力，
否则新领域会把本次偏离固化，拆分成本更高。

卡点 A —— inbound hook 侧拿不到 senderIsOwner（2026-08-31 定性，2026-09-01 根因已更正）

  A.1 【已更正，2026-09-01】原判断"Host 尚未解析主人身份（时序问题）"是错的
    原表述：构造 inboundClaimEvent（dispatch:1145）早于 resolveCommandAuthorization
    （dispatch:1496），故 hook 触发时主人身份在 Host 内尚不存在。
    实测否证：dispatch-DnzGTpPs.js:1496-1507 在调用 inbound_claim 之前就已经
    调用 resolveCommandAuthorization，并显式构造了带该位的事件：
        1496  const bindingAuthorization = resolveCommandAuthorization({...})
        1504  const authorizedInboundClaimEvent = {
        1505    ...inboundClaimEvent,
        1506    senderIsOwner: bindingAuthorization.senderIsOwner
        1507  }
    即 Host 完全有能力、也确实在传这个字段。原判断把"我们收不到"误读成
    "Host 算不出来"。
    真实情况：该赋值只在 pluginOwnedBinding 分支内（dispatch:1489 起），
    而本机 current_conversation_bindings 表为 0 行 → 该分支从不进入 →
    整个 inbound_claim 钩子从不触发（详见十、卡点 C）。
    所以"insufficient 字段"只是表象，真正的事实是"该钩子根本没跑"。
    仍然成立的部分：toPluginInboundClaimEvent（message-hook-mappers-CLWKm8aG.js:165-196）
    确实不产出 senderIsOwner，非绑定路径下该字段确实缺失；
    PluginHookInboundClaimEvent.senderIsOwner?: boolean 确实在契约里
    （hook-types-DQ9eTy2x.d.ts:233），插件读它并不违约。

  A.2 不对称性（关键事实，决定了修复方向）
    工具边界拿得到该位：dist/agent-tools-BD8WL7ny.js:959 senderIsOwner: options?.senderIsOwner
    → index.ts:753 isTrustedOwnerPrivateQq 与 confirmation-gate.ts:108
      scopeFromToolContext 都能正常判定主人。
    实证：22:13:18 proposal 成功生成，证明工具侧主人判定是好的；
    仅 inbound hook 侧缺该位。所以这是单侧缺口，不是整体身份体系失效。

  A.3 后果【已更正，2026-09-01】
    原表述：index.ts:775 与 confirmation-gate.ts:122 的 senderIsOwner === true
    要求导致每条真实入站消息提前 return，是 approval_grants 无行的原因。
    更正：这两处 owner 门确实会 return，但它们从不被执行到 —— 承载它们的
    inbound_claim 钩子在本机从不触发（十、卡点 C）。因此它们不是 2026-08-30
    LIVE-07-A 失败的原因，只是一层"若能跑到也会挡住"的冗余阻塞。
    S4/S5 删除这两处后，approval_grants 仍为 0 行 —— 2026-09-01 两次真实验收
    （18:50、19:13）已实证这一点，也正是发现卡点 C 的契机。
    结论不变的部分：任何真实 QQ 确认都不可能成功，与主人回复内容无关；
    LIVE-05/06/07 等正向写入验收全部被阻塞。只是阻塞点比原判断更靠上游。

  A.4 候选方案与取舍（方案 C 已获批准并实施，见 9.0/9.1）
    方案 A 用 commandAuthorized 代替：否决。它表达"是否按命令解释该消息"
      （dist/channel2.runtime:215 shouldComputeCommandAuthorized），
      不是主人身份，语义错位且会放宽边界。
    方案 B 插件自行用 senderId + allowlist 反推：否决。等于在插件内重建
      Host 的信任判定，违反 tp.txt 原则五与本文既定禁止绕法。
    方案 C（推荐）把主人断言下移到工具边界：
      inbound hook 只记录"发生了什么"（messageId、content、scope、时间），
      不再自称已验证主人、不签发 grant；grant 改在 commit 时签发，
      此时 toolContext.senderIsOwner 可用（A.2 已证明）。
      安全性不降低，理由：proposal 只在主人已验证的工具上下文中创建；
      候选仅在 scope 匹配该 proposal 时才可能被选中（scopesMatch，
      confirmation-gate.ts:395）；QQ 私聊中他人 conversationId/senderId 不同，
      无法与主人 proposal 的 scope 匹配；commit 仍要求
      isTrustedOwnerPrivateQq() === true。"必须存在提案之后到达的真实入站消息"
      这一条——即防同轮自提交的核心性质——完整保留。
    方案 D 上游修 Host：正当但当前不可行。不应改已安装 dist 充当生产方案。
      【2026-09-01 更正】该方案的原描述"把主人解析移到第 1145 行之前"基于
      A.1 的错误前提，现已不成立：Host 本来就在 hook 之前解析了主人身份。
      真正值得上报上游的是卡点 C —— runInboundClaim（非定向版）在整个 dist
      中零调用点，见 10.5。

  A.5 本节整体定性【2026-09-01 追加】
    卡点 A 作为"独立卡点"实际上不存在，它是卡点 C 的一个症状：
    因为钩子不触发，所以字段看起来永远缺失。
    保留本节的意义是记录这次误判的过程与证据，避免下次再从
    "字段缺失"直接跳到"时序问题"这个结论 —— 正确的下一步本应是
    先确认钩子是否真的被调用（即先验证执行，再解释字段）。
    这条教训已写入 10.6。

  禁止的绕法（保持不变）：改已安装 dist 当生产方案；从 senderId / QQ 白名单 /
  消息正文 / 模型上下文反推主人身份；手工插入 approval_grants。

7.1 模型行为问题（需落到 AGENTS.md 的行为约束）

① 编造后端要求。后端只返回错误码 approval_required，其中没有"需显式包含
   proposalId/payloadHash"这一信息，模型却将其讲成具体机制。与 doc 6 记录的
   Search 把 platform.openai.com 改写为 providers.openai.com 属同一类保真度问题。
② 自创绕过确认闸门的协议。doc 6 第三节已明令禁止"要求 Kurumi 通过纯确认/换前缀
   规避解析缺陷"，模型恰好做了此事，且它并未被授权定义确认格式。本条最需警惕。
③ 它教的咒语本身无效。已实测：`我确认变更 proposalId=...` 在
   confirmation-gate.ts:384 前缀正则上失败（确认 后紧跟 变，既非分隔符也非串尾）。
   反而第一次朴素的"确认"能过解析器，只卡在 senderIsOwner。
   即模型"更明确"的建议严格更差：原本只坏 Host 一处，新话术在解析器与 Host 两处都坏。
④ 让主人做了两次注定失败的劳动，含手抄 64 位 SHA-256。
⑤ 有只读工具却不用。模型列了三条假设，但 personal_profile_state_get 会直接返回
   提案真实 ID/hash/TTL/状态。猜了三条，没查一次。
⑥ TTL 假设错误。profile.ts:19 PROPOSAL_TTL_SECONDS = 24*60*60（24 小时），
   全程仅 39 秒，不可能过期。
⑦ 把内部测试编号泄漏进真实对话（"这可能是 LIVE-03 测试要观察的行为之一"）。
   且属误引：LIVE-03 是 Planning 同轮负向，与 Profile 确认链无关。
   模型把主人的开发测试框架与真实请求混同。

应记一功：模型两次失败后停止重试并如实上报，未谎称成功、未无限重试。
失败模式是"诊断错误"而非"伪造结果"，该边界守住了。

⑧b 编造不存在的状态机（2026-09-01 两次会话新增，与 ① 同类但更严重）

      但语义是"一次 agent run"而非"一条消息"，等价性需先论证再落地。
    isGroup/conversationId：不直接给，但 chatId 镜像会话目标，
      可从其前缀（c2c: / group:）推导。属推导而非直取，需测试固定。

  候选 B：message_received
    触发性：确定触发，且无条件 —— dispatch:1568 只检查
      ctx.SuppressMessageReceivedHooks !== true 与 hasHooks（:1436）。
      不需要任何绑定。这是它最大的优点。
    执行方式：fireAndForgetHook（:1438）→ runVoidHook，
      源码注释明写"Runs in parallel (fire-and-forget)"。
      fireAndForgetHook（hook-runner-global-BmIrGlLG.js:141-145）只挂一个
      .catch()，不 await。
    时序：调用点 :1568 在 agent 运行之前，但因为不被 await，
      与 agent run 构成真实竞态。插件的 SQLite 写入是同步且很快，
      实践中大概率先完成，但没有任何硬保证。
      风险的具体形态：偶发地在同一轮 commit 时 grant 还没落库 →
      主人看到一次莫名的 approval_required，再发一轮才成 ——
      这正是最难复现、最伤信任的失败形态。
    字段（hook-types.d.ts:237-256 + mapper :221-267 实际填充）：
      messageId ✓（重放保护可直接沿用，这是它相对 A 的关键优势）、
      senderId、sessionKey、runId、from、content、replyToIsQuote、
      metadata.to（形如 qqbot:c2c:<id>）。
    缺口：无 channel、无 isGroup、无 conversationId、无 senderIsOwner。
      channel 可从 metadata.provider 取；isGroup 与 conversationId 可从
      metadata.to 的前缀推导。
      注意 message_received 的 metadata 不含 groupId（inbound_claim 的含），
      所以 isGroup 只能靠 to 前缀推导，比 A 更间接。
      senderIsOwner 完全拿不到 —— 但按 9.0 已论证的"scope 匹配是重复约束"，
      这一项不构成安全损失。

  候选 C：让插件真正建立 conversation binding（走 Host 设计的定向路径）
    结论：否决。不是成本问题，是语义不可接受。
    实测依据：绑定存在时，dispatch:1489-1567 会把该会话交给插件处理，
      而 runClaimingHookForPluginOutcome（hook-runner-global:545-571）的返回语义是：
        处理器返回 handled → status "handled" → dispatch:1517-1526 直接 return，
          agent 完全不运行；
        处理器注册了但没返回 handled → status "declined"（:571）→
          dispatch:1544-1553 发一条"binding declined"通知后 return，agent 同样不运行；
        只有 no_handler / missing_plugin（:546-548，即根本没注册处理器）才会
          fallthrough 到 agent。
      也就是说：一旦注册了处理器，这个会话就再也不会到达 kurumi。
      而我们要的恰恰是"记录确认之后让 agent 继续正常对话"，
      在这套返回语义下没有对应的出口值。
    附带：绑定还会改变该会话的路由语义（binding 一旦建立会持续生效，
      touchConversationBindingRecord 会续期），影响范围远超确认闸门。
    因此 C 不再作为候选保留，除非上游提供"observe 但不接管"的返回值。

  倾向（供主人裁决，非决定）：A 与 B 各有一处硬缺口，且互补 ——
  A 缺 messageId（影响重放保护的键），B 缺时序保证（影响可靠性）。
  倾向 A：时序保证无法在插件侧补救，而重放键可以（runId 或 messageId
  的等价替代可以论证并用测试固定）。用不可补救的缺口去换可补救的缺口不划算。
  但 A 需要先解决重放键的等价性论证，不能直接开工。

10.5 值得上报上游的两项（不阻塞本地闭环）

  ① runInboundClaim 零调用点。SDK 导出了一个遍历全部插件 inbound_claim
     处理器的运行器（hook-runner-global-BmIrGlLG.js:689），
     但 dist 内无任何调用点。看形态像是回归：非定向的 inbound_claim
     分发路径被移除或改造，只剩下定向（绑定）版本，
     而 PLUGIN_HOOK_NAMES 与类型契约仍完整保留 inbound_claim。
     后果：任何插件按契约注册 inbound_claim，在没有绑定的情况下静默永不触发，
     且无任何警告或日志提示。这是最坏的一类失败 —— 契约在、代码在、就是不跑。
     建议上报时附本节 10.1 的条件链。
  ② before_agent_run 事件缺 messageId。
     该钩子被定位为输入闸门，而任何需要"每条消息只生效一次"的闸门
     都需要一个消息级幂等键；当前只能退到 runId。
     建议上游在事件里补 messageId。

  两项都不改已安装 dist（保持既定禁止绕法），仅作为 issue 记录。

10.6 本轮流程教训（写给下一次的自己）

  ① 先验证"是否被执行"，再解释"字段为何缺失"。
     本轮最大的浪费是：看到 senderIsOwner 缺失，直接去读 dispatch 找时序解释，
     得出一个自洽但错误的结论（§六 A.1），并基于它改了 S4/S5。
     正确的第一步本应是加一行日志或用一次真实消息确认"钩子有没有被调用"。
     一个自洽的解释不等于一个被验证的解释。
  ② 测试全绿不代表链路可用。136 项全在插件进程内，
     完全绕过 Host 入站链路。更严重的是 S8 发现的那件事：
     旧 5 项测试显式传 senderIsOwner: true，把 Host 从不设置的字段
     当成既有事实 —— 测试不仅没发现缺陷，还在积极地掩盖它。
     凡是跨进程边界的字段，测试里不应替 Host 填值。
  ③ 构建 ≠ 生效。Node ESM 模块只在进程启动时求值一次，
     不重启 Gateway 的改动完全不生效。凡涉及插件代码变更的验收，
     "重载 Gateway"必须是我主动执行并声明的步骤，不能并入交给主人的步骤里。
     18:50 那次失败完全由此造成。
  ④ 不要在未验证前提上动手。19:13 之后我没有立即改钩子，
     而是先做完本节调查 —— 这是对的，应保持。
