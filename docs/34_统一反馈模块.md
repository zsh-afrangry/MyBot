# 统一反馈模块

## 功能

反馈按业务动作接入。主人可分段查询 QQ 私聊文本的受理和主动回认，日常聊天无需回认。同步操作在当轮回告结果，后台操作沿用原收件人和通知，详细证据按需查询。

一次性提醒支持核对创建、改期和取消后的实际调度状态，到点后可按同一次执行查询通知生成、QQ 逐段受理和主动回认。账单和共享提醒列表可按原 QQ 消息查询写入结果，列表逐项显示。

编码任务按执行轮次核对检查、合入或回写和通知。邮件按草稿查看确认情况和 SMTP 投递结果。 [文档28](28_本机编码工具委托与实验任务.md#执行结果与完成回传) · [文档20](20_邮件能力与横切扩展.md)

论文按任务和产物核对译稿生成、QQ 投递与邮件草稿关联。 [文档22](22_论文PDF翻译与文件投递.md#工具)

白名单按提案核对仓库写入及运行实例当前采用的名单。 [文档24](24_统一身份与权限管理.md#主人代办白名单)

提醒列表和天气的每日播报按计划时间核对当次是否应发、正文是否生成、QQ 是否受理。天气取数失败时，仍可单独查到错误通知的投递结果。 [文档23](23_KnowledgeMap业务能力桥接.md#每日播报) · [文档2](2_天气模块.md)

E7 发图按原请求核对检索、图片就绪和 QQ 受理。当前所在地和行程在确认后回告保存结果，并可按原提案核对。 [文档27](27_E7数据插件设计.md) · [文档2](2_天气模块.md)

| 查到的事实 | Kurumi 可以怎么回答 |
| --- | --- |
| 两段都取得有效的平台消息 ID | “两段都已被平台受理，收件情况还未核实。” |
| 收件人引用第一段明确回复“收到了” | “你已确认收到第一段，第二段还未核实。” |
| 第一段取得回执，第二段响应丢失，第三段尚未尝试 | “第一段已受理，第二段结果未知，第三段未发出。” |

## 接口

- 渠道选项 `channels.kurumi-qq.privateTextFeedback` 默认开启，控制 QQ 私聊回复及本机 Cron 私聊文本的分段登记和主动回认采集。关闭后已有证据仍可查询。
- 主人使用现有只读工具 `kurumi_logs`，传 `view=events`、`sources=["channel-delivery"]`。可按入站原请求、出站消息或回认证据的 `messageId` 定位，用返回的 `eventKey` 查询同一次回复的各段。多条候选应按收件人和消息澄清。查询权限见[文档24](24_统一身份与权限管理.md)。
- 分段字段 `part` 从 1 开始，`parts` 是计划总数。`platformStatus` 取 `accepted`、`rejected`、`unknown` 或 `not_attempted`。`recipientStatus=acknowledged` 附回认消息 ID、来源和观察时间，其余为 `unverified`。`clientDelivery` 和 `readStatus` 当前均为 `unknown`。
- 一次性提醒沿用 `personal_reminder_state_get`。传 `proposal_id` 可查对应提案是否仍待确认，传 `reminder_id` 可核对单条提醒的当前计划和历史取消结果。返回 `feedback` 时以实际调度时间为准。`notification` 显示最近一条匹配的 Cron 执行记录及对应的 QQ 分段。
- `plugins.entries.personal-reminders.config.feedbackActions` 可独立选择 `reminder.create`、`reminder.update`、`reminder.cancel`、`reminder.delivery`，省略时启用这四项，空数组关闭反馈。提醒的业务权限和确认流程见[文档3](3_个人提醒.md)。

- 账单写入结果附 `feedback`，核对用 `knowledge_bills_get` 的 `action=receipt` 和原请求 `message_id`。返回原事务的动作、账单 ID、版本、金额和日期。删除记录附删除标记。通过 `plugins.entries.kurumi-knowledgemap.config.feedbackActions` 可单独选择 `bill.create`、`bill.update`、`bill.delete`，省略时三项均启用。 [文档23](23_KnowledgeMap业务能力桥接.md#账单维护)

- 共享提醒列表的五项维护动作分别返回 `feedback`。主人可用 `kurumi_logs` 的 `sources=["personal-reminder-list"]`、`kind=reminder-list.feedback` 和原请求 `messageId` 查询。同条消息的不同事项各自保留 ID、版本或失败原因。配置 `plugins.entries.personal-reminder-list.config.feedbackActions` 可选择 `reminder-list.add`、`reminder-list.update`、`reminder-list.complete`、`reminder-list.void`、`reminder-list.reopen`，省略时启用全部五项。 [文档23](23_KnowledgeMap业务能力桥接.md)

- 每日播报使用 `kurumi_logs` 的 `view=daily-feedback`，传 `broadcast=reminder-list` 或 `weather`，以及原计划时间 `scheduledAt`，如 `2026-11-22T08:00`。省略时区时按上海时间解释。多条计划候选可用 `cronJobId` 指定。CLI 对应参数为 `--daily-feedback`、`--scheduled-at` 和可选的 `--cron-job-id`。
- 每日播报返回 `feedback.evidence` 中的 `shouldSend` 和 `bodyStatus`，以及 `notification` 的类别、平台状态和分段回执。只受理部分段落时状态为 `partially_accepted`。长通知汇总所有段落并展示前 20 段，可用 `notification.deliveryRunId` 作为 `runId` 查询 `channel-delivery` 的完整回执。
- E7 发图核对使用 `kurumi_logs` 的 `view=events`、`sources=["channel-delivery"]`、`kind=qq.image_feedback` 和原发图请求的 `messageId`。`e7_image` 返回该引用 `sourceMessageId`。`imageStatus` 显示无匹配、图片就绪、失败或未知，`notification.platformStatus` 单独显示 QQ 受理状态。
- 所在地和行程的提交反馈与提案回查入口见[文档2](2_天气模块.md#接口)。

## 原理

- 业务在自己的组合入口选择是否观察反馈。共享包 `chatbot/packages/feedback-core/` 提供反馈写入的故障隔离及业务、渠道结果格式。QQ 适配器负责判断证据。确认仍由[文档6](6_二次确认.md)管理，诊断与查询复用[文档18](18_跨模块链路日志查询.md)。
- 正式 OneBot 入站使用已登录的发件账号和通过身份校验的对话主体。发送前按既有投递键登记各段，原出站账本提供受理、明确拒绝或未知结果。查询只读账本，按计划时间展示当前状态。附表只保存账号、消息引用、段号和时间。反馈写入故障时，发送沿用原账本和去重规则。
- 主动回认只接受同一私聊中的单个结构化引用，以及独立的肯定短句，如“收到”“我已经收到了”。引用须经 `get_msg` 核对原消息 ID、发件账号和收件人，再与唯一已受理的出站段匹配。重复回认可查首个有效证据。平台受理响应晚于回认时，取得对应消息 ID 后即可关联。普通回复、否定、错人、歧义 ID 和合成测试入口均不会提升状态。

- 提醒适配器通过只读的 `cron.list` 和 `cron.runs` 核对提醒记录。提案提交和当前调度状态分别显示。Cron 名单无法读取、任务与提醒记录不一致或查询时记录发生变更时，调度结果为未知。结果查询只读现有账本和宿主状态。到点反馈按 Cron 任务、当次执行时间和收件人连接 QQ 出站账本。平台响应丢失时保留未知并停止自动重试。

- 账单只读核对使用当前受信会话与原消息 ID 推导原幂等键。KnowledgeMap 在账单事务中保存回执。响应丢失且暂无回执时显示未知，后续核对通过 GET 读取原结果。

- 列表适配器按原请求和事项槽位保存观察结果，业务状态仍以 KnowledgeMap 为准。只读日志查询保留每次尝试的结果。

- 每日播报从原生 Cron 的计划标识定位当次执行。列表使用对应时刻的账本和生成审计，天气使用当次隔离会话的天气工具结果和宿主记录的正文。QQ 回执按任务执行及收件人核对，天气任务的投递起点须唯一落在该次执行区间内。
- 图片适配器用宿主当前私聊请求关联生成结果。出站预留与该次图片证据同事务登记，QQ 平台状态取自现有出站账本。回查只读，重复查询不会触发取图、渲染或投递。

## 限制与已知问题

- SnowLuma 1.14.21 的 `get_msg` 与 `message_sent` 可提供发件侧证据。当前链路缺少可核验的客户端自动送达和已读信号。主动回认只覆盖被引用的那一段。
- 缺少反馈记录的历史发送只显示留存的原账本事实。旧 Cron 执行可能只有宿主通知结果，实际 QQ 分段状态以对应的渠道账本为准。
- 图片按原请求无反馈记录时，结果未核实。
- 每日播报缺少计划或正文证据时，相应结果为未知。天气回查依赖仍可识别的 Cron 任务和留存工具记录。
