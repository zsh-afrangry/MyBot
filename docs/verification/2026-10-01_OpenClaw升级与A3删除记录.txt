### 2.4 修复 allowFrom（重要回归）

旧版 qqbot 插件（`@openclaw/qqbot 2026.7.1`）把 `allowFrom` 同时用作
**私聊白名单**与**审批人列表**（`getQQBotExecApprovalApprovers`）。
doctor 按 2.0 语义写入哨兵值后，主人 QQ ID 从私聊白名单消失 →
`dmPolicy: "allowlist"` 下**主人将无法与 Kurumi 私聊**。

新版 schema 对 `allowFrom` 的要求是：每项要么是 `openclaw:approval-disabled`，
要么匹配 `^[^a-z]*$`（全大写 ID）。主人 ID `275E81F98DE0DB44476B0FA1B97965EC`
**本来就合规**，因此直接改回：

```
channels.qqbot.allowFrom = ["275E81F98DE0DB44476B0FA1B97965EC"]
```

改回后配置仍被新版接受（重启无 invalid/restored 记录），`groupAllowFrom` 未被动过。

## 3. fallback 真实故障切换验证（已完成）

**这是此前唯一未验证的实质缺口**：B2 只证明了配置与 `models list` 显示 fallback#1，
从未证明主模型失败时**真的会切换**。

新增可复用脚本 `chatbot/tests/acceptance/run-fallback-failover.mjs`，做法：

- 主模型指向 `http://127.0.0.1:9/v1`（立即 ECONNREFUSED/超时），
- fallback 保留真实 `deepseek-search/deepseek-v4-flash`，
- 全程写临时目录，**生产 `openclaw.json` 只读、不碰生产 key、不投递 QQ**，
- 用 `agent --local` 在嵌入式模式跑一个无需工具的问题。

结果：

```json
{
  "winnerProvider": "deepseek-search",
  "winnerModel": "deepseek-v4-flash",
  "fallbackUsed": true,
  "attempts": [
    "fallback-probe-broken/unreachable-probe:timeout",
    "deepseek-search/deepseek-v4-flash:success"
  ],
  "answer": "哈希表是一种通过哈希函数把键直接映射到存储位置、从而以平均 O(1) 时间完成插入、查找和删除的数据结构…"
}
```

日志侧同证：`[model-fallback/decision] decision=candidate_succeeded
requested=fallback-probe-broken/unreachable-probe candidate=deepseek-search/deepseek-v4-flash`。
**结论：fallback 链真实可用。**

## 7. DSH 更新：0.1.5-rc.3 → 0.2.0-rc.2（已安装并验证，待重启）

主人提供 sudo 密码后执行。**没有采用 `npm install` 直接改写**，原因：

- `/opt/deepseek-harness` 下**没有 package.json / package-lock.json**，只有 `node_modules`（189 个包）。
  在这种目录里跑 `npm install --prefix … <pkg>` 会新建 package.json，并把不在清单里的包
  当作 extraneous **清掉**，有整棵树被削坏的风险。
- 改用「隔离暂存 → 整体替换」：

```
# 1. 暂存安装（普通用户即可，不碰生产目录）
cd /tmp/dsh-stage && npm install --no-audit --no-fund @deepseek-ai/dsh@0.2.0-rc.2
#    首次同样被 npm 11 的 install-scripts 拦截（5 个包），补跑：
npm install-scripts approve @deepseek-ai/dsh-subprocess-local koffi node-pty @google/genai protobufjs
npm rebuild
# 2. 验证暂存树
/tmp/dsh-stage/node_modules/.bin/dsh --version          # → 0.2.0-rc.2
#    并在 3099 端口隔离启动成功
# 3. 放到最终位置、整体替换（旧树保留）
sudo cp -a /tmp/dsh-stage/node_modules /opt/deepseek-harness/node_modules.new
sudo chown -R dsh:dsh /opt/deepseek-harness/node_modules.new
sudo mv /opt/deepseek-harness/node_modules     /opt/deepseek-harness/node_modules.0.1.5-rc.3.bak
sudo mv /opt/deepseek-harness/node_modules.new /opt/deepseek-harness/node_modules
```

**三重验证（全部通过）**：

1. 最终路径 `dsh --version` → `0.2.0-rc.2`。
2. 从最终路径在 3098 端口隔离启动 → 正常监听、鉴权返回 401。
3. **以真实状态的副本**（`cp -a /var/lib/dsh/.dsh`，4.6M）在 3097 端口启动 → 正常。
   新版会做一次状态迁移：`settings.yaml` → `settings.yaml.imported`（**原文件保留**），
   新增 `storages/session_projcache/` 投影缓存，会话目录与 `.credentials.yaml` 完整保留，
   仅当前活动会话的转录被重写为 `session.v3.jsonl.zstd`。**未见丢数据。**

**踩到的坑**：把新树放在 `node_modules.new` 时执行会报
`does not provide an export named 'StartupError'` —— 这不是新树坏了，而是 Node 的解析规则：
目录名不叫 `node_modules` 时，它向上找到隔壁**旧的** `node_modules`，加载了 0.1.5 的
`@deepseek-ai/dsh-app-boot`。改名为 `node_modules` 后即正常。

**待主人执行最后一步**（会中断当前 DSH 会话）：

```sh
sudo systemctl restart dsh-web.service
```

回滚：`sudo mv node_modules node_modules.0.2.0-rc.2.failed && sudo mv node_modules.0.1.5-rc.3.bak node_modules`。

## 7.1 qqbot 插件迁移：`@openclaw/qqbot 2026.7.1` → `@tencent-connect/openclaw-qqbot 2.0.3`（已完成）

起因：主人先问「新版是 openclaw 新还是 qqbot 新」，随后指示「腾讯方有新版 qqbot，
那 OpenClaw 的 qqbot 插件就应该更新」。事实是**只有核心升了级，qqbot 插件仍是旧版**——
这正是 §2.4 那个 allowFrom 回归的根因：新核心按 QQBot 2.0 语义改写配置，插件却还是 1.0 的。

| 组件 | 版本 | 状态 |
| --- | --- | --- |
| OpenClaw 核心 | `2026.9.7 (c074824)` | 已升级 |
| `@openclaw/qqbot` | `2026.7.1` | **旧版，已退役** |
| `@tencent-connect/openclaw-qqbot` | `2.0.3` | **新版，现役** |
| `@openclaw/tavily-plugin` / `deepseek-provider` | `2026.9.7` | 自动升级 |

新插件的官方定位（取自核心内置目录）：插件 id `openclaw-qqbot`，频道 id 仍是 `qqbot`，
`legacyNpmPackageNames: ["@openclaw/qqbot"]`，`install.npmSpec` = `@tencent-connect/openclaw-qqbot@2.0.3`。
**故版本取核心锁定的 2.0.3**（npm 上已有 2.0.4，但核心目录锁的是 2.0.3）。

### 执行步骤

1. 备份：`backups/manual-snapshots-20261004/openclaw.json.bak.before-qqbot-migration-20261001T143533`；
   旧插件打包 `state/backups/qqbot-legacy-plugin-20261001T143533.tar.gz`（1.3M）；
   状态库 `state/openclaw.sqlite.bak.before-qqbot-migration-cleanup`。
2. 安装：`openclaw plugins install @tencent-connect/openclaw-qqbot@2.0.3 --accept-capabilities`
   → 自动向 `plugins.entries` 与 `plugins.allow` 加入 `openclaw-qqbot`。
3. 停用旧插件：`openclaw plugins disable qqbot`。
4. 群组工具策略迁移：`groups."*".tools.deny:["*"]` → `groups."*".toolPolicy:"none"`。
5. 移除旧插件：从 `plugins.allow` / `plugins.entries` 删除 `qqbot`，包目录移出
   `npm/projects/`（备份在 `state/backups/removed-legacy-qqbot/`）。
6. 清理孤儿迁移记录（见下）。

### 重要发现：两条迁移互相矛盾（核心 2026.9.7 行为，非我方误操作）

`channels.qqbot.groups.*` 的策略键在 doctor 里出现**方向相反的两条迁移**：

- 核心内置迁移：「groups.*.tools 必须迁移到 Tencent QQBot 2.0 的 toolPolicy」
  → `migrateGroupTools()` 写入 `toolPolicy` 并删除 `tools`。
- **旧插件自己注册的迁移**：「groups.*.toolPolicy 是 legacy 且被 QQBot 组策略忽略，请改用 tools」。

只要旧插件还留在磁盘上，两条就互相抵消：doctor 每次都说要迁移，`--fix` 执行后配置在两种
形态间反复横跳，**永远收敛不了**。实证结论：移走旧插件包目录后，`toolPolicy` 那条投诉立即
消失，doctor 变干净。最终保留核心 2.0 迁移的结果 `toolPolicy: "none"`。
（`groupPolicy: "disabled"`，群聊本就永久禁用，该键实际不生效。）

### 孤儿迁移记录

`state/openclaw.sqlite` 的 `migration_runs` 中留下 `deferred-plugin-migration:qqbot`，状态永久
`pending`，原因 `The installed plugin has not confirmed that its saved data and settings are
