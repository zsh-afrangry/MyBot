## A1 / T-A：为 Gateway 配置代理，让 web_fetch 能访问被墙站点

状态：**已完成并通过真实验证**。

### 背景与判据

- 实测中国大陆直连 Google / DuckDuckGo 失败（HTTP `000`），Wikipedia 同样 `000`。
- Clash Verge 混合端口 `127.0.0.1:7897` 可用（Google 200 / 0.65s，Wikipedia 200 / 0.95s）。
- 当前 Clash profile 为 `R7DrwkpoR7Hs`（LanPangYun，套餐到期 2026-10-26）；
  **未启用 fake-IP**（无 `enhanced-mode`，`/dns/query` 返回真实公网 IP）。

### 方案

Host 的 `tools.web.fetch.useTrustedEnvProxy` 打开后，`web_fetch` 会走
`resolveProxyFetchFromEnv`（undici `EnvHttpProxyAgent`，尊重 `NO_PROXY`）。因此：

1. 在 `gateway.systemd.env` 增加 `HTTP(S)_PROXY` 指向 `127.0.0.1:7897`；
2. 用 `NO_PROXY` 把模型/搜索 API 与本地地址排除，避免本可直连的请求绕行；
3. `openclaw.json` 打开 `tools.web.fetch.useTrustedEnvProxy`。

因 Clash 未启用 fake-IP，**未**开启 `ssrfPolicy.allowRfc2544BenchmarkRange` /
`allowIpv6UniqueLocalRange` —— 无必要，避免无谓削弱 SSRF 防护。

### 改动

- `gateway.systemd.env`（追加到末尾）：
  ```
  HTTP_PROXY=http://127.0.0.1:7897
  HTTPS_PROXY=http://127.0.0.1:7897
  http_proxy=http://127.0.0.1:7897
  https_proxy=http://127.0.0.1:7897
  NO_PROXY=naiccc.com,api.deepseek.com,api.tavily.com,qq.com,127.0.0.1,localhost,::1
  no_proxy=naiccc.com,api.deepseek.com,api.tavily.com,qq.com,127.0.0.1,localhost,::1
  ```
- `openclaw.json`：`tools.web.fetch.useTrustedEnvProxy: true`
- 备份：
  - `backups/manual-snapshots-20261004/openclaw.json.bak.before-A1-20261001T004947`
  - `state/acceptance/gateway.systemd.env.before-A1-20261001T004947`

### 测试与证据

- Gateway 重启：MainPID `2638845`；进程环境确认 6 个代理变量已注入；
  journal 显示 tavily 插件加载、QQ WebSocket 正常连接、gateway ready。
- 真实 agent turn（隔离会话 `a1verify01`，不投递 QQ、不写业务库）：
  `web_fetch("https://en.wikipedia.org/wiki/SQLite")` → `"status": 200`；
  `toolSummary: calls=1, failures=0`；模型仍为 `naiccc/gpt-5.6-terra`（证明 `NO_PROXY` 生效）。
- 对照：wikipedia 直连 `000 / 6.2s`，走代理 `200 / 0.95s`。

### 结果

T-A 达成：`web_fetch` 可访问被墙站点，同时模型与搜索 API 保持直连。

### 备注（非本次改动）

Gateway 启动日志提示 OpenClaw 有可用更新：`v2026.9.7`（当前 `2026.7.1-2`）。
本次未升级；若升级，需重新核对检索链路与本文所有结论。

## A7：`web_fetch` 是否传 `query` 的决策

状态：**已决策，不新增参数**。

- 事实：模型可用的 `web_fetch` schema 只有 `url`、`extractMode`、`maxChars`；
  Host 调 Tavily extract 的 provider fallback 也只传 `{url, extractMode, maxChars}`。
  带 `query` 的 `tavily_extract` 工具并未对模型开放（owner 工具列表中不存在）。
- 因此 R6（传 `query` 片段化、可能造成“读到原文”的假象）在生产路径**不可达**。
- 决策：不新增 `query` 参数；若将来要按 §九候选 2 做相关性裁剪，必须先做隔离实验证明
  裁剪后仍能支撑事实核验，否则不采用。控制上下文仍以 `maxChars` 为准。

## B3 / B4：R1 并发误报与 R2 旧故障

状态：**均已解决**（R1 实测；R2 结构性消失）。

### R1：并发 `QUOTA_EXCEEDED`

- 根因确认：`QUOTA_EXCEEDED` 来自 personal-search 的 `dist/quota.js` ——
  `maxConcurrent` 默认 1，`inFlight >= maxConcurrent` 即抛 `QUOTA_EXCEEDED`（与每日额度无关）。
  Host 原生 `web_search` 没有等价的单工具并发闸门。
- 实测：隔离 Host 中并行执行两次 `web_search`（`Promise.all`），两次均成功返回
  `provider=tavily, count=5, untrusted=true`，无任何拒绝。
- 复现命令：`KURUMI_SMOKE_CONCURRENCY=1 node chatbot/tests/acceptance/run-retrieval-smoke.mjs`

### R2：旧方案历史故障

- `INVALID_RESPONSE` 与来源域名改写逻辑都位于 personal-search 的
  `deepseek-client.js` / `parser.js`；插件已停用且未加载（隔离工具列表无 `personal_web_search`），
  因此这些故障在新链路中**结构性不可达**，无需再逐条复现。
