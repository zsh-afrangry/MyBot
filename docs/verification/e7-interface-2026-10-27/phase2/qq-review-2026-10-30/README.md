已存在的[10-29公开取数证据](../live-model-2b.json)中，`content/faq`用“团战”返回4条，包含41号“团战比对方少人时，防御塔的血量如何变化？”。当时现行模型样本也曾从组合词改为短词，再读取该问答。历史样本通过不能保证QQ下一回合同样选择正确。

问题在检索编排与结果解释：后端按原关键词返回空列表是现有契约；模型没有完成同一资料类型的关键词缩短，就转向外网，并把有限查询表述成站内没有找到。优先修复方向是给短篇FAQ提供确定性的关键词降级/候选匹配，再让模型选取正文；至少应在工具使用规则中明确同类型短词重试、空结果范围与外部来源区分。两种方案需结合上下文开销和接口次数选择，本次没有变更生产行为，也没有开始2C。

## 日志接口之外的信息与纳入建议

| 信息 | 是否在统一接口内 | 是否应纳入及边界 |
| --- | --- | --- |
| 工具参数/结果、业务状态、来源时间、缺图及裁剪标记 | 在`--expand`内，外部安全包装中仍需人工解包 | 不必增加重复数据源；宜提供基于白名单的业务摘要，分别展示工具执行与业务结果，避免“成功=答案正确” |
| SnowLuma多行预览 | 原生日志可读，但适配器对本样本只保留首行；原生日志自己也在约50字符处截短 | 应修复续行解析并标明预览/完整性未知；补齐续行仍不能恢复原生已截短的正文 |
| 频道`channel.sqlite`投递账本 | 接口没有该适配器 | 优先加入只读回执适配器；显示`sent/failed/unknown`、消息ID、时间与可信关联。账本状态是当前快照，不能伪装成历史状态迁移，更不能声称用户已读 |
| SnowLuma `messages.db`完整入站/出站 | 接口没有该适配器；本次必须直接只读核对 | 建议按需接入，默认只给长度/哈希、方向、消息ID与精确匹配结果；正文仅显式展开。先按回执ID或已确认会话范围取数，不全库复制或按时间强行绑回合 |
| E7真实HTTP与缓存路径 | 工具结果有来源时间及`stale`，没有每次HTTP状态、缓存命中、304、退避的完整历史轨迹；`traceFile`仍未实现 | 建议记录固定资源种类、状态码、缓存命中/降级、耗时及可信run/toolCall关联；禁止记录query、正文、任意URL和凭据。不能拿27次工具调用推算27次HTTP，也不能用当前缓存补造过去事件 |
| 是否漏掉已存在的FAQ | 仅凭本回合空结果无法知道；需要既有公开证据及独立公开查询 | 不纳入日志接口的自动联网范围；把搜索覆盖范围、零结果及业务元数据纳入摘要，答案质量保留独立验收 |
| 源码/配置、当前健康状态 | 需要读源码及现有只读检查脚本 | 继续使用专用检查；如提供快照，明确采集时刻及版本，不当作历史调用事实 |
| QQ视觉排版与已读 | 本次没有独立证据 | 不通过抓取更多私聊数据库来冒充；需要客户端截图/人工确认，或未来平台明确支持的遥测 |

接口补充需求归[文档18](../../../../18_跨模块链路日志查询.md#验收内容与投递核对的补充需求)，沿用N1排期；未实施项不宣称已可用。
