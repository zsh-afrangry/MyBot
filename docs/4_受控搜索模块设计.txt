kurumi 受控搜索模块设计（MVP）

首次立项：2026-08-12
最后更新：2026-08-22
状态：主人 QQ 私聊中的受控公开搜索已经可用并完成端到端验收；它仍是 MVP，尚未达到可完全归档的
质量、留存和多账号治理状态。

======================================================================
一、现在应该从哪里继续
======================================================================

当前不应继续扩张为通用浏览器、通用抓取器或任务引擎。下一项工作只能由真实需求触发：

- 出现稳定的检索质量问题时，做小样本质量评估、来源路由或结果展示改进；
- 使用方式将从单机主人私聊变为多账号、远程访问或云同步前，先完成会话/trajectory 留存与权限治理；
- 拿到第二个 QQ 账号时，补一次真实非主人拒绝测试；
- 出现需要“搜索结果再读取单页”的真实场景时，单独设计受控 Fetch；
- 天气、提醒、搜索至少出现第二或第三种真实组合需求后，再讨论公共任务边界。

在没有这些触发条件前，保持当前窄能力，不因抽象欲望新建 Task Engine、DAG 或通用 Agent 工作流。

======================================================================
二、已上线能力和唯一数据路径
======================================================================

当前公开搜索只服务于主人 QQ 私聊，工具名为 personal_web_search：

  Kurumi（Qwen 主模型；Terra fallback）
      → personal_web_search
      → personal-search 插件
      → deepseek-search Worker
      → DeepSeek Responses Web Search

- 主模型只决定是否提出工具调用和如何解释结果；实际联网固定经过 DeepSeek Search Worker。
- 主模型切换不会自动切换搜索 Provider。百炼 Qwen 的模型原生联网和 Terra 的原生 /responses 搜索都未接入
  正式路径，也不替代本模块。
- 通用 web_search、web_fetch、浏览器、Shell 和任意 URL 请求均未向 Kurumi 开放。
- 搜索不是天气、股票、提醒或任何结构化外部数据的 fallback；这些领域继续使用各自受控 Provider。
- 工具只能在精确 allowlist 的主人 QQ 私聊上下文调用；群聊永久关闭。

这是“允许模型发起受控检索”，不是“允许模型自由上网”。

======================================================================
三、任务与功能的解耦边界
======================================================================

当前系统处于“领域功能已分开、跨领域任务尚未抽象”的状态：

- 天气/行程、提醒、搜索各自有明确工具、状态、审计和写入边界；
- 模型负责自然语言理解、选择工具、汇总结果；
- 后端负责外部调用、状态变更、确认、时间、审计和错误语义；
- 还没有统一的 TaskSpec、TriggerSpec、ExecutionContext 或 Provenance 运行时。

这不是缺陷，而是当前 MVP 的合理取舍。天气、提醒与搜索尚未出现足够多可复用的真实组合，过早建设
通用 Task Engine 会把未验证的假设固化为基础设施。未来若出现重复的“定时检索后提醒”“行程改变后重算天气”
等组合，再以实际共性提取：

- TaskSpec：任务目标、输入、输出和副作用；
- TriggerSpec：人工确认、定时、事件或状态变化触发；
- ExecutionContext：用户/会话/时区/权限/预算；
- Provenance：数据来源、时间、工具版本、核验和不确定性。

在那之前，组合由窄领域流程明确表达；不构造通用 DAG，也不让模型自行编排高权限任务。

======================================================================
四、输入、权限和隐私边界
======================================================================

1. 输入限制

- 查询长度上限 200 个字符；固定返回数量 5；不接受调用方指定 Provider、模型、URL、请求头、深度、
  重试次数或抓取参数。
- 搜索请求在进入上游前检查明显敏感标识符（如票号、证件号、OpenID 等）。命中时在本地以
  INVALID_INPUT 拒绝，不提交公开搜索服务。
- 搜索查询被当成数据而非指令；上游网页、摘要和引用均不能改变权限、系统提示或工具策略。

2. 身份和工具准入

- 仅主人 QQ 私聊可用；工具自身和 OpenClaw 精确 allowlist 双重限制。
- 群聊没有业务工具权限；陌生人或不满足上下文条件的调用必须失败，而不是降级为通用搜索。
- 没有第二个 QQ 账号时，代码/夹具的拒绝测试可以证明逻辑，真实非主人 QQ 验收仍列为待办。

3. 密钥、流量和超时

- DeepSeek Key 仅通过 SecretRef 读取 gateway.systemd.env，文档、仓库、日志和工具结果不输出 Key。
- 上游固定为 DeepSeek API 与指定 Responses Search 模型；调用超时 60 秒，响应上限 1 MiB，
  最大并发 1，不做自动重试。
- 本地配额为每分钟 6 次、每日 50 次。触顶、无 Key、鉴权失败和 402 预算耗尽均必须明确返回，
  不伪造搜索答案。

4. 留存的 MVP 妥协

personal-search 自己只审计查询摘要（哈希、长度、时间、结果类型、错误/耗时等），并在持久化的工具副本中
脱敏查询与结果；它不自行保存搜索原文。主人已接受单机 MVP 中 OpenClaw 仍可能保留原始 QQ 会话和
trajectory 的现状。

这不是“没有隐私风险”的承诺。多用户、远程访问、共享设备、云同步或备份外发之前，必须重新定义
访问权限、保留期、清理、备份加密和恢复流程；详见第八节待办。

======================================================================
五、结果、来源和失败契约
======================================================================

1. 正常结果

当前个人工具通常归一化为 answer：包含综合文本 content、可选 citations，以及 externalContent.untrusted
标记。来源与结论属于搜索 Provider 报告，不等于本机 Fetch、浏览器或逐页原文核验。

回复用户时应：

- 说明使用的是受控搜索和检索时间；
- 有引用时给出来源链接或可辨识来源名称；
- 清楚区分“Provider 报告”“本地独立 Fetch 核验”和“无法核验”；
- 资料不足、冲突或过期时说明不确定性，不用记忆补全。

OpenClaw 通用 WebSearchOutput 还可表达 results、raw 和 error 等封闭形状；这仅是兼容边界。
当前 personal_web_search 的正式成功路径以 answer 为准，不依赖模型猜测某个 Provider 的私有原始载荷。

2. 错误语义

错误以稳定 code 反馈给模型和用户，当前包括：

- CONFIG_INVALID、AUTH_NOT_CONFIGURED、AUTH_FAILED、FORBIDDEN_CONTEXT、INVALID_INPUT；
- RATE_LIMITED、QUOTA_EXCEEDED、BUDGET_EXHAUSTED（HTTP 402）；
- TIMEOUT、UPSTREAM_UNAVAILABLE、INVALID_RESPONSE、INTERNAL_ERROR。

其中 INVALID_RESPONSE 表示上游返回无法安全核验的形状，不应被包装成“找到了来源”；
AUTH_FAILED 只说明本次认证失败，不泄露 Key 或请求细节。错误默认不自动改走其他搜索 Provider，
避免数据来源和计费路径在用户无感知时改变。

======================================================================
六、实现落点与运维约束
======================================================================

- 插件目录：chatbot/plugins/personal-search/；其测试、输入校验、DeepSeek 客户端、审计和持久化脱敏
  逻辑均在该模块内。
- 运行配置：openclaw.json 中注册 deepseek-search Provider，并只在 exact tools.alsoAllow 中开放
  personal_web_search。
- 密钥环境：gateway.systemd.env 中的 DEEPSEEK_BASE_URL、DEEPSEEK_API_KEY；示例文件只保留变量名。
- 人格/提示：chatbot/AGENTS.md 和 chatbot/TOOLS.md 只描述工具边界与来源表述，不赋予模型通用网络权。

变更搜索配置后的最小检查顺序：

1. 检查 JSON、SecretRef 和 allowlist，没有把 Key 写入配置或输出；
2. 执行插件测试、构建、插件检查和 openclaw config validate；
3. 重载并重启 Gateway，确认 QQ 连接和工具清单；
4. 用主人 QQ 做一条普通公开问题和一条拒绝路径测试；
5. 核对审计只有摘要、没有明文敏感查询或密钥。

======================================================================
七、已完成验收（保留正式结论）
======================================================================

| 范围 | 正式结论 |
| --- | --- |
| 离线实现 | personal-search 的测试套件、构建、插件校验和 OpenClaw 配置校验均通过。 |
| 无 Key | Gateway 启动/配置路径 fail-closed；不会伪装为可搜索。 |
| 错误契约 | INVALID_RESPONSE、AUTH_FAILED、INVALID_INPUT 等路径已验证为明确失败，不产生编造来源。 |
| 敏感标识 | 测试标识符在输入校验阶段被拒绝，未向上游发出网络请求。 |
| 真实 QQ 鉴权 | 临时错误 Key 的主人 QQ 调用返回 AUTH_FAILED；恢复正确 Key 后正常工作。 |
| 主人 QQ 搜索 | Qwen 主模型实际调用 personal_web_search，并获得 DeepSeek 的 answer / citations；结果明确说明未经过本地 Fetch 独立核验。 |
| 工具最小化与回滚 | 通用 web_search 的诊断验证结束后已移出正式工具策略；禁用/恢复 personal-search 的回滚路径已验证。 |

已知性能事实：受控搜索为“模型判断 + 外部搜索 + 模型汇总”的串行链路，单次可能显著慢于普通对话；
超过上游/Agent 总超时应如实返回 TIMEOUT，而不是无限等待或静默改用别的 Provider。

======================================================================
八、MVP 未完成项与重新评审条件
======================================================================

- [ ] Provider 运营确认：由主人确认实际套餐、计费/日配额、Key 轮换与注销流程；文档不记录动态价格。
- [ ] 留存治理：在改变单机主人私聊边界前，完成会话、trajectory、日志、备份与同步的权限和 TTL 方案。
- [ ] 真实非主人 QQ 验收：获得第二账号后，验证非主人无法发现或调用 personal_web_search。
- [ ] 质量评估：按真实问题构造小样本，评估来源质量、时效性、中文回答、失败率与延迟；只有证据证明
  路由不足时才添加新的 Search Provider。
- [ ] 来源路由：如需要固定官方来源、学术来源或站点白名单，先定义可解释的策略和失败回退，
  不让模型临时决定信任边界。
- [ ] 受控单页 Fetch：只有真实场景需要阅读单一搜索结果时再单独设计 URL 许可、SSRF 防护、
  内容大小/类型限制、注入隔离、审计和引用语义。
- [ ] 原生模型联网：Qwen/Terra Harness 或 /responses 仅作为独立实验；通过可复现验收和权限评审后
  才可能成为另一条明确的数据路径。
- [ ] 任务抽象：仅当出现多种被证实的跨领域组合时，评估 TaskSpec / TriggerSpec /
  ExecutionContext / Provenance；不是当前开发事项。

======================================================================
九、回滚与资料
======================================================================

出现安全、质量或成本问题时，优先从精确 allowlist 移除 personal_web_search 或禁用
personal-search 插件，随后重载/重启 Gateway。保留业务数据和最小审计以便排查；不要通过开放
通用网络工具来“临时修复”。
