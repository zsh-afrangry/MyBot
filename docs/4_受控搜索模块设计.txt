======================================================================
一、本轮结论
======================================================================

1. “模型能力”不是一个单独字段，也不全部属于执行策略。
2. 模型的理解、抽取、规划、比较、综合和生成默认是 Agent/LLM Runtime 的内部认知过程，
   不为每个动词注册 `model.extract`、`model.plan`、`model.synthesize` 等 Tool。
3. 只有某个认知阶段具有独立模型、计费、超时、缓存、验证或重试需求时，才把它提升为显式
   Plan Step。此时它是可独立执行的“模型阶段”，不是把所有思考动作工具化。
4. Calculator、Current Time、Web Search、OCR 等是可复用的 Primitive Capability。它们会改变
   任务输入或结果，必须作为显式依赖/调用留下来源，不能像日志一样透明插入。
5. Weather、Stock、Paper、Git、Travel 等是 Domain Capability；领域操作可以声明并复用基础
   能力，但不会自动继承基础能力的权限。
6. Scheduler、Workflow、Notification 是内部 Control Plane。领域服务可以通过受限 adapter 使用，
   但不因此把通用 Scheduler、任意发送或 Workflow 管理权限交给模型。
7. 身份检查、权限、审计、限流、预算、追踪、输入输出校验、不可信内容标记和幂等适合采用
   AOP/中间件式横切设计。
8. 数据模型可为 DAG 预留版本和依赖字段；第一版执行器不实现任意 DAG、分支、循环或模型生成
   的工作流。

一句话概括：

  模型负责认知；显式 Capability 提供可验证的外部能力；领域操作声明依赖；控制平面负责触发和
  投递；横切中间件在每次调用前后强制执行权限与安全策略。

======================================================================
二、避免“模型能力”概念膨胀
======================================================================

认知能力在架构中是一等概念，但默认不是 Capability Registry 中的一等 Tool。

建议的概念模型：

  LLM Runtime
  ├── understanding
  ├── extraction
  ├── planning
  ├── comparison
  ├── synthesis
  └── generation

普通任务不需要把这些过程序列化。例如：

  用户问天气
      -> Agent 理解问题
      -> weather.get_brief
      -> Agent 组织回答

不创建：

  model.extract -> weather.get_brief -> model.synthesize

否则 Registry 很快会膨胀为 `model.classify/reason/compare/rewrite/translate/rank/reflect/...`，
只是把模型内部动词重新包装成几十个“工具”，既增加上下文，也不能带来稳定的执行边界。

显式提升模型阶段的条件：满足以下任一真实需求时才考虑。

- 使用不同模型或不同 Provider；
- 独立计费、预算或 Token 上限；
- 独立超时、重试或 fallback；
- 独立缓存且输入输出可以稳定寻址；
- 需要结构化输出校验或专门 Eval；
- 需要第二模型复核、人工确认或可审计重放；
- 该阶段的失败需要与其他步骤分别恢复。

例如复杂金融分析可以是：

  stock.get_kline
      -> web.search
      -> model.financial_analysis（专用模型、结构化输出）
      -> model.review（第二模型、独立验证）

此处两个模型阶段有独立执行语义，才值得成为显式 Step。

需要区分：

- “模型能够理解/总结”属于 LLM Runtime 的能力事实；
- “这一任务要不要独立运行一个模型阶段”属于 Plan；
- “选择哪个模型、thinking level、预算、超时和 fallback”属于 ExecutionPolicy。

======================================================================
三、任务表达式与 Plan IR
======================================================================

此前的设计为：

  任务 = 能力 × 操作 × 目标 × 触发方式 × 执行策略 × 权限策略 × 投递方式

它继续作为概念检查表使用，不直接等同于 v1 的序列化 schema。

保留这套分解，但显式执行计划是可选项，且第一版不强制设置全局 Target：

  TaskSpec
  ├── Goal
  ├── ExplicitPlan?          // 可选；仅在需要显式 Capability 时存在
  ├── Trigger
  ├── ExecutionPolicy
  ├── PermissionPolicy
  └── DeliveryPolicy

其中：

- Goal：用户真正想得到的结果；
- ExplicitPlan：可选的显式能力调用，不包含普通的隐式理解和措辞过程；
- Trigger：立即、绝对时间或受控周期；
- ExecutionPolicy：模型/Provider、超时、重试、预算、缓存、fallback、失败策略；
- PermissionPolicy：谁、在哪个通道、对什么数据和副作用有权限；
- DeliveryPolicy：结果送到哪里、格式、去重、静默时段和失败可见性。

纯模型任务可以没有 ExplicitPlan。例如改写句子、解释稳定知识或总结当前上下文时，LLM Runtime
直接围绕 Goal 工作，不为了统一格式虚构 `model.generate`、`model.explain` 等 Capability。

第一版也不设置容易产生歧义的全局 Target。目标放在真正使用它的局部位置：

- `Step.target`：该能力步骤操作的对象，例如 `NVDA` 或“最近 30 天 NVIDIA 新闻”；
- `DeliveryPolicy.target`：投递对象，例如当前主人 QQ 私聊；
- `Goal`：保留跨步骤的全局意图。

若未来多个领域证明存在稳定且唯一的“任务主体”，再通过新 schemaVersion 增加可选 TaskTarget，
不在 v1 提前占位。

第一版 Plan IR 只支持三种外形：

1. `single`

   一个显式能力调用，例如 `weather.get_brief` 或 `web.search`。

2. `sequence`

   少量固定顺序步骤；前一步的受控输出成为后一步输入。首版不支持任意分支、循环、动态新增
   Step 或模型生成命令。

3. `scheduled`

   对 `single` 或 `sequence` 增加受控 Trigger。语义上 Schedule 属于 Trigger，不是新的计算
   拓扑；序列化格式可以提供 `scheduled` 包装，便于实现和阅读。

示意结构：

  {
    "schemaVersion": 1,
    "goal": "查询公开网页中的最新信息",
    "explicitPlan": {
      "kind": "single",
      "step": {
        "capability": "web.search",
        "operation": "search",
        "target": "public_web"
      }
    },
    "trigger": { "kind": "now" },
    "executionPolicy": {
      "timeoutMs": 8000,
      "maxAttempts": 1,
      "fallback": "none"
    },
    "permissionPolicy": {
      "context": "owner_qq_private",
      "dataEgress": "fixed_search_provider"
    },
    "deliveryPolicy": {
      "kind": "reply_private_chat",
      "target": "trusted_owner_from_context"
    }
  }

不要求每一次普通对话都持久化 TaskSpec，也不要求每个 TaskSpec 都含 ExplicitPlan。`single` 可只在
本轮内存中执行；只有定时、可恢复、多步写入或需要审计重放的任务才需要持久化结构化计划。

未来可在 schema 中预留 `stepId`、`dependsOn`，但 v1 执行器忽略/拒绝并行依赖。只有出现真实的：

          ┌-> search A -┐
  input --|             |-> synthesis
          └-> search B -┘

并且顺序执行无法满足延迟、成本或语义要求时，才设计 DAG 的并发、汇合、失败传播、补偿和恢复。

======================================================================
四、Capability 分类与共享方式
======================================================================

A. LLM Runtime（默认隐式）

  理解、抽取、规划、比较、综合、生成。通常不进入 Registry；满足独立执行条件时，才以有限的
  `model_stage` 进入 Plan。

B. Primitive Capability（显式、可复用）

  calculator、time、web.search、OCR、文件解析等。它们不是某一业务领域，但其输出会参与任务
  结果，所以必须留下显式调用、来源、时效和失败状态。

C. Domain Capability（显式、领域语义）

  weather、stock、paper、travel、git 等。它们拥有受控数据结构、领域规则和操作语义。

D. Internal Control Plane（默认不向模型暴露）

  scheduler、workflow runtime、notification dispatcher、proposal/commit coordinator、outbox、
  reconciler。模型可以通过领域工具表达意图，但不直接获得通用控制权限。

E. Cross-cutting Aspects（所有能力调用的强制包络）

  身份认证、权限检查、schema 校验、隐私/凭证检测、限流、费用预算、超时、审计、追踪、缓存、
  幂等、不可信外部内容标记、输出规范化和失败码收敛。

共享基础能力采用“显式依赖 + 受控注入”，不是全局继承：

  weather.realtime
    required: [qweather]
    fallback: none

  stock.explain_movement
    required: [stock.market_data, calculator]
    optional: [web.search]

  paper.discovery
    required: [paper.search]
    optional: [web.search]

领域操作只能使用声明过、当前上下文获准且当前风险策略允许的依赖。`web.search` 即使是基础能力，
也不能因此自动进入每个领域，更不能通过依赖关系把模型未获授权的能力间接放大。

有效能力集合：

  EffectiveCapabilities =
      Installed
      ∩ ContextAuthorized
      ∩ TaskRequired
      ∩ RiskPolicyAllowed

还要区分四个状态：

- Installed：代码/Provider 已安装；
- Authorized：当前身份和通道被代码允许；
- Exposed：本轮被展示给模型；
- Executed：本次实际调用并产生了可审计结果。

Tool Router 未来只影响 Exposed，不能改变 Authorized。

======================================================================
五、AOP 类比的准确边界
======================================================================

AOP 类比适用于“不改变业务目标，但每次调用都必须执行”的包络：

  身份/通道校验
      -> 参数和隐私校验
      -> 权限、预算与限流
      -> Capability 执行
      -> 输出/schema/不可信内容处理
      -> provenance 与最小审计

日志是典型切面；身份、权限、预算和审计也应统一实现，避免每个领域复制粘贴后逐渐不一致。

Search 和 Calculator 不应成为透明切面：

- 它们会改变结论，必须在 Plan/调用记录中可见；
- Search 会向第三方外发 query，并返回不可信资料；
- Calculator 是确定性结果，Search 只是候选来源，两者的 trust level 不同；
- 失败时必须由领域路由策略决定“停止、降级还是明确说明”，不能静默替代专业数据源。

因此正确关系是：

  领域能力通过显式依赖共享 Primitive Capability；
  所有能力共同经过 AOP/中间件式安全包络。

======================================================================
六、Capability Registry v1（先登记，不先造 Router）
======================================================================

Registry 是能力清单和策略输入，不是权限授予器，也不要求每项能力都是一个模型可见 Tool。

建议最小字段：

  id
  class: primitive | domain | model_stage | internal_control
  exposure: model_tool | internal_only
  operations
  input_schema_version
  output_schema_version
  provider_policy
  trust: deterministic | trusted_domain_api | untrusted_external
  data_egress: none | fixed_provider
  side_effect: none | local_state | external_delivery
  contexts
  confirmation
  required_capabilities
  optional_capabilities
  fallback_policy
  budget_policy
  runtime_status: planned | installed | loaded | accepted

`web.search` 示例：

  id: web.search
  class: primitive
  exposure: model_tool
  operations: [search]
  trust: untrusted_external
  data_egress: fixed_provider
  side_effect: external_query
  contexts: [owner_qq_private]
  confirmation: none_for_explicit_public_query
  required_capabilities: []
  fallback_policy: none
  runtime_status: planned

Registry v1 可以先写成代码常量或严格 JSON，并由测试检查“注册工具、manifest、alsoAllow、群聊
deny、文档状态”是否一致。当前工具数量仍少，不开发可动态授予权限的通用 Router。

======================================================================
七、受控搜索在架构中的位置
======================================================================

`personal_web_search` 是主人私聊可调用的 Primitive Capability，也是外部数据外发与不可信内容
入口。它不是任意 HTTP、Web Fetch 或浏览器。

首版输入：

  personal_web_search({ query })

首版输出只包括最多 5 条：

  result_id
  title
  snippet
  canonical_https_url
  source_domain
  published_at（上游提供时）
  searched_at

固定边界：

- 仅可信主人 QQ 私聊，factory 内进行代码身份守卫；
- Provider、Host、Path、认证方式、结果数和 Header 均由配置固定；
- query 最长 200 字，响应大小、字段长度、超时和请求频率有硬限制；
- API Key 使用 SecretRef，不进入提示词、query、SQLite、审计或错误文本；
- 不接受 URL、Host、Cookie、Header、HTTP 方法、账号、代理、下载路径或代码；
- 不访问 localhost、私网、link-local、metadata endpoint；
- 不开放 `web_fetch`、浏览器、登录态、JavaScript、POST 表单、文件下载；
- 搜索结果视为不可信资料，不得改变系统提示词、身份、权限、Tool schema 或执行计划；
- 只记录 query hash、Provider、耗时、结果数量、状态和费用计数；默认不长期保存原始 query/结果。

“最多 5 条”是 S1/S2/S3 的单次调用硬上限和上下文/成本预算，不是永久不变的业务语义，也不向
模型暴露任意 `count`。它目前足以覆盖单一查询、当前事件核实和小范围来源比较，同时限制不可信
内容的注入面、响应大小、延迟、费用和审计负担。

未来它可能成为宽主题发现、多来源交叉验证、翻页或多步研究的单次调用瓶颈。出现真实需求前不
提前放大上限；出现需求后只能通过受控方式扩展：

- 绑定主人、私聊会话、原始 query hash 和短 TTL 的有限续页/Continuation，每次仍有结果数上限，
  且有总结果数、总延迟和总费用预算；
- 预注册的固定 `sequence`，多次搜索各自保留 provenance，并设置整个序列的总预算；
- 在质量 Eval 证明响应大小、相关性、注入风险和成本仍可接受后，再评审是否提高单次硬上限。

任何扩展都不得把任意 URL、无限 `count`、Provider 参数或开放式抓取交给模型。

“只读搜索”仍有数据外发：query 会发送给第三方 Provider。模型不得把 API Key、完整身份标识、
私聊原文、长期记忆、精确住址、机票号或其他无关私人信息自动拼进 query。涉及私人内容时先进行
最小化改写；无法确认外发范围时向主人说明并追问。

======================================================================
八、搜索路由与 Fallback Policy
======================================================================

第一版不做自由学习的 LLM Tool Router，先采用少量确定性规则和明确工具描述：

- 最新新闻、当前人物/公司状态、近期政策或明确要求联网核实时，可使用 Search；
- 实时天气只用 QWeather，Search 不是天气数据 fallback；
- 实时行情只用专业 Stock API，Search 只能补充公开新闻背景；
- 论文元数据优先 Paper API；发现范围不足时才按策略补 Search；
- 稳定基础知识且无时效疑问时可直接回答；
- 搜索失败时如实说明，不用模型记忆伪装成最新结果；
- 专业 API 失败时，只有该领域显式声明 fallback 才能搜索，并必须标明数据源降级。

有效路由不是“模型知识 -> 专业 API -> Search”的固定阶梯，而是按 claim 类型选择信息源。

示例：

1. “广州现在多少度”

   `single(weather.get_brief)`；不暴露 Search 作为替代数据源。

2. “某公司今天发生了什么”

   `single(web.search)`；Agent 的普通理解和组织回答仍是隐式 LLM Runtime。

3. “分析英伟达最近一个月上涨原因”

   未来可用有限 `sequence(stock.get_kline, calculator, web.search)`；普通综合默认隐式。只有使用
   独立金融分析模型或复核模型时，再添加显式 `model_stage`。

4. “16:00 搜索某主题并发给我”

   `scheduled(sequence(web.search, deterministic_format))`；Scheduler 和 QQ Delivery 是内部控制
   平面，不向模型暴露通用 Cron 或任意发送目标。该能力不属于 S1 首版。

======================================================================
九、分阶段开发路线
======================================================================

这项工程按“设计冻结 -> 离线实现 -> 离线验收 -> 分阶段上线 -> 质量完善 -> 有需求才组合”推进。
S1 不修改 `openclaw.json`，S2 通过前不让模型看到 Search，S3 才逐项增加运行时暴露面。

首版搜索建议作为独立插件：

  chatbot/plugins/personal-search/

不继续塞入已经承担天气、规划和提醒职责的 `personal-weather` 插件，也不在此时重构后者。Search
与现有领域模块只共享架构约定，不直接共享业务 Store。等身份守卫、审计包络、错误模型等在至少
两个独立插件中证明接口稳定，并出现第三处实际复用需求后，再评审是否提取小型公共 Runtime。

当前“任务和功能解耦程度”的判断：

- 已经完成的部分：LLM 的理解、规划和生成与显式 Capability 分开；天气、规划、提醒等领域功能
  与各自的 Provider、Store 和副作用适配器分开；Scheduler、Proposal/Commit、Delivery 和
  Reconciler 等控制平面没有直接作为通用工具暴露给模型。
- 尚未完成的部分：项目还没有一个真正统一的 Task Runtime。天气查询、提醒、规划提案、Cron
  任务和未来搜索仍以各领域自己的请求、记录、服务和受控流程表达；Trigger、ExecutionContext、
  权限包络、投递、审计/来源和恢复语义也尚未由一个通用 Task 对象统一承载。
- 因此，当前状态是“功能已经从模型和底层副作用中解耦，但具体任务尚未从各领域工作流中完全抽象
  出来”。本文中的 `TaskSpec`、`TriggerSpec`、`ExecutionContext`、`Provenance` 和 Plan IR
  是演进边界与架构契约，不代表当前已经存在可承载所有领域任务的通用执行引擎。

这种未完全解耦在当前阶段是合理的：天气、提醒和搜索的真实任务形态、恢复要求、投递方式、数据
敏感度和失败语义还没有形成足够稳定的交集。为追求形式上的完全解耦而提前建设通用 Task Engine，
容易把尚未验证的共性固化为框架，并扩大本轮搜索的变更面和安全回归面。因此，搜索 S1 继续采用
独立插件 + 单一 `personal_web_search` + 领域内受控调用的最小路径，不因概念上存在 TaskSpec
就提前引入通用运行时。

只有在天气、提醒、搜索至少出现第二或第三种真实组合需求，并证明存在稳定、可复用且边界清晰的
共同语义后，才提取 `TaskSpec` / `TriggerSpec` / `ExecutionContext` / `Provenance` 等公共
边界，再评审是否需要小型 Task Runtime 或固定组合模板。届时应以真实复用证据、失败恢复和审计
需求为依据，而不是以“所有功能理论上都能统一”为依据。

Capability Registry v1 首先只是声明文件、校验规则和测试依据，不成为动态权限授予器；Plan IR
首先只是架构契约，S1 的 `single` 搜索不需要通用 Plan Engine。这样可以保留演进方向，同时避免
为了一个搜索工具先重构整个系统。

======================================================================
十、首版明确非目标
======================================================================

- 不把所有认知动作注册成 Tool/Capability；
- 不实现通用 DAG Workflow Engine；
- 不实现模型自由生成或修改执行图；
- 不实现动态权限授予 Router；
- 不开放 `web_fetch`、浏览器、任意 HTTP、登录态或下载；
- 不将搜索结果自动写入长期记忆、知识库、系统提示词或开发文档；
- 不自动使用 Search 替代天气、行情等专业数据源；
- 不允许领域模块通过“共享基础能力”获得未声明或未授权的联网权限；
- 不让模型直接管理 Scheduler、Notification target 或 QQ 发送；
- 不因 Search 是“基础能力”而默认每轮展示或调用。

======================================================================
十一、验收与回滚
======================================================================

上线条件：

- Provider 和费用策略已确认；
- SecretRef 配置有效且文件权限正确；
- 离线测试、插件校验、配置校验和运行时 inspect 通过；
- `messaging` profile 只增加精确 Search 工具名；
- 所有群聊策略显式 deny；
- 真实主人 QQ 私聊搜索成功，引用与时间正确；
- 群聊/非主人、无 Key、超时、429、异常响应和提示注入负向通过；
- 日志、SQLite、提示词和工具结果不含凭证或无关私人信息。

回滚顺序：

1. 从 `tools.alsoAllow` 移除精确 Search 工具名；
2. 保持群聊 deny，并禁用 Search 插件/配置；
3. 重启 Gateway，验证运行时工具清单不再包含 Search；
4. 保留最小审计和配额计数，不手工删除或伪造历史；
5. 删除/轮换 Search Key 时使用供应商与 SecretRef 的正常流程，不在文档记录密钥。

======================================================================
十二、仍需主人确认的信息
======================================================================

MVP Must Pass：

- Search Provider；
- 专用 API Key 是否已获批；
- 每分钟、每天和每月的保守调用上限，以及 Provider 账户费用硬上限；
- 原始 query 是否允许进入 Provider，以及哪些明显私人信息必须在外发前删除；
- 是否接受首版只有结果摘要和链接、不能打开网页全文。

MVP 后 Should Pass：

- 是否需要搜索缓存及其 TTL；
- audit 的长期保留/删除期限；
- 是否需要精确到单次费用的本地核算；
- 是否需要比明显 Secret 拦截更复杂的 query 隐私分类。

Must 信息未确认不妨碍完成架构与 mock 接口设计，但会阻止真实 Search API 接入和端到端验收；
Should 信息不阻止首次 MVP。

======================================================================
十三、详细开发 TODO、验收目标与停止条件
======================================================================

本节是实际开发清单。任务状态遵守以下规则：

1. 先在本文记录需求、边界、依赖和验收方法；
2. 再修改代码，并记录文件、配置、迁移和安全影响；
3. 先完成自动化/终端验收，再做需要运行时权限的真实 QQ 验收；
4. 主人报告真实结果或开发者取得等价的可复核证据后，更新验收记录；
5. 代码、测试、运行状态和文档一致后，才把对应 TODO 标为完成。

优先级分为两档：

- `Must Pass`：首次向主人 QQ 私聊开放 Search 之前必须通过；它直接保护身份、网络、Secret、输入
  输出边界、超时/响应大小、群聊拒绝、基础限流、回滚或既有功能。
- `Should Pass`：明确记录的稳定化和治理工作，可以在 MVP 已真实搜索后继续补齐；包括更完整的
  费用计数、复杂 query 隐私分类、穷举型异常映射、长期 audit retention、质量 Eval 和通用化。

Should Pass 如果在实现过程中暴露出可直接越权、泄密或无法回滚的问题，应升级为 Must Pass 并
记录原因；除此之外不能因为 Should 未完成而无限推迟首个 MVP。

这些 TODO 是验收检查点，不是一项对应一个模块、类或开发迭代。多个 Must 可以由同一条简单
代码路径和同一组参数化测试同时满足。MVP 的复杂度预算是：一个独立插件、一个固定 Provider
client、一个薄 SearchService、一个 tool factory 和测试；不新建通用治理平台、Plan Engine、
Registry Runtime、复杂隐私分类器或独立审计数据库。若某个 Must 的实现开始要求这些平台，应先
收缩实现或把非安全核心移到 Should，而不是继续扩建框架。

任何阶段不得因为“下一阶段早晚会做”而提前开放其权限。搜索失败不得影响天气简报、规划状态、
个人提醒或 QQ 基础对话；涉及现有模块的重构必须另立 TODO、单独回归、单独回滚。

十五、开发记录（2026-08-12，Search MVP 第一轮）
======================================================================

本轮开始前的运行时事实：

- OpenClaw 版本为 `2026.7.1-2`；当前未配置 `tools.web.search`，也未安装/启用 Brave Provider；
- 生产 `messaging` profile 未暴露 `web_search`、`web_fetch` 或 browser；
- 当前天气、规划和提醒仍由 `chatbot/plugins/personal-weather/` 提供，本轮不重构该插件；
- OpenClaw Plugin Runtime 已提供 `api.runtime.webSearch.search(...)`，插件可以在不依赖通用 agent
  tool wrapper 的情况下调用已选择的 Search Provider。

本轮实现决策（Provider 尚未完成可用性验收，优先验证 DeepSeek）：

1. 新建 `chatbot/plugins/personal-search/`，只注册 `personal_web_search`；
2. 包装 OpenClaw 的内部 `runtime.webSearch`，不重复实现 Provider HTTP/SecretRef transport；
3. MVP 代码固定 `count = 5` 和搜索结果边界，但不把 Provider、Host、URL、Header 或 count
   交给模型；最终 Provider 必须通过 S0.2 的结构化结果、费用、隐私、稳定性和权限审查；
4. Provider Key 或其他凭证由所选 Provider 的 SecretRef 表面管理，不进入 `personal-search` 配置；
5. 即使以后启用某个 Provider，也不把通用 `web_search` 加入 `tools.alsoAllow`；只有包装工具可见；
6. 当前先用注入的 mock runner 完成 S1/S2；本轮只预置不启用的 DeepSeek Provider 配置，
   不安装 Provider、不重启 Gateway、不向 QQ 暴露 Search，也不扩大生产权限。

DeepSeek 作为检索后端的记录方案（2026-08-12）：

1. 调用关系固定为“GPT-Terra 主 Agent -> 受控 Search Adapter -> DeepSeek Responses Web Search”。
   GPT-Terra 负责判断是否需要联网、约束 query、理解证据和生成最终回答；DeepSeek 只承担受控检索，
   不替换主 Agent，也不改变主 Agent 的图片理解路径。
2. 本地预置的 Provider 配置为 `deepseek-search`：
   - Base URL：`https://api.deepseek.com`；
   - 协议：`openai-responses`，由 Responses API 的 `/responses` 路径承载服务端 `web_search`；
   - 模型：`deepseek-v4-flash`；
   - 输入：仅 `text`，因为检索 Worker 不承担图片理解；
   - 凭证：`DEEPSEEK_API_KEY` SecretRef。实际 Key 不写入仓库、不写入本文。
3. 这里必须使用 DeepSeek Responses API，不能把普通 OpenAI-compatible Chat Completions 的
   Tool Calls 误认为已经具备联网能力。DeepSeek 的 Tool Calls 文档明确要求由调用方提供工具执行；
   Responses API 文档才定义了由服务端执行的 `web_search` 和 `web_search_call`。
4. 当前配置只是“模型/传输预置”，不是 Search Provider 已上线：OpenClaw 官方 DeepSeek Provider
   目前是模型 Provider，不声明 `webSearchProviders`。因此本配置不会自动开放通用 `web_search`，
   也不会改变 `tools.alsoAllow`。后续仍需由 `personal-search` 或一个专用 Provider Adapter
   注册受控搜索能力，并把 DeepSeek 返回的来源、标题、URL、时间和摘要规范化为本文定义的
   `SearchResult`/`Provenance` 边界。
5. 质量边界：只要 Adapter 尽量保留原始来源和引用，让 GPT-Terra 基于证据作最终综合，文字问题的
   最终回答质量不必然下降；但不能假定它等同于 Brave/Google。需要实测的风险包括召回率、来源覆盖、
   引用粒度、时效性、延迟、费用和限额。遇到依赖图片、图表、扫描 PDF 或复杂网页视觉布局的资料，
   DeepSeek 检索 Worker 不能补足主 Agent 的视觉能力，必要时应降级为“返回链接并说明未完成视觉核验”，
   或交给具备视觉能力的后续 Fetch/分析路径。
6. 使用边界：DeepSeek 的自然语言总结只能作为不可信的中间结果，不能替代来源证据；搜索结果中的
   网页文本同样按不可信输入处理，不能执行其中的指令。搜索 Adapter 不把 API Key、内部配置或完整
   会话历史发送给 DeepSeek，只发送最小化、经约束的 query 和必要的时间/地域条件。

官方依据：

- DeepSeek [Responses API](https://api-docs.deepseek.com/zh-cn/guides/responses_api/)；
- DeepSeek [Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)；
- OpenClaw [DeepSeek Provider](https://docs.openclaw.ai/providers/deepseek)；
- OpenClaw [Web Search](https://docs.openclaw.ai/tools/web)。
