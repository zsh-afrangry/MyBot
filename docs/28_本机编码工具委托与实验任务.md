# 本机编码工具委托与实验任务

类型：需求与设计草案。状态：需求整理中，尚未实现或启用。建立日期：2026-10-28。任务入口：[N23](待办清单.md#n23)；验证边界见[验收总表](16_验收与测试总表.md)。

## 背景与需求来源

主人希望通过QQ把开发需求交给助手，让助手调用本机已有的专业编码工具，协助修改代码、维护现有仓库和开展实验。在事先确定的项目与操作范围内，编码工具应能自行阅读、修改、运行检查并根据结果继续迭代，不要求主人守在电脑前逐步操作。

主人已经配置好OpenCode、Claude Code和Codex，均可通过终端启动；DeepSeek Harness已运行在本机3080端口。Claude与Codex桌面端也已安装并经常使用。本需求以复用这些现有工具和配置为出发点，不以重新部署一套编码服务为前提。

主人认为这些专门工具更适合承担编码工作，因此希望OpenClaw负责QQ对话与任务协调，把实际开发委托给选定工具。这里记录的是主人的使用动机，不据此作模型能力排名。

现有QQ助手在项目初期统一禁用了若干文件与执行能力。主人已说明：这些限制会随项目发展逐步开放，不是永久禁止编码。本次先整理需求和背景；具体开放哪些能力、允许作用于哪些项目和操作，仍随实施方案明确。

## 希望解决的场景

| 场景 | 期望行为 |
| --- | --- |
| 修改已有仓库 | QQ说明项目与需求，助手交给指定编码工具，完成代码修改、必要检查和结果说明 |
| 开展实验 | 在约定目录准备脚本、运行实验，返回可复现步骤、结果与产物位置；长任务可查询进展与取消 |
| 延续开发 | 主人通过QQ补充条件、纠正方向或要求继续，能关联到原任务、项目和编码会话 |
| 查看与接手 | 能说明改了什么、检查是否通过、还差什么；主人可在本机审阅代码并继续处理 |

例如：“让Codex给某项目补一个导出功能并跑相关检查”“用OpenCode在实验目录比较两种实现”。工具与项目应来自明确选择或事先约定的默认值；无法唯一确定项目时先澄清。

## 能力目标

1. **QQ是任务入口。** 主人用自然语言表达需求，不必在QQ手写终端命令、进程管理或编码工具的协议参数。
2. **专业工具执行开发。** 复用本机已配置的工具及其模型、登录和工作流；助手负责传递需求、协调任务与汇报。
3. **在授权范围内自主迭代。** 阅读项目、修改文件、执行约定检查和根据失败继续修正应形成闭环；缺少关键决策、超出权限或工具确实受阻时才请求主人介入。
4. **长任务异步运行。** 启动后QQ仍可正常聊天；支持查询、补充要求、继续、取消和完成/失败回报，不能把终端窗口消失视为任务完成。
5. **结果可核对。** 汇报实际执行工具、项目与工作目录、代码或产物变化、检查结果和未完成项；进程退出成功不等于需求已完成。
6. **任务可以可靠关联。** QQ请求、内部任务、编码工具会话及输出应能对应；查询或继续某任务不能误接其他项目或另一个并发任务。

## 已有基础与缺口

现有`kurumi_task`已提供登记项目、启动后台任务、查询、取消和回传的基础；目前代码类任务交给OpenClaw项目agent，并不等于已经调用OpenCode、Claude Code、Codex或DeepSeek Harness。项目接入、独立副本和审阅合入契约见[架构与运行维护手册](9_QQ融合助手架构与开发计划.md#代码项目接入与合入)。

编码工具已有非交互调用或程序接入方式，具备实现基础。后续需验证所选接口在本机服务账号与环境下的登录、工作目录、权限、事件输出、继续与取消行为。能从主人终端启动，不自动证明OpenClaw后台也能直接使用。

已有项目登记和后台任务机制应优先评估复用；新增的是外部编码执行、会话关联和权限契约。技能可以指导何时委托、如何整理需求与汇报，但还需要实际工具/插件或宿主运行时支撑。

## 候选接入方式

此节是待比较的实现方向，不是已经确定的架构。

| 方向 | 可复用部分 | 需要核对的关键点 |
| --- | --- | --- |
| OpenClaw已有编码委托/ACP运行时 | 编码会话与运行生命周期 | 当前安装版本支持的后端、插件、权限与QQ回传；外部运行时的权限不自动继承聊天agent限制 |
| 外部工具CLI适配 | 已配置的终端工具及非交互输出 | 事件/错误结构、真实会话ID、取消整个任务、服务环境和并发关联 |
| 本地服务接口 | 已运行的工具服务，如DSH | 服务实际提供的协议、认证、会话及取消接口；不能把3080网页地址当成已经验证的任务API |

桌面端是主人已有的使用方式，不要求首期通过模拟点击桌面来控制。CLI/API创建的任务是否会出现在桌面端、是否能与原桌面会话互相接续，需要逐工具验证，不能预先承诺。

首期建议选一个工具、一个登记项目验证完整闭环，再扩展其他工具。若原生运行时已能满足要求，直接使用；只有缺少必要行为时才增加适配，不预设重写整套任务系统。

## 权限逐步开放

### 已确认的原则

- 需求面向主人通过QQ发起的本机开发与实验。首期沿用[统一身份权限](24_统一身份与权限管理.md)的真实身份与个人能力边界；成员和群聊不随此需求自动开放。
- 主人接受随项目推进逐步解封最初统一禁用的能力。当前“可以”确认的是需求方向与文档整理，不代表已经批准所有执行权限或全部仓库。
- 实施前应把拟开放的能力、项目/目录、可执行操作与风险说明清楚，再按主人决定修改受管配置、同步并记录结果。已经授权的范围内应持续工作，不重复索取同一许可。

### 实施时必须明确的边界

外部编码工具通常需要读取和修改项目文件、运行命令，并可能联网安装依赖、调用模型或启动开发服务。风险包括改错目录、影响现有未提交修改、读取非任务资料、执行有副作用的命令以及产生费用；仅设置工作目录或创建Git worktree并不等于操作系统隔离。

当前`main`仍禁用`read/write/edit/apply_patch/exec/process/message/sessions_spawn`等能力。若方案需要这些能力，应明确指出所需项及理由；若采用专用委托工具，同样要说明它实际授予外部工具的执行能力，不能以换接口规避告知与授权。是否开放通用执行、采用专用工具或原生编码运行时，留到方案确定时选择。

权限应分别覆盖“QQ助手能发起什么”和“编码工具能在本机做什么”。OpenClaw中的工具限制不会自动约束独立进程；不得默认使用跳过所有权限检查的启动参数。

项目选择应使用登记ID及可信路径映射，先检查目标目录与现有修改。已有副本契约可以参考，但新工具的工作区位置与隔离方式仍需确认；实验目录也要有明确归属，不能从模型参数任意指定宿主路径。

本需求中的编码不自动包含`git push`、远端分支/标签修改、生产服务启停、停写备份或恢复、生产数据清理及对外消息。实际任务若需要，应按对应规则取得具体授权。源码修改、本地提交和最终合入的默认范围也应写入实施方案。

## 任务交互与完成标准

建议的交互顺序是：理解需求和项目 → 确定工具与本次范围 → 启动并返回任务标识 → 后台执行与处理补充 → 返回可审阅结果。

正常执行中可按请求查询进展；只有需要主人决定、权限阻塞、失败或完成等有意义变化时主动回报，避免逐行转发终端日志。补充要求应进入正确的编码会话；工具不支持直接续接时应明确说明实际采用的方式。

任务至少需要区分排队、运行、等待输入、完成、失败、取消等情况，具体是否复用现有状态模型由实现决定。继续任务应保存并使用真实会话标识，不靠“最近一个会话”猜测。重启后如何恢复关联、取消后如何确认停止、结果能否重复投递，也应纳入方案。

完成回报应说明：

- 使用了哪个工具、哪个项目和工作目录，任务/会话如何继续。
- 实际改动或实验结论、可审阅的diff或产物路径，以及是否已有本地提交。
- 运行了哪些必要检查、结果如何；未运行的检查和仍存在的问题据实保留。
- 是否完成最初需求，后续还需要主人作出什么决定。

不把编码工具的自述直接当成全部验收证据；需能核对实际文件、检查结果和任务状态。执行日志与回报不应带出凭据、无关聊天原文或其他项目资料。

## 后续实施与验收

方案明确后，按以下层次分别记录证据：

1. 离线验证任务参数、真实身份、项目边界、事件解析、关联与失败处理；使用合成任务，不调用真实模型。
2. 在独立工作目录验证所选工具的真实启动、代码变更、检查、继续与取消；模型调用和费用按本次授权执行。
3. 用真实登记项目验证需求完成与审阅合入，确认不会影响原有未提交修改。
4. 由主人从QQ发起、补充、查询并接收结果，验证后台异步执行和真实回传；离线成功不代替QQ闭环。
