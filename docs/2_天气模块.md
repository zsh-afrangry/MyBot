# 天气模块

涵盖三个相关的插件：`personal-weather`（天气）、`personal-profile`（当前所在地）、`personal-planning`（行程）。三者独立启停，实现都在共享包 `chatbot/packages/personal-domains`。

## 功能

- **天气查询**：返回实况、今日预报、未来 24 小时降雨趋势和官方预警，并说明数据时间、来源和缓存状态。不带地点时查主人的有效地点；带地点时只影响本次查询，可更新天气缓存。
- **每日播报**：由主人登记的周期任务到点触发，助手调用天气工具后发到主人私聊。插件不会自己创建播报任务，任务参数里也不写死地点。
- **当前所在地**：主人明确说“我已经到了某地”时，生成待确认的变更，确认后才更新。它是个人资料事实，天气只是读取方。
- **行程**：主人明确要求记录时，生成待确认的行程，确认后保存为 `planned`。

不做的事：

- 讨论、假设、“可能出行”不落库。
- 记录行程、预计航班落地、临时查天气都不会改变当前所在地。
- 不做主动预警、机票识别、航班状态查询，也不按行程自动切换天气地点。
- 资料只有“当前所在地”一个字段，没有常住地，也没有任意字段的编辑器。

## 接口

| 工具 | 权限点 | 说明 |
| --- | --- | --- |
| `personal_weather_get_brief` | `weather.read` | 只读。可选 `location` 和 `administrative_area`，后者不能单独出现 |
| `personal_profile_state_get` | `profile.read` | 读取当前所在地 |
| `personal_profile_change_propose` / `_commit` | `profile.manage` | 只接受 `current_location.set` |
| `personal_planning_state_get` | `planning.read` | 读取地点、行程和待确认项的摘要 |
| `personal_planning_change_propose` / `_commit` | `planning.manage` | 只接受 `trip.create` |

配置在 `config/runtime.config.json` 的 `plugins.entries` 下：

| 键 | 作用 |
| --- | --- |
| `apiHost`、`apiKey` | QWeather 专属 Host 使用 `${QWEATHER_API_HOST}`，密钥使用 `QWEATHER_API_KEY` 的 SecretRef，均由宿主从环境变量解析 |
| `weatherBackend` | 天气和地点解析走哪里。当前为 `knowledgemap`，另一个取值 `qweather` 直接对接 QWeather API |
| `bridgeBaseUrl`、`bridgeTokenFile` | KnowledgeMap 助手接口的地址和令牌文件 |
| `scheduledOwnerId` | 定时播报代表的主人，由 `config/access-control.json` 编译写入，不手改 |

运维命令行在 `chatbot/plugins/personal-weather/dist/cli.js`，子命令为 `health`、`db:init`、`lookup`、`brief`、`daily-brief`。网络命令从环境读取 QWeather 配置并直接对接 QWeather API，生产工具按 `weatherBackend` 选择后端。构建入口见[文档9](9_QQ融合助手架构与开发计划.md#开发与验证)。

数据在运行目录的 `state/personal-weather/weather.sqlite`，天气缓存、当前所在地、行程和它们的待确认项共用这一个库。

## 原理

- **地点解析**：用户只给地点文字，后端用城市检索接口消歧。只有唯一候选才继续；同名地点返回候选让主人澄清；查不到就明确说查不到。模型不提供坐标、地点 ID 或 URL。理由：避免用默认地点或网页搜索去猜。
- **澄清后再提案**：所在地变更遇到歧义或无匹配时，结果带 `requiresUserInput`，同一轮后续的所在地提案由 `interaction/clarification-gate.ts` 拦下。临时天气查询返回 `LOCATION_AMBIGUOUS` 或 `LOCATION_NOT_FOUND`，由助手向主人澄清。
- **有效地点**：四个概念互不覆盖。当前所在地是事实；行程是计划；`location_periods` 是带生效时间的地点区间（表已建，目前没有写入路径）；临时查询只影响本次。天气读取时先找生效中的地点区间，没有就读当前所在地。
- **写入走二次确认**：提案冻结内容和哈希，有效期 24 小时；主人用自然语言确认后提交，事务内写入并留审计，重复提交幂等。确认机制见[文档6](6_二次确认.md)。
- **展示精度**：地点保存城市检索返回的叶子地名。播报标题用“上级市 + 叶子名”，所以县级市显示为“镇江扬中”，不会缩成“镇江”。
- **缓存**：实况 10 分钟、逐小时 30 分钟、每日 60 分钟、预警 5 分钟。返回里标明是否来自缓存。
- **网络边界**：只发 GET，地址由配置的 Host 和代码里的固定路径拼出，不接受用户提供的 URL。直连 QWeather 时走宿主的受信任代理，SSRF 策略只放行配置的那个 Host。理由：本机代理使用 Fake-IP，严格策略会把它误判为内网地址。

## 限制与已知问题

- 当前所在地的地点解析依赖天气服务的城市检索，资料和天气没有分开。
- 校区、景点这类比区县更细的地点查不到，返回城市候选时要求主人澄清。
- Fusion 的当前所在地和 KnowledgeMap 网站的默认城市各存各的，不同步。
- 每日播报需要模型生成。天气接口失败时应说明失败，当次没有可核实的天气正文。
