# 记忆系统

类型：需求方案（开发指导）。状态：**阶段1–3已实现并隔离验证，生产尚未切换。** 运行仍保留P2；新增记录/原文工具、迁移及配置切换须具体授权后部署。现行运行规则仍为[文档25](25_人格、记忆与会话连续性.md)的P2本人记忆；本方案生产切换后，文档25的记忆章节迁入本文，25只保留人格、关系与会话生命周期。决定来源见[设计记录](临时_记忆系统设计记录.md)，任务进度见[待办N2](待办清单.md#n2-尝试更多优化记忆的方案)。

## 范围

**目标**：让她跨会话延续对主人的了解、共同经历和她自己的成长，同时保持助手工作可靠。“有人味、有自己脾气”与“做事越来越好”同等重要，取舍时优先前者（D04）。

**使用者**：只有主人一人（D20）。成员长期记忆保持现行关闭，本方案不为成员设计，也不改变成员现有能力。

**不在本文**：

| 内容 | 归属 |
| --- | --- |
| 何时唤醒、唤醒后能做什么、是否联系主人 | [N3唤醒设计](待办清单.md#n3-尝试主动唤醒)；本文只定义“整理”这个动作需要的工具与契约 |
| 人格卡、关系素材 | 文档25与`roles/`；本文不自动改写人格卡（D11） |
| 账单、事项、天气等业务当前状态 | 各业务文档；记忆只引用业务记录ID |
| 日志查询工具本身 | [文档18](18_跨模块链路日志查询.md)；本文定义她使用的只读适配要求 |

## 总体结构

```text
原始层（只追加，唯一事实源）
  宿主会话原文 · 工具调用与结果 · 领域日志 · 附件
        │  程序维护                          │  她自己整理
        ▼                                    ▼
机械索引（可重建，她不改）            印象（她可整理、删改）
  全文索引 · 作息统计 · 游标            片段 · 推断 · 未了之事 · 自身笔记 · 两份画像
        └──────────────┬─────────────────────┘
                       ▼
              回忆三层：L0常驻 → L1按需 → L2原文
```

- **原始层**按职责定义：原样、完整、只追加、未经解释的数据，放在哪里都算（D15/P01）。向量和摘要都不是原始层。
- **派生层**分两类（D15/P03）。机械索引由程序维护，丢了可以重建。印象是她对事情的理解，允许和原文逐渐有出入，需要时回原文核对。
- **回忆分三层**（D06），类比text-to-SQL的表间关系→字段→字段值：L0每回合常驻；L1是片段与记录，按需检索；L2是原文与日志。往下查多深由她决定。

## 原始层

| 来源 | 位置 | 内容 |
| --- | --- | --- |
| 宿主会话 | `agents/main/agent/openclaw-agent.sqlite` 的 `transcript_events`，重置/删除时进入 `session_transcript_archives` | 主人入站、她的回复、工具调用与结果 |
| 领域日志 | 各插件 `events.jsonl`、`channel/*.jsonl` | 业务、投递、授权事件，见文档18的适配器表 |
| 附件 | 宿主媒体目录与业务文件 | 图片、PDF等；记忆只存引用 |

规则：

- 记忆系统不写、不删宿主原始层。记忆自有的只追加镜像保存可信入站、宿主活动与归档原件；SQLite触发器拒绝更新/删除。采集在主人回合、结束、重置和压缩钩子进行；损坏归档哈希不忽略、不推进整理游标。
- 每条原始数据都有一个**来源类别**，由程序根据宿主字段确定，模型不能指定：`owner_said`（主人可信私聊原文）、`she_said`（她的回复）、`tool_result`（本地工具与业务结果）、`external`（网页、社交媒体等外部内容）。
- 派生记录用**原始引用**使用稳定`rawId`，携带会话ID、原事件序号及内容指纹；同序号被宿主替换后，两份原件分别保留。可信入站另保留消息ID与原文，只由真实owner私聊钩子登记为`owner_said`；宿主user形消息可能是投影或转发，不能单凭role提升身份。会话被重置或归档后，引用仍需能解析（见V01）。

## 记录

印象统一存为**记录**（D15/P04）。新增一类信息就是新增记录或新的类型值，不改表结构；只有程序要对它计算时才加结构化属性，并可从原始层回填。

| 字段 | 含义 |
| --- | --- |
| `id`、`version` | 稳定ID；每次修改版本加1，写入带期望版本（CAS） |
| `kind` | 类型，见下表；开放集合 |
| `about` | `owner` 或 `self` |
| `text` | 自然语言正文 |
| `basis` | `stated`（主人明说）/ `inferred`（她的推断）/ `observed`（程序统计）/ `self`（她对自己） |
| `sources` | 至少一个：原始引用或其他记录ID |
| `attrs` | 可选结构化属性，例如日期、截止时间、话题标签 |
| `valid_from`、`recorded_at` | 成立时间与记录时间（借鉴Zep） |
| `state` | `active` / `superseded`（被新记录取代，保留历史）/ `retracted`（她撤回）/ `forgotten`（主人要求忘掉） |
| `external` | 来源含外部内容时由程序置位，她不能清除 |

| kind | about | 写入者 | 规则 |
| --- | --- | --- | --- |
| `fact` | owner | 她，后端校验 | 现行P2的明说事实。来源必须含逐字匹配的`owner_said`原文；遗忘屏障继续有效 |
| `inference` | owner | 她 | 自由形成，`basis=inferred`，至少一个来源；不需要主人确认（D05） |
| `rhythm` | owner | 程序 | 作息与发消息时间分布，`basis=observed`；她只读，可在笔记里解读 |
| `episode` | — | 她 | 一段对话或一件事的概要：时间、话题、经过、情绪基调；来源指向原文区间 |
| `thread` | — | 她 | 未了之事：主人提到的待发生事项、她答应的事；`attrs.due`可选，过期后仍保留到她处理 |
| `milestone` | — | 她 | 共同经历里值得记住的节点，例如第一次一起完成某件事 |
| `note` | self | 她 | 自身笔记：做事经验、兴趣、态度、自我认识；标签由她自己定，不预设栏目 |
| `portrait` | owner / self | 她 | 两份画像：她眼中的主人、她对自己的描述。各只有一条活跃记录，来源列出依据的记录ID |

**存储**：沿用 `workspace/.kurumi-memory/` 下的SQLite，从现有单行JSON快照改为记录表、版本表、原始引用表与游标表。现有P2事实迁移为 `kind=fact`，保留ID、来源与遗忘屏障；首期事实上限继续128条，不静默淘汰；其他记录不占事实限额。迁移需要备份、预览差异、显式配置切换和回退路径，不静默回退。

**修改方式**：提供增量动作（追加、替换某段、取代、撤回），不要求每次整篇重写，避免越整理越空（借鉴ACE）。画像允许整篇重写，旧版本保留。每次修改记录谁、何时、哪次运行、前后内容。

**她自己的话**：`she_said`原文可以作为`about=self`记录的来源（D15/P05），使她说过的“喜欢下雨天”能被记下并保持一致。`fact`仍只接受`owner_said`。

**边界**：`note`里写关于主人的内容不会被程序语义拦截；记录工具的说明里写明`note`只记她自己、关于主人的认识写成`inference`。这是已知的软边界，靠观察和对话引导，不靠后端判定。

## 回忆

### L0：每回合常驻

L0是“浮在脑子表层的东西”，有侧重（D15/P02）。主人私聊的每个回合，以及她被唤醒的每次运行，都由程序组装L0：

| 顺序 | 内容 | 来源 |
| --- | --- | --- |
| 1 | 她对自己的描述 | `portrait(self)` |
| 2 | 她眼中的主人 | `portrait(owner)` |
| 3 | 未了之事，按到期远近排列 | 活跃`thread` |
| 4 | 话题索引，一行一个：话题、最近时间、次数 | 程序从`episode`的话题标签统计 |
| 5 | 作息摘要 | `rhythm` |
| 6 | 本条消息相关的记录 | 按本条原文在记录上做全文匹配挑出的少量`fact`/`inference`/`note`/`episode` |

- 1–5在两次整理之间基本不变；6每回合按消息变化，相当于text-to-SQL的schema linking。
- 每项带记录ID和`basis`标记，她能据此往下查，也能分清“主人说的”和“我猜的”。
- 预算沿用现行`maxContextChars`思路，按上表顺序整条放入，超出整条跳过，不截半条。
- 画像还没写过时，1、2为空，L0退化为现行P2的事实注入。

### L1：记录检索

- 工具按关键词、类型、时间范围检索记录，返回概要、ID和原始引用。
- 全文索引使用SQLite FTS5 `trigram` 分词；少于3个字的查询回退到子串匹配。宿主自带的会话全文索引用 `unicode61` 分词，中文整句会成为一个词，不适合中文检索，不复用。
- 向量检索不在首期。trigram对“换了说法的同一件事”帮助有限，若验收发现S2、S3召回不足，再加embedding索引；它属于机械索引，可随时重建。

### L2：原文与日志

- 她使用的只读适配：按原始引用读取原文上下文，按关键词和时间检索原文，查询自己的工具调用和业务结果。
- 范围限定为主人私聊会话与她自己的运行；执行时遵守遗忘遮罩（见下文）。
- 适配的读取逻辑从`scripts/fusion/log-query.mjs`中抽到`chatbot/packages/`下的共享包，开发CLI与插件都使用这个包；共享包不反向导入`scripts/fusion/`（根AGENTS后端代码边界）。
- 主人、开发AI使用的日志查询保持完整视图，不受她的遗忘遮罩影响（D07、D10）。

## 写入

### 聊天中

- 现行`observe/upsert/delete`继续负责`fact`，以文档25现行契约为准（2026-11-07 delete增加当前遗忘要求evidence与有限疑问/引用拒绝边界）；v3复用同一策略与事务，生产仍为P2。
- 她可以在聊天中直接写`thread`和`about=self`的记录，例如刚答应主人的事、刚说出的自我看法。
- 其余类型主要在整理时写。

### 自己整理

唤醒后的她可以选择整理，整理就是唤醒后能做的一个动作（D17）。由主模型完成，不另设反思模型，不设请求或费用上限（D19）；每次运行的用量写入日志，供主人查看。

整理的机制要求：

| 要求 | 内容 | 理由 |
| --- | --- | --- |
| 游标 | 程序记录“原文已整理到哪个事件序号”。整理工具按批取出游标之后的未整理原文；她提交本批结果后游标才前进，提交“本批无需记录”也算处理 | 旧OpenClaw dreaming连续三晚写同一话题、三晚空跑；增量处理避免重复与空转（借鉴AstrBot片段游标） |
| 基于原文 | 新记录必须引用本批原文或已有记录；记录与模型输出本身不算独立证据 | 防止越读越相信自己写过的东西（借鉴AstrBot来源区分） |
| 允许不改 | 一批原文可以什么都不写 | 不为凑数产生记录 |
| 漏记的明说事实 | 整理时可从旧原文补建`fact`，前提是引文逐字出现在该原始引用中且来源类别为`owner_said`，并通过遗忘屏障和遮罩检查 | 扩展现行“只从本回合原文提取”，保留逐字证据 |
| 外部内容 | 来源含`external`的记录由程序置位标记；L0中显示该标记 | 防止网页内容被当成她自己的经历或指令读回 |
| 可信授权 | 唤醒运行没有主人入站消息，写入授权来自N3提供的可信后台运行身份（绑定主人、运行ID、有效期）；不伪造用户消息 | 现行写入授权绑定`trigger=user` |
| 并发 | 记录写入带期望版本；聊天与整理同时修改同一记录时后者重读再试；主人新消息优先，由N3定义在途整理怎样让出 | 现行CAS原则延续 |

她不整理时，机械索引照常更新，原文检索照常可用，只是片段、画像和L0中的印象部分会滞后。

### 纠正

- 主人纠正时，她把旧记录标为`superseded`或`retracted`，新建正确的记录，并写一条`note`记下这次被纠正（D03）。
- 旧记录保留历史，不进入L0和默认检索结果；查询历史时可以看到。

## 遗忘

主人明确要求忘掉某件事时（D10）：

1. 她找出相关记录，全部标为`forgotten`；它们不进入L0、L1检索和画像依据。
2. 程序为相关原文写入**遗忘遮罩**（原始引用区间加内容指纹）。她的L2适配、整理游标取出的批次、全文索引在读取时都排除被遮罩的原文。
3. 原始层本身不删除，主人与开发侧的日志查询仍能看到。
4. 重建任何派生索引时同样应用遮罩，遗忘的内容不会因为重建而回来。
5. 主人要求重新记住时移除对应遮罩，与现行遗忘屏障一致。

现行G3规则（被遗忘或记忆里查不到的内容不借其他工具找回）改为：**只禁止找回被遮罩的内容**；没被总结进上层、也没被要求忘掉的细节，她可以去原文查。

## 工具与权限

已实现但生产未注册开放的窄工具：

| 工具 | 动作 | 说明 |

- 这些是窄领域工具，不放开`main`的通用`read/write/edit`；新增工具和权限须主人同意，并通过`sync-config.mjs --apply`同步。

## 宿主选择

不启用宿主自带的memory-core（`plugins.slots.memory`保持`none`）。设计时调查的2026.9.7已包含dreaming模块（当前生产已升至2026.11.1，此处保留历史调查，不代表已验证新版接口），但它依赖通用文件写入维护`MEMORY.md`与每日笔记，与`main`禁用`write/edit`冲突，也没有本方案需要的来源类别、遮罩和CAS。旧系统中它产出的`DREAMS.md`出现重复与空跑。

迁移入口为`node chatbot/scripts/memory-system.mjs --workspace=... --owner=... --backup-root=...`；默认只预览。`--apply --expected-hash=<stateHash>`要求同一预览且先停Fusion写入，备份SQLite/notice后同事务改表，按独立配置选`continuityStoreAdapter=records-sqlite`。回退`--rollback=<备份目录> --expected-revision=N --apply`先保留当前v3、核对原件字节哈希与版本，不静默回退。正式备份目录只用`kurumi-backups`。

旧P2遗忘屏障只有哈希，无法恢复原被删文字：迁移保留这些屏障，并保守遮罩相应屏障时间以前的宿主原文；仍活跃的P2事实及其明确证据保持。新遗忘按记录来源和内容指纹分组遮罩，一次重新记住只解除对应组；整条原文有其他未解除遮罩时继续隐藏。

当前机制和模型观察见[本轮验收](verification/memory-system-2026-11-07/README.md)。新权限`memory.raw.read`未授予生产主人，新工具未加入main；没有自动迁移、唤醒、外发或改写人格。

## 验收

机制部分用合成数据做确定性测试；模型部分在真实模型上抽样观察，记录发生率，由主人评价体感，不承诺每次发生（D13）。

| # | 场景 | 机制测试 | 模型观察 |
| --- | --- | --- | --- |
| S1 | 周一提过周五答辩，周六她主动问结果 | 整理产生带`due`的`thread`，到期后出现在L0 | 唤醒时是否问、问得是否自然 |
