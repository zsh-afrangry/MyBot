======================================================================
一、状态与范围
======================================================================

第一阶段（P1）已于 2026-08-06 验收完成：personal-weather 插件、只读天气工具、
固定 CLI、离线测试、真实 QWeather 查询、QQ 主动投递和每日简报 Cron 均曾完成验收。
该结论是当日验收记录，不等同于当前 Gateway、插件或 Cron 仍在运行。

当前已实现的能力：

- 以固定 QWeather 专属 Host 查询当前天气、3 日预报、24 小时预报和官方预警；
- 为当前有效地点生成确定性的中文简报；
- 在主人私聊中通过 `personal_weather_get_brief` 提供只读查询；
- P2A 已实现并纳入插件的两个主人私聊专用、可选的规划工具：
  `personal_planning_state_get` 读取最小化状态摘要，
  `personal_planning_change_propose` 生成严格类型的行程待确认预览；
- P2A 的提案只写入 `change_proposals` 的 pending 草稿，不提交 `trips`、
  `location_periods` 或 `notification_preferences`，也不改变天气地点和 Cron；
- 通过固定 CLI 供运维侧创建每日简报任务；
- 使用独立 SQLite 保存默认地点、缓存和后续位置/行程功能所需的基础结构。

不属于第一阶段：

- 通用网页、任意 HTTP、Shell、文件写入、数据库直连、sudo 或 Cron 管理；
- 群聊天气工具；
- 自动位置切换、行程写入、机票 OCR、航班状态、临近降雨和主动预警；
- 由模型修改提示词、记忆或数据库来直接保存地点、行程或提醒；P2A 只允许后端
  生成受限的 pending proposal 草稿。

确认的默认地点是广东省广州市天河区。未来地点或行程只能由受限工具在主人明确
确认后保存；讨论、示例和假设不是事实。

三、对外接口与配置
======================================================================

当前模型工具分为三类：

  personal_weather_get_brief

  personal_planning_state_get

  personal_planning_change_propose

`personal_weather_get_brief` 读取有效地点，返回经验证的实况、今日预报、未来 24
小时降雨趋势、官方预警、数据时间和来源。`personal_planning_state_get` 只返回
默认/有效地点、每日简报时刻、已存在的行程摘要和未过期 pending proposal 的最小化
摘要。`personal_planning_change_propose` 只接受版本化的 `trip.create` 请求，生成
canonical facts、缺失字段、警告和预览，并写入一条短期 `change_proposals` 草稿。
三个工具都不能直接修改地点、已确认行程、提醒、提示词、记忆、Cron 或发送消息；
P2A 尚未提供 commit/discard 工具。

CLI 位于插件构建产物中，支持：

  health
  db:init
  lookup --location <区县> --adm <城市>
  brief [--json]
  daily-brief

`health` 只校验配置和本地数据库，不发起网络请求；`lookup` 和 `brief` 会调用
QWeather；`daily-brief` 输出用于主动消息的简报文本。

运行配置需要：

  QWEATHER_API_HOST
  QWEATHER_API_KEY

API Key 必须通过环境变量或插件 SecretRef 提供，不能进入源码、`openclaw.json`、
提示词、聊天记录、文档、命令行参数或日志。配置与凭证的具体位置见
`chatbot/BOT_SETUP.md`。

当前客户端使用以下固定接口：

- `GET /geo/v2/city/lookup`
- `GET /weather/v1/current/{lat}/{lon}`
- `GET /weather/v1/daily/{lat}/{lon}`
- `GET /weather/v1/hourly/{lat}/{lon}`
- `GET /weatheralert/v1/current/{lat}/{lon}`

天气查询以经纬度为主键。地点解析得到的 LocationID 仅用于显示或兼容，不能用来
镜像整个城市库。当前实现使用 API Key；2026-08-06 的真实查询证明当时的账号、
Host 与 Key 能访问上述 Weather API v1 接口。若将来鉴权或套餐变化，应显式验证或
迁移到官方 JWT 方案，不得静默回退到旧接口。

======================================================================
四、安全与数据规则
======================================================================

插件是定向数据访问，不是向模型开放互联网。实现和配置必须同时保持以下边界：

- URL 只由配置的专属 HTTPS Host 和代码内固定路径派生；不接收用户 URL、协议、
  端口或路径。
- 仅允许 GET；不跟随重定向；不使用代理或会放宽私网检查的 Host/Origin 信任策略。
- API Key 仅置于 `X-QW-Api-Key` 请求头；不得输出原始上游响应、Host 或凭证。
- 请求有超时、总预算、响应体上限、全局并发上限、有限重试与本地缓存；401/403 和
  SSRF 拦截不重试。
- 网络 JSON 必须在运行时校验。未知枚举和部分组件不可用时应以稳定结果返回，
  不得伪造实时数据或“无预警”。
- 所有展示应保留 QWeather 归因和数据时间；缓存数据必须标示缓存状态。
- 只允许可信主人私聊使用天气工具；身份与私聊状态只能来自可信频道元数据。

SQLite 使用独立数据库，不修改 `state/openclaw.sqlite`。当前 schema 包含：

- `places` 与 `notification_preferences`：默认地点和通知偏好；
- `location_periods`、`trips`、`change_proposals`：为后续确认式地点/行程写入预留；
- `notification_state`：后续通知去重状态；
- `api_cache`、`audit_log` 与 `schema_migrations`：缓存、审计和迁移。

位置时间段使用半开区间，并以约束防止已确认记录重叠。只有
`personal_planning_change_propose` 在主人私聊中通过严格校验后，才可以写入一条
`change_proposals.status=pending` 草稿；它不会写入业务事实表。其余聊天内容不能写入
这些表。

======================================================================
五、构建、验证与运维
======================================================================

在 `chatbot/plugins/personal-weather/` 中执行：

  npm run build
  npm test
  npm run plugin:build
  npm run plugin:validate

源码、依赖或插件 manifest 变更后，应先完成以上验证，再由运维人员重新安装/链接
插件，并检查 OpenClaw 的插件加载和工具准入。不要因插件存在就假定工具对模型可见；
最终权限由 OpenClaw 配置和当前会话策略决定。

每日简报必须由固定的 `daily-brief` CLI 运行，不能让模型执行 Shell。创建或修改
任务时使用 `openclaw cron`，并固定：

- `30 10 * * *` 与 `Asia/Shanghai`；
- 隔离会话、精确 argv、固定 cwd、超时和输出上限；
- QQ 私聊目标由受控配置提供，文档中不记录真实 OpenID；
- 仅向任务本身所需的工具授权，且任务失败必须保留为可见的 run error。

日常审计和回滚应先列出当前任务确认实际 ID，再操作：

  openclaw cron list
  openclaw cron runs <job-id>
  openclaw cron disable <job-id>
  openclaw cron rm <job-id>

插件回滚顺序：先从精确工具 allowlist 移除天气工具，再禁用或卸载插件并重启
Gateway。卸载 link 插件不会删除源码，也不会自动清理工具 allowlist。
