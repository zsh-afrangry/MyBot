kurumi 天气与出行模块：开发和维护记录

最后更新：2026-08-12
状态：P1 天气查询、P2A/P2B 行程 proposal/commit 和 P2C-0 规划边界已完成；地点切换、主动预警、
图片/OCR 和航班状态仍未完成。

摘要
----

当前模块是主人 QQ 私聊可用的定向天气能力：通过固定 QWeather 专属 Host 查询广州天河默认地点，
返回实况、今日/小时预报、降雨趋势和官方预警；每日 10:30 简报由固定 CLI/Cron 投递。行程部分
只允许主人明确要求保存后生成 typed proposal，再以同一私聊中的 proposal ID + payload hash 确认提交
为 `planned` trip。当前不会自动消歧目的地、切换天气地点、创建 location_period、修改提醒或调用通用网络。

======================================================================
二、当前能力与非目标
======================================================================

已实现的天气能力：

- 默认地点：广东省广州市天河区；未来有效地点由受控结构化数据决定，不修改提示词/记忆文件。
- `personal_weather_get_brief`：主人 QQ 私聊可用、无参数、只读；返回实况、今日预报、未来 24 小时
  降雨趋势、官方预警、数据时间、来源和缓存状态。
- 固定 `daily-brief` CLI + `Asia/Shanghai` 每日 10:30 Cron，隔离运行并向主人 QQ 私聊投递。
- QWeather 专属 Host 和固定路径：GeoAPI City Lookup、current、daily、hourly、weather alert。

已实现的行程能力：

- `personal_planning_state_get`：返回最小化地点、简报偏好、行程和 pending proposal 摘要。
- `personal_planning_change_propose`：只接受版本化严格 `trip.create`，规范化事实、缺失字段、警告和预览，
  写入短期 pending proposal。
- `personal_planning_change_commit`：只接受同一主人私聊中明确确认的 proposal ID + payload hash；
  事务写入一条 `planned` trip、proposal 状态和最小审计；重复提交幂等。
- 未消歧目的地只保存短文本；当前不写 `location_periods`/`notification_preferences`，不改变天气地点或 Cron。

明确非目标：通用网页、任意 HTTP、Shell、文件/数据库直写、sudo、通用 Cron、群聊天气工具、模型改提示词/记忆、
自动位置切换、主动预警、机票 OCR 和航班状态。

======================================================================
三、架构与代码路径
======================================================================

  主人 QQ 私聊
       |
       +--> personal_weather_get_brief（只读天气）
       +--> personal_planning_state_get（只读状态）
       +--> personal_planning_change_propose（pending 预览）
       `--> personal_planning_change_commit（Hash 匹配后事务提交）
                    |
                    v
             personal-weather 插件
       QWeatherClient -> WeatherService -> Formatter
       PlanningService（planning.ts） -> PlanningRepository -> WeatherStore 事务

关键文件：

- `chatbot/plugins/personal-weather/src/index.ts`：工具声明、主人私聊守卫、运行时适配。
- `src/qweather-client.ts`：固定 Host/路径、请求超时、响应限制、重试和错误分类。
- `src/weather-service.ts`：缓存和实况/预报/预警组合。
- `src/formatter.ts`：确定性中文简报。
- `src/planning.ts`：typed proposal、预览、TTL/hash/上下文、确认和幂等策略。
- `src/planning-repository.ts`：proposals/trips/audit 的受限 SQL CRUD，不解释模型输入或生成任意 effects。
- `src/store.ts`：SQLite 生命周期、迁移、读模型和 `BEGIN IMMEDIATE` 事务入口，不承载领域策略。
- `src/cli.ts`：`health`、`db:init`、`lookup`、`brief`、`daily-brief` 运维 CLI。
- `chatbot/skills/personal-weather/SKILL.md`：工具使用、提案确认和不落库规则。

数据文件：`state/personal-weather/weather.sqlite`，目录/数据库权限受限；不提交、不手改。

======================================================================
四、接口、配置与数据规则
======================================================================

天气配置：

  QWEATHER_API_HOST
  QWEATHER_API_KEY

Key 只能通过环境变量或插件 SecretRef 提供，不能进入源码、`openclaw.json`、提示词、聊天、文档、命令行或日志。
当前 API Key 请求头为 `X-QW-Api-Key`；若未来套餐/鉴权变化，必须显式评估迁移，不能静默降级。

网络边界：

- URL 只能由配置的专属 HTTPS Host 与代码内固定路径派生；不接受用户 URL、端口、协议、代理或重定向目标。
- 仅 GET；有超时、总预算、响应体上限、并发上限、有限重试和缓存；401/403、SSRF 和不可信输入不重试。
- 网络 JSON 运行时校验；组件失败、未知枚举或缓存过期必须显式标记，不伪造实时数据或“无预警”。
- 展示保留 QWeather 归因和数据时间；缓存结果必须标示缓存状态。

规划数据原则：

- 讨论、示例、假设、“可能出行”和含糊时间不落库；只有主人明确要求“记录/保存”才生成 proposal。
- 到达时间未知或仅日期级时，不自动切换天气地点；目的地未消歧时不伪造坐标或 LocationID。
- proposal commit 只接受冻结 ID/hash/上下文，后端生成实际写入；模型不提供 SQL、effects、坐标或 URL。

SQLite 主要表：`places`、`notification_preferences`、`location_periods`、`trips`、
`change_proposals`、`notification_state`、`api_cache`、`audit_log`、`schema_migrations`。
其中 `location_periods` 与通知去重表是后续 TODO 的结构预留，不代表对应业务已经上线。

======================================================================
五、P2C-0 正式结果与后续边界
======================================================================

P2C-0 的正式结果：

- `planning.ts` 负责冻结 payload 的解释、确认/过期/幂等策略和未来 effects 的决策。
- `planning-repository.ts` 只负责 proposals、trips、audit 的受限持久化。
- `WeatherStore.withPlanningTransaction()` 只负责事务生命周期和 Repository 构造；Service 在同一
  事务 callback 内组合写入，未来可以原子扩展 `trip + location_period + audit`。
- 已验证 Repository 写入后发生异常会回滚，不残留 trip；既有 committed proposal 重放幂等且不增加 trip/audit。

本结果不包含：地点消歧、location_period 创建、discard、新工具、航班 OCR、搜索、Cron 或提醒改动。
因此不再保留旧的“P2C-0 下一步提取 Service”探查记录；后续直接从顶部 P2B-location/P2C TODO 开始。

六、验证与运维
======================================================================

在 `chatbot/plugins/personal-weather/` 中执行：

  npm test -- --run
  npm run build
  npm run plugin:validate

当前全插件回归为 12 个测试文件、103 项通过；配置/插件运行时验收：

  openclaw config validate
  openclaw plugins doctor
  openclaw plugins inspect personal-weather --runtime --json
  openclaw gateway health

每日简报只能通过固定 CLI 运行，不能让模型执行 Shell。Cron 必须使用 `Asia/Shanghai`、隔离会话、固定 argv/cwd、
超时和输出上限；任务目标只能来自受控 QQ 配置。操作前先 `openclaw cron list` 确认实际任务 ID，禁止手改 Gateway SQLite。

回滚：先从精确工具 allowlist 和群聊 deny 移除相关工具，再重载/重启 Gateway；保留业务 SQLite；天气上游或配置异常时，
保持旧缓存并标记 stale，不把失败说成成功。
