截至本次更新，代码、离线测试和本机真实冒烟已经完成，但模型工具授权和 Cron 仍

本阶段目标：

1. 建立一个可测试、可审计的原生 personal-weather Tool Plugin；
2. 只让插件内部访问固定 QWeather Host，不开放通用互联网能力；

6. 保持 QQ 群聊、主机命令、文件工具、sudo、通用 Web 和 coder 能力不变。

本轮明确非目标：群聊天气、通用搜索、临近降雨轮询、自动灾害推送、机票图片
OCR、航班状态、自动修改长期记忆，以及让模型直接写文件或数据库。

======================================================================
一、结论
======================================================================

天气模块已开始开发并完成第一阶段代码，但仍必须分阶段上线。

第一版只实现：

1. 固定 QWeather 专属 Host 的只读天气客户端；
2. 私聊中按需查询当前有效地点的天气；
3. QQ 主动文本消息链路测试；
4. 每天 10:30（Asia/Shanghai）的天气简报。

第一版不同时开放：

- 通用网页搜索、web_fetch、浏览器或任意 HTTP 请求；
- Shell、exec、sudo、通用文件读写；
- 让模型直接修改 JSON、系统提示词、MEMORY.md 或数据库；
- 群聊天气工具；
- 高频灾害预警、临近降雨、机票截图解析和航班状态。

天气所需联网是“插件内部对一个固定 QWeather Host 发起只读 HTTPS GET”，
不是给模型开放互联网。两者权限和风险完全不同。

二、现状审计
======================================================================

当前真实配置：

- `tools.profile = messaging`，模型可见基线为消息、会话列表/历史/发送和状态。
  当前群聊 deny 只覆盖了其中部分会话工具，因此这不是绝对最小权限；群聊在
  正式增加业务工具前应改为仅允许 `session_status`，或全局回归测试后改用 minimal。
- 文件、主机命令、通用 Web、浏览器、Cron 管理和 coder 工具未对模型开放。
- `tools.exec.security = deny`。
- `tools.elevated.enabled = false`，不能使用 sudo/elevated exec。
- `agents.defaults.sandbox` 未配置，实际 sandbox mode 为 off；当前安全主要依靠
  工具策略。以后若开放 exec，它会直接运行在宿主机，因此天气模块绝不开放 exec。
- `heartbeat.every = 0m`，Heartbeat 已关闭。
- OpenClaw Cron 调度器本身已启用，当前任务数为 0。
- QQ 插件已经声明 `qqbot_remind` 和 `qqbot_channel_api`，但当前 messaging
  profile 未显式准入插件工具。上线天气前仍应在群聊 deny 中显式拒绝它们。
- `memory-core` 当前只涉及记忆扫描/检索，不提供可靠的动态位置写入方案。

结论：现状没有暴露主机、文件、sudo 或开放式网络能力，整体很保守；但不能
表述为“所有权限完全关闭”，因为基础消息和会话工具仍在。提示词不是权限边界，
`openclaw.json`、插件实现和 Cron 管理权限才是真正的执行边界。

三、参考文档的三项修正
======================================================================

参考：`docs/天气设计建议.txt`

1. 本机 OpenClaw 2026.7.1-2 没有 `openclaw automations` 命令；应使用：

   openclaw cron add|edit|list|show|run|runs|status

2. 第一版不优先使用 condition trigger。

   本机虽然支持 `--trigger-script`，但官方文档明确警告：启用
   `cron.triggers.enabled` 后，触发脚本属于无人值守代码执行面，并可能使用
   所属 Agent 的完整工具策略。当前最小权限阶段应保持该功能关闭。

   高频天气检查以后使用受信任的固定程序配合 command Cron：无新事件时输出
   `NO_REPLY`，有新事件才输出消息。Cron 会抑制 `NO_REPLY`，不需要反复调用模型。

3. 新天气代码不应以旧的 city-based `/v7/weather/*` 为主，但新版鉴权需实测。

   QWeather 已将相关 v7 城市天气接口标记为将弃用。新模块以经纬度和
   `/weather/v1/*` 为主；分钟级降水目前仍可作为第二阶段的可选 v7 接口。
   官方认证兼容表明确列出 API Key 支持 GeoAPI v2 和 API v7，但没有明确列出
   Weather API v1，而 v1 示例使用 JWT。因此客户端先隔离认证策略并用现有
   `X-QW-Api-Key` 做冒烟；若 v1 返回 401/403，必须让主人创建 JWT 或确认套餐，
   不能悄悄回退 v7，也不能把该兼容性写成已验收。

  QQ 私聊
     |
     v
  kurumi Agent
     |  只能看到显式准入的窄工具
     v
  personal-weather 原生 Tool Plugin
     |-- QWeatherClient：固定 Host、固定路径、只读 GET
     |-- WeatherService：组合实况、日预报、小时预报、官方预警
     |-- LocationService：读取有效位置；后续受控修改位置时间线
     |-- RuleEngine：后续处理预警、降雨、高温、去重、冷却
     |-- Formatter：确定性生成中文天气消息和数据来源
     v

  OpenClaw Cron
     |-- 每天 10:30：生成并向 QQ 私聊投递每日简报
     |-- 后续每 10 分钟：无 LLM 检查官方预警
     |-- 后续每小时：无 LLM 检查高温与小时趋势
     v
  QQBot announce -> qqbot:c2c:<OWNER_OPENID>

系统提示词只定义边界；Skill 告诉模型何时、怎样使用工具；插件 Tool 执行查询；
SQLite 保存结构化事实；Cron 负责时间；规则引擎负责去重。模型不承担可靠计时、
数据库事务或预警判定。

======================================================================
六、QWeather 客户端
======================================================================

凭证只从环境变量读取：

  QWEATHER_API_HOST
  QWEATHER_API_KEY

鉴权验收状态（2026-08-06）：官方兼容表没有明确列出 Weather API v1 的 API Key
兼容性，但本机专属 Host 已用 `X-QW-Api-Key` 成功读取 current、daily、hourly 和
alerts，因此当前账号/Host 可用。第一版只实现 API Key。若未来必须改用 JWT，
应使用私钥按官方规则生成短期 Token，不能把会过期的静态 Bearer 字符串当长期
配置，也不能静默回退 v7。

安全要求：

1. URL 只能由客户端从 `https://${QWEATHER_API_HOST}` 和固定路径内部派生；配置
   类型不接受第二个 baseUrl。
2. Host 必须是配置中的完整专属 Host；拒绝用户传入 URL、协议、端口和路径。
3. API Key 只通过 `X-QW-Api-Key` 请求头发送，不进入 URL、日志、提示词或工具结果。
4. 只允许 GET；`maxRedirects=0`，禁止自动跟随重定向。
5. 使用 OpenClaw 默认严格 SSRF Guard 和 DNS pinning；不添加会放宽私网检查的
   Host/Origin 信任 policy，不使用环境代理，不允许私网或 metadata 地址。
6. 使用绝对超时、总预算、响应体 1 MiB 上限、全局并发上限 4 和本地缓存。
7. 对 JSON 做运行时校验，未知枚举保留，不能导致程序崩溃。
8. 关闭请求 capture；日志和稳定错误不含 Host、地点请求、原始 body 或凭证。
9. 401/403 不重试；429、网络错误和指定 5xx 有上限重试；SSRF 拦截不重试。
10. 每条输出记录 `fetchedAt` 和 fresh/cached-fresh，过期数据不伪装成实时数据。
11. 按响应中的 `attributions`/来源要求展示和风天气归因。
12. 上线前轮换曾在聊天中出现过的 QWeather Key。

建议接口：

  地点解析
    GET /geo/v2/city/lookup
    参数：location、adm、range=cn、number、lang=zh
    保存：经纬度、行政区、IANA 时区和可选 LocationID。

  当前天气
    GET /weather/v1/current/{lat}/{lon}?localTime=true&lang=zh

  每日预报
    GET /weather/v1/daily/{lat}/{lon}?days=3&localTime=true&lang=zh

  小时预报
    GET /weather/v1/hourly/{lat}/{lon}?hours=24&localTime=true&lang=zh

  官方预警
    GET /weatheralert/v1/current/{lat}/{lon}?localTime=true&lang=zh

  可选临近降雨（第二/三阶段）
    GET /v7/minutely/5m?location={lon},{lat}&lang=zh

新模块以经纬度作为天气查询主键。LocationID 只用于地点解析、显示或兼容，
不能把整个 GeoAPI 城市库永久镜像到本地；只保存主人实际选择的少量地点。

======================================================================
七、模型可见工具
======================================================================

工具名称应唯一、窄且标记为 optional。

第一阶段只开放：

  personal_weather_get_brief
      读取当前有效地点，返回实况、今日高低温、未来 24 小时降水趋势、官方预警、
      数据更新时间和来源。它不接收任意 URL，也不能修改位置或文件。

第二阶段再增加：

  personal_weather_lookup_place
      只读地点解析，返回少量候选供主人消歧。

  personal_weather_location_get_effective
      读取某个时间点的有效地点。

  personal_weather_location_propose
      根据明确的当前位置/旅行陈述生成结构化修改预览，不落库。

  personal_weather_location_commit
      仅在可信主人私聊中，用 proposal ID 提交已确认的位置时间线变更。

  personal_weather_location_cancel
      取消指定的未来位置或行程，返回实际变更结果。

模型可以生成工具参数，但不能直接获得数据库连接、通用 write/edit、Shell 或
任意 HTTP 工具。位置写工具必须校验发送者元数据、私聊场景、时间格式、地点
候选、时间段重叠和 proposal ID，并通过事务和审计落库。

启用工具时保持最小授权：

- 保留 `minimal` 或 `messaging` profile；
- 只用 `tools.alsoAllow` 加入精确工具名，不切换为 coding/full；
- 群聊优先使用只含 `session_status` 的 allowlist；若暂不改为 allowlist，则显式
  deny `message`、`sessions_list`、`sessions_history`、`sessions_send`、
  `personal_weather_*`、`qqbot_remind` 和 `qqbot_channel_api`；
- 位置写工具第一版不开放；
- 每个 Cron 再使用 `--tools` 收窄当次 Agent 工具，但它不能替代全局策略。

======================================================================
八、SQLite 数据结构
======================================================================

单机、单主人场景使用一个独立 SQLite 足够，不需要 MySQL、MongoDB 或向量库。
向量数据库适合语义检索，不适合有效时间范围、唯一约束、事务和通知去重。

当前已经创建 v1 Schema：

1. `places`

   保存少量实际使用的行政区/城市：展示名、国家、省、市、区、行政区中心经纬度、
   IANA 时区、精度、QWeather LocationID、来源和时间戳。第一条 seed 仅为主人已
   确认的默认地点广东省广州市天河区：LocationID `101280109`、纬度 `23.1356`、
   经度 `113.3354`、`Asia/Shanghai`。不保存家庭住址或精确 GPS。

2. `notification_preferences`

   以 `subject_id=owner` 保存 `default_place_id`、每日是否启用、分钟数 `630`
   （10:30）、固定/有效地点时区模式、安静时段、官方预警/雨/高温开关、阈值、
   冷却和旅行日双城偏好。当前只初始化默认值，没有启用 Cron。

3. `location_periods`

   这是“已确认的天气地点覆盖时间线”，不是模型草稿。字段包含 place、
   `[effective_from_utc, effective_until_utc)` 半开区间、basis、关联 trip、
   record_state、脱敏来源摘要和 revision。应用查询和数据库 trigger 双重禁止
   confirmed 区间重叠，允许首尾相接；没有覆盖时自动回退 default_place。

4. `trips`

   保存主人已经确认要记录的真实出行。`state=tentative` 表示计划真实存在但细节
   待定，不表示模型推断。目的地、交通工具、日期/时间窗均可未知；未知字段为
   NULL/unknown，`weather_mode=none`，不会切换地点或自动创建提醒。以后支持
   planned/in_progress/completed/cancelled、出发/到达时间窗、精度、车次/航班号的
   非敏感部分、next_review_at 和 revision。禁止保存 PNR、票号和证件号。

5. `change_proposals`

   在模型理解与业务事实之间建立硬边界。proposal 冻结 payload_json/hash、预览、
   base revision、过期时间和状态；commit 将来只能接收 proposal_id，不能顺便改
   payload。讨论/示例不生成 proposal；明确保存意图可生成 proposal；主人确认后
   才在固定事务中写 trip/location/preferences。重复 commit 必须幂等。

6. `notification_state`

   为后续官方预警、降雨、高温和每日消息保存 event key、payload hash、首次/末次
   观察、投递、冷却和状态，用于去重；当前没有主动预警任务。

7. `api_cache`

   保存不含凭证的 QWeather 原始 JSON、endpoint、place、metadata tag、SHA-256、
   fetched/expires 和字节数，上限 1 MiB。当前 TTL：current 10 分钟、alerts 5
   分钟、hourly 30 分钟、daily 1 小时；daily cache key 还含地点当地日期，防止
   跨日误用。真实冒烟已验证第二次查询显示 `cached-fresh` 且无需联网。

8. `audit_log` 与 `schema_migrations`

   audit 只保存动作、实体、proposal 和脱敏变更摘要，不复制完整私聊；迁移表与
   `PRAGMA user_version` 管理版本。目前 Schema version=1。

所有数据库时间存 UTC Unix 秒，输入/展示使用地点 IANA 时区。启用 foreign_keys、
WAL、busy_timeout、secure_delete；状态目录权限 700，数据库权限 600，并拒绝目录
或数据库符号链接。当前生产状态库中 places=1、preferences=1，trips=0、
location_periods=0、change_proposals=0。SQLite 足够，不需要 MySQL、MongoDB 或
向量数据库。

九、每天 10:30 简报
======================================================================

执行流程：

1. 获取可信系统时间；
2. 从 location_periods 查询当前有效地点；
3. 查询 current、daily、hourly 和 alerts；
4. 检查数据更新时间和缓存；
5. 确定性生成中文简报；
6. 附天气来源和查询时间；
7. 通过 QQBot announce 发送给主人私聊；
8. 记录投递结果，失败时按策略告警。

推荐第一版使用 operator 创建的 command Cron，并使用精确 argv 调用固定程序。
这样不调用 LLM，也不向模型开放 exec。command Cron 本身仍是在宿主机运行的可信
代码，因此必须先审计程序，使用固定绝对路径、固定 cwd、输出上限和超时。

计划命令形态（仅设计示例，当前未执行）：

  openclaw cron add \
    --name "kurumi 每日天气简报" \
    --cron "30 10 * * *" \
    --tz "Asia/Shanghai" \
    --exact \
    --command-argv '["node","dist/cli.js","daily-brief"]' \
    --command-cwd "/home/afrangry/.openclaw/chatbot/plugins/personal-weather" \
    --timeout-seconds 60 \
    --output-max-bytes 65536 \
    --announce \
    --channel qqbot \
    --to "qqbot:c2c:<OWNER_OPENID>" \
    --account default

不得把真实 OpenID 写入本设计或系统提示词。真实 Cron 配置会由 OpenClaw 自己保存
在共享 SQLite 中，使用 CLI 管理，不手改 `state/openclaw.sqlite`。

每日简报示例格式：

  早上好，主人～
  广州天河：当前 29°C，体感 32°C；今天 27～35°C。
  下午有较高降雨概率，出门建议带伞；当前无官方气象预警。
  数据：和风天气，查询于 10:30。

真实字段必须完全来自工具结果，不得让模型凭常识补写实时天气。

======================================================================
十、主动预警与去重（后续阶段）
======================================================================

建议频率应服从 QWeather 官方缓存建议和实际套餐：

- 官方预警：每 10 分钟检查一次；
- 临近降雨：中国支持区域内，06:00～23:00 每 10 分钟检查一次；
- 高温和小时趋势：每 60 分钟最多刷新一次；
- 每日简报：固定 10:30 单独运行。

高频检查必须是无 LLM 的确定性程序。有新事件才输出消息；没有事件输出
`NO_REPLY`，避免 QQ 刷屏和 Token 浪费。

官方预警去重键至少包含：

  alert.id
  messageType.code
  issuedTime
  supersedes
  metadata.tag

规则：新预警发送；同一预警 update 只发送一次更新；cancel 可发送一次解除；
无变化不发送。未知预警类型保留原文，不因枚举表未更新而丢弃。

临近降雨：从“无雨”变为“未来两小时有雨”时发送；同一轮降雨不重复；强度
明显升级可再次发送；无升级时遵守冷却时间。

高温阈值属于个人通知偏好，不能冒充政府法定预警。官方高温预警仍以 alert
接口为准。

十一、旅行、地点切换与机票
======================================================================

动态位置不写入 SOUL.md、USER.md、MEMORY.md 或 QQ systemPrompt，也不需要在
到达当天让模型“修改记忆”。每次任务按当前时间查询有效位置，时间到后自然切换。

广州飞往无锡、8 月 16 日只是架构示例，不是主人的事实，当前数据库和记忆中均未
写入该行程。主人真实的“最近出行”目前只有需求背景：可能出行，但目的地、日期、
时间和交通工具都尚未确定；由于主人没有要求 kurumi 保存一条具体计划，本轮也未
创建 tentative trip。

以后处理类似广州飞往无锡的真实行程时：

- 如果这是实际行程，必须由主人确认准确的出发/预计到达时间和目的地区域；
- 常规天气地点建议在“预计到达目的地”时切换，不在 8 月 16 日 00:00 切换；
- 10:30 仍在广州时，常规简报仍使用广州；
- 可额外启用旅行日双城简报：出发前给广州天气，同时给预计到达时段的无锡天气；
- 没有航班状态 API 时，机器人不知道延误，只能按已确认时间或主人手动修订；
- 以后接入航班状态工具，优先使用 actual_arrival，其次 estimated_arrival，最后
  scheduled_arrival 更新位置生效时刻。

机票截图不是天气第一版能力。以后流程应为：

1. 验证 QQ 图片接收和图像理解/OCR；
2. 解析为 proposed trip，不直接落为 confirmed；
3. 向主人回显航班号、出发/到达机场、当地日期、时区和预计到达时间；
4. 主人明确确认后调用位置/行程 commit 工具；
5. 原图按隐私策略删除或短期保存，数据库只留必要的脱敏摘要。

主人只是讨论、举例或询问某城市时，绝不能修改位置。只有明确表达“我现在在”、
“我将在某时到达”并且明确要求记录时，才可生成 proposal；只有确认 proposal 后
才允许写入事实。主人可确认保存一条目的地/日期/交通方式仍未知的 tentative trip，
但它不会改变天气地点。位置切换必须另有已确认且足够精确的到达时刻。
