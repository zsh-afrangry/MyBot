摘要
----

当前模块是主人 QQ 私聊可用的定向天气能力：通过固定 QWeather 专属 Host 查询 Profile 当前所在地
（首次迁移时为广州天河），
返回实况、今日/小时预报、降雨趋势和官方预警；每日 10:30 简报由固定 CLI/Cron 投递。行程部分
只允许主人明确要求保存后生成 typed proposal，再以同一私聊中的 proposal ID + payload hash 确认提交
为 `planned` trip。当前不会自动消歧目的地、切换天气地点、创建 location_period、修改提醒或调用通用网络。

二、当前能力与非目标
======================================================================

已实现的天气能力：

- 当前所在地：Profile P0 迁移初始值为广东省广州市天河区；后续只能由受控 Profile proposal/commit 修改，
  不修改提示词/记忆文件。天气是该事实的消费者。
- 已持久化地点的工具结果保留完整 `displayName`；确定性简报可使用“上级市 + GeoAPI 叶子名”的紧凑标题，
  但不得把县级市或区县只写成上级市。
- `personal_weather_get_brief`：主人 QQ 私聊可用、只读；可省略参数读取当前有效地点，也可提交可选
  `location` 与 `administrative_area` 查询一个临时地点。返回实况、今日预报、未来 24 小时降雨趋势、
  官方预警、数据时间、来源和缓存状态；P1D 的 QQ 验收已通过。
- 临时查询不得改变任何持久化地点状态；省略地点时保持既有当前有效地点行为。
- 固定 `daily-brief` CLI + `Asia/Shanghai` 每日 10:30 Cron，隔离运行并向主人 QQ 私聊投递。
- QWeather 专属 Host 和固定路径：GeoAPI City Lookup、current、daily、hourly、weather alert。

已实现的行程能力：

- `personal_planning_state_get`：返回最小化地点、简报偏好、行程和 pending proposal 摘要。
- `personal_planning_change_propose`：只接受版本化严格 `trip.create`，规范化事实、缺失字段、警告和预览，
  写入短期 pending proposal。
- `personal_planning_change_commit`：只接受同一主人私聊中明确确认的 proposal ID + payload hash；
  事务写入一条 `planned` trip、proposal 状态和最小审计；重复提交幂等。
- 未消歧目的地只保存短文本；当前不写 `location_periods`/`notification_preferences`，不改变天气地点或 Cron。

明确非目标：通用网页、任意 HTTP、Shell、文件/数据库直写、sudo、通用 Cron、群聊天气工具、模型改提示词/记忆、
任意 Profile 字段编辑、基于行程/预计航班的自动位置切换、主动预警、机票 OCR 和航班状态。

三、架构与代码路径
======================================================================

  主人 QQ 私聊
       |
       +--> personal_weather_get_brief（只读天气）
       +--> personal_profile_state_get（只读当前所在地）
       +--> personal_profile_change_propose/commit（确认式 Profile 写入）
       +--> personal_planning_state_get（只读状态）
       +--> personal_planning_change_propose（pending 预览）
       `--> personal_planning_change_commit（Hash 匹配后事务提交）
                    |
                    v
             personal-weather 插件
       QWeatherClient -> WeatherService -> Formatter
       ProfileService（profile.ts） -> ProfileRepository -> WeatherStore 事务
       PlanningService（planning.ts） -> PlanningRepository -> WeatherStore 事务

关键文件：

- `chatbot/plugins/personal-weather/src/index.ts`：工具声明、主人私聊守卫、运行时适配。
- `src/qweather-client.ts`：固定 Host/路径、GeoAPI City Lookup、请求超时、响应限制、重试和错误分类。
- `src/weather-location.ts`：受限地点意图的 GeoAPI 消歧、唯一候选判断和最小候选摘要。
- `src/profile.ts` / `src/profile-repository.ts`：`current_location` 的读模型、冻结提案、确认/过期/幂等策略和
  受限 SQL 写入；逻辑所有权是 Profile，当前由该插件承载。
- `src/weather-service.ts`：Profile 当前/未来地点区间与临时地点的缓存和实况/预报/预警组合。
- `src/formatter.ts`：确定性中文简报。
- `src/planning.ts`：typed proposal、预览、TTL/hash/上下文、确认和幂等策略。
- `src/planning-repository.ts`：proposals/trips/audit 的受限 SQL CRUD，不解释模型输入或生成任意 effects。
- `src/store.ts`：SQLite 生命周期、迁移、读模型和 `BEGIN IMMEDIATE` 事务入口，不承载领域策略。

- `chatbot/skills/personal-weather/SKILL.md`：工具使用、提案确认和不落库规则。

数据文件：`state/personal-weather/weather.sqlite`，目录/数据库权限受限；不提交、不手改。

四、接口、配置与数据规则
======================================================================

天气配置：

  QWEATHER_API_HOST
  QWEATHER_API_KEY

Key 只能通过环境变量或插件 SecretRef 提供，不能进入源码、`openclaw.json`、提示词、聊天、文档、命令行或日志。
当前 API Key 请求头为 `X-QW-Api-Key`；若未来套餐/鉴权变化，必须显式评估迁移，不能静默降级。

网络边界：

- URL 只能由配置的专属 HTTPS Host 与代码内固定路径派生；不接受用户 URL、端口、协议、代理或重定向目标。
- 仅 GET；有超时、总预算、响应体上限、并发上限、有限重试和缓存；401/403、SSRF 和不可信输入不重试。
- 网络 JSON 运行时校验；组件失败、未知枚举或缓存过期必须显式标记，不伪造实时数据或“无预警”。
- 展示保留 QWeather 归因和数据时间；缓存结果必须标示缓存状态。

规划数据原则：

- 讨论、示例、假设、“可能出行”和含糊时间不落库；只有主人明确要求“记录/保存”才生成 proposal。
- 到达时间未知或仅日期级时，不自动切换天气地点；目的地未消歧时不伪造坐标或 LocationID。
- proposal commit 只接受冻结 ID/hash/上下文，后端生成实际写入；模型不提供 SQL、effects、坐标或 URL。

地点与定时简报的解耦原则：

- `profile_current_location` 是主人当前所在地；trip 是计划事实；location_period 是未来经确认、带生效时间的
  地点上下文；临时天气查询只是本轮只读输入。四者不能相互覆盖或混成“默认天气地点”。
- 主人明确陈述已到达某地时，Profile 只在确认后更新 `current_location`。机票或行程确认只更新 trip；
  即使目的地与到达时间窗齐全，也不能在记录机票或预计落地时自动修改当前所在地。
- 每日简报 Cron 继续执行固定 `daily-brief`，不把某个地点硬编码到任务参数。运行时由
  `getEffectivePlace(now)` 解析生效中的 location_period，没有匹配区间时读取 Profile current_location；
  因而未来地点变化不需要重写 Cron。
- 当前每日简报为 630 minute-of-day，即 Asia/Shanghai 10:30，时区模式为 fixed。是否在跨时区旅行时
  改为 active_place 是独立产品决定，不能由记录行程自动推断。

SQLite 主要表：`places`、`profile_current_location`、`notification_preferences`、`location_periods`、
`trips`、`change_proposals`、`notification_state`、`api_cache`、`audit_log`、`schema_migrations`。
其中 `profile_current_location` 已由迁移 v3 上线，`places.locality_name` 已由迁移 v4 上线；`location_periods` 与通知去重表仍是后续 TODO 的结构预留，
不代表基于行程的自动地点切换已经上线。

五、Profile P0、P2C-0 正式结果与后续边界
======================================================================

Profile P0 的正式结果：

- `profile_current_location` 以 `places` 的受控地点引用、来源、确认时间和 revision 表示主人当前所在地；
  没有 `home_location`、自由 Profile JSON、精确地址或聊天原文。
- Profile 提案使用既有 `change_proposals` 的封闭 `location_set` kind，但拥有独立的 ProfileService/
  ProfileRepository；这是复用已验证的 proposal/transaction 边界，不是提前建设通用 Task Engine。
- 迁移 v3 从旧天气默认地点种子化当前所在地；迁移 v4 为持久地点补存 GeoAPI 叶子名。有效天气地点没有
  active location_period 时读取该 Profile 地点；展示精度不依赖 Provider `type`，也不改变坐标查询。
- 本轮不创建 location_period，不改行程、提醒、Cron、长期记忆，也不会在航班预计到达后自动更新 Profile。

P2C-0 的正式结果：

- `planning.ts` 负责冻结 payload 的解释、确认/过期/幂等策略和未来 effects 的决策。
- `planning-repository.ts` 只负责 proposals、trips、audit 的受限持久化。
- `WeatherStore.withPlanningTransaction()` 只负责事务生命周期和 Repository 构造；Service 在同一
  事务 callback 内组合写入，未来可以原子扩展 `trip + location_period + audit`。
- 已验证 Repository 写入后发生异常会回滚，不残留 trip；既有 committed proposal 重放幂等且不增加 trip/audit。

本 P2C-0 结果本身不包含：location_period 创建、discard、航班 OCR、搜索、Cron 或提醒改动。
P1D 已另行完成临时天气查询所需的 GeoAPI 消歧，Profile P0 复用同一受控解析边界；因此不再保留旧的
“P2C-0 下一步提取 Service”探查记录，QQ 验收完成后再从 P2B-location/P2C TODO 继续地点区间派生。

在 `chatbot/plugins/personal-weather/` 中执行：

  npm test -- --run
  npm run build
  npm run plugin:validate

持久地点展示修复后全插件回归为 14 个测试文件、120 项通过；TypeScript 构建、`plugin:validate` 与
`openclaw config validate` 已通过。生产 SQLite 已完成 v4 迁移并只读核验：地点仍为江苏省镇江扬中、
`locality_name=扬中`、Profile revision 仍为 2。Gateway 已重启且健康检查正常；2026-08-24 12:02 QQ
`formattedText` 验收以“镇江扬中：”通过。配置/插件运行时检查：

  openclaw config validate
  openclaw plugins doctor
  openclaw plugins inspect personal-weather --runtime --json
  openclaw gateway health

每日简报只能通过固定 CLI 运行，不能让模型执行 Shell。Cron 必须使用 `Asia/Shanghai`、隔离会话、固定 argv/cwd、
超时和输出上限；任务目标只能来自受控 QQ 配置。操作前先 `openclaw cron list` 确认实际任务 ID，禁止手改 Gateway SQLite。

回滚：先从精确工具 allowlist 和群聊 deny 移除相关工具，再重载/重启 Gateway；保留业务 SQLite；天气上游或配置异常时，
保持旧缓存并标记 stale，不把失败说成成功。
