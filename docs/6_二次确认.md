# 二次确认

改变外部状态的操作先生成预览，主人确认后才执行。公共部分在共享包 `chatbot/packages/confirmation-core`，QQ 侧入口是插件 `personal-confirmation`。

## 功能

- 主人看到预览后，用自然语言确认即可，不用抄确认码。
- 使用它的领域：一次性提醒（`personal_reminder`）、当前所在地（`personal_profile`）、行程（`planning`）、邮件发送（`mail`）、编码任务的合入或回写（`coding`）。
- 一条消息可以确认多项，最多 16 项。提醒、所在地、行程、邮件支持；编码任务只能单项确认。
- 旧的“确认 <12 位码>”和完整 ID 加哈希的写法仍然可用。

不做的事：

- 只读操作不需要确认。
- 提醒列表和账单的明确维护请求直接执行，不走这套机制，规则见[文档23](23_KnowledgeMap业务能力桥接.md)。
- 它不是通用的任务引擎，也不替代身份权限。

## 接口

工具 `personal_confirmation`，动作 `list`（查候选）、`preview`（重新展示某项）、`confirm`（确认指定项）。`domain` 必须显式填写，未知的领域被拒绝。读类动作和 `confirm` 分别需要该领域的读权限和管理权限。

领域接入方式：领域的存储在服务启动时注册一个确认后端，停止时注销。提案、业务数据和事务都留在领域自己的库里，没有共享的确认数据库。

## 原理

确认要回答两个问题：确认的是哪一份提案，以及确认是不是真的来自主人。

- **提案冻结**：提案生成时冻结参数和哈希，有效期 24 小时。参数变了就是一份新提案。
- **展示成功才可确认**：预览的全文经 QQ 成功送达后，才登记为“已展示”。没送达、只送达一部分、过期、已取消的提案不能用自然语言确认。
- **来源取自宿主**：确认时，共享层从宿主拿当前这条 QQ 原文，绑定实际的会话和工具调用，复核身份、账号、提案和有效期。模型的总结、工具输出、引用、网页和附件内容都不能授权。
- **模型只判断意图和指代**：刚展示一项后说“确认”可以执行；多项时“确认今晚八点那条”可以唯一选中；多项时只说“确认”无法区分，要追问。否定、讨论、转述不算确认。“确认，不过改成九点”先生成新预览，再等下一条确认。
- **授权单次消费**：确认后在领域库的事务里签发授权，最长 5 分钟，且不超过提案的截止时间。业务提交在同一个事务里消费它，重复提交按幂等返回已有结果。新消息到来、回合结束或 `/new` 会让没消费的授权失效。
- **多项确认**：目标集合在这条消息第一次确认时冻结，之后不能扩充或替换。先逐项检查权限，任何一项越权则整批拒绝。各项在自己的领域库里提交，不保证跨库原子；结果逐项返回，失败和未知的项不自动重试。
- **领域要求澄清时不重试**：领域返回 `requiresUserInput` 时，助手提问并等待新消息，同一回合不能自己换参数再试。
- **邮件先消费授权再发信**：发送失败不会复用这次授权重发。

## 限制与已知问题

- 语义判断由模型承担。后端检查的是来源和快照，不能证明模型每次都理解对了。排除否定、引用、讨论的文本规则是有限的，不是完整的语义证明。
- 没有展示记录的旧提案要重新生成预览才能自然确认。
- 进程重启后，持久化的预览仍可查询，但未消费的授权失效。

```bash
npm --prefix chatbot/packages/confirmation-core run build
npm --prefix chatbot/packages/confirmation-core test
npm --prefix chatbot/plugins/personal-confirmation run build
/usr/bin/node --test chatbot/tests/backend-boundaries/*.test.mjs
```
