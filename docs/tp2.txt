文档与开发工作规范（给 AI 开发助手；人类协作者同样适用）
版本：2026-10-21。本文件在多个项目里通用。项目自己的入口、检查命令、禁止操作写在该项目的 README / AGENTS.md 里，两者冲突时以项目文件为准。

一、文档分类：每份文档只回答一个问题

| 类型 | 回答的问题 | 什么时候写 | 生命周期 |
| 入口（README） | 项目是什么、先读哪几份、各模块做到哪 | 结构变化时 | 长期 |
| 规则文档 | 某个模块现在怎么工作、为什么这样 | 需求完成时一次写定，之后只改写不追加 | 长期 |
| 验收总表 | 哪些能力已验收、哪些没做完 | 每次验收后 | 长期 |
| 证据 | 测试输出、日志、真人验证记录 | 验证当时 | 长期，只新增不改写 |
| 临时工作记录 | 正在做的事：todo、猜测、方案、中间结论 | 开发过程中随时 | 需求完成后删除 |
| 历史资料 | 旧设计、已作废方案 | 不再写 | 只读，文首注明"不是当前规则" |

开发过程中的计划、猜测、试错、中间结论，都写进临时工作记录，不写进规则文档。
需求完成时，从临时工作记录提炼一次，写进规则文档。
这样规则文档里不会出现"此前""本轮""打算"这类过程措辞，事后也不用再清理。

二、规则文档模板（按顺序，没有内容的节可以省略）

1. 背景：要解决什么问题；范围边界（做什么、不做什么）。
2. 当前规则：系统现在怎么工作。用现在时，不回顾旧方案。
3. 已定决策：每条写"决定了什么 + 原因 + 被否决的方案（一句话）"。
4. 现状：已完成 / 未完成 / 已知问题。整份文档只在这一节写状态。
5. 术语：本文用到的项目内部名词。
6. 证据：指向证据文件的链接。

三、写作规则

1. 一句话只说一件事。一句里超过两个逗号就拆开。
2. 状态带日期和提交号，例如"2026-10-21（072a327）已验收"。不写"刚刚""目前""本轮"。
3. 项目内部名词第一次出现时解释一句，或链接到术语节。
4. 测试数量、耗时等数字只写在证据里，规则文档写"见证据"。
5. 写精确路径，不指向随时会删的临时文件。
6. 写现在怎样，不写曾经怎样。旧结论被推翻时直接改写。旧坑值得警告时，写成规则："不要做 X，因为 Y"。
7. 同一件事只在一个地方展开，其他地方一句话加链接。
8. 状态词用固定词表。项目有就用项目的；没有就用：待处理 / 处理中 / 待复验 / 已验收 / 阻塞 / 经用户确认延期。"延期"必须有用户确认。

四、单一状态源

每个事项的状态只记在一个地方：验收总表，或对应规则文档的"现状"节。
README 和其他文档只放链接，不复述状态。复述的状态迟早会和原处不一致。

五、需求完成时的收尾清单

1. 从临时工作记录提炼结论，按第二节模板写进规则文档。
2. 删除规则文档里过期、与事实不符的内容。
3. 同一方案在多处展开的，保留一处，其余改成链接。
4. 删除已被正式结果替代的临时探查，以及探查脚本的改造过程（Git 历史里有）。
5. 回顾旧方案的段落，改为直接说明当前规则。
6. 更新验收总表和 README 入口。
7. 运行项目的文档检查脚本（如果有）。
8. 删除临时工作记录。

六、工作习惯

1. 开工前在临时工作记录顶部写 todo，随实际情况增删改。每项做完，把结论覆盖到该项下面。
2. 每个阶段开始前，重新完整读一遍相关文档同步状态，不依赖对话记忆。
3. 中途被 compact 后，先重新确认用户的需求、当前进展、文档里的记录，再继续。
4. 有了计划、方案、结论，或发现之前的结论错了，及时写进临时工作记录。
5. 遇到多个方案时，自己查找信息后选最优解，记录选择和理由，便于回滚。涉及范围变化、删除数据、对外发送的操作，先问用户。
6. 新建脚本或数据表时写注释说明用途。同一业务逻辑不要出现多个随意命名的版本：新版本直接替换旧版本（Git 保留历史）；确实需要并存时用 v2、v3 后缀，不再需要时删掉旧版本。
7. 关键细节宁可多测试、多探查，也不随意下结论。
8. 写"已完成"之前先跑验证，并写清楚验证了什么、没验证什么。
