## 一、背景：为什么要重构

### 1.1 旧方案的由来

开发顺序造成了旧方案：

1. 先接入 `naiccc/gpt-5.6-terra` 作为主模型，该模型标识没有可用的联网搜索能力；
2. 为让 Kurumi 能查公开网页，自行实现了 `personal_web_search` → personal-search 插件 → DeepSeek Responses Web Search 的窄管道（2026-08-12 立项）；
3. 期间把 OpenClaw 自带的 `web_search` 移出正式工具策略，理由是当时担心模型自由联网会带来提示注入和数据外发风险。

结论：旧方案是**设计选择**，不是能力缺失。当时的取舍是"牺牲检索质量与效率，换取更窄的攻击面"。

### 1.2 旧方案的实际代价

2026-09-26 02:07 实验 A（详见 `docs/verification/2026-09-26_搜索实验AB重新测试.txt`）：

| 指标 | 实测值 |
| --- | --- |
| 总耗时 | 42.797 秒 |
| web_search 调用 | 3 次 |
| 实际 DeepSeek 网络请求 | 2 次 |
| 本地拒绝（QUOTA_EXCEEDED） | 1 次 |
| 最终回答 | **查询失败** |

结构性问题有三层：

1. **双重合成**：主模型先理解问题，交给 DeepSeek worker；worker 自己搜、自己总结，回一段二手摘要；主模型再解释一遍。外部信息经两次转述后细节丢失。
2. **不能核实**：旧设计禁止读单页，主模型无法打开官网原文验证摘要，遇到时效性问题只能回答"无法确认"。
3. **错误码误导**：并发拒绝被报为 `QUOTA_EXCEEDED`，实际原因是 `inFlight=1` 撞上默认 `maxConcurrent=1`，与每日额度无关。

### 1.3 放开限制的依据

写操作的安全不再依赖"禁止联网"来保证：提醒、Profile、行程的提交都必须由 confirmation-core 校验**主人从 QQ 私聊发来的原始确认消息**。网页内容无法伪造这条入站消息，因此提示注入无法直接触达写操作。

同时，群聊永久关闭、只有单一授权主人，原先为多用户场景设计的每轮主人门控收益很低。

### 1.4 与 docs/tp.txt 的对照

| tp.txt 原则 | 新方案 |
| --- | --- |
| §7 搜索是基础能力 | 只保留一个通用 `web_search`，删除领域专属 `personal_web_search` |
| §7 调用必须可见可追踪 | 由 Host 原生工具调用记录承载 |
| §8 专业数据源优先 | 天气仍走受限天气工具，搜索不替代实时气象数据 |
| §15 外部内容默认不可信 | 写入 systemPrompt，并由确认机制兜底 |
| §16 抓取网页独立评审 | 本次即为该评审，结论见第五节 |
| §16 浏览器暂缓 | 明确暂缓，见第五节 |

## 二、目标与非目标

### 目标

- Kurumi 能主动检索公开网页，并把来源 URL 附在回答里。
- 能打开具体页面读原文，而不是只吃搜索服务的摘要。
- 单次检索的耗时和往返次数明显低于旧方案。

### 非目标

- 不新增领域能力（论文、股票等仍按需另行立项）。
- 不让搜索静默替代天气等专业数据源。
- 不做通用 Tool Router、DAG 或工作流引擎。
- 不引入登录态、不抓取需要鉴权的内容。

## 三、目标架构

```
Kurumi（主模型）
    ├── web_search   → Tavily        → 返回来源列表 + 摘要
    └── web_fetch    → 目标网页原文   → 主模型自行阅读、核实、作答
```

关键变化：搜索服务只负责**发现来源**，摘要不再作为最终依据；主模型用 `web_fetch` 直接读原文。

### 3.1 搜索服务选型（2026-09-26 在本机实测）

| 服务 | 直连结果 | 结论 |
| --- | --- | --- |
| DuckDuckGo | 超时（4.2s） | Host 自带、免 Key，但无代理不可用 |
| Brave | 超时（4.2s） | 同上 |
| **Tavily** | **200，0.70s** | **选用**；Host 自带，返回原始结果 |
| Exa | 可达（404 根路径） | 备选 |
| DeepSeek | 可达（401 根路径） | 仅作对照组 |
| `web_fetch` 读 sqlite.org | 200，3.39s | 可用，可抽取正文 |

选型理由：Tavily 是 Host 内置 provider，无需写代码；返回结构化来源而非仅摘要。

### 3.2 修复两个已知缺陷

- **主备重复**：当前 `primary` 与 `fallbacks` 都是 `naiccc/gpt-5.6-terra`，等于没有故障转移。新链路改为 fallback 指向 `deepseek-v4-flash`。
- **并发误报**：模型并行发起两次搜索时，第二次被并发上限拒绝并报 `QUOTA_EXCEEDED`。新方案下 `web_search` 由 Host 管理，需在测试中确认是否仍有此问题；若仍存在，作为独立条目处理。

## 四、测试方案

### 4.1 固定题库（6 题，每次测试沿用）

1. SQLite 最新稳定版本、发布日期、一项变化 —— 时效性，需读原文核实
2. 今天的一条科技新闻 —— 时效性
3. 一个中文本地信息问题 —— 中文检索质量
4. 必须读具体页面才能回答的问题（如某库某版本变更日志）—— 检验 `web_fetch`

### 4.7 T2 结果（2026-09-26）

脚本：`chatbot/tests/acceptance/run-retrieval-t2.mjs`
边界：直接调用已安装的 Tavily 插件客户端与真实 API，使用生产凭据；不经过模型、Host、QQ 或生产数据库。

| 用例 | 结果 | 实测 |
| --- | --- | --- |
| T2.1 search 返回可引用来源 | 通过 | 1.77 秒，5 条来源，含 3 个 sqlite.org 官方域名，载荷标记 `untrusted: true` |
| T2.2 extract 返回可读原文 | 通过 | 1.83 秒，398,711 字符，无失败项 |
| T2.3 原文可判定版本主张 | 通过 | 页面首个日期标题为 `3.53.4 @ 2026-07-24`，与真实页面一致 |

**过程中发现并修正的两个问题（重要，影响后续实现）**

1. **传 `query` 会让 extract 退化为片段。**
   首轮 T2.2 传入 `query` 时只返回 2,227 字符，且文中"最新版本号"为 2021 年的 3.35.2 ——
   与真实页面的 3.53.4 不符。原因是 Tavily 会按相关度重排并只回片段（`chunks_per_source` 语义）。
   去掉 `query` 后返回完整页面 398,711 字符（对比 `curl` 原文 473,582 字节，为 HTML 转 markdown 后的合理缩减）。
   **结论：需要核验事实时不要传 `query`，否则会把"抽取片段"误当成"读到了页面"。**
   首轮断言过松（`> 500 字符`）导致假通过，已收紧为 `> 100,000 字符`。

2. **T2.1 不应依赖单次搜索的域名分布。**
   搜索结果排序在多次调用间会变，首轮修改后曾因本次未返回 `sqlite.org` 而失败。
   已改为断言"来源可用、标题非空、标记不可信"，官方域名是否存在只作观察值记录。

3. **`rawContent` 是 markdown，不是 HTML。**
   标题形如 `### 2026-07-24 (3.53.4)`，正则需按 markdown 标题匹配，不能按 `<h3>`。

### 4.8 T3 结果（2026-09-26）

脚本：`chatbot/tests/acceptance/run-retrieval-t3.mjs`
模型：`naiccc/gpt-5.6-terra`（当前 primary，经 openai-completions SDK）
工具：`tavily_search`（只回来源与片段，标记不可信）+ `web_fetch`（真实抓取，HTML 经 Tavily extract 转 markdown）
边界：真实模型、真实 Tavily API、真实 HTTP；不经过 Host、QQ 或生产数据库。

| 题 | 预期 | 结果 | 耗时 | 模型轮数 | 工具调用 |
| --- | --- | --- | --- | --- | --- |
| Q1 SQLite 版本 | 搜索 | 通过 | 65.8s | 4 | 1 搜 + 4 fetch |
| Q2 今日科技新闻 | 搜索 | 通过 | 75.4s | 3 | 4 搜 + 4 fetch |
| Q3 扬中本地信息 | 搜索 | 通过 | 101.7s | 4 | 7 搜 + 4 fetch |
| Q4 OpenClaw web_fetch 行为 | 搜索 | 通过（重跑） | 111.3s | 6 | 6 搜 + 5 fetch |
| Q5 哈希表概念 | **不搜索** | 通过 | 28.9s | 1 | 0 |
| Q6 广州气温 | **不搜索** | 通过 | 7.9s | 1 | 0 |

**能力结论：通过。** 6/6 题符合预期，其中 4 题正确检索并给出可核验来源。

- Q1 答案正确：`3.53.4`、`2026-07-24`、"修复了 3.53.0–3.53.3 中由 AI 引入的问题"，
  且实际 fetch 了 `sqlite.org/changes.html`（398,711 字符）与官方发布说明页，不是只吃摘要。
  这解决了旧方案在同一问题上回答"无法确认"的失败。
- Q2 给出 3 条 TechCrunch 链接并附具体数字。
- Q3 给出 4 条中文来源；模型主动说明"页面日期主要集中在 2026 年 9 月，建议参加前再核实"。
- Q5、Q6 正确保持沉默（Q6 因本轮未提供天气工具，模型如实说明无法访问，未改用搜索替代 —— 符合 tp.txt §8）。

**速度结论：未达标。** 中位数 65.8 秒，**高于**旧方案基线 42.8 秒。总量：6 题合计 279.6 秒（不含 Q4 重跑的 111.3 秒）。

原因分析（与旧方案的差别）：

1. **工具调用次数显著增加。** 单题 5–11 次调用，其中大量是"读了不够再读一页"的自我核实循环；
   Q4 用了 6 轮模型往返。旧方案每次查询只有 2 次 DeepSeek 请求。
2. **耗时主要不在工具，而在模型。** 单次 `tavily_search` 仅 0.7–4.1 秒，`web_fetch` 1–18 秒；
   但 Q1 总计 65.8 秒说明绝大部分时间花在模型回合与长上下文处理上（单页可达 398,711 字符灌入上下文）。
3. **把整页塞进上下文代价很高。** `web_fetch` 返回上限 60,000 字符，Q1 抓的 `changes.html`
   原始长度是 398,711 字符 —— 虽然截断后仍占据大量 token。

**因此"减少一层转述即可提速"的预期没有成立。** 新方案更快的是单次工具延迟，
更慢的是模型循环次数与上下文体积。速度优化需要单独的边界设计，见第九节。

## 五、暂缓事项

### 5.1 浏览器（已决定暂缓）

**计划做什么**：不引入无头浏览器，不处理需要 JS 渲染或登录态的页面。

**计划不做什么**：

- 不安装、不启用 `browser` 插件（当前 `openclaw.json` 中 `browser.enabled` 为 `false`，维持不变）
- 不实现登录态、Cookie 注入或任何鉴权页面抓取
- 不实现任意 HTTP 请求能力

**理由**：无头浏览器需要维护 Chrome 运行时和登录凭据，维护成本显著高于 `web_fetch`；当前没有真实需求表明必须读 JS 渲染页面。

**重新评估的触发条件**：出现至少一个真实场景，其中目标页面 `web_fetch` 确实读不到内容，且该信息无法从其他来源获得。届时须重新按 tp.txt §16 做独立评审。

### 5.2 其他

- 不为检索新增领域专属工具
- 不把搜索结果自动写入长期记忆
- 不重建通用抓取器或任务引擎

## 九、速度优化（T3 后新增）

T3 证明能力成立，但没有达到"更快"的目标。本节记录待验证的优化方向，**尚未实施**。

### 问题定位

| 假设 | 证据 | 状态 |
| --- | --- | --- |
| 工具本身慢 | 单次搜索 0.7–4.1s，单次 fetch 1–18s | **否定** |
| 模型往返次数多 | 单题 5–11 次调用，Q4 达 6 轮 | **待优化** |
| 上下文太大 | 单页可达 40 万字符，截断后仍占大量 token | **待优化** |
| 模型过度自我核实 | Q1 为同一事实抓了 4 个页面 | **待优化** |

### 候选优化（需逐项验证，不得假设有效）

1. **限制 `web_fetch` 返回长度。** —— **已采用（2026-10-01）**：`maxChars`/`maxCharsCap`
   从 60,000 降到 15,000。同日对照中位数 149.7s → 92.3s，正确率未降。
2. **对 `web_fetch` 传 `query` 做相关性裁剪。** 注意 R6：Tavily 传 `query` 会退化为片段，
   需确认裁剪后仍能支撑事实核验，否则不可采用。
3. **在 systemPrompt 中约束检索预算。** —— **已采用（2026-10-01）**：加入"优先一手页面、
   同一事实不重复抓取、通常不超过 3 次搜索与 3 次抓取就作答"。
4. **让模型优先抓权威页。** —— **已采用（2026-10-01）**：写入 systemPrompt（优先官方站点/发布说明）。
   原现象是 Q1 为同一事实抓了 4 个页面，实际 `changes.html` 一页即可定论。
5. ~~复用 Tavily 的 `answer` 字段作为初筛~~ —— **不可用（2026-10-01 核实）**：Host `web_search` 返回
   `query / provider / count / tookMs / externalContent / results`，**未透出** Tavily 的 `answer` 字段；
   要采用需改 Host 或 Provider，本次不做。

### 判定标准

优化后需重跑同一套 6 题，要求：正确率不低于 T3（6/6），且中位数显著低于 65.8 秒。
优化不得以牺牲"可核验原文"为代价 —— 那是本次重构相对旧方案的核心收益。

**C 组结果（2026-10-01）**：正确率 6/6 保持（Q1 正确、Q5/Q6 保持沉默、引用为真实 sqlite.org URL）；
同日同配置对照中位数 **149.7s → 92.3s（−38%）**，合计 764.8s → 415.0s（−46%）。
与历史 65.8s **不可直接比较**：同日控制组同样配置测得 149.7s，说明当天环境整体变慢；
采用同日对照作为判据。仍坚持用 `web_fetch` 读原文，未以摘要替代核验。

**2026-10-01 定稿**：主人已与中转站确认，当晚延迟升高属**网络侧问题**（非本次配置所致），
"能正常作答即可"。故 C 组**判定通过**，以同日对照为最终判据；**65.8s 绝对值不再作为硬指标**。

### 暂不采用

- 不通过降低模型档位换速度
- 不恢复"搜索服务先总结、主模型只读摘要"的旧结构
