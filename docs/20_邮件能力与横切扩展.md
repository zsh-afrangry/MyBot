# 邮件能力与横切扩展

助手提供“草稿预览 → 主人自然语言确认 → 投递 → 查看状态”的邮件能力。实现是插件 `chatbot/plugins/kurumi-mail/`，不要求助手执行命令，也不新增 MCP 进程。

## 功能

- 已验证的生产发信配置是 QQ 邮箱 `smtp.qq.com:465` 隐式 TLS；已实现并完成隔离验收的收件箱能力使用 QQ 邮箱 `imap.qq.com:993` 隐式 TLS（默认 `1794511189@qq.com`，预留多账号 `account` 字段），待[文档38](38_月度邮件账单导入与多格式读取.md)阶段 4 授权启用。正文为纯文本，发信可附受管 PDF。
- 仅主人私聊可用。成员不继承邮件权限；消息正文和模型参数不能授予身份、收/发件人或批准。各工具先经共享 access-control 检查真实身份、路由和权限点，再进入领域策略。权限归[文档24](24_统一身份与权限管理.md)。
- 发信收件人只能是 `mailRecipients` 白名单内地址；收件箱对非 `mailSenders` 白名单或 `Authentication-Results` 含 `spf=fail`/`dkim=fail` 的邮件默认只返回不可信元数据摘要，读取正文与下载附件须经主人二次确认当场放行，删除/整理仅支持 `mark_read`/`mark_unread` 或确认后移入已删除文件夹（禁 `EXPUNGE`/`CLOSE`）。
- 触及被禁用的能力时的处理规则见 [AGENTS.md](../AGENTS.md) 的“触及禁用限制时必须先告知”。

## 接口

| 工具 | 权限点 | 说明 |
| --- | --- | --- |
| `email_status` | `mail.status` | 报告 SMTP/IMAP 配置是否就绪，不回显凭据。`probe=true` 连 TLS 并认证，不发信也不改邮箱状态 |
| `email_draft` | `mail.draft` | 生成预览和草稿 ID。附件只收 `attachments:[{documentId}]`，不接受路径、URL 或 base64 |
| `email_send` | `mail.send` | 校验草稿、策略和已记录的授权后投递。重复、过期、跨 scope 的授权被拒绝，模型给的 approval 字符串被忽略 |
| `email_outbox` | `mail.history` | `list`（默认）、`audit`、`receipt` 和 `cancel`。按 `draftId` 查单封回执或取消待确认草稿。只有取消会写入 |
| `email_inbox` | `mail.inbox.read` / `mail.inbox.attachment` / `mail.inbox.manage` | 仅主人（生产待启用）。`folders`/`list`/`search`/`read`/`save_attachment`/`propose_access`/`commit_access`/`mark_read`/`mark_unread`/`propose_manage`/`commit_manage`/`status`；附件按 `account`/`uidValidity`/`uid`/`partId` 幂等暂存到默认工作区 `mail-attachments/<YYYY-MM-DD>/` |

配置：

- 凭据在运行目录 `runtime-env.json`，由 `scripts/fusion/run-gateway.mjs` 注入进程环境，不进 Git，不回显。键是 `KURUMI_MAIL_USER`、`KURUMI_MAIL_AUTH_CODE`（授权码），可选 `KURUMI_MAIL_HOST`、`KURUMI_MAIL_PORT`（默认 `smtp.qq.com:465`）及 `KURUMI_IMAP_HOST`、`KURUMI_IMAP_PORT`（默认 `imap.qq.com:993`）。变更后重启服务。
- 发信收件人白名单 `mailRecipients` 与收件箱长期发件人白名单 `mailSenders` 的唯一编辑来源均为 `config/access-control.json` 的 owner 行，由 `sync-config.mjs` 分别派生为 `allowedRecipients` 与 `allowedSenders`。不直接编辑运行名单。同步规则见 [config/README.md](../config/README.md)。
- 草稿、收件箱确认状态及审计共享运行目录 `state/kurumi-mail/mail.sqlite`；单封邮件原始抓取与附件均受 25 MiB 上限约束，关键动作写入 [trace-events](18_跨模块链路日志查询.md#日志来源与范围)。日志不含授权码、正文或附件字节。
- `plugins.entries.kurumi-mail.config.feedbackActions` 可分别启用 `mail.draft` 和 `mail.send`，默认都启用。创建、发送及按草稿回查返回相应的 `feedback`。发送回执区分待确认、已确认、过期、已取消、SMTP 已受理、明确失败和结果未知。能取得 SMTP 应答时提供应答码，受理时附实际受理和拒绝的收件人数。

## 原理

- 消费授权时在同一事务保留草稿和邮件 Message-ID，初始投递结果为未知。收到 SMTP 最终 `250` 后登记受理，明确拒绝或提交前失败可登记失败。提交后断连、应答丢失或进程中断时保持未知。回查只读草稿、确认记录和审计，同一份草稿最多尝试一次发送。确认流程见[文档6](6_二次确认.md)。
- 白名单拒绝发生在消费授权前，仍有效的授权可保留。发送明确失败后，再次发送需新建草稿并确认。适配器与生命周期见[文档21](21_后端职责分层与代码整理.md)。
- **收件人校验**：To 和 Cc 必须精确命中白名单，忽略大小写和首尾空格，不支持通配符，名单为空时全部拒绝。创建草稿和发送时各校验一次，所以收紧名单后旧草稿也发不出去。`cc` 会进入 SMTP 信封收件人，当前 MIME 只生成 `To` 头。
- **批量确认**：多封已展示的冻结草稿可以在一条消息里确认（最多 16 项）。逐项检查邮件权限，只对授权成功的草稿调用 `email_send`，结果逐项返回，失败和未知的不自动重试，不保证跨库原子。

| 文件 | 职责 |
| --- | --- |
| `index.js`、`inbound.js` | 工具、可信权限和确认 scope、生命周期；停止或启动失败时注销确认后端 |
| `contracts.d.ts`、`adapters.js`、`application.js` | Policy/Store 契约和启动选择，默认实现 `default`/`sqlite`，未知实现报错，不静默回退 |
| `policy.js`、`service.js` | 收件人与输入策略、发送编排 |
| `store.js`、`inbox-store.js` | 同步 SQLite：发信草稿/审计快照与收件箱 `mail_inbox` 确认/附件暂存/审计（预留 `account_id`） |
| `mime.js`、`smtp.js` | RFC 2047/2231 编码与折行、原始字节编码、465 TLS 的 SMTP 协议 |

### 受管 PDF 附件

论文导入、翻译和受管 PDF 的来源归[文档22](22_论文PDF翻译与文件投递.md)。附件规则在这里：

| 规则 | 内容 |
| --- | --- |
| 数量与大小 | 最多 10 份，每份非空且不超过 10 MiB，合计不超过 20 MiB。`store.js` 的 `MAX_ATTACHMENTS`、`MAX_ATTACHMENT_BYTES`、`MAX_TOTAL_ATTACHMENT_BYTES` 按实际字节校验 |
| 创建时快照 | 在 `attachments_json` 中固定字节、文件名、MIME 类型、大小、SHA256 和来源 documentId。预览只展示元数据，附件字节不交给模型 |
| 确认范围 | 提案和授权的 payload hash 绑定规范化后的 To/Cc、主题、正文，以及每份附件的文件名、MIME 类型、字节数和 SHA256。源文件之后变化，不影响已确认的草稿 |
| 发送前校验 | 数据库中的字节或摘要变化则拒绝发送，始终从固定快照取件 |
| 超限 | 超过邮件限制的文件走 QQ 文件投递，邮件限制不放宽，也不开放通用 read/exec |

邮件构建的结果要能被标准 MIME 解析器还原出正文、中文文件名和相同 hash 的附件。附件复用既有字段，没有 SQL 迁移。

## 限制与已知问题

- Gmail 未实施。它依赖尚未设计的非 HTTP 代理：`tls.connect`、`net.connect` 不自动读取 `HTTP_PROXY`，QQ SMTP 直连，保持证书验证。HTTP 类能力使用受信环境代理和精确 host 约束。
- 没有覆盖实际配额和退信、多收件人真实链路。
- 新增收件地址必须先取得主人授权，并修改 `access-control.json`。不得沿用历史测试授权扩大真实外发对象。
- SMTP 回执只证明服务器受理。收件箱送达和已读均留为未知。历史连接失败若缺少提交阶段证据，回查显示未知。

## 如何验证

```bash
/usr/bin/node --test chatbot/plugins/kurumi-mail/test/*.test.js
/usr/bin/node chatbot/scripts/scenario-acceptance.mjs --target isolated --scenario mail-feedback
/usr/bin/node chatbot/scripts/scenario-acceptance.mjs --target isolated --scenario mail-inbox
```

隔离场景分别验证本地 TLS SMTP 批量确认/拒收/断连回查，以及本地 TLS IMAP 的双层发件人白名单、认证失败降级、工作区附件幂等暂存与确认移入已删除文件夹。真实 QQ 收/发信链路待[文档38](38_月度邮件账单导入与多格式读取.md)阶段 4 授权启用后验真；真实 SMTP 脚本 `scripts/fusion/test-mail-delivery.mjs` 需要单独授权。
