## 背景与需求

主人希望助手能"发邮件给指定邮箱"，体验参照 WorkBuddy 的邮箱连接器：草稿预览 → 主人确认 → 投递 → 队列状态。
需求来源是 2026-10-15 至 2026-10-16 的两次会话，其中还包含一份第三方方案摘要（外部 AI 在主人笔记本上做的调研）。

**那份第三方方案在本项目有三处错配，本文不再沿用其路线**：

| 它的主张 | 本项目实际 | 结论 |
| --- | --- | --- |
| 首推"技能路线：agent 用 `exec` 调用脚本" | `main` agent 的 `tools.deny` 含 `exec`（还有 `read`/`write`/`edit`/`apply_patch`/`process`/`message`/`sessions_spawn`） | 技能路线**不可用**，改走插件路线 |
| 声称"SnowLuma 把 QQ 群消息接进 agent，群里任何人都能塞指令" | `channels.kurumi-qq` 只服务主人私聊，群聊入口永久关闭 | 该风险前提不成立；但注入面仍在（搜索结果、论文、转发内容），确认闸门仍必要 |
| 报告"已实现并测通，48/48 断言" | 其产物（`qqmail-connector/`）**不在本机**，在主人笔记本上 | 本机需重新实现 |

## 现状核查（2026-10-16 实测）

### 1. 主人边界：确实是"仅本人私聊"，四重校验

`chatbot/plugins/kurumi-qq/src/config.js` 的 `ownerAuthorized`：

```js
ctx.senderIsOwner===true && ctx.requesterSenderId===owner &&
ctx.messageChannel===CHANNEL && ctx.sessionKey===`agent:main:${CHANNEL}:direct:${owner}`
```

其中 `sessionKey` 的 `direct:` 段直接排除了群聊；`senderIsOwner` 来自频道可信元数据，消息正文自称无效。
配置里也没有任何群相关键（`channels.kurumi-qq` 只有 `ownerId`、通道地址、限额与分段设置）。
**因此"不私聊其他人、不群聊"当前由机制保证，不是靠提示词约束。**

### 2. 确认机制是通用共享件，可直接复用

`personal-confirmation` 插件自述为 "Shared inbound confirmation governance for Kurumi capabilities"；
`chatbot/packages/confirmation-core/` 是独立包，导出 `registerConfirmationBackend`、`scopeFromToolContext`、
`ensureConfirmationGateSchema` 与 proposal/grant 状态机；`personal-weather` 已按此接入。
**结论：邮件不需要新造确认机制，按同一接口接入即可。**

### 3. MCP 受支持，但本需求不走 MCP

OpenClaw 2026.9.7 有完整 MCP 支持：`mcp.servers.<name>` 支持 stdio（`command`/`args`/`env`/`cwd`）与远程
（`url` + `transport: stdio|sse|streamable-http` + `headers`），支持 `auth: "oauth"`（含 `identity`、`authProfileId`、
`scope`、`redirectUrl`）与 `toolFilter.include/exclude`；插件清单也可声明 `mcpServers`。
另外 `mcp` **不在** `config/runtime.config.json` 的 `_managed` 列表，属"宿主自行维护"键。
不走 MCP 的理由：MCP 引入独立进程与依赖管理，且工具动态注册，与本项目两套精确边界
（`agents.entries.main.tools.alsoAllow` 白名单 + `plugins.allow` 逐个插件）不易对齐；
插件路线与现有 8 个插件同形态，可写离线测试、可被 `evidence-index.mjs` 索引。

### 4. 邮件出站：QQ 邮箱可用，Gmail 当前不可用

| 目标 | 实测结果（2026-10-16） |
| --- | --- |
| `smtp.qq.com:465` | **可用**：隐式 TLS 握手成功且**证书校验通过**（`authorized:true`、`TLSv1.3`、DigiCert 签发 `*.mail.qq.com`、有效期至 2026-11-23） |
| `smtp.qq.com:587` | 报 `ERR_SSL_WRONG_VERSION_NUMBER` —— 这是用 TLS 直连 STARTTLS 端口的正确表现，说明 587 需按 STARTTLS 流程（先明文 EHLO 再升级） |
| `smtp.gmail.com:465` | **不可用**：`ECONNRESET` |

复现命令（只做 TLS 握手与证书校验，不发信、不认证）：

```bash
node --input-type=module -e "
import tls from 'node:tls';
const s=tls.connect({host:'smtp.qq.com',port:465,servername:'smtp.qq.com',rejectUnauthorized:true},()=>{
  console.log('authorized:',s.authorized,'protocol:',s.getProtocol(),'CN:',s.getPeerCertificate().subject?.CN);s.end();});
s.on('error',e=>console.log('error:',e.code||e.message));"
```

注意：本机 DNS 把 `smtp.qq.com` 解析到 `198.18.0.48`（fake-IP 段），TCP 465/587 由透明代理转发，
证书仍能通过校验，**不需要** `rejectUnauthorized:false` 这类降级。

### 5. 代理：HTTP 层已支持"按功能选择"，缺口在非 HTTP 协议

已在用的机制：

- `runtime-env.json` 已有 `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY`（大小写两套）。
- `tools.web.fetch.useTrustedEnvProxy: true`：网页抓取走受信环境代理。
- 天气插件用 `mode: "trusted_env_proxy"` + 精确 host 白名单（`ssrfPolicyFromHttpBaseUrlFakeIpHostnameAllowlist`），
  这是为 Clash/sing-box fake-IP 环境放行**单一** Host 的做法，不放开任意私网。

因此"某功能需要代理就给它插上"在 **HTTP 层已经存在**，形态是"受信环境代理 + host 白名单"。
**真正的缺口是非 HTTP 协议**：Node 的 `tls.connect`/`net.connect` 不读 `HTTP_PROXY`，
所以 SMTP/IMAP 要走代理必须显式实现（HTTP CONNECT 隧道或 SOCKS5）。
这就是"代理插件化"应当解决的问题——见横切能力二。

## 开发路线

### 阶段一：离线可验证的骨架

1. `chatbot/plugins/kurumi-mail/openclaw.plugin.json`：声明 `id`、`contracts.tools`。
2. `index.js`：用 `api.registerTool`（本项目既有形态）注册工具，全部 owner-only（`ownerAuthorized`）。
3. `smtp.js`：465 隐式 TLS 投递；凭据从运行环境读取，**不写死、不回显**。
4. `store.js`：草稿、待发队列、`sent.jsonl` 审计（**不含授权码**）。
5. `test/*.test.js`：对本地 mock SMTP 断言——确认闸门前服务器收不到任何邮件、错误/重复令牌被拒、
   UTF-8 主题与中文附件名无损、纯文本结构正确。

### 阶段二：接入与登记

1. 在 `config/runtime.config.json` 登记：`plugins.allow`、`plugins.load.paths`、`plugins.entries`。
2. 在 `agents.entries.main.tools.alsoAllow` 加工具名（否则 `main` 调不到）。
3. `sync-config.mjs --diff` → `--apply` → 重启 `kurumi-fusion.service`。
4. 登记脚本与证据索引（`verification/SCRIPTS.md`、`INDEX.md`）。

### 阶段三：真实投递验收

1. 主人自行在 `.openclaw-fusion/runtime-env.json` 填写授权码（QQ 邮箱 → 设置 → 账户 → 开启 SMTP → 生成授权码，**不是 QQ 密码**）；
   助手不持有、不读取、不回显该值。
2. 发一封到主人指定邮箱的真实邮件，记录真实回执与到信确认（**真实回执已完成；到信确认待主人**）。
3. 明确证据边界：mock SMTP 通过 ≠ 真实投递通过；沙箱结果不得冒充真实验收。

## 横切能力一：确认机制复用

邮件**不新造确认机制**，按 `confirmation-core` 既有接口接入：

- 复用 proposal/grant 状态机与 `ensureConfirmationGateSchema`，与提醒、行程、Profile 同一套治理。
- 确认口令由后端生成，工具原样返回；模型不得改写、拼接或猜测。
- 确认必须来自**本人私聊原文**，不能用模型自述的"用户已同意"代替。

具体接口与参数以 `chatbot/packages/confirmation-core/src/index.ts`（公开接口）与 `personal-weather` 的接入代码为准，
本文不重复展开（同一条规则只在一处完整说明）。

## 横切能力二：代理接入

**问题**：HTTP 层已有"受信环境代理 + host 白名单"，但 SMTP/IMAP 等非 HTTP 协议不读 `HTTP_PROXY`，
所以将来接 Gmail（或其它境外邮件服务）时，功能无法直接复用现有代理配置。

**要解决的是"非 HTTP 协议的代理接入点"**，不是重造 HTTP 代理：

1. 明确一个位置声明"本功能需要代理"（例如插件的 config 或环境），由宿主提供代理地址；
2. 实现 HTTP CONNECT 隧道或 SOCKS5 客户端，供 SMTP/IMAP 使用；
3. 沿用现有边界：**按功能授权、不全局放开**，且不绕过既有 SSRF 守卫；
4. 代理凭据同样只存运行目录凭据平面。

**当前状态**：仅记录需求与缺口，尚未实现。若将来有第二个功能也需要非 HTTP 代理，
再考虑把这一能力提取为独立规则文档，而不是继续堆在本文。

## 权限现状与"触及禁用限制"的处理

当前 `main` agent（QQ 私聊里的助手）**不能**：执行命令、读写文件、开子会话、直接用 `message` 发消息。
它能用的只有聊天与 `tools.alsoAllow` 明列的 22 个业务工具。

**协作规则（已写入根 `AGENTS.md`）**：当后续需求触及这些禁用限制时，
**先明确告知主人"需要放宽哪一项、为什么、风险是什么"，由主人决定是否开放**；
不得默默绕道（例如改用沙箱、改用别的工具拼凑）或把需求改小后再声称完成。

需要知道的分级（供主人决策，非当前授权）：

| 放开项 | 影响 |
| --- | --- |
| `read` | 助手能读仓库文件（例如按 `docs/` 回答） |
| `exec` | 助手能在服务器执行任意 shell 命令，**风险最高** |
| 独立 agent | 参照 `project-fusion`：给特定任务一个受限工作区 + 本地 git，而**不动 `main`**（推荐形态） |

### 测试发现并修复的真实缺陷

写测试的价值在这次很具体——三个缺陷是测试抓出来的，其中第一个会让功能**完全不可用**：

1. **多行 SMTP 响应永远解析不出来**（致命）：EHLO 返回 `250-…`/`250-…`/`250 …` 三行，而解析器只看第一行就判定"响应未结束"，且不会在已缓冲的数据上重试 → 每次连接都在 EHLO 超时。已改为按 SMTP 规则扫描到第一个以空格分隔的行为止，并精确消费已解析的行。
2. **RFC 2047 分段超长**：按 47 字节切分后 base64 为 64 字符，加上 `=?UTF-8?B?` 与 `?=` 共 76 字符，超出 75 上限。已改为每段最多 45 字节（72 字符）。
3. **地址校验两处不一致**：`mime.js` 用宽松正则（接受 `a@b`），`store.js` 用严格正则（要求域名含点）。已提取单一规则 `isValidAddress` 并共用。

### 凭据与安全

- 凭据只从运行环境读取（`KURUMI_MAIL_USER` / `KURUMI_MAIL_AUTH_CODE`），工具不回显、审计不记录、错误信息不含；
  SMTP 测试专门断言"认证失败时错误与堆栈都不含授权码与用户名"。
- 发送顺序固定为：草稿存在且 pending → **先消费授权** → 才建立网络连接。因此投递失败不会留下可复用的授权（重试需重新确认）。
- 授权由宿主入站路由产生：插件通过 `registerConfirmationBackend` 注册，主人回复"确认 <短码>"才会生成 grant，模型无法自行批准。

### 收件人白名单（2026-10-16 追加，主人要求测试期生效）

- 来源：`plugins.entries.kurumi-mail.config.allowedRecipients`，**精确地址，不支持通配符**；当前只有 `365999865@qq.com`。
- **未配置时全部拒绝**（fail-closed）。理由：静默放行是这里最坏的结果——保护看着存在、实际什么都没拦；
  因此拒绝信息直接写明该去哪个配置项加地址。
- `To` 与 `Cc` 同一名单；比较忽略大小写与首尾空格。
- **草稿创建时与投递前各校验一次**：草稿建好后名单若被收紧，投递同样被拒。
- 策略拒绝**不消耗主人授权**（什么都没发出），名单放开后仍可发送。
- 已补 8 个离线用例：允许/拒绝、cc 同约束、空名单拒绝且不留下可确认的草稿、大小写与空白归一、辅助函数行为。

## 附件：已实现但不可达（待主人决定）

现状是三段不一致，必须说清楚，避免以后误判：

| 层 | 附件支持 |
| --- | --- |
| `mime.js` | **已实现**：`multipart/mixed`、RFC 2231 中文附件名、base64 折行，有测试 |
| `store.js` | **已实现**：数量上限 10、单个上限 10 MiB、文件名安全检查、附件内容进 `payloadHash` |
| `email_draft` 工具 | **不暴露 `attachments` 参数**，所以助手实际上发不出附件 |

**不暴露的理由不是"没做"，而是"拿不到"**：`main` agent 的 `tools.deny` 含 `read`，它没有任何读取本地文件的途径，
因此没有合法来源去填充附件内容。把参数暴露出来的结果只会是让模型凭空编造 base64 内容，
或者把 `web_fetch` 抓到的网页正文当附件发出去——两种都不合预期。

因此附件当前**不是待开发项，而是待决策项**。可选方向：

1. 维持不暴露，并把 `mime.js`/`store.js` 的附件能力标注为"库能力、工具未连"（现状，零成本）；
2. 若将来需要发文件，应先给助手一条**受限的取件通道**（例如某个已登记目录的只读读取），再暴露参数——
   这属于"触及禁用限制"，按 `AGENTS.md` 必须先告知主人并由主人决定；
3. 只允许把本次对话里明确给出的文本作为附件（不引入文件读取），价值有限。

## QQ 真实往返失败与修复（2026-10-16 02:01 与 02:22）

主人在 QQ 里试了两次完整往返，两次都失败。**两次是同一个根因**，且该根因意味着
**QQ 发起的确认从上线起就不可能成功**——不是偶发。

### 根因：时间戳单位不匹配（毫秒被当成秒）

| 步骤 | 事实 |
| --- | --- |
| 1 | 宿主构建入站事件时传 `timestamp: ctx.Timestamp`（`personal-confirmation/src/inbound.ts`），**单位是毫秒**——同文件用 `ctx.Timestamp > nowMs + 30_000` 做新鲜度校验即为证据 |
| 2 | 邮件 backend 直接把 `event.timestamp` 当秒用（没有毫秒护栏） |
| 3 | 于是 `nowUtc` ≈ 1.79e12，而提案 `expires_at_utc` ≈ 1.79e9 |
| 4 | 确认包的候选查询是 `WHERE status='pending' AND expires_at_utc > ?` → **恒为假** |
| 5 | 候选数 0 → 宿主 `recordRegisteredConfirmation` 报 **`no_match`** → **从不签发 grant** |
| 6 | 因此 `email_send` 永远只会得到 `approval_required`，往返不可能成功 |

**对照物**：`chatbot/plugins/personal-weather/src/store.ts` 一直写着正确形式
`event.timestamp > 10_000_000_000 ? event.timestamp / 1000 : event.timestamp`，邮件插件漏了这一步。

### 生产痕迹

- 3 次 `no_match`：`02:01:29`、`02:23:10`、`02:24:30`
- `mail_audit` 中 `approved` **仅 1 条**，来自 01:03 的验收脚本 → **QQ 发起的确认一次都没成功**
- 提案状态：3 个至今 `pending`

### 修复

1. **单位护栏**（`store.js::eventSeconds`）：> 1e10 视为毫秒并除以 1000，否则按秒；
   两处调用点（列出候选、记录授权）统一使用。超过 1e10 秒即公元 2286 年，因此该阈值可靠区分两种单位，
   同时兼容传入秒的调用方（天气域即如此）。
2. **`email_send` 放宽**：此前只改了 `email_draft` 与 `email_outbox`，漏了 `email_send`，
   模型回传 `{"draftId":…,"approval":"确认 …"}` 时仍被 `additionalProperties:false` 硬拒。
   现改为运行时校验，并**明确忽略**模型自带的确认字符串——授权只认宿主记录的 grant，
   不接受任何由模型参数提供的"批准"。

### 验证

- **离线复现**：同一份代码、同一组指令，毫秒 → 候选 0、记录失败；秒 → 候选 1、记录成功。
  修复后毫秒 → 候选 1、记录 true、可消费 true。
- **真实数据回放**：把生产库复制到临时目录（只读，不动生产状态），针对 02:22 那次真实失败的提案
  `3efdd3dd`（口令 `确认 9cce5bde0322`）用毫秒时间戳驱动，修复后 **候选 1、可签发授权 true**。
- 新增回归用例 8 个：端到端"毫秒时间戳的确认 → 投递成功"、秒时间戳兼容、缺时间戳回退、
  `eventSeconds` 边界与异常输入、`normalizeSendArgs`（含忽略回传口令）、工具层用生产失败参数驱动。
  邮件插件 **79/79 通过**。

### 测试为什么没抓到（盲区记录）

原有用例全部走 store 自身时钟（秒），**没有任何一个用例用宿主真实的毫秒时间戳驱动确认流程**；
`tool.test.js` 当时也只测到"草稿生成成功"为止，没覆盖"确认事件 → 签发授权"。
新增的毫秒用例正是补这个洞——**测试通过不等于宿主契约被验证，单位与格式这类接缝必须用真实数据形状覆盖。**

### 更正一条此前的误判

上一轮曾判断"02:01 的草稿根本没建成、主人在确认一个不存在的东西"——**该判断是错的**。
生产库显示 02:01:09 已成功建立草稿 `1eef0d2c`（模型在 schema 被拒后重试成功），那次 `no_match`
同样由上述单位 bug 造成。schema 问题真实存在且已修，但它不是失败根因。

## 适配器迁移（2026-10-16）

邮件此前是三个领域里唯一没有接入共享适配器机制的：工具直接 `new MailStore(...)` 并调用
`store.createDraft`，可信上下文检查内联在 `index.js`。本次迁移到与提醒列表、记忆相同的形态。

| 层 | 迁移前 | 迁移后 |
| --- | --- | --- |
| 契约 | 无 | `contracts.d.ts` 声明 Policy / Store / StoreOptions |
| 组合 | 工具各自 `new MailStore(...)` | `adapters.js` 注册表 + `application.js` resolve；`new MailStore` 只此一处 |
| 策略 | 工具内联调用 `normalizeDraftArgs` 等 | `defaultMailPolicy` 经注册表选定，服务持有选定接口 |
| 可信入站 | 内联 `ownerAuthorized` / `scopeFromToolContext` | `inbound.js` 独立，先于任何策略执行 |
| 写入编排 | `deliver.js` 自由函数 | `service.js::createMailService(policy)` |
| 确认 backend | 自己 `new MailStore(...)` | `application.openStore(...)`，因此换存储即被采纳 |
| 配置 | 仅白名单 | 增加 `policyAdapter` / `storeAdapter` 选择（未知 id 明确报错，不静默回退） |

**一个必须记住的差异**：注册表要求 store 契约**同步**（返回 Promise 的 store 会被直接拒绝），
而投递是异步 SMTP 动作，因此它留在服务层、从不进入 Store。同理，"在业务事务内消费 grant"
在邮件上只能做到**先消费、再投递，失败需重新确认**——邮件的发送不是数据库事务。

**迁移为什么低风险**：MIME 构造、SMTP 客户端与确认协议**一行未动**；现有 79 个用例的断言全部保留，
迁移后仍全绿（86/86，新增 7 个适配器用例）。新增用例里最关键的一条是：
**宿主的入站路由到达被选中的 store**——迁移前 backend 自己构造存储，没有任何测试能观察到
"确认究竟落进了哪个实现"，而现在这条被显式覆盖。
