# 邮件能力与横切扩展

类型：领域规则。状态：**文本邮件与受管PDF附件已部署；Gmail/非HTTP代理未实施，收信不在需求范围。** 验收结论见[文档16](16_验收与测试总表.md#分领域验收摘要)。实现范围基于2026-10-21记录；2026-10-23只调整阅读结构。阅读入口：[README.md](README.md)，分层/确认归[文档21](21_后端职责分层与代码整理.md)，权限归[文档24](24_统一身份与权限管理.md)。

本文先列现行投递契约与代码，再列附件、未实施的代理扩展和复验入口。复用确认与授权规则时只从归属文档进入，不把SMTP投递当作数据库事务。

## 需求与当前规则

助手提供“草稿预览 → 本人带码确认 → 投递 → 查看状态”的邮件能力，采用 `chatbot/plugins/kurumi-mail/` 插件，不要求聊天agent执行命令，也不新增MCP进程。当前只支持QQ邮箱465隐式TLS和纯文本正文，可附受管PDF；不提供HTML或IMAP。

邮件仍**仅本人私聊**；整个QQ频道已支持登记成员聊天，不能据邮件限制推断频道只服务本人。各工具先用共享access-control检查真实身份/路由及对应权限，再进入领域策略。成员不继承邮件权限，消息正文或模型参数不能授予身份、收件人或批准。

| 工具 | 功能与边界 |
| --- | --- |
| `email_status` | 默认报告配置是否就绪，不回显凭据；`probe=true`真实连接TLS并认证，但不发信 |
| `email_draft` | 生成预览、草稿ID和后端确认口令；附件只收 `attachments:[{documentId}]`，不接受任意路径/URL/base64 |
| `email_send` | 校验草稿、策略与已记录grant后投递；重复、过期、跨scope授权拒绝；忽略模型提供的approval字符串 |
| `email_outbox` | list/audit/cancel；取消待确认草稿是写入，不是只读。没有flush，投递由email_send异步等待SMTP回执 |

确认通用契约只在文档21展开。邮件的外部副作用不属于数据库事务：**先消费授权、再连接SMTP**，失败需重新确认；SMTP状态未知时不声称送达或自动补发。名单等策略拒绝发生在消费前，不消耗仍有效的授权。服务器接受入队和本人收到分别记录。

- 草稿和审计位于 `state/kurumi-mail/mail.sqlite`，保留payloadHash、提案/grant和投递状态，不记录凭据。日志不含授权码、正文或附件字节。

## 受管 PDF 附件

论文导入、翻译和受管PDF来源归[文档22](22_论文PDF翻译与文件投递.md)；邮件附件完整契约在本节维护。`email_draft`只接受`attachments:[{documentId}]`，不接受路径、URL或base64。

| 契约 | 唯一规则与实现 |
| --- | --- |
| 附件数量与字节上限 | 最多10份，每份非空且不超过10 MiB，总计不超过20 MiB；`store.js`的`MAX_ATTACHMENTS`、`MAX_ATTACHMENT_BYTES`、`MAX_TOTAL_ATTACHMENT_BYTES`校验实际字节 |
| 创建时快照 | 在既有`attachments_json`固定实际字节、文件名、MIME类型、大小、SHA256及受管documentId；预览只展示元数据，不把附件字节交给模型 |
| 确认覆盖范围 | proposal/grant的payload hash绑定规范化To/Cc、主题、正文，以及每份附件的文件名、MIME类型、实际字节数和SHA256；documentId作为来源记录。源文件后来变化不改变已确认草稿 |
| 发送前完整性 | 数据库字节或摘要变化时拒绝发送；仍从已固定快照取件，不重新读取后来变动的源PDF |
| 超限与权限 | 超过邮件限制可在既有QQ文件能力范围投递；不自动扩大邮件限制或开放通用read/exec |

`readAttachments`属于同步Store契约。邮件构建须可被标准MIME解析器还原正文、中文文件名及相同hash附件，不能只检查multipart标记。附件复用既有字段，没有新增SQL迁移；回退须匹配源码、配置和状态，“schema未变”不代表旧代码可安全发送新草稿。代码位于[store.js](../chatbot/plugins/kurumi-mail/store.js)、[service.js](../chatbot/plugins/kurumi-mail/service.js)与[mime.js](../chatbot/plugins/kurumi-mail/mime.js)，确认共享契约归文档21。

## 代理扩展与未完成项

HTTP能力已有受信环境代理与精确host约束；`tls.connect/net.connect`不自动读取HTTP_PROXY。QQ SMTP当前无需新增代理通道，仍保持证书验证。Gmail支持依赖后续非HTTP代理设计：按功能选择HTTP CONNECT或SOCKS5、凭据来自私密平面、有限超时且不旁路既有防护；**尚未实现/验收**。若未来出现第二个消费者，再评估抽取共享能力。

未覆盖实际配额/退信、多收件人真实链路和Gmail代理；IMAP未提出，不作为已承诺待办。新增收件地址须先取得本人授权并修改权威来源，不沿用历史测试授权扩展真实外发对象。

## 权限现状与"触及禁用限制"的处理

当前main仍禁用通用read/write/edit/apply_patch/exec/process/message/sessions_spawn，只能使用受管工具白名单；成员为更窄能力。后续需要扩大能力时，先说明具体权限、可写对象与风险，待本人决定；不绕道其它工具或削减需求后称完成。独立后台agent、窄接口和通用exec是不同授权范围，不能相互替代。开发侧规则只在根[AGENTS.md](../AGENTS.md)维护，运行身份规则见文档24。
