## 背景、需求与工作约定

用户需要一个持久提醒列表，兼顾有 DDL 的日程/作业与没有 DDL 的待办。可以说“帮我在提醒列表里加一条……”“我在提醒列表中 xxx 事项做好了”，助手维护记录并每天汇总。

字段：创建时间、标题必需；内容、备注、DDL 可空。支持修改、手动作废、完成；DDL 到期退出有效列表。已完成、作废、过期不进入后续播报，历史保留。初始每天 **08:00、12:00、18:00、00:00，Asia/Shanghai**；“24:00”统一为次日 00:00。每日时刻、次数可通过修改时刻集合变更，也支持暂停/恢复。

用户举例包括汇报、换届选举、党费整理、党员材料、组会、Web 作业、携带身份证。它们是需求样例，**没有作为真实待办导入**。缺少可确定时间的“下次课前”等需要询问；“越快越好”可直接保存为备注，不捏造 DDL。

用户选择 A：有明确方案即可实施；计划、编码、架构、测试、调整均在本文件记录，维护当前状态快照，不保留冗长的被替代草稿。可自行选择推荐分支并写原因；关键且不能自主决定的方向标为阻塞，等待用户回答，同时可继续其它工作。目标是本文件范围闭环，不止完成第一步。用户开放项目/数据库编辑权限；SQL 留在本地仓库；新增后端脚本放 `chatbot/scripts/`，测试放 `chatbot/tests/`；本任务不新增 archive 文件。

## 已定边界与理由

1. 新建 `personal-reminder-list` 插件，独立领域库；不把“到点单条提醒”与“待办周期汇总”混在同一表。文档 1 的窄领域、确定性后端、最小权限、可审计原则继续适用，不新增通用工作流/DAG/第二套调度宿主。
2. 本人明确的列表维护直接执行。这承接用户认可上一轮方案和一句话追加的需求；现有 `personal_reminder_*` 带码提案/确认规则保留。维护使用本人本次原文与幂等键；已开启的连续上下文仅延续追加，修改/完成/作废/播报设置仍要求本次明确请求。列表内容不成为指令；多候选/缺字段先澄清。
3. 使用 SQLite 保存 `active/completed/void/expired`。自动过期与手工作废区分，以便追溯；无 DDL 不过期。读列表、写入与播报均执行到期判定；后台周期扫描使停机后的状态也能收敛。
4. DDL 支持明确到分钟或仅日期；仅日期表示该日结束（次日 00:00 到期），不虚构一天中的具体时刻。过去 DDL 不新建有效事项。修改终态记录不自动恢复；恢复必须明确发起。
5. 原生 Cron 调用固定脚本，仅汇总/投递本人，不调用模型、不接受任意命令/收件人。时刻集合存领域偏好，初始值来自仓库配置；用户修改后以领域库为准，不由 config 同步覆盖。
6. 有 DDL 排前并按 DDL 升序，无 DDL 按创建时间；空列表跳过。允许不到 2 分钟的短延迟，超过窗口的时段不积压补发；同日同一时刻防重。程序输出与实际 QQ 送达分别记账，未知送达不自动重发。
7. 汇总使用中性“提醒列表”措辞，不写死人格称呼。标题/内容/备注当普通数据，不让模型执行其中的请求。

## 产物与数据契约

### 自然录入与可空 DDL 当前规则

用户七句验收从“你能维护一个提醒列表吗？……需要你定期提醒我”开始，后续六句分别追加选举、组会、党员材料、数学作业、Web 作业、选举后的党费整理。第一句只查询能力/现状，不创建事项或修改播报时间；后六句每句一条。原始七句集中保存在 `chatbot/tests/reminder-list/dialogue-cases.mjs`；它们是测试资料，不导入生产。“帮我加紧提醒列表”在该上下文按“加进提醒列表”的笔误处理，只授予追加，不解释为更高播报频率。“发压缩包到钉钉”仅是作业资料，不授权文件外发。

确定的实施规则：

- 支持“加一个”“加一条”“加到”等当前明确请求。本人明确要求维护并继续逐条提供事项，或成功追加一项后，开启仅追加的连续录入；纯能力询问不写入。后续有明确待办特征的原文可省略列表名，仍不能从旧消息/引用拼接事实。
- 连续录入仅存进程内，在工具执行时绑定宿主上下文的实际 `sessionId`（`reply_dispatch` 在会话初始化前执行，没有可靠 UUID）（SDK 明确说明 `/new`、`/reset` 会更换），10 分钟闲置或 30 分钟总窗口后失效；结束、换题、非追加维护、显式一次性提醒、生命周期重置/结束与服务重启均清除。没有实际 UUID 的宿主不开放隐式追加。当前消息维护授权仍为 5 分钟且单项幂等。
- 当前请求指向列表时，失败须说明原因或澄清；提示词与 `before_tool_call` 同时禁止转成一次性提案或改用自动化任务。原一次性提醒带码确认不变，不新增“最后一起确认”或批量提交。
- “无 DDL”“没有 DDL”“不设置 DDL”保存 `ddl=NULL`、`deadline_ms=NULL`；“越快越好”保留在内容/备注。“活动结束后”“选举后”等条件原文也保留，未给具体截止时间时不能从前一个活动的日期补造 DDL。无 DDL 不过期，继续参加固定时段汇总直到完成/作废。条件不是事件触发器，当前不自动等到活动结束才播报。
- SQL schema v1 已支持上述空值，本轮不增表、不手改生产 SQL。测试先覆盖原文准入与会话失效，再用真实模型、竞争的一次性工具与隔离 OpenClaw 验证；保留初版证据，本轮结果写入同领域 `natural-input/` 分组。

运行产物增加 [intake.js](../chatbot/plugins/personal-reminder-list/intake.js)，只管理原文准入与会话状态，不存第二套待办。DDL/条件检查仍在存储前统一执行。本轮无需 SQL 迁移；初版证据保留，本轮结果集中于 [natural-input/README.md](verification/reminder-list-2026-10-11/natural-input/README.md)。

| 操作 | 规则 |
| --- | --- |
| `get` | 默认仅 active；`history=true` 包含终态；可按标题查询，返回当前时间、设置和调度状态 |
| `add` | 标题必需，内容/备注/DDL 可空；重复 active 标题拒绝；过去 DDL 拒绝 |
| `update` | 查询真实 ID/版本后只改指定字段；null 清除可空字段；终态仍保留原状态 |

| `pause` / `resume` | 保留时刻集合；停/恢复本领域 Cron，普通提醒和天气等任务保留 |

每条维护绑定本人可信原文，5 分钟内有效，一个入站消息维护一项；连续上下文只指明列表目标，不复制旧消息中的事项事实；同参数重试返回已保存结果，不同参数需新消息。标题/内容/备注取原文；模型可解析明确日期，但不可猜测“下次课前”等缺失时间。有效事项上限 100；标题 120 字、内容 800 字、备注 400 字。多人、群聊、Cron/后台会话、引用或网页均不获得写权限。

调度服务每 30 秒收敛到期状态与 Cron 声明；只操作 `kurumi.reminder-list.daily:HH:mm` 且固定命令/路由匹配的任务。失败时保留领域设置、返回 pending 并重试，不声称已生效。固定脚本从领域库读事实，输出完整有效事项；主模型不负责定时文案或投递。

`plugins.entries.personal-reminder-list.config.backendRoot` 由部署配置指定为 `/home/afrangry/kurumi-fusion/chatbot`，程序固定拼接 `scripts/reminder-list.mjs`。缺失、相对路径或找不到固定程序时拒绝注册；不能从模块 `import.meta.url` 推导持久 Cron 路径，因为 OpenClaw 可能从临时捕获目录加载插件。更换部署目录时必须按相同所有权规则审阅并迁移已保存的 Cron payload；前缀相同但不符合所有权的任务仍拒绝接管。

汇总先原子记录 prepared 再输出，回执决定 delivered/failed/unknown；超过 5 分钟仍无匹配回执标 unknown，后续可靠回执可补正状态。全程不自动重发。空列表记录 skipped 并静默。更换设置版本/进程重启仍用同一日期时刻的 slot key 防重。程序输出不保证送达，OneBot/Cron 实际回执才是证据。

### 运维与回退

维护列表/设置通过工具；禁止直接编辑生产 SQL 来修复状态。仅次数无时刻、日期/星期冲突、模糊 DDL、同名目标先澄清。查询链路可使用 `log-query.mjs --source personal-reminder-list --json`；按事项 ID 使用 `--reminder-id`，按本人消息使用 `--message-id`。该适配器读坏库明确失败。
