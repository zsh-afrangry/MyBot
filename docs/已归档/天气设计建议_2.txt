kurumi 天气与个人计划能力：P2 设计建议（评审修订版）

原始讨论：2026-08-06 06:38
最近修订：2026-08-11

======================================================================
一、问题与结论
======================================================================
建议采用“薄架构 + 垂直切片”：
先固定少数稳定边界：领域模块、强类型接口、权限层、数据迁移、测试与审计。
内部实现保持简单，不提前创建大量抽象、空函数和通用框架。
每次只完成一个端到端功能，但新增代码必须放进已有边界，避免临时补丁散落。
出现第二个真实重复场景时再抽象；只有一个用例时不要设计通用框架。
每完成一个阶段安排一次小型重构，不让技术债长期累积。
一句话：提前设计边界，不提前设计所有细节；先做通，再从真实重复中抽象。

主人提出的问题可以概括为：

1. 如果每想到一种自然语言指令，就增加一个工具，机器人是否会变得僵硬？
2. 主人只告诉 kurumi 一段行程、没有提天气时，kurumi 能否自动让天气提醒跟随行程？
3. 这种自然、可组合的行为是否真正可实现，还是必须为每条命令单独写程序？

结论：可以实现，但需要正确划分模型与程序的职责。

  自然语言
      -> 模型提取候选事实和用户意图
      -> 受限工具生成结构化变更计划
      -> 程序完成消歧、校验和确定性策略推导
      -> 向主人显示完整预览
      -> 主人确认
      -> 程序在事务中提交并审计

不需要为每一种说法新增工具，但每一类现实执行能力仍必须有程序接口。模型可以理解
“明天晚一点发”“周日去无锡”“回来后恢复广州”等不同表达，却不能凭空获得修改
数据库、调度任务、发送 QQ、查询航班或操作 Git 的现实能力。

P2 的目标不是让模型自由修改一切，也不是堆积十几个对象专用工具，而是建立少量、
可组合、强类型、可审计且限定领域的个人计划能力。

======================================================================
二、设计原则
======================================================================

1. 不按句子设计工具，按能力域设计工具。

   同一能力的不同说法由模型理解；新的外部能力才需要新的客户端、权限和验收。

2. 通用不等于万能。

   P2 的通用接口只覆盖个人计划域：天气地点、行程、天气提醒时间和通知偏好。
   文件、Git/coder、日历写入、外部消息、智能家居、购买等高风险或不同信任域继续
   使用独立插件、工具或 Agent，不能塞入一个已经获准的万能 change 工具。

3. 模型提交候选事实和请求，程序生成最终 effects。

   模型不得提交任意 action、SQL、URL、命令、Cron 参数、收件人或数据库字段。
   程序从封闭的类型集合中生成规范化 effects、预览和 Hash。

4. 写入默认需要主人确认。

   P2 第一版的行程、地点、提醒时间和策略修改全部执行：

     propose -> 回显预览 -> 主人明确确认 -> commit

   “临时”或“可撤销”不等于低风险。错误地点可能泄露行程或错发天气，错误时间也
   可能导致漏提醒，因此第一版不启用自动提交。

5. 策略引擎负责跨功能联动。

   模型负责判断“这是不是主人的真实行程、信息是什么”；程序负责确定性执行
   “已确认行程如何影响天气地点和旅行日简报”。不能依赖模型每次都记得补充关联
   effects。

6. 按垂直切片开发。

   每一阶段都交付一个可测试、可回滚的完整能力。可以在文档里列未来接口，但不要
   先写大量空函数、空 Service 或未使用的工具骨架；那会过早固化错误抽象。

======================================================================
三、能力边界与插件归属
======================================================================

现有 `personal-weather` 保持以下职责：

- 固定 QWeather Host 的只读查询；
- 获取当前有效地点；
- 生成确定性天气简报；
- 继续暴露只读工具 `personal_weather_get_brief`。

P2 的个人计划能力可先在同一代码仓内开发，但模型可见接口必须限定在
weather/trip/reminder 这一信任域。若以后它需要服务日历、健康、财务等更多领域，
再评估抽成独立的 `personal-planning` 或 `personal-core` 插件；不要现在为了形式完整
提前拆成多个空插件。

建议的 P2 模型工具面：

1. `personal_planning_state_get`

   只读当前个人计划状态。输入只能选择受控 section 和时间范围，例如：

     {
       "sections": ["weather", "trips", "reminders"],
       "horizon_days": 30
     }

   不接受 subject_id、任意 SQL、路径或原始表名。subject 固定由可信主人私聊上下文
   注入。默认只返回最小摘要，不返回原始私聊、精确住址、完整票号/PNR 或审计流水。

2. `personal_planning_change_propose`

   接收强类型的候选事实/请求，生成不可变 proposal。模型不能直接提供最终 effects。
   示例输入形态：

     {
       "schema_version": 1,
       "requests": [
         {
           "kind": "trip.upsert",
           "client_ref": "trip-1",
           "destination_text": "江苏省无锡市",
           "transport_mode": "unknown",
           "arrival": {
             "earliest": "2026-08-16T17:00:00+08:00",
             "latest": "2026-08-16T18:00:00+08:00",
             "precision": "window",
             "timezone": "Asia/Shanghai"
           },
           "return": null
         }
       ]
     }

   插件应进行地点消歧、时间/时区校验、权限检查和策略计算，并返回：

     proposal_id
     status
     missing_fields
     canonical_facts
     derived_effects
     warnings
     preview_text
     requires_confirmation
     expires_at

   任意未知 kind、额外字段、超长数组、过远日期、重叠时间段或不受支持的 effect 都要
   拒绝，不能因为 payload 是合法 JSON 就接受。

3. `personal_planning_change_commit`

   只接收：

     { "proposal_id": "..." }

   commit 时必须再次验证主人私聊、pending 状态、TTL、payload Hash、策略版本、所有
   base revision、幂等键和数据库约束。不能在 commit 参数里临时修改 proposal。

4. `personal_planning_change_discard`

   只用于丢弃尚未提交的 pending proposal。

   已经提交的行程、地点覆盖、提醒或偏好不能通过 discard 直接删除。取消或修改已
   提交事实本身是一项新变化，必须重新 propose、预览、确认和 commit，以保留审计、
   并发检查和补偿语义。

为什么不使用无限扩张的 `personal_change_*`：OpenClaw 的权限通常以工具为边界。
如果一个已授权的通用工具以后加入 Git、文件、购买或任意外发能力，会在不新增工具
授权的情况下扩大实际权限。因此“通用”只能存在于事先定义好的低风险能力域内。

======================================================================
四、事实、策略、动作三层
======================================================================

第一层：候选事实与已确认事实

模型从自然语言提取的是 candidate，不应立刻称为真实事实。至少区分：

- mentioned：对话中出现，可能只是例子、假设或他人的行程；
- proposed：主人明确想记录，已生成预览但尚未提交；
- committed：主人确认并通过事务写入；
- superseded/cancelled：后来被新的已确认变化替代或取消。

来源和时间精度必须保留。地点应先消歧到受控 place_id；时间保存 UTC，同时保留原始
时区、earliest/latest 和 precision。诸如“周日”“下午”“下周回来”不能伪装成精确
到达时刻。

第二层：长期策略

策略表示主人预先授权的稳定关联规则，而不是每条指令。例如：

     {
       "schema_version": 1,
       "weather": {
         "follow_confirmed_trips": false,
         "switch_basis": "confirmed_arrival",
         "travel_day_mode": "off",
         "temporary_changes": "confirm",
         "permanent_changes": "confirm",
         "ambiguous_changes": "ask"
       }
     }

初始值应保守：`follow_confirmed_trips=false`，由主人通过 proposal 明确开启；所有写入
仍需确认。策略自身也有 revision、审计和查看/撤销入口，不能藏在系统提示词或由模型
直接修改配置文件。

以后运行稳定并完成审计、幂等、补偿和权限负测后，可以让主人对非常窄的操作授予
standing consent，例如“未来 30 天内、明确到达时刻的已确认本人行程，可以自动生成
临时天气位置覆盖”。授权必须限定 operation、期限、范围和撤销方式，不能笼统写成
`auto_for_reversible_changes`。

第三层：确定性动作

程序内部通过固定 action registry 执行：

- trip.upsert / trip.cancel；
- location.override / location.restore；
- reminder.schedule.override；
- notification.preferences.update；
- audit.append / outbox.enqueue。

这些内部 action 不全部暴露为模型工具，也不能接受任意字符串。每个 action 都有独立
Schema、业务校验、事务处理、权限等级和测试。

======================================================================
五、只说行程，天气自动跟随的正确流程
======================================================================

该体验可以实现，但必须满足两个前提：

1. 主人已经明确开启 `follow_confirmed_trips` 策略；
2. 行程已经 committed，且目的地与到达时刻精度足以安全切换。

示例：“我周日去无锡，下周回来。”

这句话说明可能存在真实行程，但没有明确到达时刻、返回日期和返回时刻。第一版应：

  模型识别候选行程
      -> propose 返回 missing_fields
      -> kurumi 追问必要信息
      -> 回显完整 trip 与天气影响预览
      -> 主人确认
      -> commit

不能把“出发时间”当成“到达时间”。例如“明天下午两点去深圳”通常更像出发时间，
在不知道行程时长或实际到达时间时不能于 14:00 直接切到深圳天气。

信息完整并确认后的事务：

  写入 planned trip
      + 由后端策略引擎派生 location_period
      + 写入 audit_log
      + 写入 outbox event

建议让 trip 与派生的 location_period 在同一 SQLite 事务中提交，或把待处理事件写入
同一事务的 outbox。不要仅依赖易丢失的进程内 `trip.created` 事件，否则可能出现行程
已经保存、天气地点却没有切换的半完成状态。

天气任务每次运行都按可信系统时间读取当前 effective place，因此到达时不需要模型
修改提示词、MEMORY.md 或 Cron；location_period 到点后会自然生效，结束后自然回退
默认地点。

仅日期级或未知到达时刻的 tentative trip 可以保存，但不能派生自动位置切换。旅行日
可先使用主人确认的双城简报，等到达信息足够精确后再启用切换。

======================================================================
六、动态提醒时间与 Cron 的缺口
======================================================================

当前每日天气 Cron 固定为 `30 10 * * *`、`Asia/Shanghai`。SQLite 中虽然已有默认提醒
分钟等偏好字段，但只修改数据库不会让固定 Cron 自动改到 14:00。

因此，在支持“明天下午两点发”“未来一周晚点提醒”“周末改下午”等自然语言请求前，
必须先实现调度桥梁。两种可选方案：

A. 固定频率 dispatcher

- 由 operator 创建一个固定、隔离、无 LLM 的 command Cron；
- 程序读取 DB 中的 next_due、临时覆盖和时区；
- 使用事务 claim、event key 和幂等记录判断本分钟是否应发送；
- 未到期时不请求天气、不发送 QQ；
- 到期时才查询天气并投递。

B. 受信任 reconciler

- 数据变化后由受信任程序计算下一次运行；
- 幂等维护一个或多个 one-shot Cron；
- 模型只能写 proposal，不能获得 Cron 管理能力。

P2 建议优先使用 A，逻辑更集中，容易测试和恢复；具体轮询粒度应在实现前评估本机
开销与时间精度。无论采用哪种方案，都要定义：

- 时区与 DST；
- 停机后的补发窗口；
- 重复启动和并发锁；
- next_due 重算；
- 投递失败重试与去重；
- 临时覆盖结束后的恢复规则；
- declaration key 和回滚方式。

在 dispatcher/reconciler 验收前，继续保留已上线的每天 10:30 固定任务，不开放自然
语言修改提醒时间，也不让模型直接编辑 Cron。

======================================================================
七、现有 Schema 与建议的 v2 迁移
======================================================================

现有数据库已经提供良好基础：

- places；
- trips；
- location_periods；
- notification_preferences；
- change_proposals；
- notification_state；
- audit_log 与 api_cache。

但它目前只是预留结构，不是已经可用的通用变更系统。当前 `change_proposals.kind`
表示一个单一变化，base/result entity 也是单数；WeatherStore 还没有 proposal、commit、
TripService、LocationService 或 PolicyEngine 的业务方法。

建议通过正式迁移增加或调整：

1. proposal schema/version

   保存 proposal_schema_version、policy_revision、owner/session binding、request hash、
   idempotency key、expires_at 和状态。

2. proposal_operations

   每个 proposal 包含有序、强类型的多个 operation；每项保存 kind、规范化 payload、
   base entity/revision 和 Hash。也可暂时使用严格验证的 operations_json，但不能只做
   `json_valid` 后直接执行。

3. proposal_results

   记录一个 proposal 产生的多个实体或 effect，避免单一 result_entity 无法表达
   trip + location_period + schedule override。

4. automation_policies

   保存版本化策略和主人授权；不进入系统提示词或长期记忆。

5. schedule_overrides / notification_jobs

   表达临时提醒时间、next_due、claim lease、attempt、投递状态和幂等键。

6. outbox_events

   在事实提交事务中可靠记录需要异步处理的派生动作或通知，避免进程崩溃造成半完成。

所有迁移都必须有向前测试、旧库备份/恢复办法、事务回滚和权限检查。单机单主人阶段
继续使用 SQLite 即可，不需要 MySQL、MongoDB 或向量数据库。

======================================================================
八、安全、隐私与可靠性要求
======================================================================

1. 新状态和写工具只允许可信主人 QQ 私聊；群聊必须在工具准入前显式 deny 并负测。
2. subject_id、QQ 目标和 owner 身份只能从可信配置/通道元数据注入，不能由模型传入。
3. `personal_planning_state_get` 默认最小披露，不返回精确住址、票务凭证、原图、完整
   私聊、原始 source_summary 或无界审计历史。
4. proposal 输入使用版本化 discriminated union、`additionalProperties=false`、操作数、
   字符串长度、日期跨度和 payload 大小限制。
5. commit 必须校验 pending、TTL、Hash、policy revision、base revisions 和幂等状态，并
   在一个事务中提交；重复 commit 返回原结果，不能重复创建记录。
6. 取消已提交事实使用补偿 proposal，不物理删除历史；用户要求删除隐私数据时走单独
   的保留/删除策略。
7. QQ 收件人不来自 proposal；发送动作是调度器/策略引擎内部能力，不暴露通用 send。
8. facts、派生 effects、audit 和 outbox 同事务写入；后台处理使用 claim lease、稳定
   event key、有限退避和 dead-letter/failed 状态。
9. 新的航班、日历、智能家居或搜索能力分别使用固定 Host、路径和方法的客户端，单独
   评估凭证、网络和数据边界；通用 change 工具不得接受 URL、header、命令或 SQL。
10. API Key 继续只通过 SecretRef/header 使用，禁止进入 proposal、数据库、提示词、
    文档和日志。

======================================================================
九、什么时候需要新代码
======================================================================

同一能力的不同说法：通常不需要新工具。

  “明天两点发”
  “明天下午再告诉我天气”
  “明天晚一点提醒我”

它们可以由同一个强类型提醒时间变更表示。

已有动作的新组合：通常不需要新模型工具，但可能需要增加确定性策略。

  确认行程 -> 天气跟随目的地
  旅行日 -> 出发地与目的地双城简报
  临时提醒结束 -> 恢复默认提醒时间

新的外部能力：必须开发独立接口并重新授权。

  查询航班是否延误
  读取单位日历
  控制空调
  修改 Git 项目
  购买机票或修改座位

模型可以智能组合已经存在的能力，但不能凭空创造未接入的现实能力。

======================================================================
十、建议的分阶段开发路线
======================================================================

P2A：只读状态与 proposal 预览

- 定义个人计划域的 action/type registry；
- 设计并测试 Schema v2 迁移；
- 实现 `personal_planning_state_get`；
- 实现 `personal_planning_change_propose`，但暂不提供 commit；
- 对真实行程、假设、他人行程、转发内容、模糊地点/时间和跨时区做测试；
- QQ 私聊验收 proposal 预览；允许写入受限的 `change_proposals.pending` 草稿，但确认
  不写入 trips、location_periods、notification_preferences 等业务事实表。

P2B：显式确认与事务提交

- 实现 commit/discard、TTL、Hash、revision、幂等和审计；
- 所有写入要求主人明确确认；
- 群聊、非主人、过期 proposal、篡改 payload、重复提交和并发冲突负测；
- 先支持一种完整变化，例如“创建/修改 tentative trip”，再扩展其他 operation。

P2C：行程与天气的确定性联动

- 新增并由主人确认 `follow_confirmed_trips` 策略；
- commit planned trip 后，在同一事务或 outbox 中派生 location_period；
- 到达/返回、半开区间、重叠、取消、延误、日期级时间和跨时区测试；
- 再加入旅行日双城简报；仍不启用自动 commit。

P2D：动态提醒调度

- 实现 dispatcher 或 reconciler；
- 支持一次性、临时区间、永久时间和恢复默认值；
- 完成停机补发、并发、重复投递、时区和回滚测试；
- 验收后再开放自然语言修改提醒时间。

P3：主动天气通知

- 官方预警优先；
- 再开发临近降雨与个人高温规则；
- 使用 notification_state/outbox 去重、冷却和失败恢复；
- 无新事件时不调用模型、不向 QQ 发送内容；
- 启用前确认安静时段、哪些官方预警可突破安静时段和个人阈值。

P4：图片与航班

- 单独验收 QQ 图片输入、OCR/图像理解与隐私保留；
- 机票识别只生成 proposal，主人确认后 commit；
- 航班状态 API 作为独立外部能力评估，不因已有天气网络权限自动获得联网。

======================================================================
十一、对下一步方向的明确建议
======================================================================

下一步建议继续完善天气模块，但重点不再是增加天气接口，而是开发与天气紧密相邻的
P2“个人计划状态 + 最近出行 + 地点时间线”能力。

理由：

1. P1 天气查询和 10:30 推送已经形成可工作的垂直闭环；P2 可以直接复用现有 places、
   trips、location_periods、notification_preferences 和 change_proposals 基础。
2. 这是主人已经明确提出的真实需求，能够验证长期记忆之外的结构化事实、确认式写入、
   策略联动和时间生效机制，是以后日历、提醒等模块的公共基础。
3. 开放搜索会增加通用网络、来源可信度、引用、隐私和提示注入风险，却不能解决状态
   修改、行程确认、调度和跨功能联动的核心问题，因此不应作为紧接 P1 的下一项。
4. 并列创建大量只有空函数和列表的新模块会制造“看起来架构完整、实际没有一项可用”
   的假进度，并可能过早固定错误接口。未来能力可以先写在路线图和 capability registry
   中，但代码继续按一个可运行的垂直切片逐项实现。

P2A 的本地垂直切片已经完成，当前等待 Gateway 可运行后做 QQ 私聊回归；下一步仍是
P2B，而不是开放搜索或铺设空模块。

此前推荐的 P2A 端到端切片是：

  主人自然语言描述行程
      -> kurumi 生成强类型 proposal 预览
      -> 明确指出缺失/歧义字段
      -> 只写 pending proposal 草稿，不写业务事实表

P2A 验收后再实现 commit。这样既能让 kurumi 开始表现出“理解事实并规划影响”的智能，
又不需要立即开放写权限或自动提交。

搜索功能建议放在个人计划 P2B/P2C 稳定之后，作为独立能力开发；coder/Git、文件和
其他高风险能力继续保持独立 Agent/插件与逐项授权。

======================================================================
十二、P2A 验收标准
======================================================================

只有同时满足以下条件，P2A 才算完成：

1. 运行时新增的读取/propose 工具数量、Schema 和权限边界可审计；群聊明确拒绝。
2. 只允许主人私聊；消息正文不能伪造 owner 身份。
3. 真实行程、示例、假设、他人行程和普通城市讨论能够正确区分。
4. 当前 P2A 对地点保留 `resolution=pending` 和缺失字段；地点消歧候选属于 P2B，
   模糊时间保留 earliest/latest/precision，不擅自精确化。
5. proposal 返回 canonical facts、derived effects、完整预览、警告、TTL 和 payload Hash。
6. P2A 没有 commit 工具，运行前后 trips、location_periods、preferences 均不变化。
7. 不修改 Cron、系统提示词、MEMORY.md、USER.md 或配置文件来保存动态事实。
8. 不开放通用 Web、任意 HTTP、文件、exec、sudo、Cron 管理或 coder 能力。
9. 正常、篡改、越权、超长 payload、并发、过期和重放测试通过。
10. 文档、回滚步骤、能力声明和 QQ 私聊端到端测试同步更新。

达到以上标准后，再决定 P2B 的第一个可提交 operation；推荐从 tentative trip 开始，
不要一次同时开放行程、地点、提醒和策略的全部写入。
