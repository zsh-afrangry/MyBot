智能体能力、控制与编排分层设计讨论整理
整理日期：2026-08-11

======================================================================
一、背景与目标
======================================================================

当前正在逐步搭建一个通过 QQ Bot 与 OpenClaw 交互的个人智能体。

已经开始落地的能力包括天气模块，后续还设想继续加入论文搜索、代码仓库维护、
股票查询等能力。

当前重点不是一次性把“完整智能体操作系统”全部做完，而是先把底层能力与控制方式
设计清楚，避免未来每增加一个功能，就再增加一整套专用工具，导致系统越来越僵硬。

这次讨论的核心问题是：

1. 智能体是否必须“一个功能对应一套工具”？
2. 天气、论文、代码仓库、股票等不同能力，如何与“立即执行、定时执行、
   暂停/禁止执行”等控制方式解耦？
3. 是否应该现在就实现复杂的多 Step Workflow？
4. 如何让当前单元能力设计，为以后多 Step 编排留下自然的扩展空间？


======================================================================
二、最初的总体设想
======================================================================

原始设想是把智能体任务抽象为若干维度的组合：

任务 =
能力
× 操作
× 目标
× 触发方式
× 执行策略
× 权限策略
× 投递方式

示例：

论文
× 搜索与总结
× AI 安全领域
× 立即执行
× 结果保存
× 自动允许
× 下午 4 点 QQ 投递

代码仓库
× Git push
× town 仓库
× 立即执行
× 测试通过后执行
× 必须确认
× QQ 返回结果

天气
× 每日简报
× 当前有效地点
× 每天 10:30
× 正常执行
× 暂停直到显式恢复
× QQ 投递

进一步设想的目标架构包括：

Capability Registry        能力注册表
Action Plan / Plan IR       统一任务计划
Policy Engine               策略与权限引擎
Workflow Orchestrator       工作流编排器
Scheduler                   时间与事件调度器
Command Bus                 动作分发器
Domain Adapters             领域工具适配器
State Store                 状态和审计存储

完整流程设想：

用户自然语言
→ LLM 生成 Plan IR
→ Policy Engine 审核
→ Scheduler 确定何时运行
→ Orchestrator 解析依赖
→ Command Bus 分发动作
→ Domain Adapter 真正执行
→ State Store 记录结果
→ Messaging Adapter 反馈用户


======================================================================
三、对“每个功能都加一套工具”的担心
======================================================================

一个重要担心是：

如果每想到一种操作，就新增一个专用工具，例如：

weather_change_time
weather_change_location
weather_disable
paper_schedule
paper_disable
stock_schedule
stock_disable
repo_schedule
repo_disable

那么最后虽然外层有 LLM，但系统本质上仍然像一个传统菜单程序：

用户自然语言
→ 模型识别意图
→ 匹配某个预先写好的按钮/函数

这种设计的问题是：

1. 工具数量会随着“功能 × 控制方式”快速膨胀；
2. 不同领域会重复实现“定时、暂停、恢复”等相同逻辑；
3. 新增能力时需要复制大量控制代码；
4. 多功能组合越来越难维护；
5. 智能体的“组合能力”无法真正体现出来。

因此，后续设计应避免：

“每个自然语言命令 = 一个工具”

更合理的是：

“每一类现实执行能力 = 一个领域能力”
+
“时间、权限、状态、投递 = 通用控制能力”


======================================================================
四、关键原则：智能体可以组合已有能力，但不能凭空创造现实能力
======================================================================

需要明确一个边界：

模型可以非常灵活地理解自然语言、提取参数、组合已有能力、生成计划。

例如同一个天气能力可以理解：

“明天两点再告诉我天气”
“以后天气都下午三点发”
“明天不要发天气”
“后天恢复”
“我去无锡以后天气按无锡算”

这些不同说法不需要分别开发一个自然语言接口。

但是，如果系统从未接入某类现实能力，模型无法凭空做到：

- 查询真实天气；
- 搜索论文数据库；
- Git push；
- 修改代码仓库；
- 查询股票 K 线；
- 控制空调；
- 修改机票；
- 读取某个外部账号。

所以真正需要开发的是：

“现实能力接口”

而不是：

“每一句自然语言指令对应的函数”。


======================================================================
五、能力层与控制层应该解耦
======================================================================

以未来四类能力为例：

1. weather.get_brief
2. paper.search
3. repo.commit / repo.push
4. stock.get_kline

这些属于“领域能力”。

而下面这些不应该分别写成天气版、论文版、股票版：

- 立即执行
- 定时执行
- 暂停
- 禁止
- 恢复
- 是否需要确认
- 执行成功后如何投递

这些应该是横向的通用控制逻辑。

因此，结构可以理解为：

                   ┌──────── 天气
                   ├──────── 论文
领域能力 ----------├──────── 代码仓库
                   └──────── 股票
                         │
                         ▼
                  通用 Action 模型
                         │
              ┌──────────┼──────────┐
              ▼          ▼          ▼
          Scheduler   Policy      State
          时间控制     权限控制     状态控制


例如：

“下午 4 点查询 AI 安全论文”

不应该存在：

paper_search_at_4pm()

而应该表示为：

Action:
    capability = paper.search
    target = AI 安全

Trigger:
    type = at
    time = 16:00

即：

Scheduler.schedule(Action)


同样：

“禁止天气推送直到我下次允许”

不应该存在：

weather_disable_until_resume()

而应该是某个状态/策略：

capability = weather.daily_brief
enabled = false
resume_condition = explicit_user_enable


======================================================================
六、当前阶段不建议直接实现完整 Workflow Orchestrator
======================================================================

一个例子是：

“查阅相关领域论文，并在下午 4 点时向我推送。”

这实际上可能包含多个 Step：

Step 1：搜索论文
Step 2：整理/总结结果
Step 3：保存结果
Step 4：下午 4 点发送 QQ

如果现在立刻围绕这个例子开发完整 Workflow，很容易提前引入：

- Step 定义
- depends_on
- DAG
- 中间结果传递
- 失败重试
- 部分成功
- 超时
- 并行执行
- 回滚
- on_success
- on_failure
- Workflow 状态机

这会让第一阶段过度复杂。

当前已经达成的建议是：

现在先不要开发完整的 Workflow Orchestrator。

先把“单元工作”做好。


======================================================================
七、当前阶段应该优先实现的内容
======================================================================

当前阶段优先完成三个核心概念：

1. Action
2. ActionResult
3. Scheduler 能够引用并触发 Action

最简结构：

LLM
 ↓
Action
 ↓
Capability Adapter
 ↓
ActionResult

横向增加：

Scheduler
State Store


----------------------------------------------------------------------
7.1 Action
----------------------------------------------------------------------

Action 表示“要执行什么”。

例如天气：

{
  "action_id": "a001",
  "capability": "weather.get_brief",
  "target": {
    "place": "current_effective_place"
  }
}

论文：

{
  "action_id": "a002",
  "capability": "paper.search",
  "target": {
    "topic": "AI 安全"
  }
}

Git：

{
  "action_id": "a003",
  "capability": "repo.push",
  "target": {
    "repo": "town"
  }
}


----------------------------------------------------------------------
7.2 ActionResult
----------------------------------------------------------------------

建议现在就统一每个原子能力的返回结果格式。

天气示例：

{
  "action_id": "a001",
  "status": "success",
  "result_type": "weather_brief",
  "result_ref": "result://a001",
  "summary": "广州天河今日天气……",
  "created_at": "..."
}

论文搜索：

{
  "action_id": "a002",
  "status": "success",
  "result_type": "paper_search_result",
  "result_ref": "result://a002",
  "summary": "找到 12 篇相关论文",
  "created_at": "..."
}

Git 提交：

{
  "action_id": "a003",
  "status": "success",
  "result_type": "git_commit",
  "result_ref": "git://repo/town/commit/abc123",
  "summary": "提交成功",
  "created_at": "..."
}

统一 ActionResult 的意义非常大。

未来多 Step 工作流需要传递的，不应该是某个插件内部的私有变量，而应该是标准化结果。


======================================================================
八、为什么 ActionResult 对未来多 Step 很重要
======================================================================

例如：

“现在帮我查 AI 安全论文，下午 4 点把刚才查到的结果发给我。”

正确逻辑应该是：

Step 1
paper.search
→ ActionResult R1

Step 2
16:00
message.send(result_ref = R1.result_ref)


下午 4 点时不应该重新执行：

“再查一遍 AI 安全论文然后发送”

而应该发送：

“之前已经查到并保存的结果”。

所以：

ActionResult / result_ref

就是当前“单元能力”和未来“多 Step Workflow”之间最重要的接口之一。


======================================================================
九、区分两种看起来相似但实际不同的任务
======================================================================

例 1：

“下午 4 点查一下 AI 安全论文。”

这仍然是一个单 Action：

Trigger = 16:00
Action = paper.search

Scheduler 到时间后执行 Action。

不需要 Workflow。


例 2：

“现在查 AI 安全论文，下午 4 点把结果发给我。”

这是两个 Action：

Step 1:
paper.search

Step 2:
message.send(previous_result)

其中 Step 2：

- 依赖 Step 1 的结果；
- 有自己的触发时间；
- 需要引用 Step 1 的 result_ref。

这才是真正的多 Step Workflow。

======================================================================
十一、未来再逐步增加的 Workflow 概念
======================================================================

当天气、论文、代码仓库、股票等原子能力已经稳定后，再引入：

Plan
Step
depends_on
input_from
on_success
on_failure

未来可以扩展为：

Plan
 ├── Step 1: paper.search
 │       ↓
 │    result_ref
 │
 ├── Step 2: paper.summarize
 │       depends_on = Step 1
 │       input_from = Step 1.result_ref
 │
 └── Step 3: message.send
         depends_on = Step 2
         trigger = 16:00
         input_from = Step 2.result_ref


到那时 Workflow Orchestrator 的职责才真正明确：

1. 管理 Step 之间的依赖；
2. 决定哪些 Step 已经可以执行；
3. 把上一步结果传给下一步；
4. 处理成功/失败关系；
5. 与 Scheduler 配合处理时间条件。


======================================================================
十二、关于“执行、定时执行、禁止执行”三个设想
======================================================================

原设想中希望抽象三个通用操作：

1. 执行操作
2. 定时执行操作
3. 禁止执行操作

这个方向是成立的，但建议不要把三者都理解成同一级别的“工具”。

更准确地说：

执行操作：
    由 Capability Adapter 完成。

定时执行：
    由 Scheduler 控制 Action 的触发时间。

禁止执行：
    由 Policy / State 控制某类 Action 当前是否允许执行。

也就是说：

“做什么”
和
“什么时候做”
和
“允不允许做”

应该是三个正交维度。


示例：

天气每日简报

Capability:
    weather.daily_brief

Trigger:
    cron 10:30

Policy / State:
    enabled = false

此时 Scheduler 即使到了 10:30：

Policy 检查
→ 当前禁止
→ 不执行


股票：

Capability:
    stock.get_kline

Trigger:
    immediate

Policy:
    read_only
    auto_allow


Git push：

Capability:
    repo.push

Trigger:
    immediate

Policy:
    require_confirmation = true
    precondition = tests_passed


这样就形成真正的组合能力。

十三、目前推荐的开发顺序
======================================================================

第一阶段：原子能力

逐个实现并验收：

weather.get_brief
paper.search
repo.commit
repo.push
stock.get_kline

要求：

- 输入结构化；
- 输出结构化；
- 可单独测试；
- 可审计；
- 不依赖 Workflow。


第二阶段：统一控制

实现：

Action
ActionResult
State Store
Scheduler
基础 Policy

目标：

- 任意 Action 可以立即执行；
- 任意 Action 可以定时执行；
- 某类 Action 可以暂停/恢复；
- ActionResult 可以保存和引用。


第三阶段：领域扩展

继续增加新的原子能力，而不是先做复杂编排。


第四阶段：Workflow

当出现越来越多真实的多 Step 需求以后，再加入：

Plan
Step
depends_on
input_from
on_success
on_failure


第五阶段：更高级的智能体系统

再继续考虑：

- 用户习惯；
- 长期记忆；
- 偏好；
- 联想触发；
- 自动推导关联任务；
- 历史行为学习；
- Prompt 优化；
- Context 管理；
- Workflow 自动生成；
- Plan IR；
- 更完整 Policy Engine；
- Capability Registry。

十四、关于“旅行后自动改变天气”的问题
======================================================================

这个问题目前暂时不作为本阶段重点。

未来可以实现：

用户只说：
“我周日去无锡。”

智能体识别：
这是一个本人真实行程。

保存：
Trip

根据用户长期策略：

weather_follow_confirmed_trips = true

自动派生：

到达无锡后
→ weather 当前有效地点切换为无锡

返回后
→ 恢复原地点


这一部分更接近：

- 用户习惯；
- 历史记忆；
- 偏好；
- 联想；
- 规则推导；
- 工作流和提示词工程。

因此当前阶段不展开。

先把：

“Action 能执行”
“Action 能被调度”
“Action 能被禁止”
“ActionResult 能被引用”

这些基础打稳。


======================================================================
十五、当前阶段最重要的设计结论
======================================================================

结论 1：

不要把“每一句自然语言指令”映射成一个工具。

模型负责理解自然语言，
工具负责提供现实世界能力。


结论 2：

不要为每个领域分别开发：

schedule
disable
resume

这些应该属于通用控制层。


结论 3：

当前阶段不用急着实现复杂 Workflow。

“下午 4 点执行某个动作”
仍然只是：

Scheduler + Action。


结论 4：

真正的多 Step 是：

一个动作的结果成为另一个动作的输入，
或者多个动作之间存在依赖关系。


结论 5：

现在就应该统一：

Action
ActionResult
result_ref

这样以后增加 Workflow 时不需要推倒重来。


结论 6：

领域能力、触发方式、权限状态应该正交：

Capability
× Trigger
× Policy


结论 7：

目标不是不断增加工具数量，
而是提高：

- 工具的组合性；
- 状态模型的通用性；
- 控制层的复用能力；
- 后续工作流的可编排性。

十六、现阶段推荐保留的目标架构
======================================================================

长期目标仍可保留：

自然语言层
    ↓
意图解析与计划器
    ↓
统一任务计划 Plan IR
    ↓
策略引擎 / 权限检查
    ↓
工作流编排器
    ↓
调度器 + 命令总线
    ↓
各领域能力插件
    ↓
状态和审计存储

但是当前开发不需要一次全部实现。

当前实际版本可以先是：

自然语言
    ↓
LLM
    ↓
Action
    ↓
Policy Check
    ↓
Capability Adapter
    ↓
ActionResult
    ↓
State Store

Scheduler 独立负责：

时间条件满足
    ↓
取出 Action
    ↓
Policy Check
    ↓
执行


等单元能力足够稳定以后，再自然升级成：

自然语言
    ↓
Plan
    ↓
多个 Step
    ↓
Workflow Orchestrator
    ↓
Scheduler / Policy / Capability
    ↓
ActionResult 在 Step 之间传递


======================================================================
十七、一句话总结
======================================================================

现阶段不要为了“查论文后下午 4 点发送”这个多 Step 示例，提前把整个工作流系统
做复杂。

先把每个能力做成可靠的原子 Action，并统一 ActionResult，让 Scheduler 能够调度
任意 Action，让 Policy / State 能够暂停或禁止任意 Action。

等这些基础稳定以后，再增加 Plan、Step、依赖关系和结果传递。

这样既不会退化成“一个命令一个工具”的传统程序，也不会过早进入复杂的工作流
系统设计。
