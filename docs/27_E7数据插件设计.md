# E7数据插件设计

类型：数据插件设计（仅方案）。状态：**方案，未实施**；仓库无插件代码，生产未加载，未向E7·WIKI发出生产请求。更新：2026-10-26。入口：[文档目录](README.md)。

## 背景与范围

主人希望QQ助手能回答《第七史诗》（Epic Seven）的角色、神器、技能和兑换码等问题，数据来自 [E7·WIKI](https://e7.wiki/)。wiki内容会随游戏版本更新，一次性下载会过时，每次提问都实时抓取又慢且依赖对方站点稳定性。本文采用混合方案：变化慢的资料按日条件刷新到本地缓存，变化快的资料按需实时查询并短时缓存。

纳入范围：

- 角色卡片、别名/昵称检索、单个角色详情（技能、属性、专属装备、记忆印记）。
- 神器列表与详情。
- 兑换码与公告、更新日志（先核实接口后再纳入）。

不纳入范围：

- 站点的任何写接口（点赞、计数、心愿、评论、提交测评等），也不登录。
- 用户个人账号或战绩数据。
- RTA对战统计（`rta-api.e7.wiki` 有限流，需单独评估）。
- 把wiki数据批量复制进仓库或作为训练、再分发材料。

排期与下一步唯一归[待办 N20](待办清单.md#n20)。

## 数据来源事实（2026-10-26只读核对）

E7·WIKI是Vue/Vuetify单页应用，前端axios的baseURL为 `https://admin.e7.wiki/api`。公开读取接口在 `/open/...` 下，无需登录。普通接口返回 `{code:1000,message:"success",data}`，`hero_summary/hero-list` 直接返回数组。站点没有公开的API文档或数据许可；关于页说明站点非营利，游戏素材版权归官方。

2026-10-26只用GET读取下列接口，各取一次样本，未调用写接口：

| 接口 | 大小 | 缓存头 | 内容 | 用途 |
| --- | --- | --- | --- | --- |
| `GET /open/epicseven/hero/card-list` | 约97KB | 无ETag | id、code、name、昵称、属性、职业、星级、星座、上线时间、update_time | 角色索引、别名检索 |
| `GET /open/epicseven/hero_summary/hero-list` | 约743KB | ETag；`private, must-revalidate` | 增益/减益、其他加成 | 按效果筛选 |
| `GET /open/epicseven/artifact/artifact-list` | 约322KB | ETag、Expires；带If-None-Match时返回304 | 神器列表与效果 | 神器检索 |
| `GET https://assets2.e7.wiki/static/heroes/<code>.json` | 每份约6KB | etag、last-modified | 技能、属性、专属装备、记忆印记、故事、语音等 | 单角色详情 |

前端代码中还能看到下列接口，**均未请求核实**，纳入前须逐个确认参数、响应和缓存头：

- `hero_equipment_scheme/getSchemeByHeroCode`（POST，参数 `hero_code`，配装方案）。
- `chaos_fate/*`、`hero_review/*`、`updates/*`、`gvg_defense/*`。
- 强度榜、兑换码列表与最新兑换码、公告、攻略、FAQ、礼包、道具词典、字典。
- RTA接口 `https://rta-api.e7.wiki/api/v1`（核对时遇到429限流）。

连接偶发TLS中断。核对时绕过本机代理并重试才取得样本；插件实施时须按[文档20](20_邮件能力与横切扩展.md)的可信环境代理与精确主机约束重新验证连通性，不默认绕过代理。

接口没有稳定性承诺，字段和路径可能随前端改版变化。实施前、启用前都要重新核对，本节日期只代表当次结果。

## 混合刷新策略

按数据变化频率分为两档：

| 档位 | 数据 | 获取方式 | 新鲜度 |
| --- | --- | --- | --- |
| 慢变 | 角色卡片、效果汇总、神器列表 | 每日一次条件刷新到本地缓存 | 最长约1天 |
| 慢变·按需 | 单角色详情JSON、配装方案 | 首次提问时拉取并缓存，过期后用ETag/Last-Modified条件请求 | 默认24小时 |
| 快变 | 兑换码、公告、更新日志 | 提问时实时查询，短TTL缓存 | 默认10–60分钟 |

刷新规则：

- 有ETag或Last-Modified的接口一律带 `If-None-Match` / `If-Modified-Since`。304只更新检查时间，不重写缓存。
- 没有ETag的 `card-list` 按内容哈希比对，哈希不变只更新检查时间。
- 每日刷新串行请求列表接口，单角色详情不批量预取，只拉被问到的角色。
- 新数据先完整写入临时文件，校验JSON结构和条数后再原子替换。条数骤减（例如少于上一版的90%）视为异常，保留旧版并记录。
- 刷新失败不清空缓存。

降级规则：

- 上游不可达、超时、5xx或429时返回本地旧数据，并在结果中标明 `stale: true` 和上次成功刷新时间，由模型告诉主人数据可能过时。
- 本地没有任何缓存且上游失败时返回错误码，不编造内容。
- 429按 `Retry-After` 或指数退避暂停该主机请求，暂停期间只用缓存。

别名检索在本地完成：用 `card-list` 的名称、昵称和code建索引，支持简繁体、全半角和常见空格差异的归一化。多个候选时返回候选列表，由模型澄清，不自动挑一个。

## 插件结构

拟新建独立插件 `chatbot/plugins/kurumi-e7/`，按[文档21](21_后端职责分层与代码整理.md)分层，结构参照 `kurumi-web-deepseek`：

| 文件 | 职责 |
| --- | --- |
| `openclaw.plugin.json` | id、版本、`activation.onStartup:false`、configSchema（路径须为绝对路径） |
| `client.js` | HTTP访问：主机白名单、超时、响应大小上限、并发上限、条件请求、错误码映射 |
| `store.js` | 本地缓存读写与原子替换，不读取聊天原文 |
| `policy.js` | 默认TTL、刷新时刻、条数异常阈值、别名归一化规则 |
| `service.js` | 编排：查缓存、判断新鲜度、调用client、降级 |
| `index.js` | 注册工具与刷新任务，实现 `stop(ctx)` 释放定时器和未完成请求 |
| `test/` | 离线测试，注入fetch，不访问真实站点 |

缓存放在运行目录 `state/kurumi-e7/`（具体路径由配置给出），只存公开wiki数据和检查元数据，不进仓库。缓存可从上游重建，是否纳入备份在实施时按[文档12](12_目录资产与Git备份整理.md)登记。目前没有第二个消费者，不抽共享包。

## 工具契约

注册一个只读工具 `e7_data`，按 `action` 区分：

| action | 参数 | 返回 |
| --- | --- | --- |
| `search` | `query`，可选 `kind`（hero/artifact）、`limit` | 候选列表：名称、code、属性、职业、星级 |
| `hero` | `code` 或唯一可匹配的 `name` | 角色摘要与技能、属性、专属装备、记忆印记 |
| `artifact` | `id` 或 `name` | 神器效果与适用职业 |
| `filter` | 效果、属性、职业等条件 | 符合条件的角色列表（基于 `hero_summary`） |
| `codes` | 无 | 当前可用兑换码（接口核实后启用） |
| `news` | 可选 `limit` | 最新公告/更新日志摘要（接口核实后启用） |

每条结果带：

- `source: "E7·WIKI"` 与原页面链接，回复时注明“数据来自 E7·WIKI”。
- `fetchedAt`（数据取得时间）、`stale`（是否为降级旧数据）。
- 内容标记为外部不可信数据。wiki文本里出现的指令不执行，只作为资料引用。

返回体按字段裁剪，单次返回设长度上限，不把743KB原始JSON交给模型。故事、语音等长文本默认不返回，主人明确要求时再取。

## 权限与配置

`e7_data` 是新工具，按[文档24](24_统一身份与权限管理.md)处理：

- 在 `chatbot/packages/access-control/permissions.js` 新增权限键 `e7.read`，`toolPermission` 映射 `e7_data` 的全部action，未知action拒绝，并补对应测试。
- 默认只授予主人。成员是否可用由主人决定；若开放，须把 `e7.read` 列入共享权限、加入成员工具上限，并同步 `config/access-control.json`。
- 主人Agent的 `tools.alsoAllow` 增加 `e7_data` 属受管键改动，须主人同意后经 `sync-config.mjs --apply` 部署。

拟定的插件配置（`plugins.entries.kurumi-e7.config`）：

| 键 | 含义 | 拟定默认 |
| --- | --- | --- |
| `cacheRoot` | 缓存目录绝对路径 | 运行目录 `state/kurumi-e7/` |
| `refreshTime` | 每日刷新时刻（本地时间） | 05:30 |
| `detailTtlHours` | 单角色详情TTL | 24 |
| `liveTtlMinutes` | 兑换码/公告TTL | 30 |
| `timeoutMs` | 单次请求超时 | 15000 |
| `maxResponseBytes` | 单次响应上限 | 2MB |
| `traceFile` | 可选调用轨迹（0600，只记次数与状态码，不记内容） | 不启用 |

上游主机固定在代码里，只允许 `admin.e7.wiki` 与 `assets2.e7.wiki`，不接受配置扩展任意URL。

## HTTP防护

- 只发GET。配装方案接口是POST读取，核实无副作用后才纳入，并单独列入允许清单。
- 写接口路径不出现在代码中。
- `redirect: 'error'`，不跟随跳转到白名单外主机。
- 并发上限2，每日刷新串行。
- 遇到429或连续失败退避，不自动重试刷爆对方。
- 请求带可识别的User-Agent，例如 `kurumi-e7/<版本>`，方便站长识别和联系。
- 错误映射为固定错误码返回模型，不回显上游错误正文。

## 刷新调度

每日刷新有两种实现，实施前由主人选定：

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| 插件内定时器（倾向） | 插件启动后按 `refreshTime` 安排下一次刷新，`stop(ctx)` 清除 | 自包含，不依赖Cron和外部runner | 服务停机期间错过刷新，下一次提问时按TTL补拉 |
| 宿主Cron | 由Cron定时调用刷新入口 | 与现有定时任务一同管理 | 要新增Cron条目和执行地址，多一处受管配置 |

两种方案都要求刷新任务不与提问时的按需请求同时打同一接口。

## 署名与使用约束

- 只供主人（及经授权成员）个人查询，不对外提供数据服务，不再分发缓存。
- 每次回答注明“数据来自 E7·WIKI”，能给出页面链接时附上。
- 请求频率保持在每日一轮列表刷新加按需少量详情的量级。
- 建议启用前联系站长说明用途和频率；站长要求停止或限制时，以站长要求为准。

## 已定决策

| 决定 | 原因 | 否决的方案 |
| --- | --- | --- |
| 慢变资料每日条件刷新，快变资料实时查询 | 兼顾新鲜度与对方负载；角色和神器按版本更新，兑换码与公告时效性强 | 纯实时：每次提问都拉743KB列表，慢且完全依赖对方可用性。纯每周爬取：兑换码和新角色会滞后数天 |
| 独立插件与专用只读工具 | 大JSON需要本地索引、别名匹配和字段裁剪 | 直接用 `web_fetch`：返回体过大、无法做别名检索，也拿不到结构化字段 |
| 别名检索在本地完成 | 不依赖对方搜索接口，离线可用 | 每次调用站点搜索 |
| 只读、固定主机白名单 | 站点无API文档和许可，写接口会改动他人数据 | 开放任意 `e7.wiki` 子域或允许写接口 |
| 默认只授予主人 | 文档24规定新工具在主人决定前保持owner-only | 直接加入成员共享权限 |
