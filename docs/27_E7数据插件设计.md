## 背景与范围

主人希望QQ助手能回答《第七史诗》（Epic Seven）的角色、神器、技能和兑换码等问题，数据来自 [E7·WIKI](https://e7.wiki/)。wiki内容会随游戏版本更新，一次性下载会过时，每次提问都实时抓取又慢且依赖对方站点稳定性。本文采用混合方案：变化慢的资料按日条件刷新到本地缓存，变化快的资料按需实时查询并短时缓存。

纳入范围：

- 角色卡片、别名/昵称检索、单个角色详情（技能、属性、专属装备、记忆印记）。
- 神器列表与详情。
- 兑换码、站点更新日志，以及配装、测评、榜单、攻略和FAQ。
- 游戏公告先提供标题与原文链接。正文为PDF的条目须另行解析后才能摘要。

`e7_data`开放`search/hero/artifact/dictionary/codes/news/builds/reviews/rankings/content`。角色包含7个view；`news`仅`game/wiki_update`，词典包含`effect/item`。权限为本人专用`e7.read`，验收范围见文档16。插件服务定时器在本地05:30串行刷新基础目录，按需详情采用24小时TTL，公告/兑换码30分钟TTL。为保证服务启动后可安排刷新，插件采用`activation.onStartup:true`，启动本身不立即请求上游。

不纳入范围：

- 站点的任何写接口（点赞、计数、心愿、评论、提交测评等），也不登录。
- 用户个人账号或战绩数据。
- RTA对战统计（`rta-api.e7.wiki` 有限流，需单独评估）。
- 把wiki数据批量复制进仓库或作为训练、再分发材料。

排期与下一步唯一归[待办 N20](待办清单.md#n20)。

## 数据来源与读取契约

E7·WIKI是Vue/Vuetify单页应用，前端axios的baseURL为 `https://admin.e7.wiki/api`。下表列出的公开读取接口无需登录。普通接口返回 `{code:1000,message:"success",data}`，`hero_summary/hero-list` 直接返回数组。接口方法与参数从站点前端定位，再用少量真实请求核对。`/open/`前缀本身不代表只读，点赞、计数、心愿与提交接口仍排除。公开页面未找到API稳定性承诺或数据许可；关于页说明站点非营利，游戏素材版权归官方。

2026-10-27抽测的字段、条数、字节数、请求参数、状态码与哈希见[接口盘点证据](verification/e7-interface-2026-10-27/README.md)。下表路径以API根地址为前缀，静态角色JSON除外：

| 数据 | 已抽测的读取接口 | 返回形式与接入要点 |
| --- | --- | --- |
| 角色索引 | `GET /open/epicseven/hero/card-list` | 名称、code、昵称、属性、职业、星级、星座、上线及更新时间；无ETag |
| 角色效果 | `GET /open/epicseven/hero_summary/hero-list` | 直接数组；效果标记、满觉醒属性；有ETag，须在本地筛选 |
| 角色详情 | `GET https://assets2.e7.wiki/static/heroes/<code>.json` | 技能描述为嵌套文本段，包含倍率、强化、烧魂、专属装备与印记；ETag条件请求已返回304 |
| 神器 | `GET /open/epicseven/artifact/artifact-list` | 效果、职业、属性与上下限；优先使用已填值的`skill_display_desc`，去除颜色标记并处理`%n`；ETag条件请求已返回304 |
| 配装 | `GET /open/epicseven/hero_equipment_scheme/hero-scheme-counts`；`POST .../getSchemeByHeroCode`，`hero_code` | 按角色返回套装、面板、神器、来源和更新时间；数值有字符串形式；样本不是最优解承诺 |
| 测评 | `POST /open/epicseven/hero_review/page`；`POST .../by-hero`，`heroCode` | 文本正文、分类、作者与更新时间；同一角色可有多个玩法分类，也可为空 |
| 强度榜 | `POST /open/epicseven/tier/list` | 返回分档及归属，样本中未按`size`分页；`type`可为`artifact`、`hero`或空，不能只凭`heroAssignments`字段判断对象 |
| 攻略 | `POST /open/epicseven/guide/page` | HTML正文；`size/keyWord`生效，前端使用的`pageSize/keyword`在样本中未生效；`page`翻页未抽测，分类和标签是JSON字符串 |
| FAQ | `POST /open/epicseven/faq/page` | 问答文本；使用`page/size/keyWord`，不能照搬前端参数大小写 |
| 兑换码 | `GET /open/epic7/redeem_code/lastest?count=...` | `lastest`为实际拼写；含生效、过期时间和服务器，时间未带时区；未执行兑换 |
| 站点更新 | `GET /open/epicseven/updates/latest?count=...` | wiki功能更新日志，不能当成游戏版本更新 |
| 游戏公告 | `POST /open/epicseven/announcement/page` | 样本只有标题、服务器、日期和相对PDF路径；文件根为`https://assets2.e7.wiki/announcement`，不含正文 |
| GVG | `POST /open/epicseven/gvg_homework/page`；`GET /open/epicseven/gvg_defense/hot-defenses?limit=...` | 阵容结构化，配装和操作为文本；低样本胜负计数不能当可靠胜率 |
| 混沌命运 | `GET /open/epicseven/chaos_fate/fate-list`；`GET .../recommend-heroes`；`GET .../recommend-hero-fates?seasonId=...&heroCode=...` | 按赛季的效果、条件、推荐英雄及宿命条目；用`recTier`区分推荐，不能把所有候选都称为推荐 |
| 道具与礼包 | `GET /open/epicseven/item-dictionary/by-category`；`GET /open/epicseven/gift-pack/list` | 道具分组及估值、礼包条目与价值比；估值依赖站点假设，不是实时商城报价 |
| 效果词典 | `GET https://assets2.e7.wiki/static/effects.json` | 强化/弱化等效果的名称、类型、说明与图标相对路径 |
| 站内公告 | `GET https://e7.wiki/announcements.md` | Markdown通知，含标题、日期与正文；与游戏公告、站点版本更新分开 |

只读抽测不证明每条资料完整或游戏结论正确，也不证明生产HTTP封装已能访问：

- 配装数量、测评覆盖、榜单日期分别保留，不能由“有角色详情”推断“有最新攻略”。神器昵称覆盖稀疏，匹配不到时返回候选或未找到，不靠模型编造别名。
- HTML提取文字时移除脚本和样式，不读取`file:`等地址。依赖图片的攻略可能缺失关键信息，应附原文链接并标出文字范围。
- 兑换码只表示站点列示且符合已确认的日期/服务器条件，不能承诺账号可兑换。上游时间的时区待核实。
- 带自定义User-Agent的抽测收到403，而普通curl请求成功；不循环换头重试。生产请求标识和站点兼容性须单独解决。
- 其它详情、筛选参数、推荐接口的所有赛季与通用字典未逐项抽测；RTA继续排除，未重试此前的429。

生产访问按[文档20](20_邮件能力与横切扩展.md)使用可信环境代理与精确主机约束，不默认绕过代理。外部内容只作数据处理，不执行其中的指令。

接口字段和路径可能随前端改版变化，启用前须用实际client重新核对。旧开发侧核对不替代生产验证。

## 固定程序与AI的职责判断

这是依据接口样本提出的实现建议，首期范围仍由主人决定：

- **固定程序负责取数和事实回答**：名称/昵称检索、效果筛选、技能和神器数值、配装样本、榜单分档、FAQ匹配、兑换码日期过滤与来源展示。技能文本段展平、HTML清洗和神器标记解析都可确定性处理。
- **现有聊天模型负责理解和解释**：把口语转为查询条件，在多个角色间澄清，按PVE/PVP等场景概括已有测评或比较配装。检索结果须带日期和来源；没有测评、资料过旧或缺少个人阵容时明确说明。
- **公告正文另设解析层**：PDF链接本身不够生成游戏公告摘要。需下载和提取文字，必要时另行评估OCR；不能仅给模型一个URL就声称读过正文。

首期不需要另接一个专门的AI服务，也不需要向量库才能查询这些结构化资料。若后续需要跨长篇攻略的语义检索，再用真实问题评估召回质量后决定。固定检索与已有聊天模型可以组合，不把所有问题都写成固定话术，也不让模型补齐缺失事实。

## 混合刷新策略

按数据变化频率分为两档：

| 档位 | 数据 | 获取方式 | 新鲜度 |
| --- | --- | --- | --- |
| 慢变 | 角色卡片、效果汇总、神器列表、效果/道具词典；扩展阶段的宿命总表 | 每日一次条件刷新到本地缓存，仅刷新已启用类别 | 最长约1天 |
| 慢变·按需 | 单角色详情JSON；扩展阶段的配装、测评、榜单、攻略/FAQ、礼包及宿命推荐 | 首次提问时拉取并缓存，有ETag/Last-Modified时过期后用条件请求，否则按TTL读取 | 默认24小时 |
| 快变 | 兑换码、公告、更新日志；扩展阶段的GVG查询 | 提问时实时查询，短TTL缓存 | 默认10–60分钟 |

刷新规则：

- 有ETag或Last-Modified的接口一律带 `If-None-Match` / `If-Modified-Since`。304保留数据、hash和取得时间，只原子更新缓存记录中的检查元数据。
- 没有ETag的 `card-list` 按内容哈希比对，哈希不变只更新检查时间。
- 每日刷新串行请求列表接口，单角色详情不批量预取，只拉被问到的角色。
- 新数据先完整写入临时文件，校验JSON结构和条数后再原子替换。条数骤减（例如少于上一版的90%）视为异常，保留旧版并记录。
- 刷新失败不清空缓存。

降级规则：

- 上游不可达、超时、5xx或429时返回本地旧数据，并在结果中标明 `stale: true` 和上次成功刷新时间，由模型告诉主人数据可能过时。
- 本地没有任何缓存且上游失败时返回错误码，不编造内容。
- 429按 `Retry-After` 或指数退避暂停该主机请求，暂停期间只用缓存。

别名检索在本地完成：用 `card-list` 的名称、昵称和code建索引，支持简繁体、全半角和常见空格差异的归一化。多个候选时返回候选列表，由模型澄清，不自动挑一个。

## 工具契约

### 接口数量与数据分类建议

本节记录2026-10-27的完整接口划分；首批6个action及第二批的`builds/reviews/rankings/content`已实现，其余3个action仍是扩展设计。设计核对见[契约记录](verification/e7-interface-2026-10-27/query-contract/README.md)，实施见[首批记录](verification/e7-interface-2026-10-27/phase1/README.md)与[第二批记录](verification/e7-interface-2026-10-27/phase2/README.md)。按“数据对象 + 展示视图”组织，不按每个字段或每条上游HTTP路径新增工具：

- **QQ查询入口**可以有“角色、面板、倍率、印记”等多个说法，由现有聊天模型识别意图。
- **模型工具**先规划一个只读查询工具 `e7_data`，完整目录为13个查询action；第三个任务另设发图工具 `e7_image`。
- **内部服务方法**按action接线明确的查询函数，复用client与缓存。目前没有其它消费者，不为这套查询另开HTTP服务。下表是插件业务契约，不是新增13条网络路由。

| 数据分类 | action | 主要参数与选择方式 | 返回内容与边界 |
| --- | --- | --- | --- |
| 查找对象 | `search` | `kind: hero/artifact`、`query`或结构化`filters`、`limit/cursor` | 名称、别名、稳定ID及简短分类；角色可按属性、职业、星级、效果ID筛选。仅搜索已建索引的角色/神器，其它资料在各自action内查询 |
| 角色资料 | `hero` | `heroCode`、`view`、可选`skill: 1/2/3` | 按下表返回技能、基础面板、倍率、印记、专属装备或人物资料 |
| 神器资料 | `artifact` | `artifactId`、`view: effect/stats/overview` | 效果、适用职业、来源明列的属性上下限；不把社区评价混入基础效果 |
| 社区配装 | `builds` | `heroCode`、套装/面板条件、`limit/cursor` | 套装、面板、神器、来源、更新时间；社区样本不等于唯一最优解 |
| 社区测评 | `reviews` | `heroCode`、`category`、`limit/cursor` | 对应玩法的测评正文、署名、时间；没有测评时返回空结果 |
| 社区榜单 | `rankings` | `mode: list/get`、`rankingId`、`objectType: hero/artifact` | 榜名、适用场景、日期、分档及条目；保留榜单来源，不能把不同场景合成统一强度 |
| 攻略与问答 | `content` | `kind: guide/faq`、`mode: search/get`、`query/contentId`、搜索可用`limit/cursor` | 搜索摘要后按ID取纯文本/问答，返回已验证列表页链接，单篇深链未知；图片依赖、文本裁剪和正文缺失须标明 |
| GVG实战 | `gvg` | `view: homework/hot_defenses`、`defenseHeroCodes`或`offenseHeroCodes`、`limit/cursor` | 进攻作业或热门防守；阵容匹配默认精确匹配、无视槽位顺序，部分阵容须显式`match: contains`。搜索能力限已验证参数或完整本地索引，不假设上游支持全部组合 |
| 混沌宿命 | `fates` | `view: list/recommended_heroes/hero_fates`、`seasonId`，角色视图另需`heroCode` | 宿命效果、条件、站点角色推荐、某角色的候选与推荐；推荐分档和普通候选分开 |
| 效果与道具词典 | `dictionary` | `kind: effect/item`、`query`或`entryId`、`limit/cursor` | 强化/弱化说明，或站点道具名称、说明、估值；两类条目使用各自ID空间 |
| 礼包估值 | `packs` | `mode: list/get`、`packId`、`limit/cursor` | 礼包物品、价格与站点估值假设；不作实时商城报价 |
| 兑换码 | `codes` | 可选`server`、`limit` | 站点列示兑换码、生效及过期条件；时区未确认时不承诺“当前可用” |
| 公告与站点动态 | `news` | `kind: game/site_notice/wiki_update`、可选`server`、`limit/cursor` | 分别表示游戏公告、站内通知和wiki版本日志。游戏公告目前只返回标题、日期与PDF链接，不返回未提取的正文摘要 |

这里合并的是取数和格式契约，不合并资料的含义。例如道具词典与效果词典可以共用查询框架，但礼包估值、技能效果和角色强度仍分别返回。`search.filters`替代原先独立的`filter` action，避免两套角色筛选逻辑。

每个action用独立参数分支校验，未知action/view/kind或多余参数拒绝。名称先经`search`解析为稳定ID；同名或别名歧义返回候选，不默认选第一项。跨action不共用可任意拼接的查询字符串，不接受模型提供URL、文件路径、上游方法或收件人。

`get`使用已验证列表/详情中取得的ID，在对应缓存或明确登记的读取接口中取单项；上表不意味着已经发现每类资料的独立详情路由。`cursor`只表示经验证的上游翻页或完整本地结果集的续页；未验证翻页前须标明覆盖范围，不能声称搜索了全站。新闻的`site_notice`需要单独登记`e7.wiki/announcements.md`；公开读取成功不会自动开放主机。

### 角色的展示视图

“角色”和“面板”是同一个对象的不同投影，共用同一份详情缓存。默认`view: skills`，附姓名、属性、职业等最小身份信息，避免每次返回全部角色资料。

| QQ里的意图举例 | `hero.view` | 返回范围 |
| --- | --- | --- |
| “角色 梅铃”“梅铃技能” | `skills` | S1–S3名称与说明、冷却、魂量、烧魂；指定`skill`时展开该技能的强化明细 |
| “面板 梅铃” | `stats` | 生命、攻击、防御、速度、暴击、暴伤、夹攻、命中、抗性及来源面板口径；单列来源中的被动属性，不自行重复加算 |

### 共同响应与首批建议

只读结果统一包含：

- `status`与结构化`data`：区分成功、歧义、未找到、上游不可用和功能未启用，空列表不伪装成请求失败。
- `source: "E7·WIKI"`与`sources[]`：保留实际来源链接、各份数据的`fetchedAt`、可空的`upstreamUpdatedAt`及`stale`。抓取时间不能冒充内容更新时间；多来源结果各自标日期。
- `missingFields`、`truncated`及适用时的`nextCursor`：明确空值与裁剪。只有上游确实提供或完整本地索引可计算时才返回总数。
- 外部不可信内容标记；wiki文本里的指令只作为资料，不执行。回复注明“数据来自 E7·WIKI”。

列表默认5项、最多10项，单次完整结果上限16KiB；长正文按段裁剪，提供已验证的来源页链接，不能破坏JSON结构。技能强化、倍率和故事按所选view返回，不用一次“角色”请求塞入全部内容。单个角色有详情，不代表有测评、配装或当前版本结论。

基础action为`search/hero/artifact/dictionary/codes/news`，社区与横向资料为`builds/reviews/rankings/content`。`news`只做`game/wiki_update`，`site_notice`待明确主机/路径清单。`gvg/fates/packs`作为扩展目录，不在模型schema中提前宣告可用。即使属于开放action，尚未启用的kind/view也拒绝。神器效果同时返回`effectBasis`：来源没有说明参数上下限对应等级/突破，不擅称满级；基础属性也不推算满级。兑换码与wiki日志各读取上游最新50条后筛选，返回覆盖范围；游戏公告每页10条，续页绑定服务器与页内快照。

图片属于第三个任务，建议另设`e7_image({heroCode,kind,skill?,effectId?})`，`kind`限`avatar/detail/cover/skill/effect`。技能图要求`skill`，效果图要求当前角色已关联的`effectId`；不接受任意图片链接。该工具真实发送一张图，只返回投递回执，权限与只读查询分开。

装备强化模拟是待定义的计算能力，RTA统计与外链伤害计算器也未完成读取验证，均不纳入这13个查询action。站点介绍作为来源元数据即可，不另开查询接口；完整立绘、皮肤、动画和语音文件仍受已验证资源范围限制。

### 第二批文本查询开发

第二批按2A配装/测评、2B榜单/攻略/FAQ、2C玩法/估值分组。分组契约如下；授权与分层验证见[第二批证据](verification/e7-interface-2026-10-27/phase2/README.md)，验收结论见文档16。

2A参数固定为`builds({heroCode,filters?,limit?,cursor?})`和`reviews({heroCode,category?,limit?,cursor?})`。配装的`filters.sets`为1–3个站点套装名，按同时包含匹配；`filters.minStats`仅接收`hp/atk/def/spd/chc/chd/eff/efr`的非负数值下限。暴击、暴伤、命中、抗性按百分数点（例如暴伤289表示289%），不按角色基础JSON的比例值解释。缺失面板返回`null`，不当成0；套装未知不参加匹配。测评分类限`RTA/PVP/PVE/综合`，空列表表示来源未列出。两类资料均先核对角色目录，再读取该角色的完整返回列表，本地筛选分页；游标绑定角色、条件和数据快照。

配装取`hero_equipment_scheme/getSchemeByHeroCode`的只读POST（`hero_code`），测评取`hero_review/by-hero`的只读POST（`heroCode`）。不透传模型提供的路径或请求体。结果包含作者、上游更新时间和来源；配装明确含装备，来源没有说明的等级/觉醒口径仍为未知。每日基础目录刷新不预取这些社区资料，按需缓存24小时。

2B沿用同一个只读工具，契约如下：

- `rankings({mode:list/get,rankingId?,objectType?,limit?,cursor?})`：先列榜单，再用返回的真实`rankingId`取分档条目；`objectType`限`hero/artifact`，只筛来源明确标注的类型。来源`type=null`时保留未知，不能因字段名`heroAssignments`就归为角色榜。完整榜单列表按需缓存24小时；详情按分档关联的条目分页，默认5项、最多10项，分档与对象代码不因长文裁剪而丢失。
- `content({kind:guide/faq,mode:search/get,query?/contentId?,limit?,cursor?})`：搜索使用已验证的只读`POST guide/page`或`faq/page`，请求固定`page/size:10/keyWord`，不传前端旧式`keyword/pageSize`。FAQ原词零结果时最多3个分词短词重试（同一FAQ接口，非抓全站）；返回requestedQuery/effectiveQuery、attemptedQueries及candidate提示，候选仍须读正文核对。分页游标绑定kind、原关键词、实际短词、页号及页内快照；总数采用该次上游分页的`total`，不声称离线全站索引。
- 攻略/FAQ未发现独立只读详情接口。搜索返回真实`contentId`，并把该ID到已验证列表页的定位元数据保存在公开资料缓存中；`get`仅沿此定位读取同一页并核对ID。无定位或条目移出原页时明确要求重新搜索，不猜路由、不扫全站，也不调用阅读计数或点赞接口。搜索只回摘要，`get`才回纯文本正文/问答；保留作者和上游日期。
- 返回已核实的站点列表页链接，未核实单篇深链时`detailUrl=null`并标明缺失。HTML脚本/样式和图片不执行、不下载；实体与段落转为文本，正文依赖图片时标明图片未提取。长正文裁剪、来源陈旧和正文缺失分别标记，整个工具结果继续限制16KiB。
- `query`原值作为上游关键词，不做语义搜索或自动拆词。单次返回0条只说明该关键词与该资料类型的搜索结果为空，不能据此声称全站没有答案。FAQ与攻略是不同列表，攻略的短词查询不能代替FAQ的同词查询。零结果降级/候选匹配的改进需求见下文；现有接口不自动执行该降级。

接口取数、分页、缓存及模型的分层证据见[2B记录](verification/e7-interface-2026-10-27/phase2/README.md#2b榜单攻略与faq)。模型样本通过不保证下一回合也能恢复关键词，本轮增加确定性有界短词重试；历史FAQ漏检实例见[QQ核对](verification/e7-interface-2026-10-27/phase2/qq-review-2026-10-30/README.md#faq问题与独立复核)。榜单对象名称由既有`search`按返回代码解析，不猜未标注的榜单类型。

沿用上面的13类契约，第二批共7个action，2A/2B已实现4个，余下3个按下表推进。第二批仍由`kurumi-e7`独立装配，只扩展`e7_data`已验证的参数分支。取数和字段清洗由固定程序完成，聊天模型负责理解问题及解释已有资料。当前没有第二个消费者，不抽共享E7包，也不开新HTTP服务。

| 建议顺序 | action | 实施前要补核 | 验收重点 |
| --- | --- | --- | --- |
| 2A：角色使用资料 | `builds/reviews` | 实际client读取、配装筛选字段、测评分类和分页；空测评/无配装样本 | 与基础面板分开；保留署名、日期和来源；样本不承诺最优配装 |
| 2B：横向资料 | `rankings/content` | 榜单对象类型与列表覆盖；攻略/FAQ的关键词、分页、稳定ID及详情来源 | 区分场景与榜单日期；HTML去脚本/样式；依赖图片的正文标缺失；长文裁剪和游标有效 |
| 2C：玩法与估值 | `gvg/fates/packs` | GVG阵容匹配与实际筛选范围；赛季/角色关联；礼包价格和估值字段 | 阵容精确/包含匹配分开；低样本不推导可靠胜率；候选与推荐分档分开；估值假设可见 |

每组按“少量只读取样→严格参数与投影→离线回归→实际client→隔离宿主/模型→主人QQ”推进。未验证的分页注明覆盖范围，不能声称全站搜索。结果继续执行默认5项、最多10项和16KiB完整JSON上限，长攻略不能整篇常驻上下文。

权限沿用本人专用`e7.read`。实现某个action时才同步登记`permissions.js`、schema和测试；尚未实现的action继续拒绝，成员权限不自动增加。图片继续按`e7_image/e7.image`独立设计，公告PDF正文、RTA及模拟器不随第二批文本查询引入。

未完成的组仍是开发准备，不提前把对应action开放到生产。任务排期见[待办N20](待办清单.md#n20)，结构前置核验见[2026-10-28复核](verification/capability-review-2026-10-28/README.md)。

### 取图规则

- 只由拟定的 `e7_image` 工具取图，且只在主人明确要看图时调用。资源名称按实际种类表述，例如“梅铃的半身详情图”；尚未确认完整立绘来源时，不把详情图称为完整立绘。查文本资料时不附带取图。
- 一次调用只取一张。多张图片由模型逐张调用，受每日张数上限 `imageDailyLimit` 约束。
- 不批量预取，每日刷新不下载任何图片，也不做全角色图库。
- 只接受详情JSON里的路径，限定 `assets2.e7.wiki` 的 `/static/avatar/`、`/static/detailImage/`、`/static/cover/`、`/static/skills/`、`/static/effects/` 前缀。模型不能传入任意URL。
- 下载时校验 `content-type` 与文件头均为图片，单张上限 8MiB，与QQ频道上限一致。
- 图片缓存与文本缓存分开存放，设总容量上限（拟定 50MB）和保存期（拟定 7天），超出按最近最少使用淘汰。缓存不进仓库，也不纳入备份。

### QQ发图链路

QQ频道现有的发图底层是 `chatbot/plugins/kurumi-qq/src/transport.js` 的 `sendPayload`，2026-10-26代码核对结果如下：

- 只发送频道暂存目录（`mediaRoot`）内的本地文件，拒绝软链接逃逸和目录外路径。
- 单张上限 8MiB，按文件头接受 PNG、JPEG、GIF、WEBP，以base64交给OneBot。
- 一条回复只带一张图片，多图会报错。
- 表情工具 `kurumi_sticker` 先用 `stageImage` 暂存再调用 `sendPayload`，收件人固定为当前主人私聊。

对其它插件公开的投递接口只有 `kurumi-qq/delivery.js`，目前只提供 `sendDocument` 与 `sendText`。按[文档21](21_后端职责分层与代码整理.md)，其它插件不得导入 `kurumi-qq/src/*`。因此方案为：

1. 在 `delivery.js` 新增 `sendImage({to, bytes, contentType, key, signal})`。频道内部完成暂存、大小与类型校验、账本登记，再调用 `sendPayload`。暂存、校验和账本逻辑都留在频道里。
2. `kurumi-e7` 的组合入口通过 `createQqDelivery` 接线，与 `kurumi-papers` 的做法一致。
3. 收件人取自可信宿主上下文中的当前请求者，不接受模型参数指定收件人。群聊入口保持关闭。
4. 发送成功后工具只返回投递回执，不把图片内容交给模型。

`delivery.js` 是QQ频道的共享接口，新增 `sendImage` 要同时补频道测试，并更新文档21的投递接口说明。

### WebP兼容

频道底层接受WEBP文件头，但QQ客户端能否正常显示由OneBot转发的WebP，**尚未验证**。首选直接发原图，真人QQ验收若发现显示异常，再改为转成PNG/JPEG后发送。转换需要引入图片处理依赖，要按固定版本登记，并经主人同意。

### 版权边界

- E7·WIKI关于页说明游戏素材版权归官方。角色立绘、头像和图标都属于游戏素材，插件只是经E7·WIKI获取。
- 图片只发到当前请求者自己的私聊，供个人查看。不发群、不转发给他人、不做公开展示或再分发。
- 不批量复制图库，不修改或裁剪图片，不去除标识，不用作训练材料。
- 发图时附文字说明：“图片版权归《第七史诗》官方，经 E7·WIKI 获取”。
- 站点或官方要求停止时，立即关闭取图功能并清空图片缓存。
- 以上是使用约束，不构成法律判断。如果以后要扩大使用范围，需要另行确认授权。

## HTTP防护

- GET与POST都按精确路径登记读取允许清单。POST仅允许上表经前端读取用途与真实响应核对的查询路径，不能开放通用POST；其它路径默认拒绝。
- 写接口路径不出现在代码中。
- `redirect: 'error'`，不跟随跳转到白名单外主机。
- 并发上限2，每日刷新串行。
- 图片请求单独限制：`content-type` 与文件头须为PNG/JPEG/GIF/WEBP，单张不超过8MiB，超限即中止下载。
- 遇到403暂停该主机至少1小时；429/5xx按Retry-After或递增等待退避，不自动重试。
- 首批固定User-Agent为`kurumi-e7/0.1 (personal read-only wiki client)`。此前curl的403证据保留，本轮client已取得200/304，但未确定此前拒绝原因；不循环改头规避拒绝。
- 错误映射为固定错误码返回模型，不回显上游错误正文。

## 刷新调度

首批已采用插件内定时器。下表保留两种方式的取舍，当前不增加Cron条目：

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| 插件内定时器（首批采用） | 插件启动后按 `refreshTime` 安排下一次刷新，`stop(ctx)` 清除 | 自包含，不依赖Cron和外部runner | 服务停机期间错过刷新，下一次提问时按TTL补拉 |
| 宿主Cron | 由Cron定时调用刷新入口 | 与现有定时任务一同管理 | 要新增Cron条目和执行地址，多一处受管配置 |

两种方案都要求刷新任务不与提问时的按需请求同时打同一接口。

## 已定决策

| 决定 | 原因 | 否决的方案 |
| --- | --- | --- |
| 慢变资料每日条件刷新，快变资料实时查询 | 兼顾新鲜度与对方负载；角色和神器按版本更新，兑换码与公告时效性强 | 纯实时：每次提问都拉743KB列表，慢且完全依赖对方可用性。纯每周爬取：兑换码和新角色会滞后数天 |
| 独立插件与专用只读工具 | 大JSON需要本地索引、别名匹配和字段裁剪 | 直接用 `web_fetch`：返回体过大、无法做别名检索，也拿不到结构化字段 |
| 别名检索在本地完成 | 不依赖对方搜索接口，离线可用 | 每次调用站点搜索 |
| 只读、固定主机白名单 | 站点无API文档和许可，写接口会改动他人数据 | 开放任意 `e7.wiki` 子域或允许写接口 |
| 默认只授予主人 | 文档24规定新工具在主人决定前保持owner-only | 直接加入成员共享权限 |
| 图片按需单张获取，不批量下载 | 图片是游戏官方素材，按需取用对站点负载和版权风险都最小 | 刷新时预取全部头像与立绘，建本地图库 |
| 发图经 `kurumi-qq/delivery.js` 新增 `sendImage` | 复用频道已有的暂存目录、类型和大小校验与投递账本，且不越过插件边界 | 插件直接导入 `kurumi-qq/src/*`，或自行调用OneBot |
| 发图单独设权限键 `e7.image` | 发图是真实外发，与只读查询风险不同 | 与 `e7.read` 共用一个键 |
