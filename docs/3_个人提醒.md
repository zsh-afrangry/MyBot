# 个人提醒

插件 `personal-reminders`，实现在共享包 `chatbot/packages/personal-domains`。它只管“到某个时刻提醒我一件事”。网站和 QQ 共用的待做列表是另一个功能，见[文档23](23_KnowledgeMap业务能力桥接.md)。

## 功能

- 创建、修改、取消一次性提醒，查询当前有效的提醒。只有主人可用。
- 每个写操作都先生成预览，主人确认后才执行。
- 到点后由固定的后台服务选中已批准的提醒并投递到主人私聊。通知的措辞由助手按当前人格生成，时间和内容由后端冻结，模型改不了。

约束：时间按 `Asia/Shanghai` 理解，至少提前 1 分钟、最多 366 天；内容 1 到 200 字。

不做的事：不做周期提醒，不开放通用 Cron，模型不能指定收件人、命令、任务 ID 或任意内容载荷。

## 接口

| 工具 | 权限点 |
| --- | --- |
| `personal_reminder_state_get` | `reminders.read` |
| `personal_reminder_propose` / `_commit` | `reminders.manage` |
| `personal_reminder_change_propose` / `_change_commit` | `reminders.manage` |
| `personal_reminder_cancel_propose` / `_cancel_commit` | `reminders.manage` |

配置在 `plugins.entries.personal-reminders`：`reminderBackend` 固定为 `native-service`，`reminderRunnerRoot` 指向插件目录。

数据在运行目录的 `state/personal-reminders/reminders.sqlite`，和天气库分开。主要的表是提醒、提案、重试状态、审计，以及确认用的提案和授权。

## 原理

- **提案和确认**：提案冻结内容和哈希，有效期 24 小时。主人确认后，授权在提醒库的事务里被消费一次。模型只知道提案 ID 拿不到授权。确认机制见[文档6](6_二次确认.md)。预览里“确认截止时间”和“提醒触发时间”分开显示。
- **调度**：提交时由可信的后台服务向宿主注册一个定时任务。地址、命令和收件人都由服务持有，不接受工具参数。
- **原地修改**：只改内容时不碰宿主的定时任务；改时间时更新原任务，不新建第二个。
- **结果不确定时停住**：本地库和宿主的定时任务之间没有真正的原子事务。注册或更新的结果无法确认时，提醒标记为未知，状态对主人可见，后续的修改、取消和重发都被阻断。理由：宁可停下来让人处理，也不要重复注册或在错误的时间提醒。
- **重试**：只有明确的投递失败才重试，总共最多 3 次。未知结果不自动重试。
- **对账**：后台每 60 秒把本地状态和宿主的任务状态核对一次。
- **查询只返回有效提醒**：已完成、已取消的提醒和审计不进入模型上下文。

状态：`scheduling` → `scheduled` → `delivering` → `delivered`，另有 `failed`、`cancelled`。

## 限制与已知问题

- 没有后台清理。已结束的提醒、提案和审计一直保留在库里。
- 处于未知状态的提醒需要人工核对后处理，不要手工删库里的行或宿主的任务，也不要用“取消旧的再新建”绕过。
- `chatbot/plugins/personal-weather/dist/reminder-cli.js` 必须保留：从备份恢复出来的旧定时任务可能仍以它为执行地址。

## 如何验证

```bash
node chatbot/scripts/build-personal-plugins.mjs
npm --prefix chatbot/packages/personal-domains test
```

真实创建、到点投递和重启恢复需要单独授权，脚本是 `scripts/fusion/test-domain-reminder.mjs`、`test-reminder-delivery.mjs`、`test-domain-due.mjs`。
